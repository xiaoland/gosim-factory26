# Alignment Extension

Alignment is an optional coordination grammar, not a truth layer. Use it only when humans and agents repeatedly disagree about references, boundaries, operations, state, or evidence after normal owners and stable code anchors are already in use.

## Admission

Require a repeated, costly drift pattern such as:

- names or visual references do not identify a stable object
- object boundaries are interpreted differently
- operation words hide different side effects
- state or context changes whether a reference is valid
- proposed mutations repeatedly lack evidence or a credible blast radius

Do not create Alignment when code identifiers, tests, schemas, existing owner docs, or a clearer request solve the problem cheaply.

## Ownership

Alignment may own:

- shared object and address conventions for coordination
- calculable maps derived from stable anchors
- controlled operation vocabulary tied to verification meaning
- request shapes that expose boundary, state, evidence, and protocol

It does not own product rules, technical invariants, runtime topology, evidence sources, mutation authority, or acceptance. Those remain with their normal owners.

## Coordination Shape

For alignment-heavy work, make these explicit enough to verify:

1. object
2. address
3. intended operation
4. boundary and invariants
5. relevant state or context
6. evidence
7. confirmation protocol

Prefer semantic identifiers, route names, typed handles, and symbols that can be derived from current code over positional prose, screenshots, or static maps. Express mutations as an objective current-to-desired state diff. Give an operation name durable meaning only when it implies a verification boundary.

Use [the alignment request template](../assets/alignment-change-request.template.md) only after this extension's admission rule is satisfied. The current task and Human authority still govern mutation; Alignment only makes the proposed object, operation, boundary, state, and evidence precise.
