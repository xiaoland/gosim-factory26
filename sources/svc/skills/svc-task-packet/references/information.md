# Information and Result Use

Keeping material, explaining it, and adopting its result are different actions.
Raw files, logs, queries, and returns preserve observations and provenance.
A current synthesis explains which of them support the task's answer, which alternatives remain live, and what should happen next.
Neither is sufficient alone: a transcript requires reconstruction, while an unsupported summary prevents reconsideration.
Keep the current answer near the decision it serves and link the detail needed to challenge or resume it.

## Follow the Same Question Through the Work

Consider the editor and importer sharing a configuration format.
The imported file reopens with a different preference, and the task has not yet established whether this violates the shared rule.
Preserve the original file, the requirement and agreed format entry, the exact observed behavior, and the relevant candidate version.
State the current hypotheses and the condition that would distinguish them; do not turn an early guess into a confirmed cause.

A query of the stored value and an observation of the editor's interpretation may eliminate one hypothesis.
The next owner should find that adopted answer and its limits in the current inquiry, rather than rediscovering it among dated notes.
If the observed condition was not covered by the rule, keep the product interpretation unresolved and obtain the relevant decision before using a convenient expected result.
Once the rule is settled, update its project owner and record how that decision changes this task's design and next work.

An implementation return is then consumed against that current basis.
A local success can establish the importer's behavior under its conditions but leave the connected reopen journey unknown.
Record that distinction and obtain the observation that matters to the remaining question.
If later feedback contradicts the assumption, revise the current explanation and route; preserve the original output and the reason for the revision.
File creation, a report saying “done,” and accumulated evidence are not proof that a result has been understood or used.

## Give Information an Address When It Helps

Use a separate module when its distinct question or semantic owner reduces reconstruction, stale-state, or conflicting-edit cost.
Keep the information inline in `packet.md` or a plan while that is cheaper.
One stable entry can link supporting depth; file count does not define the module.
The following are available responsibilities, not required documents.

### Inquiry

Inquiry owns the current answer to a material question, evidence, candidate explanations, and unresolved observations.
Distinguish facts from inferences and retain scope or freshness that affects the conclusion.
Record the next observation that could distinguish remaining explanations and why its outcomes would change the route.
Replace a superseded current answer when new evidence changes it, retaining the source and reason needed to avoid repeating a rejected approach.
Diagnosis is an inquiry into a mismatch, not a separate mandatory document.

### Design

Design owns the current coherent proposed solution, important constraints and forces, live alternatives, consequences, and remaining uncertainty.
Use a diagram, pseudocode, prototype, or code when it conveys the solution cheaply without hiding material reasons or obligations.
It expresses the solution; a plan or task map controls the work that produces or realizes it.
Distinguish proposed choices from accepted decisions and actual implemented behavior.

### Decision

Decision records a choice that needs stable retrieval: its subject and state, responsible authority, selected option, causal reason, consequences, and conditions for reopening or supersession.
It is distinct from a design that is still evolving.
A large register can be split for editing or retrieval while retaining one current entry; shard size does not create a new semantic owner.
When the choice becomes reusable project knowledge, update its project owner rather than maintaining a second definition here.

### Verification

Keep observations and judgments with the work they concern.
Add `verification.md` only when several returns need a shared account of what is supported, what remains unknown, and what action follows.
Verification can change the route at any point; it is not only a final phase.
Use [verification guidance](../../svc-verification/SKILL.md) when interpreting the evidence needs more depth.

Do not create default Implementation, Delivery, Acceptance, Retrospective, Agent, Track, Phase, Slice, or generic module files.
Use a distinct surface because its owner or retrieval need is real, not because a template exists.
