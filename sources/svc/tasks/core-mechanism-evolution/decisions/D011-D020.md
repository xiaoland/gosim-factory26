# Decisions D-011..D-020

## D-011 — Capability-by-Capability Design and Projection Boundary

- **State**: superseded by `D-012`
- **Authority and date**: Sir, 2026-08-03
- **Decision**:
  - Before defining an exact landing, discuss the six synthesized capability
    clusters one at a time, including their rough SVC file and directory
    consequences.
  - Progressive disclosure is a root principle of SVC content organization,
    not a whole-system topology option that still needs approval.
  - Most eventual landing is expected to change the SVC method and canonical
    source content. SVC CLI changes are exceptional mechanical projections,
    not a parallel semantic design track.
- **Rationale**: An overall landing topology would freeze provisional
  abstractions before the content, coupling, and existing owner fit of each
  capability are understood. The six rounds give Sir concrete material to
  review while preserving cross-cluster revision.
- **Consequences**:
  - Each round covers capability meaning, outcome contribution, operating
    sequence, owner boundaries, progressive loading, and rough file/directory
    placement before an exact change is proposed.
  - Six capability clusters do not imply six modules, files, or implementation
    slices.
  - Cross-cluster reconciliation and an Impact Handshake remain necessary
    before durable source mutation.
- **Reopen trigger**: The sequential discussions hide a cross-cutting invariant
  that cannot be evaluated per cluster, or stable semantics later justify a
  distinct CLI-enforced contract.

## D-012 — Five Functional Clusters Across Coupled Loops

- **State**: accepted
- **Authority and date**: Sir, 2026-08-03
- **Supersedes**: `D-011` where it defined six capability clusters and a
  sequential discussion
- **Decision**:
  - Organize the design around five functional clusters: task packet, working
    protocol, sub-agents, verification, and tastes plus the ability to design.
  - Evaluate and connect these clusters through four operating loops—Human
    collaboration, Agent task work, system change, and work-system adaptation—
    and the three outcome scales `O-INTERACTION`, `O-TASK`, and `O-SYSTEM`.
  - Begin discussion with task packet, but do not force a linear sequence. Keep
    one foreground issue while moving across cluster interfaces when necessary.
  - Retain `D-011`'s progressive-disclosure and CLI projection boundaries.
- **Rationale**: The former six-item list promoted cross-cutting analytical
  concerns such as context control, obligation propagation, action routing,
  and adaptation into peers of concrete SVC functional surfaces. The five
  clusters better match the parts of SVC that need substantive design while
  the loops and outcomes preserve the system-level causal view.
- **Consequences**:
  - The five clusters are neither modules nor lifecycle stages, and their
    numeric order is not a dependency graph.
  - Former analytical concerns remain review lenses and interface obligations
    inside or across the five clusters rather than disappearing.
  - Each active discussion must show its effect and cost across the relevant
    loops and outcomes; no cluster may optimize its own artifact in isolation.
  - Cross-cluster reconciliation and an Impact Handshake remain necessary
    before durable source mutation.
- **Reopen trigger**: A functional cluster proves to be only an implementation
  detail, a material sixth surface lacks an owner, or the four-loop view hides
  a distinct operating feedback loop.

## D-013 — Task-Packet Organization-Pattern Requirement

- **State**: accepted
- **Authority and date**: Sir, 2026-08-05
- **Decision**:
  - `packet.md` must act as the Human-Agent collaboration core of a task packet,
    not become synonymous with the whole packet.
  - SVC must provide several standard, common task-packet organization patterns
    so an Agent can recognize and maintain a package rather than defaulting to
    one monolithic file.
  - Pattern selection depends on task scale, task nature, and the Human-Agent or
    Agent-team collaboration shape. It is not one universal directory layout.
  - The exact pattern catalog and file shapes remain under discussion.
- **Rationale**: The current instruction to split supporting material only when
  `packet.md` becomes hard to scan does not teach a usable package topology.
  Without recognizable patterns and routing conditions, an Agent tends to keep
  expanding the entry file and loses the different consumers, cadences, and
  coordination roles inside the packet.
- **Consequences**:
  - The active task-packet discussion moves from five-field adequacy and general
    behavior visibility to organization archetypes, selection, composition,
    and transition.
  - `packet.md` retains a common Human-facing contract across every pattern;
    supporting artifacts carry Agent depth, evidence, decisions, slices, or
    coordination state according to pressure.
  - Progressive disclosure must apply both inside a packet and when SVC teaches
    the pattern catalog.
  - No packet schema, fixed directory family, template set, or CLI mechanism is
    implied by this decision.
- **Reopen trigger**: Real tasks show that one organization shape handles the
  relevant scale, nature, and collaboration variation without monolith growth,
  or that recognizable patterns create more routing and migration cost than
  they save.

## D-014 — Progressive Composable Task-Packet Modules

- **State**: accepted
- **Authority and date**: Sir, 2026-08-05
- **Refines**: `D-013`
- **Decision**:
  - A task packet grows progressively from the common `packet.md` core by
    composing modules under real pressure. Inquiry, design, and implementation
    delivery are module concerns, not mutually exclusive whole-packet types.
  - Most non-trivial tasks are mixed and may activate several modules. Working
    postures cannot classify task nature or select one packet organization.
  - Each admitted module needs its own file topology, internal content
    structure, content constraints, and writing guidance; these remain to be
    discussed module by module.
  - Task slices and implementation slices are distinct concepts and must not be
    hidden behind one generic `slices/` surface.
  - The accepted common `packet.md` Human-collaboration responsibility remains
    invariant across module compositions.
  - Moving the entry template to
    `src/assets/templates/task-packet/packet.template.md` and colocating later
    file/module templates there is the preferred candidate direction, not yet
    an authorized source change or complete template design.
- **Rationale**: Task nature does not partition real long work: exploration,
  Human design discussion, implementation, verification, and delegation often
  coexist. A small fixed core plus progressively activated deep modules gives
  recognizable organization without enumerating every scale, nature, and
  collaboration combination.
- **Consequences**:
  - Compact is the absence of unnecessary modules, not a peer module or packet
    mode.
  - Module composition and module-internal growth are separate design levels.
  - Delegation is a relation to bounded task work, not automatically a packet
    type; its task-packet carrier must be clarified with the sub-agent cluster.
  - Template relocation may be Behavioral SemVer-relevant because it changes a
    packaged consumer path; exact compatibility handling waits for landing.
- **Reopen trigger**: Real mixed tasks cannot compose modules without duplicate
  state or navigation cost, or one fixed organization proves simpler across the
  intended scale and collaboration range.

## D-015 — Work Actions and Non-Linear Postures

- **State**: accepted
- **Authority and date**: Sir, 2026-08-05
- **Refines**: `D-014`
- **Decision**:
  - The task packet exists to help complete the task. Common work actions
    include exploration/diagnosis, design, implementation, verification, and
    retrospective consolidation; persistent packet modules should support
    these actions when their material outgrows the common core.
  - Working postures are non-linear, recurrent, and composable. A posture may
    need its own local plan and may invoke another posture; neither tasks nor
    modules are classified as one posture.
  - A posture describes how the Agent is working; a module owns task-local
    externalized state and artifacts. Correspondence does not make them the
    same object or a lifecycle state machine.
  - Planning and task coordination are cross-cutting. Whether their persistent
    carrier should become a module remains a design question rather than a
    posture-implied requirement.
  - Simple structure is a governing counter-pressure. The model must not imply
    a module, plan, map, slice, or template merely by naming a possible action.
- **Rationale**: Real work revisits and nests exploration, diagnosis, design,
  implementation, and verification. Treating them as stages loses feedback;
  treating every possible activity as a required module creates stale state,
  duplicated authority, and maintenance cost. Externalized modules are useful
  only where they reduce recovery, coordination, or Human review cost.
- **Consequences**:
  - Exact changes to the durable Working Protocol posture set remain for the
    working-protocol functional-cluster discussion.
  - Verification and retrospective may be light cross-cutting material or deep
    modules depending on independent content and consumers.
  - Module discussions must include local planning, cross-module invocation,
    result integration, and a no-module/simple counterexample.
  - The exact module admission and retirement rule remains the `V-038`
    hypothesis until reviewed.
- **Reopen trigger**: Real tasks are better served by a stable linear lifecycle,
  posture-aligned modules cause duplicated state, or implicit coordination is
  consistently less reliable than an always-present work graph.

## D-016 — Plan Scope and Plan Organization Are Distinct

- **State**: accepted
- **Authority and date**: Sir, 2026-08-05
- **Refines**: `D-014`, `D-015`
- **Decision**:
  - `task`, `exploration`, `diagnosis`, `design`, `implementation`,
    `verification`, and similar terms describe what a plan covers: its scope.
    They are not levels of plan detail.
  - `phase`, `slice`, and `step` are candidate ways to organize work inside a
    plan. Their exact semantics and whether a particular plan needs all of them
    remain open; SVC must not assume one universal fixed hierarchy.
  - A task-, exploration-, design-, or implementation-scoped slice is a scoped
    use of the slice construct. Implementation scope still adds mutation,
    authority, proof, and recovery obligations, but does not make the slice a
    different planning level.
- **Rationale**: Conflating semantic scope with decomposition level makes mixed
  tasks look like linear lifecycles and prevents the same planning structure
  from being used inside exploration, design, implementation, or verification.
- **Consequences**:
  - The former task-slice-versus-implementation-slice frame is superseded as a
    hierarchy or pair of exclusive work-unit kinds; its authority and proof
    distinction survives as scope-specific obligations.
  - Plan scope, work organization, posture, and module ownership remain
    separate dimensions even when their language corresponds.
  - Exact `phase`/`slice`/`step` contracts require further discussion and a
    simple-task counterexample before becoming SVC guidance or templates.
- **Reopen trigger**: Real task evidence shows that task and implementation
  slices require unrelated base semantics rather than one slice construct with
  scope-specific obligations, or a fixed hierarchy is materially simpler and
  remains faithful under non-linear work.

## D-017 — Stable Planning Primitives Are Required Common Ground

- **State**: accepted
- **Authority and date**: Sir, 2026-08-05
- **Refines**: `D-016`
- **Decision**:
  - SVC should provide a small, stable vocabulary of planning building blocks
    with explicit semantics and relations so a Human can understand how an
    Agent intends to work without guessing among `phase`, `slice`, `step`,
    `sub-task`, `segment`, and local synonyms.
  - `phase`, `slice`, and `step` were examples, not the accepted final set.
    Exact primitives, composition rules, scope qualifiers, and progressive
    activation remain to be designed from real task pressure.
  - Uniform primitives do not imply a mandatory fixed hierarchy or that every
    plan uses every primitive. The common ground must preserve simple plans and
    non-linear feedback.
- **Rationale**: Unstable synonymous planning language hides decomposition,
  ordering, return, and completion semantics from the Human and makes Agent
  plans harder to compare, steer, resume, and verify.
- **Consequences**:
  - Candidate vocabulary must define each primitive by purpose, boundary,
    relations, completion/return meaning, and counterexample—not by approximate
    size.
  - A task-local alias or domain term must map to the common primitive when it
    affects Human steering or Agent handoff.
  - No planning template or directory name follows until the vocabulary is
    reviewed against diverse real packets.
- **Reopen trigger**: A stable vocabulary proves more difficult to understand
  than locally defined terms, or real work requires materially incompatible
  decomposition semantics that cannot be expressed through scope and relations.

## D-018 — `packet.md` Is the Default Human Task-Packet Surface

- **State**: accepted
- **Authority and date**: Sir, 2026-08-05
- **Refines**: `D-013`
- **Decision**:
  - Human interaction with a task packet should ordinarily require only one
    short, simple `packet.md` that exposes the consequential current task view.
  - Supporting files primarily serve Agent recovery, reasoning depth,
    provenance, planning, and integration. They need not each be independently
    optimized as Human decision briefs.
  - Symbolic identifiers such as `D`, `V`, `O`, and `S` are useful common-ground
    handles when their meanings are established locally; the Human must not be
    required to guess or load an external codebook.
- **Rationale**: Human attention is scarce and crosses tasks. Requiring the
  Human to navigate Agent working memory defeats the coordination purpose, while
  removing stable handles makes precise Human-Agent reference harder.
- **Consequences**:
  - `packet.md` must define or plainly expand local symbols that appear in its
    current view.
  - Agent-depth files are evaluated by recovery, reasoning, provenance, and
    integration return rather than by direct Human readability alone.
  - The current task's earlier requirement that its active dossier be a
    complete Human review surface is withdrawn; the dossier remains an Agent
    synthesis owner and `packet.md` carries the Human projection.
- **Reopen trigger**: Real Human review repeatedly requires information that
  cannot fit in a short packet without losing the decision, evidence boundary,
  or material alternatives, and conversation projection does not close the gap.

## D-019 — Coordination Is a Relation View of Work Topology

- **State**: accepted
- **Authority and date**: Sir, 2026-08-05
- **Refines**: `D-015`, `D-016`
- **Decision**:
  - Coordination is not a third topology beside work and information. It is the
    task-relevant dependency, assignment, authority, expected-return, handoff,
    blocking, reopening, and integration view over work units, actors, and
    shared targets.
  - This acceptance does not imply a universal coordination graph, persistent
    module, scheduler, or runtime state. Relations remain implicit unless
    coordination pressure makes persistence useful.
- **Rationale**: A separate topology duplicates work nodes and status while a
  relation view can explain who performs which bounded work, under what
  authority, and how its return changes the shared task.
- **Consequences**:
  - A future coordination carrier, if admitted, stores only a material
    projection of work relations rather than owning a second work model.
  - Delegation method remains in the sub-agent cluster; mutation authority
    remains in Working Protocol and the applicable scoped plan contract.
- **Reopen trigger**: Actor, authority, handoff, or integration state cannot be
  represented reliably without an independently owned topology, or a relation
  view repeatedly diverges from the work plan.

## D-020 — `packet.md` Follows the Human Communication Language

- **State**: accepted
- **Authority and date**: Sir, 2026-08-05
- **Refines**: `D-018`
- **Decision**: The prose and Human-facing field labels in `packet.md` use the
  language in which the Human and Agent are communicating. Stable framework
  handles may remain when they are expanded locally and improve precise
  reference.
- **Rationale**: `packet.md` is the default Human task surface. Making the Human
  translate an Agent-internal documentation language increases attention and
  context-switching cost and weakens its common-ground role.
- **Consequences**:
  - This task's `packet.md` is Chinese-first while retaining canonical field
    names parenthetically where they help Agent recovery.
  - Agent-depth files may use the language that best supports precise work,
    unless the Human is asked to review them directly.
  - Future template guidance must distinguish semantic field identity from a
    hard-coded display language.
- **Reopen trigger**: Bilingual or localized field labels materially damage
  mechanical discovery, or mixed-language collaboration requires another
  explicit language-selection rule.
