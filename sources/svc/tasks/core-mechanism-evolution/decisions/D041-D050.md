# Decisions D-041..D-050

## D-041 — Implementation Is a Slice Contract, Not a Default Module

- **State**: accepted
- **Authority and date**: Sir, 2026-08-06
- **Refines**: `D-034`, `D-039`, `D-040`; accepts `V-077`
- **Decision**: Do not standardize `implementation.md`,
  `implementation-plan.md`, or `delivery-plan.md` as task-packet semantic
  modules. The applicable Plan owns route and state; an `IM` Slice owns its
  bounded system-state transition plus a risk-proportional mutation/return
  contract. Detailed impact maps, preflight simulations, transformation rules,
  and delegated work orders grow as Slice-owned supporting artifacts only when
  their pressure warrants it. Expressible repetitive edits prefer deterministic
  transformations; persistent migration, release, rollout, or adoption work is
  modeled as the specifically named Track/Phase/Cell obligation it actually is.
- **Rationale**: Historical implementation and delivery files combine Plan
  sequencing, design rehearsal, mutation authority, execution detail,
  verification evidence, and external recovery without one coherent owner.
  Keeping implementation control at the independently integratable return
  avoids a duplicate Plan or source shadow while still supporting bounded
  Executor feedback loops and high-impact preflight.
- **Consequences**:
  - An `IM` tag communicates return scope but grants no mutation authority.
  - File volume does not justify LLM delegation; semantic uncertainty and a
    useful feedback surface do.
  - Acceptance evidence remains with its verification owner, and continuing
    delivery state uses domain-specific topology rather than generic paperwork.
- **Reopen trigger**: Real Tasks repeatedly need one cross-Slice realization
  state consumed by several Plan owners, and neither Design, Plan/Slice
  artifacts, source truth, nor a named domain Track can own it without costly
  duplication. Such evidence may justify a specifically named realization
  module, not automatically a generic Implementation/Delivery module.

## D-042 — Verification Is a Module; Acceptance Is a Consuming Disposition

- **State**: accepted
- **Authority and date**: Sir, 2026-08-06
- **Refines**: `D-034`, `D-039`, `D-041`; accepts `V-079`
- **Decision**: Admit `verification.md` as a pressure-created semantic module
  owning integrated material claim-to-evidence state, proof horizons,
  residuals, and requalification across local returns. Keep familiar bounded
  verification inline or in a `VR` Slice-owned artifact. Do not admit a default
  peer `acceptance.md` module: acceptance is an authority-bearing disposition
  made by the consumer of the evidence at its integration, barrier, Human, or
  external-effect gate.
- **Rationale**: Current verification material has a coherent cross-Slice
  lifecycle, while current “acceptance” files variously contain protocols,
  environment facts, run certificates, external observations, and final
  dispositions. The latter do not share one owner or consequence lifecycle.
- **Consequences**:
  - The Verification module does not own work sequence, raw logs, product
    expectations, or acceptance authority.
  - Routine dispositions update the applicable Plan/barrier; consequential
    Human dispositions enter `decisions.md` and are projected in `packet.md`;
    live delivery state remains with its named Track/external system.
  - Tests remain claim-relative evidence mechanisms rather than requirement or
    acceptance authorities, and their independence is purchased in proportion
    to false-accept loss.
- **Reopen trigger**: Real Tasks repeatedly need one independently maintained,
  cross-consumer acceptance state with its own authority, lifecycle,
  invalidation, and return that cannot be owned by Plan/barrier, Decision,
  Verification, a domain Track, or the external system without costly
  duplication.

## D-043 — Diagnosis Is Inquiry; Verification Activity Remains Distributed

- **State**: accepted
- **Authority and date**: Sir, 2026-08-07
- **Refines**: `D-037`, `D-042`; accepts `V-085`, `V-086`
- **Decision**:
  - Standardize one pressure-created `inquiry.md` information module. Diagnosis
    is an Inquiry question/method activated by an observed mismatch, not a peer
    module or alternative stable `diagnosis.md` entry.
  - Verification activity remains distributed through Slice feedback and
    returns, Cell contributions, Phase barriers, task-level composition, and
    acceptance/effect gates. Optional root `verification.md` owns only shared
    task-level claim/evidence synthesis across those local owners; it is not a
    final whole-Task verification stage.
- **Rationale**: Diagnosis changes the epistemic starting condition and likely
  probes without changing evidence, freshness, synthesis, consumer, or return
  lifecycle. Likewise, local verification must stay close to the candidate and
  control owner, while only cross-owner claims and proof composition need an
  independent task-level information owner.
- **Consequences**:
  - Diagnosis-dominant Tasks use an explicit diagnostic title and semantic
    artifacts under `inquiry/`; no `diagnosis.template.md` is admitted.
  - Routine focused verification stays inside the relevant Slice/Plan. A
    separate `VR` Slice requires an independently useful return, authority/
    effect boundary, expensive external observation, or separable scheduling.
  - `verification.md` may be activated before implementation and updated as
    evidence arrives. Only a claim that semantically requires the joined
    candidate waits for all relevant Cells; no symmetric final Verification
    Phase follows from the module.
- **Reopen trigger**: Real Tasks reveal that diagnosis has an independently
  maintained causal-state consumer/cadence not expressible by Inquiry, or that
  shared verification synthesis cannot remain coherent without taking over
  local proof execution and state.

## D-044 — Working Protocol Semantics and Task Packet Control Topology Are Separate

- **State**: accepted
- **Authority and date**: Sir, 2026-08-07
- **Refines**: `D-015`, `D-027..D-036`; accepts `V-097`, the topology portion of
  `V-098`, and the Protocol/Packet seam reviewed through current-packet dogfood
- **Decision**:
  - Working posture is a local cognitive/action method, not a peer alternative
    to pipeline or graph work-control models.
  - Working Protocol owns the recursive semantics for selecting a bounded
    return, resolving effect authority, obtaining discriminating feedback,
    integrating state, and continuing/replanning/asking/closing.
  - Task Packet owns the progressively disclosed per-Task control topology: a
    linear Plan while one truthful control route suffices, and scoped Plan
    owners plus material graph relations when independent obligations, returns,
    or barriers justify them.
  - The two topology shapes do not create two protocol implementations. The
    same protocol operates the current Plan front in either shape.
- **Rationale**: The former Pipeline/Posture-centric/Recursive comparison mixed
  topology, temporal control, and local method. Separating them preserves a
  cheap linear shape for simple work, graph control for real non-linearity, and
  one predictable Human-Agent operating contract.
- **Consequences**:
  - Task Packet guidance defines shapes and state ownership; Working Protocol
    defines topology pressure detection, state transition, and integration.
  - Pipeline remains revisable under feedback rather than becoming a mandatory
    explore/design/implement/verify lifecycle.
  - Graph topology remains a material-relation projection over scoped linear
    Plans, not a universal DAG schema or CLI scheduler.
- **Reopen trigger**: Real Tasks require materially different control semantics
  for linear and graph shapes, or topology promotion/demotion cannot be made
  predictable without moving more responsibility into Task Packet or runtime.

## D-045 — Task Packet Is a Partial Persistent Per-Task Substrate

- **State**: accepted
- **Authority and date**: Sir, 2026-08-07
- **Refines**: `D-013`, `D-018`, `D-034`, `D-044`; accepts `V-099` and `V-100`
- **Decision**: For a non-trivial Task, Task Packet is the task-lifetime
  persistent but disposable state/collaboration substrate on which an Agent
  applies Working Protocol. It externalizes only task-local state whose future
  management, recovery, coordination, review, or authority value repays its
  maintenance. The Agent/Lead interprets and executes the protocol; Task Packet
  is not the protocol implementation, complete Agent/runtime state, event log,
  chain of thought, external-state mirror, or durable project-truth owner.
- **Rationale**: A filesystem package can preserve consequential state across
  turns, compaction, delegation, and Human task switching without requiring a
  semantic runtime orchestrator. Treating it as a complete protocol instance
  would instead encourage schemas, inferred state, logs, and duplication whose
  maintenance and freshness cost defeat progressive disclosure.
- **Consequences**:
  - Working Protocol defines read/integrate/write-back behavior; Task Packet
    supplies the partial persistent projection for one Task.
  - Packet state remains fallible and freshness-bounded; the Agent combines it
    with current semantic owners and environment evidence before consequential
    action.
  - Trivial work may compress without a packet; every admitted packet begins at
    the smallest useful `packet.md` shape and grows only under real pressure.
  - CLI remains a deterministic carrier/navigation surface, not the protocol
    interpreter or Task-state authority.
- **Reopen trigger**: Representative non-trivial Tasks cannot recover or
  coordinate correctly from a partial filesystem projection, or the state
  needed by Agents cannot be maintained there at lower total cost than another
  existing owner/runtime mechanism.

## D-046 — Task Packet Has Three Coupled State Views

- **State**: accepted
- **Authority and date**: Sir, 2026-08-08
- **Refines**: `D-018`, `D-024`, `D-036`, `D-040`, `D-042`, `D-045`; accepts
  `V-102` and `V-103`
- **Decision**:
  - Treat Human collaboration, work-control, and semantic working state as
    coupled functional views, not three independent stores or a strict layer
    pipeline.
  - Human collaboration state is a bidirectional boundary: `packet.md`
    combines native Human/task contract with consequential projections from
    semantic and work-control owners.
  - Work control requests and consumes bounded semantic returns; integrated
    semantic changes may satisfy, invalidate, reopen, or replan control state.
  - Permit thin, labeled semantic contracts/snapshots in Human and control
    owners when routing, gating, integration, recovery, or collaboration needs
    them. Detailed evidence/design/decision/proof state retains one semantic
    owner.
  - Route write-back by event meaning and consequence rather than one mandatory
    Semantic-to-Work-to-Human sequence or runtime event journal.
- **Rationale**: Strict separation cannot express Phase exit predicates, Cell
  obligations, Plan returns, Human authority input, or control-only changes.
  Unbounded mixing creates competing owners. Coupled views with bounded
  projections preserve both control and semantic authority.
- **Consequences**:
  - `packet.md` is deliberately compositional; semantic modules should not
    absorb work Plans, and Task map/Cell Plans should not copy semantic depth or
    completed-process history.
  - Conflicts resolve from Human authority or the freshest applicable deeper
    owner, followed by outward projection; Human authority changes integrate
    inward before re-projection.
  - Exact examples, freshness handling, and checks remain subject to
    real-task evidence rather than becoming a schema now.
- **Reopen trigger**: The bidirectional model causes persistent drift or owner
  ambiguity, or a real concern demonstrates a fourth independent state
  lifecycle that cannot be represented as a semantic owner or controlled
  projection.

## D-047 — Working Posture Exists to Supply a Reusable SOP

- **State**: accepted
- **Authority and date**: Sir, 2026-08-08
- **Refines**: `D-015`, `D-044`; accepts the simplified proposition in `V-110`
- **Decision**:
  - Working Posture exists primarily to give an Agent a reusable,
    progressively loaded SOP for a recurring work situation.
  - A posture is the recognizable name and activation point for its useful
    method, not a separate mode ontology, Task stage/type, persistent status,
    or information owner.
  - Its minimum useful SOP explains when it applies, how to perform the work
    well, and when to return, stop, or switch.
  - Postures may recur or invoke one another inside mixed, non-linear work.
    A proposed posture without a distinct useful SOP is only a label and does
    not merit admission.
- **Rationale**: The problem is method inconsistency when an LLM improvises a
  recurring kind of work, while one universal protocol cannot contain every
  specialist procedure without losing progressive disclosure. The earlier
  dimensional model introduced more concepts than were needed to establish
  this purpose.
- **Consequences**:
  - Derive and compare candidate posture boundaries by drafting their SOPs
    rather than first enumerating a cognitive-mode taxonomy.
  - A flat catalog of directly triggered specialist SOPs remains the simpler
    baseline where no useful posture family exists.
  - Human predictability and later role/sub-agent specialization are possible
    benefits, not the definition of Working Posture.
- **Reopen trigger**: Direct trigger-based SOPs prove consistently simpler than
  posture handles, or named postures do not improve Agent method selection and
  task results enough to repay vocabulary and switching cost.

## D-048 — Explore Finds Key Information Through an Adaptive Evidence Loop

- **State**: superseded by `D-049`
- **Authority and date**: Sir, 2026-08-08
- **Refines**: `D-015`, `D-038`, `D-043`, `D-047`; accepts the backbone in
  `V-112` with Sir's coarser purpose language
- **Decision**:
  - Define Explore's coarse purpose as **finding key information**.
  - Determine “key” relative to the current useful Task return while allowing
    evidence to reframe the question, owner, route, or return itself.
  - Use an adaptive backbone: frame the inquiry, locate relevant authority and
    context, seek a discriminating observation, test evidence, update the
    problem model/next question, and return a compact synthesis.
  - Do not optimize for exhaustive understanding or treat search records,
    matches, file lists, and context volume as the return.
- **Rationale**: The coarse purpose is easier to understand than a formal
  uncertainty-control definition, while return-relative keyness prevents
  unbounded collection. The adaptive loop integrates the existing Explorer,
  freshness, evidence, counterexample, and synthesis gleanings without fixing
  a query plan before new information arrives.
- **Consequences**:
  - Expand the SOP one step at a time and route earlier gleanings into the
    applicable step.
  - Detailed tool routing, Explorer delegation, rules matching, ablation, and
    independent review remain conditional methods rather than universal steps.
- **Reopen trigger**: Representative Explore work needs broad discovery that
  cannot be guided by even a revisable useful-return frame, or the six-step
  backbone adds more translation cost than it prevents.

## D-049 — Preserve Explore Purpose and Frame; Re-derive the Remaining SOP

- **State**: accepted
- **Authority and date**: Sir, 2026-08-08
- **Supersedes**: `D-048`'s six-step backbone while preserving its coarse
  purpose; accepts the correction in `V-116`
- **Decision**:
  - Preserve Explore's purpose as “find key information.”
  - Preserve Frame as the first non-trivial Explore step: identify the purpose
    or useful return, what is not understood enough, and—when possible—the
    kind of finding that could change direction. Keep it lightweight and
    revisable.
  - Withdraw Locate/Test/Update/Return and the other former steps as an accepted
    Explore sequence. Their occurrence during exploration does not establish
    posture-specific ownership.
  - Keep Explorer sub-agent method distinct from Explore posture. Tool routing,
    filtering, meta-planning, and context isolation cannot define the posture
    merely because they were supplied for a role named Explorer.
  - Do not force unrelated gleanings into Explore. Re-derive the remaining SOP
    from recurring Explore situations, distinctive behavior, and concrete
    failure prevention.
- **Rationale**: The former model organized adjacent concerns into a generic
  information lifecycle rather than proving an Explore-specific method. Its
  apparent completeness came from slot-filling, not semantic derivation.
- **Consequences**:
  - There may be no fixed steps after Frame; a loop, branching strategy, or
    small repertoire remains possible.
  - Universal Working Protocol, Verification, adaptation, and Sub-agent content
    retain their own owners even when invoked during Explore.
  - No Human decision is requested until the Lead has a smaller derived
    proposition with distinct management value.
- **Reopen trigger**: Comparative Explore cases demonstrate that the withdrawn
  six-step sequence is both distinctive and cheaper than a branching or
  lighter-weight method.

## D-050 — Frame Provisionally Defines Relevance for Explore

- **State**: accepted for design; outcome evidence pending
- **Authority and date**: Sir, 2026-08-08
- **Refines**: `D-049`; accepts `V-119` as the current Frame method rather than
  as proven real-task effect
- **Decision**:
  - Frame provisionally defines what information would count as key for the
    current Explore; later findings may revise the definition.
  - Its smallest common prompts are purpose, sought answer/target, material
    scope/resolution, and keyness test. They are thinking questions, not four
    mandatory fields; obvious lookup remains direct.
  - Treat goal-relative minimal sufficient causal structure as conditional
    deepening for explanation, prediction, and intervention work. Use
    `Y/A/E/Z`, counterfactuals, and invariance only when they improve the useful
    return enough to repay cost.
  - Preserve non-causal key information and local/one-off detail when the Frame
    makes them relevant.
- **Rationale**: Software context-location, exploratory-search, sensemaking,
  design-framing, relevant-information compression, and causal-invariance
  research jointly support target-relative but revisable relevance. They do
  not support one universal causal Frame.
- **Consequences**:
  - Frame may be externalized proportionally but is not an approval gate or
    final problem truth.
  - The next Explore design question is how the current Frame selects a fitting
    exploration strategy without recreating a linear pipeline.
  - Real Consumer Tasks must test framing quality, added cost, reframing, and
    downstream task effect before durable SVC confidence is justified.
- **Reopen trigger**: Real tasks show that the four prompts bias or slow
  exploration without improving key-information discovery, or that a simpler
  frame preserves the same behavior.

## Withdrawn Premature Decision Frame

The earlier register pre-created `D-003` through `D-007` for product hierarchy,
responsibility, failure classes, evaluation, and evidence gates. Those meanings
were never accepted and are no longer active decision objects.

Sir's correction showed that the underlying outcome model and inquiry topology
were not yet faithful enough to support those rulings. New IDs will be created
only when the shared problem model is adequate and a real alternative with
lasting consequences is ready for an explicit decision.
