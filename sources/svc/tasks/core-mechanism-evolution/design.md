# Design Synthesis

## Role

This file owns mutable cross-capability design synthesis, the current design
question, and design-content admission rules. [`task-map.md`](task-map.md) owns
the Task/Cell/Plan front and integration route. Accepted decisions belong in
[`decisions.md`](decisions.md), claim evidence in
[`verification.md`](verification.md), and the full active argument in one
linked dossier. Reference-intake notes are not parallel fronts.

## Design Module Navigation

1. Read [`packet.md`](packet.md) for the complete Human current view.
2. Read [`task-map.md`](task-map.md) and its active Cell for work state.
3. Read the **Current Design Question** below only when the active return needs
   design synthesis.
4. Read only its linked dossier.
5. Follow a disputed decision or claim into `decisions.md` or
   `verification.md`.
6. Load [`inquiry.md`](inquiry.md) or notes `00..10` only when the active dossier cites
   their evidence or counterexample.

Conversation transcript, Agent telemetry, and reference notes are never task
state authorities.

## Accepted Outcome and Inquiry Boundary

`D-008` owns the accepted task-local working model: `O-INTERACTION`, `O-TASK`,
and `O-SYSTEM` remain separate observation scales inside one Human-led
software-evolution loop. Inquiry moves from desired result and current failure
through capabilities, candidate mechanisms, vertical rehearsal, quality/cost
evidence, and only then durable SVC or DX projection.

This model is accepted for the design task; it is not yet durable SVC product
truth. A mechanism cannot replace an outcome, and a neat process artifact
cannot establish terminal result quality.

## Functional Topology

The five functional clusters are:

1. task packet
2. working protocol
3. sub-agents
4. verification
5. tastes and the ability to design

The list gives the initial discussion entry, not a linear workflow, dependency
graph, or implementation order. Each cluster participates in multiple loops:

| Operating loop | Cluster contribution under review |
| --- | --- |
| Human collaboration | Task packet exposes the current issue; protocol defines control; verification and taste make consequential decisions judgeable; sub-agent work is integrated by the Lead |
| Agent task work | Packet preserves task-local continuity; protocol routes work; sub-agents isolate bounded contexts; verification returns discriminating evidence; design ability shapes choices |
| System change | Packet bounds the current change; protocol resolves authority and mutation; sub-agents perform bounded work; verification checks changed claims; taste/design preserves system quality |
| Work-system adaptation | Task evidence reveals recurring loss; protocol routes intervention; sub-agents may diagnose or implement it; verification tests effect; taste and methods may be revised or retired |

Keep one active Human question, but follow causal or interface dependencies in
either direction. A discussion may temporarily enter another cluster and then
return; it must not silently turn the numbered list into stages.

## Per-Cluster Discussion Result

Each foreground-cluster discussion should leave a compact, reviewable account of:

1. the capability and its explicit non-goals
2. how it can improve `O-INTERACTION`, `O-TASK`, and `O-SYSTEM`
3. its operating sequence and decisions
4. current SVC footholds and ownership conflicts
5. progressively loaded content and use conditions
6. rough existing-file changes and conditional new file/directory candidates
7. failure modes, simple-task counter-pressure, and unresolved claims

This result is still design input. Cross-cluster reconciliation precedes any
exact landing plan or Impact Handshake.

## Human Discussion Contract

Before requesting a ruling, the Lead provides the question and why it matters,
accepted facts versus hypotheses, status quo and real alternatives, expected
benefit and total cost, failure modes, reversibility, falsifier, downstream
consequences, a conditional recommendation, and the smallest decision Sir must
make. Foreground one issue without hiding material dependencies.

Sir supplies product intent and personal taste, reviews whether the model is
faithful, and owns material scope, design, trade-off, and acceptance decisions.
No decision is inferred from silence. If the shared problem model is contested,
landing discussion pauses.

## Admission Rules

- Prefer an existing owner. A new content surface requires useful content plus
  a distinct owner, trigger, consumer, conflict behavior, verification, and
  marginal complexity return.
- Separate personal preference authority from project product/technical truth.
  An Agent may challenge a rebuttable default but may not silently overwrite
  either authority.
- Keep `packet.md` as the Human semantic current view; do not turn it into a
  runtime status projection, scheduler, work graph, or complete Agent memory.
- Route work by semantic uncertainty and feedback need, not edit volume or a
  fixed Agent pipeline.
- Verification starts from a changed claim and a discriminating observation;
  another Agent is useful only when it contributes relevant independence or
  new information.
- Adaptation may select a candidate intervention but cannot create durable
  mutation authority. Later evidence must be able to keep, revise, or retire
  the intervention.
- Preserve `S-SIMPLE` and compare the status quo. No universal Task IR,
  Grounding Gate, status bar, Reviewer, memory system, ECCA layout, assurance
  schema, retrospective hook, or CLI semantic orchestrator is pre-approved.
