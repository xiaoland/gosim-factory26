## Accepted Boundary

Explorer is a candidate **delegated work contract**, not another Working Method
and not yet an admitted SVC preset. Its boundary is a local, high-entropy
information problem that has a known downstream consumer but does not justify
Primary absorbing the retrieval trajectory.

```text
bounded information / owner / constraint question
  -> adaptive local acquisition, source comparison, noise filtering,
     relation modeling, and counterexample search as useful
  -> concise question-shaped report with decisive evidence anchors,
     uncertainty, freshness limits, and next discriminator when needed
  -> Primary or another semantic owner consumes the report
```

The Primary can use Explore directly. An Explorer-shaped Child may apply
Explore plus Model, Generate, or Discriminate locally; no profile name fixes a
single posture sequence. The report is the intended product, so the semantic
consumer must understand it. Delegation fails economically when that requires
absorbing substantially the same raw retrieval trajectory.

## Candidate Contract

This is a semantic contract, not a mandatory Assignment schema:

| Concern | Candidate boundary |
| --- | --- |
| use condition | a consumer-relevant information gap has non-obvious evidence paths and meaningful local search complexity/noise whose trajectory can be compressed |
| task-specific input | bounded question, intended consumer/use, evidence/authority scope, freshness or snapshot pressure, and read-only/default effect constraint |
| local work | select/compose retrieval modes, follow source/owner/causal relations, test material counterexamples, preserve consequential anchors, stop at sufficient answer or bounded incompleteness |
| report | answer/findings first; decisive source handles; material conflicts, uncertainty, freshness/scope limits; next discriminator only when useful; never a transcript or downstream decision |
| consumption | the Primary or named semantic owner reads the report and selectively inspects consequential sources; this is Inquiry/decision support, not validation of Child completion |
| effect | report publication only; no Task Packet, durable truth, code, or external-state mutation by default |
| escalation | a bounded ambiguity or authority mismatch that prevents the requested report or materially changes the global route |

The model follows `D-087`: information results use the report route and do not
receive a generic validator. Individual claims can later be qualified through
Verification when the consumer's use and loss justify it.

## What the Profile Must Add

If Explorer becomes a preset, it cannot merely repeat “use Explore.” It must
add a stable, economical delegation boundary:

- isolate a local evidence trajectory from coupled Task context;
- make the report legible to its downstream semantic consumer;
- preserve evidence authority, freshness, and unknowns rather than emitting a
  polished but uncheckable answer;
- avoid effectful action and prevent findings from silently becoming a decision;
- stop/escalate when the local question turns into global design, authority,
  or acceptance work.

Whether these properties save more Primary context than report consumption and
claim-checking cost remains the economic test; a familiar `Explorer` label
does not answer it.

## Guidance Ownership to Derive

The next inquiry distinguishes three homes:

1. **Explore Working Method guidance**: generally useful information-work
   logic such as framing, evidence sufficiency, choosing a discriminating
   observation, modeling relations, and treating no-evidence as bounded rather
   than negative proof.
2. **Explorer profile**: isolation-specific work boundary, report compression,
   read-only/default effect guardrail, and failure behavior.
3. **On-demand skill/tool guidance**: concrete AST, symbol-graph, text,
   structured-data, provenance, runtime, remote-probe, or external-research
   tool usage. The profile chooses/combines appropriate modes; it should not
   duplicate every tool manual into SVC.
