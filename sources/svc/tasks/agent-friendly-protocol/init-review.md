# `svc init` Command and Output Review

## Discussion order

Review `svc init` in this order so that presentation does not freeze an
incorrect information service:

1. command purpose, ownership, and trigger;
2. plan/apply state machine, including noop, blockers, and stale plans;
3. default plan content and text presentation;
4. apply terminal result and recovery information;
5. compact JSON projections for deliberate script/CI consumption;
6. stdout, stderr, and exit-status routing;
7. self-sufficient layered help;
8. consistency with root `status` and `adopt`, followed by implementation
   impact, mental rehearsal, and real-project acceptance.

The accepted removal of the generated SVC Skill and `--agent codex` is an
already known input to every item. The accepted dev-profile migration remains
outside this command review.

## Correction

`svc init` is the project-wide SVC integration command. It is not the owner of
the dev domain and must not become a carrier for the accepted dev-profile
schema migration merely because both touch `svc.json`.

The earlier next-step framing also overstated the plan digest. A
`plan -> digest -> apply` sequence is not inherently Human-Agent
collaboration. It is an exact-state mutation protocol that can be used by one
script, one Agent, one Human, or a handoff. The actors and their authorization
remain outside SVC.

## Current actual ownership

Current `plan_init()` owns a bounded integration reconciliation over:

- missing `svc.json`: create the minimal current-schema project/adoption state;
- existing `svc.json`: validate it, but do not rewrite its dev/run declarations;
- `.gitignore`: maintain the marked `svc.local.json` ignore block;
- `AGENTS.md`: maintain a marked SVC navigation/router block;
- `docs/index.md`: maintain the retained marked navigation block;
- `.agents/skills/svc/SKILL.md`: currently maintain the Codex Skill, already
  accepted for removal in this unit.

It preserves unmarked Consumer content, blocks modified managed regions, and
refuses unsupported/old configuration schemas. Current code explicitly says
that SVC does not automatically migrate schema-v1 projects. The accepted
profile flattening therefore belongs to a separate configuration/release
migration plan and real Consumer edits, followed by ordinary validation and
adoption. It is not an `init` sub-feature.

After the already accepted Skill removal, the smallest init ownership is:

```text
minimal project state when absent
+ managed local-config ignore block
+ managed AGENTS router block
+ managed docs/index navigation block
```

Remove `--agent codex`; there is no remaining provider choice.

## What the plan digest actually does

`LocalPlan.digest` binds:

- command, canonical repository, and target SVC version;
- every planned path/action/reason;
- before content hash and file mode;
- parent path states;
- generated after-content hash;
- blockers.

Apply recomputes the plan from current state, requires the supplied digest to
match, rechecks path preconditions, stages generated bytes, performs atomic
per-file replacements, verifies postconditions, and rolls back ordinary
partial failure. The digest therefore provides:

1. **request-to-plan binding** — apply cannot silently execute a different
   operation set than the caller selected;
2. **stale-plan rejection** — repository or generated-target changes force a
   new plan;
3. **deterministic automation** — a script can obtain one exact plan and apply
   only that result.

The SVC CI and publish workflows demonstrate the third service: both call
`svc init --json`, extract only `plan_digest`, and immediately apply it to a
fresh acceptance repository. No Human-Agent handoff occurs.

The current plan output does **not** contain generated after-bytes or a diff.
A Human can review paths, action kinds, reasons, hashes, and blockers, but
cannot review the exact proposed content from that output alone. Consequently:

- do not call the digest Human authorization, approval, or an intrinsically
  collaborative receipt;
- do not claim that the Human reviewed exact generated content;
- retain or remove the mechanism based on exact-state mutation value, not a
  collaboration slogan.

## Provisional recommendation

Retain plan-first plus exact-digest apply. `init` can touch several
Consumer-owned files, and the digest prevents a later apply from silently
expanding or changing the previously observed mutation scope. This is useful
even with one caller and is already exercised by real SVC automation.

The collaboration value, where present, comes from the project integration
that init maintains: Human and Agent participants encounter the same adopted
SVC state and the same bounded AGENTS/docs routing surfaces. The digest is only
the safe mutation mechanism underneath that shared project state.

This recommendation remains challengeable. If the resulting plan presentation
does not give a caller enough information to decide whether to apply, requiring
the digest may be ceremony rather than a useful review boundary. The next
command review should therefore evaluate the actual plan content and
presentation before treating the current two-step grammar as frozen.

## 1. Command purpose, ownership, and trigger — accepted

### One bounded integration command, two state-derived paths

Keep one public `svc init` command. Its information service is:

> Establish or reconcile the bounded, project-wide SVC integration owned by
> the installed corpus, without changing Consumer-owned configuration or
> unmarked content.

The missing-project and existing-project cases are not the same adoption
lifecycle. The first path records an initial adoption baseline; the repair path
must not advance an existing baseline. They can still remain one command
because both operate over the same bounded integration owner set and converge
on the same narrower integration invariant:

```text
valid current-schema svc.json exists
managed svc.local.json ignore block is current
managed AGENTS router block is current
managed docs/index navigation block is current
unmarked Consumer content is preserved
```

The first path establishes a missing minimal project state and the managed
surfaces. The existing-project path validates the effective configuration and
only verifies or repairs managed surfaces. Both use the same plan/apply
mutation boundary and block on the same provenance conflicts. Splitting
`init` and `repair`/`sync` would make callers first classify repository state
even though SVC can derive the path without ambiguity. It would add an
interface without a distinct managed owner or invocation pattern.

The name `init` is slightly narrower than the full idempotent behavior, but it
is preferable to adding or renaming to a broad `sync`: `sync` could imply
Corpus, dependency, configuration, or version synchronization that the command
does not perform. Self-sufficient help must therefore state explicitly that
`init` plans first-time establishment **or** repair of managed integration.

### Owned effects

After Skill removal, `init` may plan only:

- creation of a missing minimal `svc.json` containing schema and adopted
  baseline state;
- creation or refresh of SVC's marked block in `.gitignore`;
- creation or refresh of SVC's marked router block in `AGENTS.md`;
- creation or refresh of SVC's marked navigation block in `docs/index.md`.

One bounded retirement operation is also required by the accepted removal:
delete `.agents/skills/svc/SKILL.md` only when it is still provably the clean
whole-file artifact generated by SVC. A recognizable generated file whose
marker/body has been modified becomes a blocker requiring explicit review; a
file with no SVC provenance is outside the plan. Neither is silently deleted.
This operation is visible in the plan; merely ceasing to generate the Skill
would leave the rejected interface installed in real Consumers.

It validates an existing `svc.json` and effective local overlay before repair,
but does not rewrite their `dev`, `run`, or other Consumer declarations.

### Explicit non-ownership

`svc init` does not:

- discover whether a project should adopt SVC;
- migrate configuration schema or flatten dev profiles;
- migrate configuration or advance an existing project's Corpus baseline
  (`svc upgrade` owns those targets);
- create or edit `svc.local.json`;
- install or update the CLI/package;
- probe, start, stop, or execute project runtime declarations;
- rewrite unmarked Consumer content.

### Triggers

Valid triggers are explicit and state-oriented:

- a Human, Agent, or bootstrap script wants to establish SVC integration in a
  repository;
- root `svc status` identifies missing or stale managed integration and points
  to `svc init` as the repair continuation;
- SVC's own release/acceptance automation verifies that a fresh integration
  can be planned, applied, and then becomes a noop.

`init` is not an implicit prelude to every SVC command and must not silently
run during `status`, `adopt`, `dev`, or `run`. The caller chooses the mutation
workflow; the digest binds state, not Human authorization.

One current state-machine inconsistency must be repaired in the later
plan/apply review: root `status` classifies a repository with missing
`svc.json` but an orphan `svc.local.json` as malformed, while current
`plan_init()` can still plan creation of the base file without first validating
that overlay. `init` must not make an invalid orphan overlay effective by
accident. This does not require another command; it requires the same invalid
state to block consistently.

### First review decision

Accept or revise this public definition before discussing plan fields:

```text
svc init [<repo>] [--apply <plan-digest>] [--json]

default: plan establishment or repair of bounded project-wide integration
--apply: apply only the exact currently reproducible plan
```

No `--agent`, `--repair`, `--sync`, dev selector, or migration flag is added.

Sir accepted this definition on 2026-08-08.

## 2. Plan/apply state machine — accepted

### One computed snapshot, no stored approval object

Every invocation computes a fresh integration snapshot from the current
repository and installed corpus. SVC does not save the earlier plan and does
not deserialize it during apply. The supplied digest is a snapshot-selection
token: it must equal the freshly computed plan before mutation may begin.

```text
svc init <repo>
        |
        v
compute current plan P
        |
        +-- blockers ----------------------> blocked
        |
        +-- no operations -----------------> noop
        |
        `-- one or more operations --------> ready

svc init <repo> --apply D
        |
        v
recompute current plan P
        |
        +-- D != digest(P) ----------------> plan-digest-mismatch
        +-- P is blocked ------------------> plan-blocked
        +-- P is noop ---------------------> verified noop
        `-- P is ready
                |
                +-- state changes before/during commit -> stale-plan
                +-- stage/commit/verify fails ---------> apply failure + rollback outcome
                `-- all postconditions pass -----------> applied
```

This remains optimistic concurrency, not a lock, approval record, or shared
execution. Two participants may exchange the digest, but SVC records neither
participant nor authorization. The first successful apply changes the next
computed plan, so a second caller holding the old digest normally receives a
digest mismatch instead of silently repeating the old writes.

### Planning results

The default non-mutating call has exactly three resolved results:

- `ready`: at least one owned operation can be applied and there are no
  blockers;
- `noop`: the bounded integration invariant already holds and there are no
  blockers;
- `blocked`: at least one decisive configuration, path, or provenance conflict
  prevents mutation.

`blocked` is a plan result, not a partially applicable plan. Even if SVC can
derive hypothetical writes for other paths, it must not apply any of them. The
valid continuation is to resolve the blockers and compute a new plan. A
blocked plan must not advertise an apply command.

`noop` is also a meaningful terminal result. Default text need not encourage a
redundant apply, but `--apply <noop-digest>` remains valid and returns verified
`noop`. This preserves the real CI pattern that mechanically computes a plan
and applies its digest without adding a branch solely for idempotence.

### Apply selection and concurrency conflicts

Keep these two conflicts distinct:

1. `plan-digest-mismatch`: the caller's digest does not identify the plan just
   recomputed from the current repository and corpus. It may be a typo, an old
   observation, a repository change, or a corpus change; SVC cannot truthfully
   claim which. Recovery is to inspect the newly computed plan.
2. `stale-plan`: the approved current plan passed digest selection, but a
   target's bytes, mode, or parent-path state changed before or during commit.
   This is a demonstrated concurrent-state race. SVC stops, rolls back any of
   its already committed writes where safe, and requires a fresh plan.

Neither condition permits SVC to substitute the new plan, auto-approve it, or
continue with unaffected operations.

### Transaction terminal results

Only two apply results are successful:

- `applied`: every planned write committed, every after-hash verified, and the
  result identifies the selected plan digest and changed paths/count;
- `noop`: the selected plan contained no writes and the current state still
  matched it.

All other apply outcomes are failures. Staging, commit, or postcondition
failure triggers best-effort rollback of writes owned by this transaction.
Rollback has three materially different outcomes:

- `succeeded`: the pre-apply state was restored;
- `conflicted`: a concurrent writer replaced at least one value, so SVC
  preserved that newer content rather than overwriting it;
- `failed`: SVC could not restore at least part of its own mutation.

`conflicted` requires a new observation and remains a state/concurrency
conflict. `failed` is an infrastructure failure and must use the infrastructure
exit boundary even when the original trigger was a stale-plan conflict. No
failure may emit `applied` or claim that integration is healthy; the recovery
is to run root `status` or compute a fresh init plan after inspecting the
reported rollback state.

### State consistency correction

The orphan-local-overlay case identified in item 1 belongs in the planning
transition: missing `svc.json` plus existing `svc.local.json` produces
`blocked`, with no applicable writes. The caller must explicitly preserve,
move, or remove that local state before initial adoption. `init` must not create
a base configuration that silently activates an unreviewed overlay.

### Second review decision

Accept or revise this state machine before selecting plan fields and text:

- plan: `ready | noop | blocked`;
- successful apply: `applied | noop`;
- selection/concurrency conflicts: `plan-digest-mismatch | plan-blocked |
  stale-plan`;
- infrastructure/transaction failure carries `rollback: succeeded |
  conflicted | failed` when mutation may have begun.

The exact stdout/stderr routing, exit table, and serialized fields remain later
review items; this section fixes their semantics first.

Sir accepted this state machine on 2026-08-08.

## 3. Default plan content and text presentation — accepted

### Information move

The default plan serves one bounded decision:

> Understand which SVC-owned project integration extents would change, why,
> whether any conflict prevents the whole mutation, and the exact continuation
> that selects this plan.

It is not a file browser, generated-content approval record, configuration
migration preview, or substitute for `status`. The text must nevertheless make
the init/upgrade boundary impossible to misread.

### Minimum plan context

Every default plan result identifies:

- terminal plan status: `ready`, `noop`, or `blocked`;
- canonical repository root;
- intent: `establish` missing integration or `repair` existing integration;
- installed corpus version used to derive generated content;
- adoption-baseline disposition:
  - `create <version>` for first establishment;
  - `<version> (unchanged)` for every existing project;
- for `ready`, the complete operation count and each operation's action, path,
  owned extent, and semantic reason;
- for `blocked`, every decisive blocker with code, path, and explanation;
- one self-contained continuation appropriate to the result.

Do not call the corpus version `target_version` in default text. On a real
10.0.1-adopted project, current output says `ready for SVC 11.0.1` even though
`init` does not update `svc.json`. `Corpus: 11.0.1` plus
`Adopted baseline: 10.0.1 (unchanged)` states the two facts accurately.

### Operation vocabulary and extent

Use the smallest filesystem verbs that distinguish actual effects:

- `create`: create an absent whole file;
- `append`: add a bounded SVC-managed block to a Consumer-owned file;
- `refresh`: replace only an existing clean SVC-managed block;
- `delete`: remove a clean whole-file artifact previously generated by SVC.

Path plus verb is insufficient for Consumer-owned files because
`refresh AGENTS.md` can sound like a whole-file rewrite. Text must name the
owned extent, such as `SVC navigation block`, and use domain-specific reasons
such as `update Agent router` or `update documentation navigation`. Preserve the
distinction between whole-file `svc.json` creation, managed-block mutation, and
clean generated-Skill deletion.

### Ready example

After the accepted Skill removal, a real adoption-pending Consumer repair would
have this shape:

```text
svc init: ready
Repository: /Volumes/WorkSSD/Development/InKCre/core-py
Intent: repair managed integration
Corpus: 11.0.1
Adopted baseline: 10.0.1 (unchanged)

Would change (3):
  delete  .agents/skills/svc/SKILL.md (clean generated file) - retire CLI Skill
  refresh AGENTS.md (SVC navigation block) - update Agent router
  refresh docs/index.md (SVC navigation block) - update docs navigation

Apply exact plan:
  svc init /Volumes/WorkSSD/Development/InKCre/core-py --apply <full-plan-digest>
```

The apply command includes the canonical, shell-quoted repository argument and
the full digest. Do not print the digest once as metadata and then repeat it in
the command. The executable continuation is the useful representation and can
be handed to another participant on the same host without relying on cwd.

### Noop and blocked examples

`noop` is deliberately shorter and does not advertise a redundant text-mode
apply:

```text
svc init: noop
Repository: /repo
Intent: repair managed integration
Corpus: 11.0.1
Adopted baseline: 11.0.1 (unchanged)
Managed integration is current; no changes.
```

Compact JSON retains the noop digest for the demonstrated unconditional CI
plan/apply loop; default text serves a participant deciding what to do next.

`blocked` leads with the consequence and blockers, not hypothetical independent
writes or an unusable digest:

```text
svc init: blocked; no changes can be applied
Repository: /repo
Intent: repair managed integration
Corpus: 11.0.1
Adopted baseline: 10.0.1 (unchanged)

Blockers (1):
  AGENTS.md [generated-guidance-drift] - SVC navigation block is modified or malformed

Next: resolve the blocker, then recompute the plan:
  svc init /repo
```

The compact JSON projection also omits independently derived operations and an
unusable digest for a blocked plan. Blockers are the complete public result.

### No inline diff or hashes by default

Do not inline whole-file after-content, unified diffs, per-file SHA-256 values,
file modes, or parent-path states in default text:

- `AGENTS.md` and `docs/index.md` are Consumer-owned files; whole-file diffs
  repeat unrelated content;
- the same generated navigation body may be projected into multiple files,
  duplicating tokens without adding a new decision;
- hashes and parent-state tuples establish exactness for machine comparison but
  do not explain the semantic change;
- this plan asks whether SVC may reconcile proven owned extents, not whether the
  caller approves generated prose byte by byte.

The operation reason and owned extent must therefore be strong enough to make
the scope non-opaque. Do not add `--diff`, `--preview`, or another output mode
without real evidence that bounded semantic operations fail this decision
service. If later acceptance proves that exact generated content must be seen
before apply, the smallest reopening is a preview of SVC-owned spans only, not
whole Consumer files.

### Third review decision

Accept or revise this default-text contract before specifying apply receipts or
the compact JSON projection. In particular, decide whether semantic
`action + path + owned extent + reason` is sufficient, or whether real use
justifies an additional bounded content preview.

Sir accepted this contract on 2026-08-08 with one wording correction. Use
`Would change (<count>):`, not `Changes` or the ungrammatical `Will changes`:
the conditional form makes clear that the default plan has not mutated the
repository and only an exact apply would realize the listed operations.

## 4. Apply terminal result and recovery — accepted

### Information move

The apply result serves a different moment from the plan:

> State which selected operations actually reached their approved
> postconditions, what repository effect remains, and which independent
> observation or recovery action is valid next.

It must be a self-contained bounded receipt. It must not require the initiating
participant to remember the earlier plan, and it must not broaden file-level
verification into a claim that the project is healthy or fully adopted.

### Successful `applied` result

An applied result identifies:

- canonical repository root;
- applied plan digest;
- corpus version and adoption-baseline disposition;
- complete changed operation count;
- every realized action, path, and owned extent, using past-tense counterparts
  of the plan vocabulary: `created`, `appended`, `refreshed`, `deleted`;
- exact verification scope: every planned path reached its approved
  postcondition;
- root `svc status <repo>` as the next independent observation.

```text
svc init: applied
Repository: /Volumes/WorkSSD/Development/InKCre/core-py
Corpus: 11.0.1
Adopted baseline: 10.0.1 (unchanged)
Applied plan: <full-plan-digest>

Changed (3):
  deleted   .agents/skills/svc/SKILL.md (clean generated file)
  refreshed AGENTS.md (SVC navigation block)
  refreshed docs/index.md (SVC navigation block)

Verification: all planned path postconditions passed
Next observation:
  svc status /Volumes/WorkSSD/Development/InKCre/core-py
```

Do not say merely `N project files changed`: paths and extents are the actual
handoff value. Do not say `integration verified`, `healthy`, or `adopted`.
Current verification compares each approved after-state; root status still owns
configuration, version, runtime, and generated-integration observation. Real
SVC CI already keeps this horizon separate by running status after apply.

### Successful applied-noop result

Applying an exact noop digest returns a receipt because scripts deliberately
use the unconditional plan/apply loop:

```text
svc init: noop
Repository: /repo
Corpus: 11.0.1
Adopted baseline: 11.0.1 (unchanged)
Verified plan: <full-plan-digest>
Changed: none; no managed operation required a write
Next observation:
  svc status /repo
```

This means only that the selected init plan remained a noop. It does not claim
that root status will be healthy; for example, an existing project may still
need adoption even when its managed integration surfaces are current.

### Apply conflict before mutation

`plan-digest-mismatch` and `plan-blocked` state explicitly that SVC changed
nothing. Do not print the newly computed digest as an apply shortcut: the
caller has not observed that new plan.

```text
svc init: plan-digest-mismatch; no files changed
Repository: /repo
The selected digest no longer identifies the current plan.
Next: recompute and inspect the plan:
  svc init /repo
```

A pre-commit `stale-plan` uses the same `no files changed` disposition. If the
race occurs after at least one operation committed, its terminal result instead
includes the rollback result below.

### Apply failure after mutation may have begun

An apply failure reports recovery disposition before internal detail:

- error code and concise message;
- canonical repository and selected plan digest;
- failing phase and path when known;
- repository effect:
  - `restored`: all SVC-committed changes were rolled back;
  - `external-changes-preserved`: rollback did not overwrite paths changed by
    another writer;
  - `uncertain`: SVC could not restore or verify at least one path;
- affected paths, including specific conflicted or unrestored paths when known;
- an exact next observation, never an automatic reapply command.

```text
svc init: postcondition-failed
Repository: /repo
Selected plan: <full-plan-digest>
Failed: verification of AGENTS.md
Repository effect: external changes preserved
  AGENTS.md - concurrent content was not overwritten
Next: inspect the affected paths, then observe project state:
  svc status /repo
Recompute the init plan before any retry.
```

The internal rollback values map deliberately:

- `succeeded` -> `restored`;
- `conflicted` -> `external-changes-preserved`;
- `failed` -> `uncertain`.

The aggregate word alone is insufficient for recovery in a large project.
Rollback must collect per-path outcomes rather than returning only
`succeeded|conflicted|failed`. If no mutation began, omit rollback entirely and
say that no files changed.

### No automatic status or retry

Apply verifies its owned filesystem transaction and stops. It does not invoke
root status internally, automatically retry a new plan, or apply independently
unblocked operations. Returning `svc status <repo>` preserves the separate
observation horizon and lets another participant continue with an ordinary
command.

### Fourth review decision

Accept or revise the distinction between:

- a successful filesystem receipt (`applied|noop`);
- a pre-mutation rejection that says no files changed;
- a post-mutation failure that reports `restored`,
  `external-changes-preserved`, or `uncertain` plus per-path recovery evidence.

The exact compact JSON fields and stdout/stderr/exit routing remain subsequent
review items.

Sir accepted this receipt/recovery contract on 2026-08-08.

## 5. Compact JSON projection — decided

Sir delegated this projection without a separate review gate. The decision is
command-local rather than a universal SVC response schema.

### Wire contract

`--json` emits exactly one compact, stable-key-order JSON value and no text
projection. It is for deliberate CI/script field consumption, not the default
Agent/Human representation.

Use init response schema version 2 because the shape deliberately renames an
ambiguous field and changes operation structure. Do not retain aliases for the
current response: the only demonstrated machine plan consumer reads
`plan_digest`, which remains top-level and unchanged.

Plan and apply success share these accurate facts:

- `command: "init"`;
- `mode: "plan" | "apply"`, which disambiguates plan-noop from applied-noop;
- `status` from the accepted state machine;
- canonical `repo`;
- `intent: "establish" | "repair"`;
- `corpus_version`, replacing misleading `target_version`;
- `corpus_baseline: {disposition, version}` where disposition is `create` or
  `unchanged`;
- top-level `plan_digest`;
- ordered `operations`;
- plan-only ordered `blockers`.

Do not include a redundant operation count/summary, prose continuation, default
text lines, or audience marker. Array length supplies the count; scripts own
their control flow.

### Exact operation shape

Each operation is self-explanatory without using presentation prose as
identity:

```text
action                create | append | refresh | delete
path                  normalized repository-relative path
surface               project-state | local-config-ignore | agent-router |
                      docs-navigation | legacy-cli-skill
extent                whole-file | svc-managed-block
before/after          state plus exact sha256 and meaningful POSIX mode
```

An absent side uses `{"state":"absent"}`; a POSIX file side uses
`{"posix_mode":420,"sha256":"...","state":"file"}`. Delete therefore has
an explicit absent after-state rather than overloading a null content hash. On
POSIX, the plan must set and verify an intended after-mode for created files
instead of letting a temporary-file default become an undocumented side
effect. On platforms without meaningful POSIX permission bits, omit
`posix_mode` rather than mislabeling a synthetic value as portable authority.

`surface` and `extent` are stable semantic names. Default text derives its
reason from them and the action; mutable prose is not stored as the operation's
identity.

### Plan example

The wire value is one line; this shortened example preserves that form:

```json
{"blockers":[],"command":"init","corpus_baseline":{"disposition":"unchanged","version":"10.0.1"},"corpus_version":"11.0.1","intent":"repair","mode":"plan","operations":[{"action":"refresh","after":{"posix_mode":420,"sha256":"<sha256>","state":"file"},"before":{"posix_mode":420,"sha256":"<sha256>","state":"file"},"extent":"svc-managed-block","path":"AGENTS.md","surface":"agent-router"}],"plan_digest":"<digest>","repo":"/repo","schema_version":2,"status":"ready"}
```

For `noop`, `operations` is empty. For `blocked`, both default text and machine
semantics treat no operation as applicable: public `operations` is empty and
`blockers` contains `{code,path,message}` values. A blocked result omits
`plan_digest`; the caller must resolve blockers and request a new plan.

### Apply example and verification

Apply success returns the realized operations in the same exact shape and adds
only an explicit verification object:

```json
{"command":"init","corpus_baseline":{"disposition":"unchanged","version":"10.0.1"},"corpus_version":"11.0.1","intent":"repair","mode":"apply","operations":[{"action":"refresh","after":{"posix_mode":420,"sha256":"<sha256>","state":"file"},"before":{"posix_mode":420,"sha256":"<sha256>","state":"file"},"extent":"svc-managed-block","path":"AGENTS.md","surface":"agent-router"}],"plan_digest":"<digest>","repo":"/repo","schema_version":2,"status":"applied","verification":{"scope":"planned-path-postconditions","status":"passed"}}
```

Applied-noop has an empty operations array and the same bounded verification
scope. Neither form includes `healthy`, an adoption conclusion, or a `next`
field.

### Digest signature versus presentation

The digest binds the effect-bearing plan signature:

- command-local plan schema, canonical repo, corpus version, intent, and
  adoption-baseline disposition;
- ordered action/path/surface/extent values;
- exact before/after state, content hash, intended POSIX mode when meaningful,
  and parent
  preconditions;
- blocker code/path for a blocked observation.

It does not bind rendered reason sentences, blocker prose, text labels, JSON
key order, or other presentation. Wording changes must not invalidate an
otherwise identical filesystem mutation.

Parent-path preconditions remain in this internal signature but not in the
public operation projection. They protect apply against topology races; no
demonstrated CI/script consumer needs to enumerate them, and the digest already
binds them.

### Error JSON

Keep the existing common compact error envelope rather than creating an
init-only envelope. Init details add exact recovery facts:

- before mutation: `command`, `repo`, selected digest when available, and
  `repository_effect: "none"`;
- after mutation began: selected digest, phase/path, and
  `rollback: {status, restored_paths, preserved_external_paths,
  unrestored_paths}`.

Do not return the newly computed digest as an apply shortcut after a mismatch.
The caller must obtain a new plan object first.

## 6. Stdout, stderr, interrupt, and exit status — accepted

### Channel law

Route by whether SVC resolved the requested information service, not merely by
whether the exit code is zero:

- resolved plan (`ready`, `noop`, or `blocked`) -> stdout;
- successful apply (`applied` or applied-noop) -> stdout;
- grammar errors, apply selection conflicts, concurrent-state conflicts, and
  infrastructure/transaction failures -> stderr;
- no progress stream: init operations are bounded local filesystem mutations,
  not long-running work.

Default text and `--json` use the same semantic routing. JSON emits one compact
value on the selected terminal channel. The other channel remains empty; do
not print text hints beside JSON.

`blocked` stays stdout with exit 3 because it is a complete non-mutating plan
observation containing the decisive blockers. `plan-blocked` during an explicit
apply is different: the caller requested mutation with a non-applicable plan,
so the structured rejection goes to stderr.

### Exit table

```text
0    ready plan, noop plan, applied, applied-noop
2    invalid CLI grammar
3    blocked plan; digest mismatch; plan blocked; stale/concurrent state with
     no mutation, successful rollback, or preserved external changes
4    staging/commit/postcondition/integrity failure; rollback failed or final
     repository effect is uncertain
130  caller Ctrl+C when no rollback failure occurred
```

An apply infrastructure failure remains exit 4 even when rollback succeeds:
the repository may be restored, but the requested SVC operation did not work.
A rollback failure also upgrades an otherwise ordinary stale/interrupt path to
exit 4 because recoverable repository state could not be established.

### Ctrl+C transaction boundary

Current code lets `KeyboardInterrupt` escape the transaction, so Ctrl+C during
commit can leave partial writes and cannot honor JSON mode. That is incompatible
with the accepted receipt.

The transaction boundary must handle interactive SIGINT explicitly:

- before any commit: report `interrupted; no files changed`, exit 130;
- after a commit: attempt the same ownership-safe rollback and report per-path
  recovery;
- rollback `succeeded` or `conflicted`: exit 130, preserving the fact that the
  caller interrupted;
- rollback `failed`: exit 4 with `uncertain` repository effect.

Default interrupt output is stderr. `--json` emits one compact error value to
stderr. A second interrupt, SIGKILL, host loss, or power loss cannot be promised
a terminal receipt; implementation rehearsal must verify the atomic-write and
post-restart observation boundary rather than claim impossible cleanup.

### Sixth review decision

Accept or revise the channel and exit law, especially the two non-obvious
boundaries:

1. a resolved blocked plan is stdout/exit 3, while an apply rejection is
   stderr/exit 3;
2. Ctrl+C normally remains 130 after recovery, but rollback failure becomes
   exit 4 because repository state is uncertain.

No product implementation is authorized by this review.

Sir accepted this channel/exit contract on 2026-08-08.

## 7. Self-sufficient layered help — accepted

### Root help owns selection

Root help needs one accurate selection line, not the full contract:

```text
init    Establish or repair bounded project integration (plan-first)
```

This distinguishes init from `status` observation and `upgrade` migration while
revealing that repeated repair is intentional. Root help also
ends with the general discovery rule `Use svc <command> --help for the complete
command contract.` Corpus lookup remains Corpus discovery, not CLI-help
fallback.

### Init help owns operation

`svc init --help` must be enough to invoke the command and correctly interpret
its result without reading a Skill, README, or Corpus document. Its minimum
content is:

```text
usage: svc init [-h] [--apply PLAN_DIGEST] [--json] [repo]

Plan first-time establishment or repair of bounded SVC project integration.
Without --apply, inspect a non-mutating plan. With --apply, SVC recomputes the
current plan and applies it only when PLAN_DIGEST still identifies that exact
plan.

Owned effects:
  - create a missing minimal svc.json;
  - maintain SVC-marked blocks in .gitignore, AGENTS.md, and docs/index.md;
  - retire a clean whole-file SVC CLI Skill generated by an earlier release.

An existing svc.json is validated but its Corpus baseline, configuration

Plan results:
  ready|noop       stdout, exit 0
  blocked          stdout, exit 3; resolve blockers and plan again

Apply results:
  applied|noop     stdout, exit 0; observe next with svc status <repo>
  state conflict   stderr, exit 3; inspect and plan again
  transaction failure or uncertain recovery
                   stderr, exit 4; inspect reported paths before retry
  interrupted      stderr, exit 130 unless rollback failed

--json emits one compact machine value for scripts/CI on the same terminal

positional arguments:
  repo                 Repository root (default: current directory)

options:
  -h, --help            Show this help and exit
  --apply PLAN_DIGEST   Apply only the freshly reproduced exact plan
  --json                Emit the compact scripts/CI projection

examples:
  svc init
  svc init /path/to/repo
  svc init /path/to/repo --apply <plan-digest>
  svc init /path/to/repo --json
```

- Human authorization language;
- a direction to use `svc lookup` to learn the CLI.

result classes, channels, exits, and continuations. Detailed per-path facts

## 8. Cross-command closure and implementation rehearsal — candidate

### Status must expose independent state dimensions

Root status currently compresses several dimensions into one ordered chain of
conditions. The target contract keeps them distinct:

```text
runtime        source-tree | current | mismatch
configuration missing | current | invalid | schema-blocked | orphan-local
corpus         absent | behind | current | ahead
integration    current | repairable | blocked
```

Overall disposition and one primary continuation are derived from those facts,
but the result must not hide secondary anomalies. The smallest deterministic
transition order is:

1. invalid/schema-blocked/orphan configuration -> Consumer repair or migration;
2. runtime/package mismatch -> repair the installation with its package manager;
3. unadopted, otherwise valid repository -> non-mutating init establish plan;
4. repairable or blocked managed integration -> init repair plan or exact
   blocker;
5. project Corpus baseline behind -> selected Corpus upgrade plan;
6. project Corpus baseline ahead -> obtain a compatible newer Corpus; never
   downgrade through upgrade or rewrite integration from an older Corpus;
7. all dimensions current -> healthy.

This removes `requires_human_authorization`, authorization-directed reasons,
and the deleted `self-update` continuation. Status reports state, consequence,
and a valid SVC observation/plan where one exists; package installation and
Consumer file repair remain outside SVC.

Every resolved root-status result also carries the canonical workspace
projection accepted by the identity review. Workspace identity qualifies the
observation but does not participate in adoption/integration health or replace
the exact probe-free `svc dev identity` query.

### Closed transitions

```text
missing svc.json, no local overlay
  -> status: unadopted
  -> init establish plan/apply
  -> status again

missing svc.json + svc.local.json
  -> status: malformed/orphan-local
  -> init: blocked, zero operations, no digest
  -> Consumer resolves local file
  -> status again

valid current schema + repairable integration
  -> init repair plan/apply; Corpus baseline unchanged
  -> status again

baseline behind + repairable integration
  -> init repair first
  -> status: Corpus baseline behind
  -> Corpus upgrade plan/read/edit/check/apply
  -> status again

baseline ahead
  -> init/upgrade writes blocked where the older Corpus cannot safely own them
  -> install a corpus compatible with the adopted baseline

invalid/old schema or modified owned surface
  -> external repair/migration
  -> status again
```

Repair-before-Corpus-upgrade is intentional when the installed Corpus is newer: the
current Agent/docs router becomes accurate before the project considers that
corpus baseline. Init still does not advance the baseline. Conversely, a corpus
older than the adopted baseline must not project older generated integration
or use upgrade as an implicit downgrade.

`init` and `upgrade` remain separate mutations. Upgrade selects one config or
Corpus target; init owns bounded integration. Either successful apply may
legitimately leave root status non-healthy for another dimension. Do not combine
plans merely to save one command.

### Legacy Skill retirement in status

Removing the Skill requirement is not enough to migrate real Consumers. Status
temporarily observes the retired path with these semantics:

- absent -> current retirement state;
- whole file with one valid SVC generated marker matching its body ->
  repairable `delete` through init;
- recognizable SVC marker with modified/malformed body -> integration blocker
  requiring explicit inspection;
- no SVC provenance -> Consumer-owned/unrelated, ignored by init and not a
  health requirement.

This retired-surface observation is not the old required `guidance` check. It
exists only so real generated Skills are discoverable and removable without
claiming authority over an unproven same-path file.

The provenance rule is deliberately the existing ownership convention, not a
new archive of historical Skill bodies: exactly one
`svc:generated skill sha256=<digest>` marker at EOF whose digest matches every
preceding byte proves an unmodified generated whole file. A marker with a
mismatching body is modified; no marker is unproven. Maintaining an allowlist
of every historical generated body would add a new release registry and still
miss real old Consumers.

### Implementation topology

Do not build an init-specific file transaction engine. Keep four owners:

1. `svc_cli/plans.py` owns neutral local filesystem mechanics: `FileState`,
   `PlannedFileMutation`, write/delete settlement, parent preconditions, POSIX
   mode where meaningful, per-path rollback, and interrupt settlement. It does
   not know init surfaces or user-facing create/append/refresh labels.
2. `svc_cli/integration.py` owns marker/provenance inspection and desired
   integration effects, including legacy-Skill retirement. It does not apply
   files or choose command results.
3. `svc_cli/project.py` owns init/status project state, version relations,
   intent, blockers, and projection data; target-specific upgrade controllers
   own config/Corpus migration semantics. `InitOperation` combines a
   neutral mutation signature with init-owned `action`, `surface`, and
   `extent`; that combined stable signature forms the plan digest. Init and
   upgrade share file mechanics but retain different public semantics.
4. `svc_cli/cli.py` owns grammar, layered help, text/JSON projection selection,
   channels, and exit mapping. Init receives a dedicated renderer; the generic
   `command: status` emitter is not extended into another universal schema.

`svc_cli/config.py` remains the strict effective-config owner. Documentation
and generated templates change only where the Consumer-facing interface
changes. No execution-store/run/dev dependency enters this path.

The neutral operation vocabulary must distinguish:

```text
before/after file state   neutral filesystem condition
action + surface + extent init-domain semantic target/effect
plan digest               exact effect + safety preconditions
rendered reason           presentation, excluded from digest
rollback report           per-path recovery evidence
```

### Implementation order

1. Deepen the neutral plan engine with explicit file states, delete,
   meaningful after-mode, per-path rollback, and interrupt-safe attempted
   operation tracking.
2. Add legacy-Skill retirement and update init planning, including blocked
   zero-operation/no-digest behavior and orphan/ahead/runtime guards.
3. Close root status transitions and version relations; preserve adopt's
   separate public projection until its own review is complete.
4. Add init-specific default text, compact schema-v2 JSON, structured recovery,
   channels/exits, and self-sufficient help; remove `--agent`.
5. Update canonical docs, AGENTS navigation generation, README/examples, and
   the real CI parser that consumes only `plan_digest`.
6. Run mechanical contracts, repository gates, built-wheel smoke checks, then
   real-project acceptance.

The integrated unit must remove the already rejected `dev setup` caller before
breaking its old `LocalPlan` assumptions, or keep a bounded adapter until that
removal lands. Do not preserve the old write-only model indefinitely merely
because a command already accepted for deletion still imports it.

This order prevents presentation code from being built on the current
write-only model and prevents Skill removal from becoming an undiscoverable
or hidden deletion.

### Mental rehearsal and failure findings

| Pressure | Required invariant / correction |
| --- | --- |
| Existing file mode | Preserve and verify meaningful POSIX mode on apply and rollback. Current rollback restores only bytes: a reproduced `0640` `AGENTS.md` failure returned `succeeded` while leaving mode `0600`. |
| New file mode | Set an intended POSIX mode explicitly; do not inherit `mkstemp`'s private default. Omit `posix_mode` where the platform cannot support that claim. |
| Delete + rollback | A clean Skill delete records original bytes/mode before unlink; rollback recreates it exactly. Unproven files are untouched. |
| Interrupt gap | Record an operation as attempted before its atomic commit. On SIGINT, compare current state with before/after and settle it; merely catching `KeyboardInterrupt` after `os.replace` can miss a committed operation. |
| Concurrent writer | Never overwrite content that no longer equals SVC's approved after-state; report the exact preserved path. |
| Blocked plan | Publish zero operations and no digest; do not leak independently derivable writes as partially applicable work. |
| Corpus or repository changes | Recompute plan; mismatch returns no current digest shortcut. |
| Version direction | Compare SemVer with a mature parser, distinguish behind/current/ahead, and prohibit downgrade. |
| Symlink/parent race | Recheck normalized target, parent topology, bytes, and meaningful mode immediately before each effect. |
| Prose-only change | Keep digest stable because rendered reason/blocker wording is not an effect or precondition. |
| Apply verification | Verify after state, content, absence, and meaningful mode; never widen this to project health. |
| Second interrupt/kill/host loss | Do not promise a receipt. Atomic single-path operations plus subsequent status/plan are the recovery horizon. |

The chosen creation policy is POSIX `0644` for new non-secret project
integration text files; existing files retain their exact meaningful mode.
Windows exposes no synthetic `posix_mode` promise. This makes first creation
deterministic while preserving real SFP7 `0600` and InKCre `0644` files during
refresh and rollback.

### Mechanical verification versus product acceptance

Temporary directories and injected failures remain appropriate for contract
tests of races that cannot be safely demanded from a real project. They are not
product acceptance evidence. Focused tests must cover:

- create/append/refresh/delete signatures and after-state verification;
- mode preservation through success and every rollback outcome;
- clean, modified, and unproven legacy-Skill provenance;
- orphan overlay, schema blocker, runtime mismatch, and version direction;
- digest mismatch versus during-apply stale state;
- per-path rollback reports, Ctrl+C before/after commit, and exit `3|4|130`;
- default/JSON channel exclusivity and command-local schema-v2 fields;
- full repo-scoped continuations and layered help;
- status -> init -> status and status -> adopt -> status transitions.

Normal verification includes the repository test/type/import/document/build
gates and an installed-wheel smoke test. A synthetic empty repository or
`tmp_path` success must not be reported as real acceptance.
