# Two-Case Pilot Design

## Purpose

Test the audit protocol on deliberately contrasting cases before scaling to all
eight archives. The pilot is a method-validation step, not the first attempt to
find a product conclusion quickly.

## Cases

| Opaque case | Contrast purpose | What it tests |
| --- | --- | --- |
| `SVC-A` | One case with associated task-packet material | Whether an attached artifact can be treated as useful parallel evidence without mistaking association for use, authority, or causation |
| `OPS-B` | A long-running case without resolved packet association | Whether episode and recovery/coordination boundaries remain legible when the archive supplies no attached task packet |

The mapping from opaque case labels to exact archive locations remains only in
the private evidence store.

## Pilot Procedure

1. Make one non-quoting case card per archive using the coding protocol.
2. Establish episode boundaries from objective, control state, checkpoint,
   recovery, or handoff—not timestamp or tool density alone.
3. Map the observable collaboration control loop for each episode.
4. Record every ambiguity, failed pointer, or missing state as a limitation.
5. Compare cards only for protocol adequacy. Do not yet call a shared feature a
   recurring pattern unless both cases truly support the same mechanism.

## Pilot Exit Criteria

- Both cards can make evidence pointers without raw excerpts or sensitive
  values.
- Both distinguish native event, turn, work episode, and case without relying
  on an unverified schema assumption.
- At least one episode in each case has an explicit outcome or uncertainty.
- The contrast either validates the task-packet treatment or produces a precise
  revision to it.
- Any preliminary SVC observation remains a within-case inference or candidate
  hypothesis; no cross-corpus claim is made from this pilot alone.
