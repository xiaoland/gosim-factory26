# 工作边界与共同材料的作用

工作项使一位负责人能够推进一个可被采用的结果。结果可以是决定所需的调查、可复用接口、完整用户操作或实现候选。若一个状态的修改与后续观察分别属于几项工作，局部交付可以各自成立，整体结果却可能没有汇总责任；分工数量并不能说明责任已经完整。

## 内聚结果与真实依赖

独立负责人、可独立采用的成果或不同结束条件，是分开工作的实际理由。已有工作能承接新增结果时，其目标与完成条件决定承接是否成立；名称相近或引用同一接口不足以说明范围相同。父子与 PR 关联保存组织和来源，实际责任与采用各需自己的依据。

业务能力有自己的需求解释、技术取舍、验收与后续协调时，父项建立并指派业务子 Issue，说明完整结果、适用材料和共同前提；负责人据此形成方案，再组织关联实现 PR。实施独立业务能力之前，需要先安置这项结果责任。已有 Issue 能完整承接的局部改动，可以增加关联 PR，无需为每个场景、文件或 PR 新建 Issue。实现候选完成不会解除关联 Issue 尚未兑现的要求；父项继续核对跨能力约束与整体结果。

例如账户管理与文件导入共享持久化设施。父 Issue 的基础 PR 可以先统一 schema 和共同接口，再顺序推进两项业务 Issue 的实现 PR；业务负责人分别持有需求、方案与验收，父项核对跨入口结果。共同文件的冲突影响实施与合并顺序，不决定业务责任是否拆分。前提尚未交付时，也可以先建立业务 Issue、明确范围和负责人，让依赖该前提的实施动作等待。

先判断哪些成果可以分别交付和取得反馈，再安排它们何时执行。顺序执行没有消除不同成果的边界；并行也没有自动建立独立性。分开能缩小各负责人的相关上下文，合并能减少必须反复共同裁决和交接的语义；判断应指出具体受益的成果或具体无法分开的条件，不能仅以“协调成本高”结束比较。

共同前提与消费它的业务能力各有完成依据。例如编辑器与导入器共享配置接口，接口的验证和提交语义需要共同确定，但两个入口仍可分别交付完整行为。共享基础的结束条件是消费者能取得并使用所需前提，不是所有消费者的业务都已实现。若一次改动在两处之间没有可用的中间状态，可以将这次改动共同实施，仍须保留各入口的行为义务与整体核对责任。

依赖的含义取决于消费者需要什么。接口语义稳定时，实现可以先行；只有服务、数据或整合提交可用后才成立的观察，仍等待对应前提。业务关联未必形成串行依赖。若未知会导致多方采用相互矛盾的共同语义，先形成可被采用的定义能减少返工；不依赖该未知的工作仍有推进价值。

局部排除说明生产范围，并没有修改整体承诺。延后义务有接手者，意味着责任已安置；完整结果取得适用依据，才意味着兑现。若原目标改变，决定的权限与影响又是另一项事实。

## 材料为何需要明确消费者

Issue description 帮助恢复当前目标、重要决定、依赖与开放责任；PR description 帮助判断候选及其证据范围。项目文档或可执行定义保存跨任务共同知识，packet 保存当前判断和下一步，讨论保存本次差异与决定的形成依据。动态答案在多个位置分别维护时，消费者可能取得不同版本；知识归属由 [svc-documentation](../../svc-documentation/SKILL.md) 展开，任务材料由 [svc-task-packet](../../svc-task-packet/SKILL.md) 展开。

共享材料只有可发现、可取得且适用于当前成果，才能支持消费者继续工作。文件已写、已提交、已发布和已采用是不同事实。与成果一起取得的项目入口、共同定义和 packet 能降低重建上下文的成本；clone 外的正确笔记无法独自承担交接。Braid 父项正文也不会递归进入所有子项上下文，独立 clone 未必拥有最新共享实现。

## 已有信息与具体未知

当前投影中的目标、正文和状态可以直接支持相应判断；重复获取同一信息未必带来新依据。投影可能折叠细节、截短正文或只保留讨论索引，通知也可能仅说明有新回复。信息是否足够，应由本次决定需要的事实区分：缺的是一段交接、当前候选、原文条件，还是实际结果。新的查询价值来自消除这个未知，而非开始或接续工作本身。

例行正文与讨论整理，目的是让既有决定和开放义务更易消费。具有整理能力的成员可以承担它；提出新解释、核实实现或结束产品义务仍需要对应判断与信息。方法入口的存在提供按需取得的能力，不构成每次工作都重读全部方法的理由。


## 核对成员实际执行与进展

先明确本次未知：是责任没有建立、执行失败、成员正在等待，还是实现与需求边界不符。普通Issue/PR view的execution只投影当前故障，null不代表空闲、完成或健康；draft或pending也不说明成员是否正在执行。`braid execution issue ID` 和 `braid execution pr ID` 查询普通负责人，`braid execution review PR REQUEST` 查询验收责任；加 `--json` 可取得机器可读结果。reviewer不是PR实施者，PR的draft或head状态不能代替reviewer执行状态；先用 `braid pr review list PR` 取得请求编号。

查询中的assignment保存最后一个指派代次及其成员、状态与退任时刻；退任后仍在停止的执行不等于后任已经启动。session和latest_turn是该代次最近的物理会话与轮次，latest_reset和pending_batches帮助区分重置与未消费输入。null表示对应事实尚不存在或证据未取得，不能自行补成成功。observed_at是查询时刻，状态仍是Braid最后记录；宿主意外退出后记录可能停在running，不能据此宣称进程存活。

执行查询提供的是证据入口，不默认展开其它成员的完整原生历史。围绕当前问题读取evidence.native_session_path中的相关近期消息、工具结果与具体错误，核对成员当时采取的动作、已经取得的结果及下一步。原生子任务或后台命令不由Braid完整跟踪，沿该成员保存的任务状态、日志或讨论继续核实；记录增长与token增长本身不足以证明有效进展。证据路径缺失保留为未知，仍可采用其它已经取得的事实。

需要核对实现时，`braid pr view PR --json headRefName,baseRefName,headRefOid,baseRefOid` 给出已发布引用与提交，按需取得分支并比较实际改动。执行查询的worktree.path给出负责人工作区；可用 `git --no-optional-locks -C PATH status --short`、`git --no-optional-locks -C PATH diff --stat` 及相关文件只读查看未发布工作，不进入其它成员的修改、checkout、reset或清理操作。diff不含未跟踪文件内容，状态中发现的相关新文件要另行读取；运行中观察只是当时截面，不能当成冻结候选。

review查询将请求的base/head、责任版本、适用性和登记checkout与execution_node分开。latest_request只是该PR最后创建的请求，不证明它已启动或尚未结束；按所查request取得执行，不能从同一PR的其它请求推断它的进展，completed或cancelled也不证明旧执行已经停止。改派时review.member可以已指向新责任，execution.assignment仍记录停止中的旧成员，二者不相同意味着交接仍在进行。实际验收产物应核对该请求的review.checkout.path及候选身份；只读查询不会替reviewer创建或更新checkout。

判断有价值的新结果、明确阻碍或方向偏差后，通过原工作项讨论、联系或改派入口给出采用或纠偏决定；已有足够事实支持继续推进时可以等待。不为获得状态而反复要求成员发布无动作回执，也不把读取到的局部错误直接当作整项失败。
