# ARC Bench

ARC Bench 的允许需求包界定本次应用的产品承诺，根 Issue 提供任务与材料入口。需求理解与完成判断属于 Agent；运行时代码负责传递材料，设计和摘要帮助组织工作，但没有自行替代原要求的权限。

## 完整承诺来自材料的语义

`requirements.md`、`requirements.yaml`、场景与参考图片可能从不同方面表达同一要求。树形提供来源和组织关系；FOLDER 正文可以包含跨路径行为，ATOMIC 标记也不意味着独立实现或验收。父层规则的适用性取决于它约束的对象、范围和条件，既不是只读叶子，也不是把所有祖先文字机械累加。

角色、初态、入口、动作、结果和例外共同确定用户获得什么。场景中“已存在”的状态可能是产品启动数据、用户正常创建的状态或检查准备条件，它们对实现有不同含义。图片的可见内容与文字共同界定界面和交互，文件名与周围说明未必表达图片中的事实。来源冲突、缺失或不可读，意味着具体解释仍有未知；允许材料中没有的答案不因此成立。相关区分见 [阅读需求](references/reading-requirements.md)。

## 来源、依赖、责任与证据各自成立

来源说明承诺来自哪里，依赖说明动作需要什么成果，责任说明谁推进剩余义务，证据说明观察支持什么结论。四种关系可以交叉，却不能互相代替：节点已映射不代表覆盖，工作已指派不代表兑现，字段关联也未必决定实施顺序。

形成工作边界时，以原树的业务子层作为第一版能力候选：它已有范围、相关行为和来源，能减少重新分类时的遗漏。候选应说明可以交付什么完整能力、适用哪些父层规则，以及需要什么共同前提。可独立交付意味着在明确前提下能取得该能力的行为结果和反馈，不要求它脱离整个应用运行。较大子树可沿已有子层细分；调整或合并候选时，说明具体的跨枝用户结果、必须共同裁决的语义，或合并能减少的理解与交接负担，同时保留各能力的反馈和完成依据。树的粒度不是强制工作项粒度，共用账户、接口或数据库也不是合并全部业务的依据。

场景与图片用于检验候选的入口、成功与失败结果、权限和状态保持是否完整；完整操作跨枝时，明确局部实施与整体核对各由谁承担。能力分类只有进入工作项的范围、责任与验收依据，才成为实际分工；设计文档列出多个能力而交给一个全量实现项，仍是一项全量工作。基础建设提供各能力共同使用的前提，不因此承担所有业务结果；实施者再按文件派出子 Agent，也没有代替产品能力的交付边界。

一个节点可以由多个 PR 兑现，多个节点也可以形成一项工作。把能力候选转为工作项，以及合并候选或调整增量范围时，读 [需求结构与工作边界](references/reading-requirements.md#依赖字段与工作边界)，明确各项结果、共同前提与整体仍欠义务；Issue 责任与关联实现 PR 的组织方法由 [braid-collaboration](../braid-collaboration/SKILL.md) 展开。

## 覆盖是候选与原承诺之间的结论

当前工作范围是否承接前序延期，取决于原节点及适用父层、跨枝要求的完整结果。责任接手与行为兑现不同：接手安置继续推进的人，适用结果支持完成。原文入口、当前工作和结果之间可恢复的关系，使局部接受之后仍欠的承诺不会消失。

新增默认行为或例外是否成立，取决于原约束与适用条件；派生合同的发布没有改变允许需求。候选是否覆盖承诺，取决于真实入口的调用条件及结果，包含原文要求的连续状态与失败状态。局部 PASS 与完整覆盖可能具有不同范围。[覆盖回查](references/tracing-and-reviewing-coverage.md)解释这些区别怎样改变接手、解释、采用和完成结论，证据设计与解释由 [svc-verification](../svc-verification/SKILL.md) 展开。

## 平台可部署与产品正确是不同条件

固定目录、安装、构建和启动流程构成实际交付前提；开发路径成功未必说明平台路径成立。确切外部约束及命令在 [平台交付合同](references/platform-delivery.md)。部署成功证明应用在相应条件下可用，不独自证明全部产品承诺已经兑现。

这些方法以独立文件按问题取得。原需求及适用材料可被实际责任人取得，才支持它们进入判断；读取次数或完成状态不证明采用效果。外部评测、参考应用与先前实验答案不属于本次允许输入，不能用它们填补需求解释的未知。
