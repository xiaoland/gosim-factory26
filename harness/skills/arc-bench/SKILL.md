# ARC Bench

处理 ARC Bench 的需求、应用设计、实现或交付时读取此技能。本次任务和允许输入位置来自根 Issue；从原始材料取得产品承诺，设计和摘要用于组织工作，不能默默替代原要求。运行时代码只传递材料，需求含义与完成判断由 Agent 负责。

## 从材料取得完整承诺

需求包通常包含 `requirements.md`、`requirements.yaml` 和参考图片，先确认实际文件及其可读部分。需求树是阅读和追溯的骨架：FOLDER 的正文可以包含自己的产品约束，ATOMIC 也不等于必须独立建工作项。读取目标节点、适用父层及跨枝对象，按语义判断祖先约束作用在哪些行为；只摘叶子会丢承诺，机械拼接全部祖先也可能混入不适用条件。

场景中的对象、角色、初态、入口、动作、结果和例外决定用户实际获得什么。区分正常启动必须提供的数据、检查自己准备的数据和明确授权的外部条件；GIVEN 写着“已存在”并不能自动推出应用必须 seed。参考图片需真实观察，以本次配方安排视觉解读，保留要求的界面文字和交互目标；周围文字或文件名不能代替图片内容，图片也不能抹去文字中的行为要求。文件缺失、损坏或冲突时保留具体来源、原错误与解释缺口，继续可理解部分，不补造要求。细化方法见 [阅读需求](references/reading-requirements.md)。

## 按成果工作，保留四种关系

先确定可被采用的成果、真实消费者和完整操作，再借需求树定位范围。父子层级不取得默认分工优先权；跨枝的共同状态或完整用户结果也可成为内聚工作，由明确负责人汇总，局部实现仍可分工。一个节点可以由多个 PR 兑现，多个节点也可以形成一项工作；已有工作能承接时直接复用。

来源说明承诺来自哪里，依赖说明某一步需要什么成果，责任说明剩余义务由谁处理，证据说明哪些观察支持哪些承诺。原 dependencies 可能表达输入、状态一致性或实施前提，先解释其含义再决定并行、等待或整合；字段本身不能替代这个决定。分工、交接和成果采用读取 [braid-collaboration](../braid-collaboration/SKILL.md)，通用方法不依赖本需求格式。

## 回核覆盖及交付

在既有项目和任务材料中保留原节点身份、原文入口、适用父层和跨枝约束，以及对应工作、实现与证据。映射足以让未完成义务可找回即可，不默认制作全节点长期同步表。共享接口的合同须包含其兑现的共同约束，普通局部要求直接落实到实现和判据；局部排除回到仍持有整体承诺的负责人；实际接手只安置责任，尚欠结果在取得适用依据或原要求被有权者改变前仍是开放义务。

父正文、共同合同或消费者改变时，回查适用子路径、跨枝行为及旧证据，不能只刷新节点自身或祖先状态。已有正确结果可以接受，但一份 ID 映射或几个局部 PASS 不证明原承诺全部兑现。接手前序工作、提出新的用户可见约定、审阅采用 PR 或判断完成时，读取 [覆盖回查](references/tracing-and-reviewing-coverage.md)，以原承诺比较当前目标、行为差异和声明范围，再决定接手、纠正、局部采用或补缺。用 [svc-verification](../svc-verification/SKILL.md) 判断判据与候选结果的适用范围；已有集合通过不能替代这项覆盖判断。

在选择目录、依赖和启动方式前读取 [平台交付合同](references/platform-delivery.md)，最终交付前据此核实候选。固定安装、构建和启动流程构成具体平台前提，开发工具路径的通过不能代替它。让承担相关工作的成员取得本次原需求与适用技能/reference 文件入口，按需读取独立材料；不向它们内联本技能正文，也不使用外部评测、参考应用或先前实验结论补充允许输入。
