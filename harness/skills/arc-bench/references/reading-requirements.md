# 如何理解 ARC 需求中的完整承诺

从根 Issue 指定的允许输入确认实际文件，读取需求正文、树形结构、场景和相关图片。Markdown 和 YAML 可以是同一承诺的不同呈现；先核对它们的关系，不因某种格式更易处理就丢弃另一份独有约束。格式损坏时保留具体错误与可读原文，图片缺失时保留路径与尚未知的观察面。冲突或关键歧义说明各解释如何改变行为、分工或判据，向相应负责人取得决定；独立可理解部分继续推进。

## 层级保存来源，也可能保存行为要求

读目标节点时回到适用父层，找正文中作用于多个入口的规则，而不只是取标题和叶子。FOLDER 可以同时组织子节点和承诺自己的行为，ATOMIC 标记不能证明它在实现或验收上没有共享依赖。判断祖先正文约束的是整个范围、特定对象还是条件下的行为；适用约束带入有关工作，不适用部分不机械复制。

沿完整用户操作追踪其它枝：同一账户、配置或业务对象是否在几个入口被修改和展示，修改后重新进入或重开时应看到什么，失败时哪些状态必须保持。单枝覆盖可能只证明操作的一半。共同状态需要明确权威来源、写入与读取时机、刷新或失效规则；选用共享接口时，让合同承载这些跨成员约束，不要求所有局部细节都变成共同合同。

## 解释依赖，而不是只排节点

对 dependencies 问：它给本项提供输入、真实状态、稳定接口，还是只说明业务关联？哪个动作必须在该成果可用后发生？稳定合同可能允许先行实现，真实服务与数据可能只阻塞整合观察。未知语义会导致相互矛盾的实现时先澄清；仅有字段连接不必让全部工作串行等待。

工作边界从可被采用的成果及真实依赖确定，子树提供候选切分和来源。完整操作跨枝时，给汇总结果一个明确责任单元；实现仍可由多方完成。分工的理由是让成果与反馈成立，不是满足“一叶一项”或“一子树一项”的数量规则。[通用协作例子](../../braid-collaboration/references/worked-example.md)说明同一共享设置约束为何仍须通过编辑器和导入器两条路径兑现；在原树中定位相应共同承诺，而不是复制该例子的实现答案。

## 场景与图片建立实际观察条件

找出用户对象与角色、先前状态、进入位置、动作、可见结果和例外。正常启动即应存在的数据由产品准备；用户通过正常流程创建的状态可以按该流程建立；只为后续检查准备的数据需明确为检查条件；外部服务或资源按本次授权核实。不要把所有 GIVEN 自动合成 seed 需求，也不要用自检已经创建的数据掩盖启动缺口。详细判据和可重复条件读取 [svc-verification](../../svc-verification/SKILL.md)。

图片需通过实际视觉观察解释，与文字共同确定布局、层级、界面文字、控件状态及交互关系；调用方式遵守本次 vision 配方。无法看到的内容保持未知，有效观察可按适用来源复用，不以逐图重开会话增加形式步骤。示例图片中的实例值是否构成需求，要由正文与场景判断，不能未经解释一律固定或删除。

完成本次理解后，留下足以支撑设计和分工的承诺、来源、重要解释与未决问题，回到原文仍能找到适用条件。实现中提出新的默认规则、例外或便利行为时，回到其作用范围的正文与场景，比较对象、边界和前后状态是否仍符合承诺。新增规则是待判断的解释，不因已写入设计或 API 合同而成为允许需求；明确冲突应纠正，真正歧义或范围改变则带原文入口与行为差异交相应负责人裁决。只有会改变共享结果的解释进入共同定义，普通局部选择留给实施者；需要追溯到工作与证据时继续读 [覆盖回查](tracing-and-reviewing-coverage.md)。
