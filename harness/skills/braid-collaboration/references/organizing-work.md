# 工作边界与共同材料的作用

工作项使一位负责人能够推进一个可被采用的结果。结果可以是决定所需的调查、可复用接口、完整用户操作或实现候选。若一个状态的修改与后续观察分别属于几项工作，局部交付可以各自成立，整体结果却可能没有汇总责任；分工数量并不能说明责任已经完整。

## 内聚结果与真实依赖

独立负责人、可独立采用的成果或不同结束条件，是分开工作的实际理由。已有工作能承接新增结果时，其目标与完成条件决定承接是否成立；名称相近或引用同一接口不足以说明范围相同。父子与 PR 关联保存组织和来源，实际责任与采用各需自己的依据。

依赖的含义取决于消费者需要什么。接口语义稳定时，实现可以先行；只有服务、数据或整合提交可用后才成立的观察，仍等待对应前提。业务关联未必形成串行依赖。若未知会导致多方采用相互矛盾的共同语义，先形成可被采用的定义能减少返工；不依赖该未知的工作仍有推进价值。

局部排除说明生产范围，并没有修改整体承诺。延后义务有接手者，意味着责任已安置；完整结果取得适用依据，才意味着兑现。若原目标改变，决定的权限与影响又是另一项事实。

## 材料为何需要明确消费者

Issue description 帮助恢复当前目标、重要决定、依赖与开放责任；PR description 帮助判断候选及其证据范围。项目文档或可执行定义保存跨任务共同知识，packet 保存当前判断和下一步，讨论保存本次差异与决定的形成依据。动态答案在多个位置分别维护时，消费者可能取得不同版本；知识归属由 [svc-documentation](../../svc-documentation/SKILL.md) 展开，任务材料由 [svc-task-packet](../../svc-task-packet/SKILL.md) 展开。

共享材料只有可发现、可取得且适用于当前成果，才能支持消费者继续工作。文件已写、已提交、已发布和已采用是不同事实。与成果一起取得的项目入口、共同定义和 packet 能降低重建上下文的成本；clone 外的正确笔记无法独自承担交接。Braid 父项正文也不会递归进入所有子项上下文，独立 clone 未必拥有最新共享实现。

## 已有信息与具体未知

当前投影中的目标、正文和状态可以直接支持相应判断；重复获取同一信息未必带来新依据。投影可能折叠细节、截短正文或只保留讨论索引，通知也可能仅说明有新回复。信息是否足够，应由本次决定需要的事实区分：缺的是一段交接、当前候选、原文条件，还是实际结果。新的查询价值来自消除这个未知，而非开始或接续工作本身。

例行正文与讨论整理，目的是让既有决定和开放义务更易消费。具有整理能力的成员可以承担它；提出新解释、核实实现或结束产品义务仍需要对应判断与信息。方法入口的存在提供按需取得的能力，不构成每次工作都重读全部方法的理由。
