# 如何确定工作边界与共同材料

先从要交付的结果及其消费者出发。结果可以是支持下一步决定的调查、可复用的接口、完整用户操作或可审阅的实现候选；范围要让负责人能够取得有意义的反馈。按目录、组织图或需求条数切分，可能把同一状态的修改与观察分到无人汇总的地方。若若干部分只有一起才能证明结果，给完整结果一个负责人，再决定局部实现是否另行分工。

复用已有工作项，检查其当前义务与交付是否足以承接新增要求。需要不同负责人、独立交付或独立结束条件时才建立新项；同一要求可以由多个 PR 实现，一项工作也可以兑现多个要求。父子关系保存组织与来源，不自动决定实施顺序；PR 的关联也不能使未指派的工作自动取得负责人。实际创建与指派语义以当前 Braid 指引和 CLI help 为准。

## 依赖决定哪个动作可以开始

说清生产者提供什么、消费者用它做什么，以及哪个动作需要它。接口语义已经稳定，消费者可能先实现；真实服务、数据或集成提交尚未可用，则只能暂缓依赖它们的观察。仅有业务关联不必形成串行等待。反过来，生产者已经合并也不证明消费者的分支取得了该实现，或它在消费者的实际条件下可用。

共享定义尚有会影响多个部分的不确定性时，先解决会改变路线的决定，发布最小可消费定义与成果，再推进依赖部分。与该未知无关的工作可以继续。若两部分需要反复协同才能形成定义，将其归入一个有整体责任的工作，往往比制造多轮交接更清楚；不必为此将所有实现交给同一个人。

整体负责人对未完成要求保持可定位的入口与下一步。局部任务可以明确排除其它行为，但排除说明要回到仍持有整体要求的工作项。复用后续工作接手时，比较其目标是否包含原来尚欠的完整消费者结果；名称相近或共享一个接口不足以覆盖。接手建立责任落点，结果仍等待兑现；没人接手时保留开放义务。原要求只有经过有权者决定才改变，不能从局部任务的范围自动推导缩减。

## 当前答案放在会被消费的位置

Issue description 让协作者恢复当前目标、本项采用的关键决定、依赖与未决责任；PR description 让审阅者判断当前候选做了什么、证据支持什么、还需要处理什么。入口需给足关键结论与用途，不能只有一堆链接，也不应复制完整源码、日志和讨论史。

跨任务共同定义归已有项目文档或可执行接口，task packet 连接当前推理、计划和证据；讨论记录这次事实、变化及所需行动。不要同时在多个 description 维护同一份动态状态，否则一处更新后其它消费者仍可能依据旧副本行动。为每项入口说明消费者要用它完成什么，引用其适用提交；稳定 API、种子值、UI 文案和操作合同留在共同定义，不在每项 PR 再次浓缩成第二份合同。开始或接续时先读取现有 packet，使它在实施过程中承接当前判断；共享文档、根入口与根 packet 先发布，再开始依赖它们的工作，PR packet 随候选发布供审阅和接续，合入后保留在共同分支。详细知识归属与任务维护分别读取 [svc-documentation](../../svc-documentation/SKILL.md) 和 [svc-task-packet](../../svc-task-packet/SKILL.md)，沿用已有材料位置。

Braid 的父项正文不会递归进入所有子项上下文，独立 clone 也不自然包含最新共享代码。交给消费者本次所需的原要求、共同定义及实际代码入口，让它按任务取得适用材料；不要以“父项写过”或“仓库里存在”为已经取得合同的依据。检查是否已经具备下一步条件后即可推进，不需预先收集所有无关历史。
