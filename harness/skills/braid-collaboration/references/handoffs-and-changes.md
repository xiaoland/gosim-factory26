# 如何交接、采用成果与处理变化

一次交接的目的，是让接收者在其范围内继续工作。给出目标结果、相关原要求与当前决定、成果身份及入口、已成立前提和剩余缺口；同时说明接收者下一步如何消费它。接收者完成本地调查、实现与诊断，不要求生产者预先替它解决所有细节。原生局部委派的方法归 [svc-sub-agents](../../svc-sub-agents/SKILL.md)，跨成员的责任通过 Braid 工作项保留。

## 分别判断生产、承接与适用

生产者发布接口或实现时，说明行为和适用条件，让接收者能找到确切结果。接收者根据当前任务确认它是否已经取得、接入并采用该结果；消费者的实际后续行动可以成为承接依据。原始检查若针对同一行为、候选与条件，可以继续支持判断；但发布和采用都不能自动证明这些检查足以覆盖原要求。

当接收者已经据此继续实现或返回所需成果，不追加纯确认回合。反之，消息已送达、assignee 已设置、parent/PR 关联已存在，只说明路由或组织状态；不知道接收者要做什么，或其仍采用旧定义时，需补充实际责任和差异。说明完整对象类型与编号，避免把同号 Issue 和 PR 当成同一对象。

接手或恢复时，从前序 packet、交付评论和局部排除找回尚欠的原承诺，比较当前工作范围是否真正包含它。延期内容要以完整消费者结果进入当前目标：必要的前态、用户动作、成功或失败后的可见结果与状态保持，而非只保留接口名或一个异常分支。给出相应原要求和成果入口，以及当前应实施或补观察的下一动作；沿用既有 description 与 packet，不另造交接表。

局部任务无法处理的义务交回整体负责人，附理由、影响与可继续的入口。整体负责人可以另行分派、保持开放并等待前提，或交有权者决定范围变化。实际接手结束责任路由的不确定性，不结束原结果的兑现义务；观察尚欠时，继续保留在接手工作及整体完成判断中。已经正确接手且结果有适用依据时，无需持续追问确认。

## 改变共同定义时找到当前消费者

先区分已批准的变化与尚待判断的新约定。新增用户可见行为按 [接受与关闭](accepting-and-closing.md) 对照原承诺：明确冲突应纠正，真正歧义交相应负责人决定。变化成立后更新既有权威定义，让当前规则和替代关系清楚。然后从实际实现、整合及检查路径识别受影响的人和工作项，包括已经交接给新负责人的工作。通知给出改变了什么、为何改变、哪个旧假设失效，以及接收者要调整的下一动作；单个文档链接不能代替这个差异。

消费者将变化与自己的设计、实现和判据比较，决定采用、无影响或具体阻塞。有适用的实现与观察支持时，记录其结论即可；旧分支检查通过不能推翻新决定，也不能证明新行为已经满足。语义有冲突时先向有关责任人解决冲突，独立部分继续推进。咨询独立意见保留原观察与反例，避免把一个偏好的解释伪装成唯一前提。

共享接口的必要参数、上下文或提交条件改变时，从真实入口找受影响的调用方，核对它们实际提供什么、接口因此走哪条分支，以及结果怎样返回用户。文档表与服务端局部通过不能证明接线成立；同一负责人实现各层时也需做这项比较。按改变的条件取得有区分力的实际观察，修正失效的调用或共同定义，不默认重复全部检查。

新增入口、消费者或派生状态也可能改变已有责任。共同格式没变，不等于新的导入、展示或缓存路径已经连接到它；回查谁写、谁读、什么时候刷新和失效，再判断是否需要调整原工作。对变化范围的理解足以支持下一步时停止扩展，不把每次普通提交都变成全员同步。

有用的交接结束于成果被正确消费及剩余义务被安置，而非永久维护回执。讨论保留本次差异，当前义务同步到对应 description，长期共同知识沿用 [svc-documentation](../../svc-documentation/SKILL.md) 的位置。
