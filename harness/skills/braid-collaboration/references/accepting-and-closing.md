# 如何接受结果并结束工作与讨论

接受结果时从本项原始承诺出发：哪些行为需要兑现，当前候选做到了什么，已观察的条件支持多大的结论，还有哪项义务尚未处理。需求来源可定位、判据足以表达要求、实际执行取得结果是三个问题。审阅结果要能区分它们；一张齐全的映射表、ready 状态或成功合并只能支持各自记录的事实。

## 新行为先取得适用依据

实现者提出便利规则、默认行为或例外时，区分实现选择与改变产品承诺的新约定。对照原要求的明确约束及适用条件，说明新增行为会怎样改变用户结果；明确违背原要求时纠正约定及候选；真正歧义或需要改变目标时，向持有相应决定权的负责人提出分歧，决定受其授权范围限制，不能借内部合同发布改写原要求。没有冲突的局部实现选择可以直接推进。

PR 披露的新约定与已批准决定分别呈现。审阅者消费这些差异后再采用候选；原要求未变而派生合同冲突时，纠正合同及实现。修正某个检查的输入或预期，只说明这项判据得到调整，须另判新约定是否成立，不能把两项判断合为“问题已修复”。

## 先消费已有结果，再补必要缺口

先把 PR 的行为声明与原承诺及前序未结事项比较，再沿 [svc-verification](../../svc-verification/SKILL.md) 判断判据的含义、实际条件与原始结果。对于本次新增或改变的行为，从用户实际入口追到必要调用条件与可见结果，包含原文要求的连续状态或失败后状态；直接接口结果不能自动支持用户入口的声明。派生矩阵、文案断言或已有检查集合只支持其中实际表达和观察的行为，未表达的原承诺仍需有针对性的依据。局部结果可以正确且值得接受，同时只覆盖完整用户结果的一部分。若两个入口都需满足同一约束，观察一个入口的通过不能代表另一个也成立；把仍欠的观察留在整体责任中，而不是拒绝已有效的局部成果。

候选变化后检查结果适用性：变了哪些相关行为、共享代码、数据、环境或判据，哪些旧观察因此失去支持。重新核实受影响路径和从未观察的义务，其它有依据的结果可继续采用。普通 head 前移不自然要求全部重跑，相同提交也不消除环境差异。没有某种测试文件与没有任何验收依据是不同事实，不按文件数或通过数量判断完成。

返回审阅结论时给出实际候选、相关变化、证据入口及其证明范围、剩余问题与所需行动。原始错误和失败保留，后续修复另有结果；不能把新成功改写成首次没有失败。执行受阻时说明尚未取得什么观察，不把设施或前提失败误计为应用已通过或已失败。

## 关闭工作项需要安置责任

PR ready 表示提出候选，merge 表示代码已合入相应分支，Issue close 表示该项不再有待推进的义务。关闭前消费当前候选的结果与尚未解除的讨论前提；合并版本保护避免候选偷换，但不能证明产品承诺。先取得操作的实际结果，再报告 merged 或 closed，避免先写成事实后才发现操作失败。

可以合并有效局部成果供后续开发，同时明确仍欠的消费者结果归哪个工作继续推进；合并理由不能扩大为这些结果已经完成。原要求已经兑现且依据适用，可以结束；局部生产完成而后续采用属于其它现有工作时，给出可用成果并确认整体责任仍有落点，也可以结束该局部工作。缺口无人接手、要求解释仍冲突或关键观察未取得时，保留明确的未决责任。若目标被有权者改变，记录改变及剩余影响，不能由某个实现者自行缩减原承诺。

## 讨论结束与当前知识保存

一个 thread 围绕可以独立结束的问题。完成决定后把本项仍欠义务及其共同定义入口留在 description，把跨任务合同与理由更新到项目文档，把当前判断、路线和恢复点留在 packet，再结束讨论；一个 thread 混有几个不同结束条件时，先为未决部分保留独立入口，不能因其中一个问题解决而折叠全部义务。

当前 Braid resolve 只接受讨论根 ID，折叠执行时已有的整段前缀，新回复仍可见；因此操作前核实整串问题与当前落点。hide 使该条及其现有、未来后代正文从普通读取中隐藏，保留后代自身的隐藏选择；取消祖先隐藏不会清除这些选择，既不能追回已送达输入，也不等于问题解决。具体接口以当前 CLI help 为准，不将历史 reply resolve 用法继续当作有效入口。

没有新事实、决定、阻塞或下一动作时，不需要新的维护回应。根项提醒是检查请求，不证明子项停滞；已经消费的交接与结果无需反复写确认。保持可恢复的当前入口即可停止，让下一次真正的变化重新触发工作。
