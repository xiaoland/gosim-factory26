子任务完成后，在约定的父 Issue 讨论中交接成果和证据入口。

实施前核实会改变路线的版本、API、共享接口和环境前提，用小规模真实操作消除关键未知；根据反馈修订方案。

非简单工作开始或接续时，读取适用的 svc-documentation 和 svc-task-packet 技能，建立或接续项目知识入口和当前任务包，随决定、依据及下一步变化维护。根 Issue 维护共同知识入口，各 Issue 在对象中留下任务包入口，关联 PR 接续同一份任务资料。复用已有文档、设计和 packet；共同约定归项目文档，Issue/PR 和 packet 引用其权威位置，相关决定变化时同步原定义与受影响任务。一次会话已读取的方法按需回看，技能正文保持独立文件。

将有歧义的需求解释发布为共同前提、确定影响多个任务的共享契约，或确定仍有关键假设的验收判据之前，先向原生 advisor 咨询；反复失败或新证据动摇方案时再次咨询。这些时机已由本配方选定，不以委派是否比自己省时或是否已通过自检来决定使用；日常明确的局部决定直接推进。

共享契约一经决议，在原 Issue/PR 记录并尽早发布最小可消费的契约或实现；消费者按该契约继续，旧分支自检通过不推翻裁决。依赖交接写明完整的 Issue 或 PR 类型与编号、目标成果；确认对应实现已进入验收候选分支且所需行为成立，才视为满足验收前提，不凭相同编号或一句“已合并”判断。共享成果持续整合到 develop，最终交付分支为 main。根负责人开始协作时，fetch origin，若还没有 develop，从 origin/main 创建并发布它，不覆盖已有分支。Issue 的初始个人工作区不一定包含最新共享实现，按需要 fetch 并查看 origin/develop。子任务 PR 使用 --base develop；需要承接已有代码时先发布相应分支，再用 --head 指定它，而不是从空白重复实现。

根 Issue 最后组织关联的 develop → main 整合 PR（braid pr create --base main --head develop ...），由其负责人在最终候选上执行覆盖完整需求范围的自动化测试或脚本，修复失败并复验，再合并交付并交接结果。复用有效的局部检查，但局部旧 PASS 不代表当前整体验收完成；结果须对应实际检查的提交与运行条件。交接写明实际检查的产物、条件与原始结果，说明当前候选的相关变化、这些结果的适用范围和剩余验收事项。合并时用 --match-head-commit 保护确认的已发布候选；合并前消费当前候选的检查结果和讨论中尚未解除的前提，head 匹配本身不代表这些前提已满足。根负责人据此判断完整交付并关闭根项，不重复同一套已经有效的验收。

根 Issue 的定时检查评论只是提醒，不代表子任务停滞；没有新事实或新决定时，无需发布重复进度总结。

检查设计、首次执行与结果解释时读取 svc-verification；先确定原始输出和真实退出值的保存入口。执行工具未完整保存两者时，读取 agent-browser 技能并使用其检查命令包装，API、构建和自带服务的检查同样适用。浏览器探索与诊断默认使用 agent-browser，也可委派 browser-operator；一次性的浏览器操作报告不能替代整合 PR 的可重复验收。检查失败先依据原需求和观察区分实现、检查与环境问题，不为迎合当前实现改写判据。

需求参考图的视觉解读交给原生 vision sub-agent：提供相关图片路径、需求背景和需要澄清的问题，读取其带来源的观察后用于需求和方案判断。把相关图一起交给它，无需逐图创建会话；已有有效观察可复用并交接。主模型是否支持图像不改变这项分工。文件名和周围文字不能代替视觉证据；尚未查看或无法确认的内容保留为未知，不声称已审阅。
