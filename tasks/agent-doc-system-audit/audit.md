# 开发 Agent 指令与文档系统审计

审计日期：2026-10-06，Asia/Shanghai。范围是整个开发说明系统如何帮助 Agent 正确理解任务、找到事实、判断授权并完成工作，而非只检查链接、费用关键词或 AGENTS.md 的长度。本报告保留修正前的调查结果与优化依据，证据反映所读基线，不作为修正后的当前操作指南。用户随后批准修正，实际改动与验证见[任务包](packet.md)。

## 结论与判断依据

当前系统已经有合理的知识归属原则，也有可用的模型提供商入口。主要缺陷在于这些原则尚不能持续约束内容演化：历史决定进入默认指令，旧操作仍被标为当前，新设计的操作说明先于可用性证明发布，任务包的当前答案又与授权沿革混在一起。读者需要跨页重建“现在什么有效、适用于谁、能否实际使用”，而 Agent 很容易用最近遇到的规则代替这项判断。

这不是单纯导航问题。导航影响能找到什么；规则作用域影响怎么解释；能力状态影响能否行动；知识更新方式决定问题是否再次出现。只把链接补到 AGENTS.md，或逐条增加“不要误解”的提醒，会保留造成误判的结构，并增加下一位读者的负担。

下表区分已观察事实与尚待验证的因果解释。优先级按对错误行动、阻塞和后续维护的影响排序，不以出现次数排序。

| 优先级 | 问题 | 证据强度 | 直接影响 |
| --- | --- | --- | --- |
| 高 | 当前操作说明与当前 CLI 不一致 | 已静态确认 | 使用公开入口会得到参数或命令错误，恢复与监控判断被引向旧协议。 |
| 高 | 稳定规则混入具体阶段的授权与操作参数 | 已确认内容混合；误判因果未隔离 | 读者可能将特定实验决定推广为新任务默认前提。 |
| 高 | 设计、源码存在与实际可用状态分散 | 已确认各页状态差异 | 接手者容易把接口说明当作可以启动的交付。 |
| 中高 | 任务入口不能充分解决相邻主题的当前归属 | 结构已确认；阅读成本缺少本轮量化 | 任务接续依赖历史串读和人工比较，增加过期授权被采用的机会。 |
| 中高 | 内容迁移缺少对旧当前描述的同步撤回 | 已有多轮历史记录和当前反例 | 同一类缺陷复发，优化退化为不断补局部说明。 |
| 中 | 防误用说明可能诱发额外证明与自设门槛 | 本次行为可观察；文档贡献属于假设 | Agent 把未知辅助事实当作阻塞，偏离用户已授权的目标。 |
| 中 | 验收偏重局部导航，未覆盖整体判断质量 | 既有报告明确记录限制 | 文件变短、链接可达或一次操作成功容易被扩大为系统改善。 |

## 触发案例：先区分责任和问题

本次案例中，Agent 将“本地自费 API”理解成个人 ARC 额度，查看 ARC 余额，并自行提出总计 ¥100、每次 ¥50 的费用停止线。用户要求查阅 deployment 下的模型信息，并明确自费 API 不需要设置阈值。Agent 还曾误解用户对重放的意图，未及时区分非正式应用评测和正式参赛。

这些行为不能全部归因于文档。提供商目录已经列出 BigModel 的 GLM-5.3 与 Flash，以及千帆普通 API 和个人 Token Plan；[运行入口](../../docs/deployment/index.md)也有模型选择入口。Agent 没有采用已有证据，是执行调查的错误。费用停止线是 Agent 新增的限制，不宜仅称为“清理过期信息”。用户澄清后，继续做预算关键词审查仍是审查方法过窄。

同时，[根指令](../../AGENTS.md:117)保留 I13“全部切回 ARC”的具体决定，紧接着出现“本轮恢复使用 ARC 额度的许可已经取得”。前句明确限制为 I13，不能据此断言文档要求所有任务使用 ARC；但后续指示脱离所属任务呈现在默认读取的根文件中，确实增加了范围误读的风险。后续改造需要同时纠正内容组织和 Agent 的证据选择方法。

“自费 API 无需费用阈值”也不能转化为删除所有预算、额度和上限。供应商余额、比赛额度、资源容量、模型使用范围及历史实验真实停止线是不同事项。费用记录仍可保留；历史证据仍应如实保存。具体约束只有在适用于本任务且有明确依据时才参与行动判断。

## 1. 当前操作合同已经发生跨版本混用

[恢复说明](../../docs/deployment/recovery.md:5)称“本页是当前恢复入口”，并给出：

```sh
python3 -m lab checkpoint RUN ATTEMPT --directory CHECKPOINT --request-id CAPTURE
python3 -m lab recover CHECKPOINT --intent RECOVERY_INTENT --environment PROFILE \
  --directory DERIVED --job JOB --request-id REPAIR
```

同期读取的 [CLI](../../lab/__main__.py:9)注册的是 start、stop、pause、resume、restart、status、wait、logs、evaluate、archive 和 serve，没有 checkpoint 或 recover。这里不是链接坏了，而是推荐了当前入口不接受的操作。

[证据说明](../../docs/deployment/evidence.md:16)仍以“新实验/attempt”描述入口，并推荐旧 run 的 `lab history`；其[等待说明](../../docs/deployment/evidence.md:87)推荐 `lab monitor EXPERIMENT` 和 `lab wait EXPERIMENT --json --timeout 60`。当前 CLI 没有 history、monitor，wait 也没有 timeout 参数。旧的监控消费者说明已删除，不能再作为入口。因此，问题横跨根导航和 Deployment，不应只在其中一页补一句警告。

这项结论来自静态接口核对，没有执行命令或接管运行。旧冻结执行器可能仍有这些能力，但使用旧能力必须明确绑定其入口和冻结版本，不能通过当前 `python3 -m lab` 调用来表达。

建议以实际使用的执行器为界重写受影响的操作说明：当前入口只给当前方法；冻结执行器的读回和恢复方法留在历史归属并明确入口。不要为了维持旧文档而给新 CLI 增加兼容命令。

## 2. 根指令承担了不适合长期默认读取的内容

根文件同时提供仓库地图、合作规则、当前赛事资料、历史授权、模型范围和具体监控编排。稳定的行为原则与阶段事实不具有相同生命周期，却获得相近的默认曝光。

例子包括 I13 的 ARC 切换、自动接续授权撤销、指定模型的 Braid session 限制、按 Braid session 的预算保护，以及 GPT-5.6-Luna / low 每十分钟消费摘要、远端三分钟/八分钟采集节奏。不能仅因具体就判定它们无效；其中一些可能仍是明确政策。但其适用对象、有效范围和持有者需要在使用位置清楚表达，不能让新任务自行判断“本轮”指的是哪一轮。

根指令新增的实验术语表有明确价值：执行位置、生成、状态继承、评分身份和正式参赛被分开，能够处理多种场景，不只是单一事件提醒。优化应保留这类跨任务判断方法，将具体实验事实归回所属任务。浏览器偏好放入 [AGENTS.local.md](../../AGENTS.local.md)也符合个人本机与共享规则的区别。

建议先按内容职责清理，不追求任意行数目标：根文件保留长期行为、授权原则和必要发现入口；操作细节留在运行文档；具体阶段决定及其历史保留在 packet。约束需要解释它保护的实际边界，不能只不断扩大禁止列表。

## 3. 设计、接口存在与可用交付之间缺少直接连接

[Lab 说明](../../lab/README.md)及[本地运行说明](../../docs/deployment/local-experiments.md)已经提供新 run API 和三参数启动方法。[技术入口](../../docs/product-tdd/index.md)提醒“架构采用”不表示部署和验收；这种区分是正确的。

但实际可用状态在另一处：[设施任务](../finals-experiment-loop/packet.md:6)明确写执行与观测草稿仍在修正接线，“尚不可当作可运行交付或验收通过”，没有启动本轮收费模型。其正文又记录 Console HTTP 200 只证明服务启动，不证明真实 run 的生产、传输和投影闭环。

这不是已经证明新设施失败，而是文档读者需要额外找到正确 packet，才能知道操作说明目前代表哪一种状态。仅在总技术页放一个通用免责声明，不能保证从搜索、子页面或命令示例进入的读者会看见。

建议在具体操作的归属页说明其适用版本及尚未完成的关键使用边界，并链接对应状态持有者；实现完成后同步更新。无需给每段加一套机器元数据，也无需把瞬态 PID、日志或所有实施进度复制到文档。

## 4. 历史分离存在形式上的完成与实际读取的缺口

[Console 说明](../../docs/deployment/console.md)已把旧协议置于历史标题下；不能把整个文件误报为仍只支持 Braid。但历史段落内仍使用“本页维护当前服务准备”等自指，以及旧控制方法。全文阅读能借标题解释，搜索摘录或定向读取则可能失去这层上下文。

[提供商目录](../../docs/deployment/model-providers.md:22)把网关启动与绑定指向已作为历史资料的 hackathon.md。即使提供商选择事实正确，后续操作仍可能被带回旧路径。[文档入口](../../docs/index.md:19)也把暂停、停止和检查点选择导向目前仍推荐旧命令的恢复门控。

这些例子说明“有 history 目录”“有历史标题”和“链接可达”都不足以证明当前与历史有效隔离。要审查的是读者实际走到的说明及其自称的适用性。

建议让历史材料按冻结对象自述，不再在内部称自己为普遍当前入口；同时撤回现行页面中指向旧操作的推荐。需要保留历史真实性的原始记录不改写，新增历史说明与原始证据应区分。

## 5. 任务包仍要求读者重建当前答案

[CONTRIBUTING](../../CONTRIBUTING.md:29)已明确：先读 packet 当前摘要；实现导航由组件说明持有；决定变化时改写当前答案，不要求接手者按日期猜。现有 SVC task-packet 方法也强调短入口和按需扩展。这些原则足以支撑改进，不必再发明一套任务管理协议。

实际任务包仍常把当前摘要、用户授权原话、多轮被替代的方案、未开工阶段和负责人变动放在连续正文中。设施 packet 的顶部已经明确开工，但下方仍有“不是开工许可”的旧授权说明，依赖读者看见另一段“旧段落是历史沿革”。开发体验 packet 也保留多轮当前状态与长篇历史验收。

这不等于顶部摘要没有价值，更不意味着应删除授权和证据。问题是历史沿革仍用可执行语气与当前正文竞争。读者要回答一次接续问题，可能被迫串读与当前决定无关的材料。

[工作主题索引](../../docs/work-index.md:23)同时导航实验启动 DX、实验 DX、实验操作、模型事实、追溯和存储生命周期等邻近任务。这些任务确有不同职责，但对“现在怎么运行、接续或查事实”的自然问题，当前主要归属及旧任务仍承担的职责不够直接。解决方法不是把所有子 packet 都加入顶层，而是让相邻任务明确哪个持有当前答案，哪个只提供历史或专项证据。

建议保留一个可直接采取下一步的当前入口，将被替代决定放入明确历史归属；当前摘要引用需要追溯的依据即可。只有已有文件无法承担真实目的时才拆新文件，不强制套统一模板或新增完成流程。

## 6. 防误判原则可能被误用为行动阻塞

项目和个人指令都要求独立判断、尊重已有授权并持续完成工作。项目的四阶段复核流程明确只适用于“采用分阶段复核的任务”，也明确用户直接要求具体修改即可作为该范围的开工依据。不能把它审计成所有任务都必须重复四次审批。

另一方面，根文件累计了大量针对过去事故的禁止与核对条件。Agent 可能把“不能推断”扩大为“任何未知都必须暂停”，把费用记录、完整恢复证明或辅助取证要求用到本来不需要它们的行动上。本次费用阈值和余额阻塞提供了行为案例，但尚不足以证明哪条文档直接诱发它。

建议按行动本身检查约束：它是否涉及尚未获得的授权、真实损失或当前缺少的必要输入？如果只缺辅助证据，就记录限制并继续能做的工作。对同类行为已有正确原则时，应修正冲突的具体说明或无效流程，而不是再添加一条免责提醒。

这里也需要保留 Agent 自身的改进：先用当前请求确定调查问题，再找可区分解释的证据；不要从一个余额结果倒推出用户的模型供应商和费用意图。

## 7. 多轮优化后的复发指向更新机制，而非缺少原则

[长期文档整理](../durable-docs-curation/packet.md)和[仓库整理](../repository-curation/packet.md)已经处理知识归属、当前与历史分离及操作入口；其范围有边界，不能因未覆盖根指令或所有任务包就断言失败。

[2026-10-03 文档审查报告](../../runs/reports/2026-10-03-core-documentation.md:73)更明确写道：“具体组件导航验收通过；整体效率尚无全面通过的证据。”它记录了实际冷启动、阅读绕路和成本限制，并未声称系统已全面有效。这个判断应继承，而不是把局部验收概括为“文档系统已优化完成”。

当前仍有同类缺陷，说明一次整理和若干入口修补不能保证后续方案变化同步撤回旧当前描述。现行 CONTRIBUTING 已要求更新受影响归属；优化重点应是每次真实变化在这条路径上闭环，而不是增加新的治理工具或审批阶段。

建议在具体任务收尾时回答：新决定现由哪里持有，原当前描述是否已撤回，下游操作推荐是否仍适用，尚未验收的部分是否能被直接看见。只核对受影响的说明，不要求每次全仓扫描。

## 8. 模型配方暴露了项目结构与配置归属的问题

用户进一步补充实际模型配方，并指出该事实可能不需要由文档重复维护：GLM-5.3 使用千帆 Token Plan → 千问普通 API；GLM-5.3-Flash 使用千帆 Token Plan → Ark Coding Plan → 千问普通 API；advisor Kimi-K2.7-code 使用 Ark Coding Plan。供应商目录只能描述可选能力，不能代表已经选定的配方。这修正了本报告此前偏重文档的调查范围。

只读核对找到了对应机器配置：GLM-5.3 的链在 `runs/iteration14/glm53-root-full-github-20261006/gateway-routes.json`；Flash 和 advisor 的链在 `runs/pi-minimal/sequential-stage2-stage3-20261006/draft/pi-i14-k27-ark-max32768/gateway-routes.json`。后者的同级目录还有派生 model-gateway.json、models.json 和网关准备代码。这证明配方并非完全没有表示，而是目前找到的准确表示附着在旧运行及其派生产物上。

同期公共 [catalog](../../materials/model-gateway.json)中的 GLM-5.3、Flash、Kimi-K2.7-code 默认 deployment 分别是 BigModel、BigModel 和 Moonshot，没有 Ark Kimi-K2.7-code 条目。显式路由和 catalog 默认具有不同语义：[prepare_catalog](../../tooling/scripts/hackathon_gateway.py:90)优先选择显式有序路由，未指定时才取 factory26_default。因此，把目录/default 当成本次配方不仅是阅读错误，也有可执行默认参与其中；这不是只有提示词的问题。

[打包代码](../../tooling/scripts/package_agent.py:79)已经接受 gateway-routes，并按公共 catalog 解析 deployment；[网关服务](../../tooling/scripts/model_gateway_service.py:66)也支持读取并保存路由。无需因本案例再发明一种配置语言。但旧派生 catalog 含有而公共 catalog 缺少的 deployment，意味着准确配方不能仅靠复制路由就直接经该公共打包函数解析。这是静态结构差异，不代表主线采用的所有执行路径都失败，主线可能明确携带派生 catalog。

本轮尚未确认哪个稳定维护入口持有跨运行复用的当前配方，也没有穷举所有历史配置，不能声称仓库完全不存在该入口。当前 [执行 packet](../pi-minimal/evolution-20261006/packet.md:13)已经补上了上述来源引用，这是本轮纠错后的状态，不证明此前已能直接发现。

结构优化应明确四类对象的关系，而非强制四个新目录：供应商/deployment catalog 持有可用端点和模型映射；可复用运行配方持有角色模型及有序路由；variant 持有 Agent 行为与接入能力；run 持有实际消费配置的冻结副本和实际请求记录。已选链、冻结链和请求最终命中的供应商分别取证，不能互相替代。

配方的作用域也需要决定：如果是多次实验复用的选路政策，应在现有配置归属中有可维护输入；如果只是某次实验的选择，任务/实验输入足以持有，不必提升为全仓默认。两种情况下，新运行都应显式消费所选配置，不能要求 Agent 从供应商文档重建选择，或以“最近一次”历史运行自动替代用户决定。文档只需要说明对象归属和使用入口，不重复维护完整链条。

## 优化方案与实施顺序建议

首先，以完整工作路径作为改造对象，贯穿入口、规则、当前状态、实际操作和结果解释。优先处理“选择模型与费用来源 → 本地运行 → 查询或接续 → 非正式评分”，同时保持正式参赛身份清楚。当前设施仍在实施，操作合同的改写需要与其实际负责人交付同步，不能由本审计抢先宣称可用。

其次，整理根指令和相邻任务的职责：长期协作规则留在 AGENTS.md，个人本机偏好留在 AGENTS.local.md，当前授权与具体矩阵归 packet，供应商事实归提供商文档和实际配置，运行方法归所属执行器的操作说明。应用这个标准时，逐项确认具体政策仍否有效，不机械清空历史或所有预算保护。

随后，将该路径暴露的同类问题推广到相关范围：恢复、监控、Console、实验状态与开发接续。范围由实际依赖决定，不能因为模型案例解决就宣布结束，也不能无依据重写所有档案。已有知识归属和目录足够；更简单的方案是纠正内容与撤回旧推荐，不建立额外索引、规则引擎或全仓文档检查器。

最后，用自然任务检验判断质量，覆盖模型选择、已获授权行动、旧运行读回、新设施未完成、恢复限制和评分身份等不同情境。实际模型运行、独立会话或官网评分属于后续验证授权，不在本次静态审计内。

## 建议的验收依据

| 情境 | 需要观察的正确结果 | 需要暴露的失败 |
| --- | --- | --- |
| 用户要求指定模型的本地自费 API 运行 | 找到对应供应商和现有配置，区分账单来源与比赛身份；不自设费用停止线 | 由 self_funded 推断只能用 ARC，或查错账户后宣布阻塞。 |
| 用户已授权具体修改 | 找到当前范围，完成必要工作，材料性变化才交回决定 | 把条件式复核流程变成重复审批，或用旧 packet 撤销当前授权。 |
| 当前接口已有源码但尚未闭环交付 | 准确说明可用与未验部分，找到状态持有者 | 从命令示例或 HTTP 200 推断真实运行已验收。 |
| 读取旧运行或准备接续 | 使用来源冻结执行器，说明继承与缺失状态 | 用当前 CLI 调旧命令，或把应用/Git备份称为完整检查点。 |
| 本地生成后寻求权威评分 | 区分独立应用评测与正式参赛，并保留产物身份 | 把“官网评分”自动当作参赛，或用重放替代参赛生成。 |
| 搜索命中历史段落 | 无须先读完整历史链也能识别适用对象 | 摘录里的“当前”被当作今天的运行方法。 |

评估应记录找到足够信息所需的阅读、无收益绕路、返工、错误决策和不必要等待。文件大小、链接数量、工具耗时和模型输入量可以辅助比较，但不能单独证明正确性或效率。不同现场、模型、授权和外部等待应分别说明，不能冒充文档的单变量收益。
