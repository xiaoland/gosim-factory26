# 设计、实施与验收的共同方法

用户已明确 Issue/PR 的一般工作分工。本页保存 SVC 方法与 Braid 产品行为之间的约定；它是给 LLM 的指导，不是由 harness 判定阶段或强制交接的协议。完整 V&V 输入以用户提供的 [verification-system.md](../verification-system.md) 为准，本页只记录本任务的应用和待补缺口，不改写原文。

## Issue 与 PR 的职责

| 工作对象 | 一般工作内容 |
| --- | --- |
| Issue：设计 | 理解、分析和完善产品需求；结合既有实现、可维护性等设计技术方案，覆盖需要的产品/Unit、HLD/LLD 层次；设计最终验收方案，明确条件、可观察结果和 Oracle。 |
| PR：实现 | 通过预演收集信息、准备材料、尽早收敛实现分支，规划尽可能线性的实施计划；执行计划并获得局部反馈；进行最终验收，交付实际结果、证据和限制。 |

技术方案与实施计划的边界在于所回答的问题：前者确定解决方案及其理由、约束，后者确定怎样把方案变成现实并获得反馈。不是按文档长短或抽象层次把 HLD 固定放在 Issue、LLD 固定放在 PR。对简单改动也不强制生成多层文档。

预演降低实施中的不确定性，不假装提前知道所有结果。PR 发现需求、技术方案或验收依据有实质问题时，通过相关讨论回到 Issue 修订理解，再继续实现；这不需要交换 Agent 角色或建立阶段事件。PR 负责执行最终验收并报告证据，根 Issue 对多项交付的整体判断不替代 PR 的这项责任，也不要求机械地再跑一份相同验收。

## 本任务如何应用 V&V

验收依据从产品意图经行为性质/约束导出，再选择观察证据和判定方法；设计假设单独识别，避免把当前实现写成需求。设计 Oracle 与选择哪些输入、历史、并发或故障条件是两个问题。检查既要能在目标性质被破坏时失败，也要允许满足要求的不同实现；必要时用有意义的破坏实验验证这一辨别能力。

自动化测试、临时脚本和 Agent 操作的“手动”校验都可以产生验收证据，按可重复性、复用价值、可信度和全生命周期成本选择。“手动”不自动意味着交给用户。先设计怎样判断，再由实现准备需要的测试工具或脚本；不要求所有代码机械地 test-first。局部快反馈与较完整的产品验收提供互补证据，保留环境设置、观察、清理和复现的能力。

验收证据回答约定结果是否成立，诊断证据解释如何发生以及为何偏离；日志、内部状态、会话结束或全部讨论 resolved，不能替代它们无法证明的产品结果。验收依据可以因产品变化或 Oracle 缺陷合理修订，但需说明原因，不能随实现一起放宽来取得全绿。Factory 既有冻结后运行官方 ARC-bench 的边界不变，运行时 Agent 的自检不能替代外部评分。

## Corpus 的组织和内容需要重新评估

撤回先前“SVC 主要骨架已覆盖、在原目录补强即可”的判断。此前只确认 [Design](../../sources/svc/corpus/methods/design/index.md)、[Test Design](../../sources/svc/corpus/methods/design/test.md)、[Implementation](../../sources/svc/corpus/methods/implementation/index.md) 和 [Verification](../../sources/svc/corpus/verification/index.md) 中存在相关概念，没有验证它们的组织、表达和内容能否帮助消费者完成实际工作。概念出现不等于方法成立，也不能成为保留当前目录的理由。

本轮有界走查发现：Design 的首层内容偏重 forces、commitments、consumer-relative return 等定义和职责边界；[Technical Design](../../sources/svc/corpus/methods/design/technical.md) 主要列关注事项并转向 Taste；Test Design 命名了 Oracle，却没有展开用户方法中“需求破坏应失败、等价实现不应误失败”的选择办法。Implementation 对线性计划的提示也未说明怎样通过预演提前收敛关键分支。这些是本次阅读中仍需消费者补出的判断，不是全部 Corpus 无效的证明。

后续先审查删除、合并和重写：删除不再承担具体判断的重复声明或术语；同一问题需要跨页拼接而没有独立使用价值的内容考虑合并；只有关注事项、没有帮助作出选择的正文考虑重写。保留必要约束及其因果理由，不追求最少字数，不用新的统一术语、模板或必填记录替代旧负担。内容、导航和 prose/表格/例子的选择一起评估，不先冻结目录再追加条款。SVC 仍是通用方法，不能把 Braid 的 Issue/PR 布局写成它的强制组织形式。

最小消费侧核验拟选一个真实行为，由独立阅读者分别使用原文和候选稿，形成方案与验收方法；比较关键约束、Oracle 的辨别能力、实现自由度及额外查阅/澄清成本。该核验尚未运行，一次结果只支持对应局部改动，不外推整个 Corpus。先给出可复核的删改样本，再授权实施；不把全面重写 SVC 当作推进 harness 的先决条件。

## Braid 与 SVC 的关系

Braid 负责使上述工作有合适的上下文与交流载体：Issue/PR 的角色说明、直接关联、可回复的讨论、resolve/hide 及上下文重建。它不解析 SVC 文档来判定阶段、打分或批准交付。SVC 保持独立可用，Factory 装配两者；共同方法不成为两个项目的源码依赖。源码与 Corpus 更新尚未开始，具体缺口及实施边界需随方案复核落实。
