# Braid 协作实用手册

这是一套写作和读取协议，不是表单。字段只在能改变下一行动时出现；没有内容就删掉，不为“完整”填空。

## 1. 开始工作的 60 秒

按这个顺序读：

1. 触发本轮的精确 comment 或状态变化；
2. 当前对象的标题、description、assignee、status 和直接关系；
3. 本次变化指向的 diff、源码 symbol 或稳定合同段落；
4. 只有遇到歧义、反例、冲突或需核来源时，才展开整 thread、linked object、原始证据与历史。

先回答四个问题再动手：

- 当前目标是什么？
- 这次到底新增或改变了什么？
- 哪个未决现在由谁负责？
- 当前合同和证据的精确入口、版本是什么？

不要把“收到了通知”当成“理解并接受”；不要每轮复读整套文档；不要先把 `--thread` 全量输出截短，再把未显示的最新目标当作不存在。

## 2. 先决定放在哪里

```text
可执行行为/接口？                 → 源码
跨任务复用、已采纳的稳定合同？   → 版本化设计文档
本工作项当前仍有效的义务？       → Issue description
当前候选的变化、证据和限制？     → PR description
一次提问、反例、建议、裁决、交接？→ comment / 独立 thread
完整日志、DB、截图、运行身份？    → 原始证据
责任、状态、结构、订阅可机器表达？→ metadata / relationship
调查、授权、计划、恢复点？       → task packet
```

链接大材料时，控制面仍要内联三件事：**为什么相关、关键结论或例外、谁下一步做什么**。

必须默认可见、不能只藏在文件或折叠历史中的内容：目标和范围变化、未决责任、当前阻塞、契约变化结论、审阅结论、替代关系、关闭理由。完整源码、字段表、长日志、历史争论和重复状态则应留在其自然权威载体。

文件入口至少给 `commit/ref + path + section/symbol`。只写工作树路径，除非所有读者明确共享同一快照；原始证据给不可变 artifact/run/DB 身份及必要校验值。

## 3. 各载体只承担一种主要职责

| 载体 | 它回答的问题 | 不要让它承担 |
| --- | --- | --- |
| Issue description | “这个工作项现在欠什么？” | 逐轮进度、完整讨论史、别人的动态 head |
| PR description | “这个候选改了什么，如何审？” | 需求全文、完整运行输出、未裁定争论史 |
| comment | “这一次新增了什么，谁要行动？” | 重抄当前正文、整份文档、无新事实回声 |
| thread | “一个具体问题如何结束？” | 多个 owner 或多种关闭条件 |
| assignee/status/relationship/subscription | “谁负责、处于什么阶段、结构是什么、谁持续获知？” | 理解、采纳、语义覆盖或验收证明 |
| task packet | “当前开发阶段、授权、计划、恢复点在哪里？” | 每个 Issue/PR 的实时镜像 |
| 稳定文档 | “跨任务合同是什么、为何如此？” | 未决争议和逐次进度 |
| 原始证据 | “事实可怎样重放或核对？” | 当前判断和下一动作 |

当前 Braid 本地实现实际提供一位 `desired_member`、Issue parent/child、PR–Issue association、显式 subscription 与对象状态；没有通用 typed dependency、label、milestone 或原生 review decision。手册中的依赖、分类、审阅结论应使用现有 comment/description 明说，不能捏造命令或假设 GitHub 字段存在。

## 4. 最小写法

### 新 Issue

```md
目标：在 <条件> 下交付 <可观察行为>。
完成：<能判断完成的场景/反例>。
合同：<commit/path#section 或原需求节点>。
依赖：#A 产出 X；本项在 Y 后消费。
未决：<问题>（@owner）。
```

不写：完整实现方案、全库文件清单、每次进度、复制的需求树。若是探索型 Issue，可先保留“已知/未知/决定门”，不要假装已有完成判据。

### PR 准备审阅

```md
Ready for review: <head>
解决：#N 的 <行为>。
变化：<2–5 个实际变化>。
合同版本：<入口>。
证据：<命令结论、exit、artifact、对应 head>。
限制：<仍未知或不覆盖>。
请审：<具体判断，不是“请看看”>。
```

实现细节让 diff/代码承担。候选或范围显著变化后刷新 description；WIP head 由 Git/PR 自身负责，冻结候选时才固定版本。

### 提出反例或疑问

```md
反例：在前提 X 下出现 Y（证据 E）。
冲突：这与合同 Z 的判断 C 不一致。
影响：若成立，会使 #A 的证据失效 / 阻塞 PR #B。
请 @owner 判断：改实现，还是修改合同？
```

不要用“我担心有问题”代替可复核观察，也不要重贴整个设计。

### 交接

```md
交给 @A：产物 X@版本，入口 E。
你需完成：Y；完成条件 Z。
仍由我负责：R / 我不再负责：Q。
阻塞或拒绝时请回到本 thread。
```

接收者只需“接手 / 有条件接手 / 拒绝并交回”，无需复述全文。发送、queued、delivered 都不是承接；正确行动或明确回应才是证据。

### 需求或契约变化

```md
决定：X → Y。
替代：#old 中的 <具体判断>。
不变：<容易被误解为一起变化的边界>。
影响：#A / PR #B；旧证据 E 仍适用…，需重核…。
权威：<commit/path#section>。
下一动作：@owner <动作>。
```

先把跨任务稳定结论写入稳定文档；comment 保留裁决和传播。若本项当前义务改变，同步 description，但不复制完整裁决史。

### 审阅结论

```md
Reviewed <head>：acceptable / needs change。
阻塞：<位置 + 行为 + 为什么>。
非阻塞：<明确标为建议或 nit>。
已核：<范围/证据>。
未核：<不要暗示已证明>。
下一 owner：@A。
```

Braid 没有原生 approve/request-changes 时，用 comment 明写结论。相关多条意见集中成一个审阅回合，避免五条意见形成五次独立唤醒；行级实现问题留在最窄位置，跨范围工作另开 Issue。

### 解决、合并、关闭

```md
结论：<问题怎样结束>。
落点：<代码/合同/新 Issue>。
剩余：无 / 见新 thread #R（@owner）。
将 resolve root #R through #C。
```

```md
已合并 <head> → <merge> / 已关闭 #N。
满足：<完成判据与证据>。
上层剩余：无 / <义务、owner、入口>。
```

先执行并核对真实状态，再使用“已合并/已关闭”。`ready`、`merged`、`closed` 都不能替代上层验收或父项交回。

## 5. thread 生命周期

### 何时开新 root

新问题能独立回答，或 owner、交付物、关闭条件发生变化时，开新 root 并互链。仅“同一模块相关”不足以共用 thread。

### 何时 reply

回复确实推进同一问题：补证据、回答、缩小选项、给出裁决、确认落点。旁支风险和新的实施任务另开 root。

### 何时上移

- 成为跨任务复用的已采纳合同 → 稳定文档；
- 改变本项当前义务或完成门 → Issue description；
- 确定当前候选及审阅边界 → PR description；
- 只解释历史选择 → 保留在 comment/thread。

“上移”是建立唯一当前入口，不是把同一全文复制三遍。原 comment 只需留下决定身份和新入口。

### hide

仅用于单条明确重复、损坏、离题或整体被替代的内容。reason 写明保留/替代 ID。hide 不会撤回已经送入会话或排队的通知；含仍有效例外、未决责任或唯一证据的评论不得只靠 hide 整理。

### resolve

当前实现只接受 root ID。resolve 时把该 thread 当时的最大 comment ID 设为 cutoff，默认投影折叠该前缀；之后的新回复仍可见。执行前：

1. 读取整条 root；
2. 列出仍在使用的决定、例外、责任和证据；
3. 把长期结论上移，把未决问题拆成新 root；
4. 核对 root 与预计 cutoff；
5. 再 resolve，并读回回执。

混合 thread 无法安全整体结束时，保持可见优于强行折叠。unresolve 清空整串 cutoff，不是任意子树的精确 undo。

### delete

当前 deleted comment 的正文会被清空且不能恢复。它不是日常整理手段；敏感内容原则上不应先写入。需要删除时遵循额外授权和证据保留规则。

## 6. 关系、责任和通知

建立关系时，至少留一句：

> `#A` 产出 X；`#B` 在条件 Y 后消费；B 的完成证据写在 Z。

`parent` 表示分解/导航，不自动继承正文；PR–Issue association 是背景关系，当前不区分 `implements`、`depends_on`、`accepts`，也不自动证明关闭意图。跨对象回复必须到目标对象自己的 thread，另一个对象只保留回链和本项义务。

排除范围必须有承接者或明确关闭理由。“不属于本项”不是交接。关系不再成立时更新/删除元数据，并短写原因及替代入口，避免多个对象同时声称拥有同一当前事实。

显式 subscribe 用于持续依赖，`@` 用于一次联系。不要让所有成员订阅所有对象。无需强制每条通知 ACK；有新事实、决定、阻塞或被要求行动才回应。reaction 或 metadata 足够表达时，不新增 comment。

## 7. 写操作和状态核对

- mutation 回包不确定时先读对象状态，不为取得 ID 重放写操作。
- 声称完成前核对实际对象状态、候选 head 和证据身份。
- 证据表格每一行绑定真实 artifact、exit、运行条件和适用 head；表格整齐不等于映射正确。
- 修改 description 前先列出必须保留的当前义务；修改后做语义读回，不只比较字符或 hash。
- Git commit、数据库备份、Braid 状态和原生会话恢复点是不同身份；需要恢复时不能拿其中一个冒充完整检查点。

## 8. 例外

- 长不等于错：高风险合同或复杂裁决可以较长，但先给决定、影响和行动，细节有稳定入口。
- 短不等于好：只有链接、没有当前责任和判断的 description 不可用。
- 真正语义变化必须通知受影响者；不要为了“少打扰”压掉 contract invalidation。
- 小修完全局部时不必另造 Issue/thread。
- 高风险、不可逆或安全事项需要更多内联前提与明确确认，但不扩张成所有通知必须 ACK。
- 历史争议仍决定当前行为时，不能只因“旧”而 hide/resolve；先建立稳定当前入口。

## 9. 方法、CLI、runtime 各负责什么

| 层 | 应负责 | 不应假装负责 |
| --- | --- | --- |
| 方法/Skill | 内容放置、读取顺序、thread 拆分/上移、交接、停止条件 | 系统不存在的继承、通知、review 或折叠保证 |
| CLI | 精确读取对象/字段/版本；写回 changed/unchanged、ID、root/cutoff、影响；失败保留具体原因 | 判断理解、采纳、语义覆盖和验收 |
| Runtime | 默认投影、预算降档、关系展开、通知、invalidate/reset、历史恢复 | 把 link/close/delivered 自动提升为承接或通过 |

当前 I13 已在源码中把 comment/title/relationship 变化改为增量而非重建，但真实运行仍未验收；方法不能把静态实现写成已观察保证。

## 10. 静态审阅清单

不用跑模型即可在既有 lineage 上桌面演练：

1. 新接手者按本手册默认读取，能否指出目标、变化、未决 owner、合同与证据入口？
2. 重排原内容后，是否产生第二份当前事实、孤儿责任、隐藏例外或不可追版本？
3. 对混合 thread 列出 root、cutoff、长期决定和拆出的未决，判断 resolve 是否安全。
4. 对 WIP hash 更新逐次判断是否改变下一行动；记录无新事实的读取/编辑/通知链，不把 token 当知识。
5. 从原需求→Issue→PR→review→证据追一条完整义务；区分 ID 出现、语义覆盖和真实执行。
6. 保留成功交接案例，确认新规范不会强迫重复 ACK 或全文复制。

只记录可行动缺口：缺失当前事实、冲突副本、孤儿责任、不可追版本、混合关闭条件、无新事实回合和规则误报。字符数、评论数和全部 closed 都不是独立成功指标。
