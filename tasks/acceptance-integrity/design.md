## 推荐的模型分工

| 层面 | 建议 | 责任 |
| --- | --- | --- |
| 根 Issue 的 Braid Agent | GLM-5.3-Flash / high | 需求理解、设计、最终验收方案、分工与整合决策 |
| 子 Issue 和全部 PR 的 Braid Agent（包括根整合 PR） | 由指派者从可用 Agent 中选择；当前提供 GLM-5.3-Flash / DeepSeek-v4-Flash | 按工作内容选择负责人，承担该工作项的设计或实施责任 |
| 原生 advisor 子 Agent | Kimi-K3 / high，fresh | 有边界的独立问题判断、关键设计选择、判据是否失真；不接管连续实施 |
| 原生 executor/explorer/browser-operator | 沿用现有Flash/视觉配方，fresh | 执行已明确的局部工作并提供相关证据 |

先推荐Flash根 + K3 advisor 一套配方；GLM-5.3根或GLM-5.3 advisor作为后续替代，不同时扩大矩阵。
advisor是Pi原生子角色，不是一个额外的Braid派工身份；当前specialist已经承担同类判断工作，应调整现有角色而非叠加近义角色。
昂贵Braid会话限制继续有效；原生advisor不占Braid名额，但仍要显式设置模型，按有界问题调用。
角色分工是建议，不宣称Flash已被证实优于K3；依据是本轮K3未防住验收偏移，先让连续工作速度与判断成本分离。

variant 配置可用 Agent 的能力和模型，并选择最初接收根 Issue 的 Agent。
随后由 Agent 通过 `--assignee` 指派工作；Braid 按指派结果启动相应配置，可以拒绝超出限制的选择，但不依据“子 Issue”“PR”“整合”身份替指派者选模型，也不在拒绝后静默改派。
Agent 面向的是可指派的名称与能力说明，无需理解 profile；具体协作者名称由指派返回，不暴露 UUID。
上表不构成 Braid 的阶段路由表，根整合 PR 也没有固定模型。

## 工作流程提示词放在哪里

沿用 variant 各成员的 `agents/<id>/instructions.md`，例如当前开发基线的 `variants/pi-team-mixed/agents/pi-glm-fast/instructions.md` 和 `pi-deepseek-fast/instructions.md`。
当前真实接线是 `run.py::native_files` 读取正文 → `profile.user_instructions` → Braid 透传 → Pi adapter 的 `--append-system-prompt`。
因此它进入成员会话的持续系统指引；源码字段名虽然叫 user_instructions，Pi 中不是一次性 user message。
本轮修订沿用此入口，不把完整工作流程追加到“请处理 Issue #…”消息中。

| 材料 | 归属与内容 |
| --- | --- |
| variant 成员 instructions.md | 本 variant 的工作顺序、Issue/PR 协作约定、develop/main 集成方式、可重复最终验收要求 |
| SVC skills | 需求解释、技术设计、判据设计、局部反馈和证据解释的通用方法；不认识根 Issue、分支名或比赛 |
| 原生 Pi 角色 agents/*.md | 角色能力与适用场景；browser-operator 用于开发中的探索和快速复现，executor 可实现测试或脚本 |
| 根 Issue description | 本次任务的需求、资料入口和实际环境约束；已有获授权的任务拆分要求保留，不把通用方法再次复制进去 |
| Braid 自带指引 | GitHub 式 Issue/PR、comment、assignee 与 Git 操作；不定义本 variant 的工作方法或原生角色调度 |

拟替换的核心工作流程正文如下，供复核，尚未写入源码：

> 在 Issue 中分析和完善产品需求，并据此共同设计技术方案与验收方案：要证明哪些结果、在什么条件下观察、怎样判断成立。两种方案相互校正，形成足够清晰的依据后再规划实现。使用关联 PR 完成实现计划与必要排障、代码和自动化测试或脚本；实现中持续获取快速反馈，再对整合后的结果执行最终验收。发现需求或方案问题时回到相关 Issue 协作调整。
>
> 子任务 PR 合入 develop。根 Issue 组织关联的 develop → main 整合 PR，由其负责人在最终候选上执行覆盖完整需求范围的自动化测试或脚本，修复失败并复验，再合并交付、关闭根 Issue。局部检查通过不代表整体验收完成；结果须对应实际检查的提交与运行条件。
>
> browser-operator 用于开发中的页面探索、复现和快速反馈。最终验收由可重复执行的测试或脚本完成，其中可以使用浏览器自动化；一次性的 Agent 浏览器操作报告不能替代它。按工作内容选择负责人，使用 SVC 的相关技能设计检查、解释结果并记录依据。

这里的最终自动化要求是本次 variant 的工作政策；通用 SVC 仍可按场景讨论一次性观察的价值。

## 降低编写可靠浏览器检查的成本

这是本轮独立的交付项，与 SVC 方法、协作恢复和最终整合并列推进。
[A 复核](../competition-budget/a-review.md) 已记录：Agent 手写 Bash 快照解析、等待和会话管理，过程中引入了递归错误；读取工具文档的范围又没有覆盖其已有的语义定位接口。
这些是工具使用摩擦的证据，不能据此断言某个浏览器工具本身无效。
此前本设计强调了最终脚本化要求，却未单独展开降低脚本编写成本的落地内容；本节恢复这一遗漏。

目标是让 Agent 将注意力用于要证明的产品行为，用成熟工具直接表达定位、操作、等待和断言，并容易复现与解释失败。
减少手工胶水不能以放宽判据或隐藏错误为代价。

| 工作 | 本轮交付 | 归属 |
| --- | --- | --- |
| 让检查容易编写和执行 | 核实并接通适合可重复浏览器检查的现成脚本接口及所需运行依赖；版本、实际可用 API 与材料一致 | variant 的原生能力材料、现有打包/运行依赖 |
| 让操作知识容易找到 | 工具入口直接导航到有作用域的定位、条件等待、断言、会话/数据准备、失败证据与复跑；提供少量通用写法示例 | 工具专属 skill/指引，不塞入 Braid 或通用 SVC |
| 让正确角色拿到能力 | 编写或执行自动化检查的主会话/executor 可取得上述材料；browser-operator 继续服务开发中的探索与快速复现 | 原生角色配置与材料接线 |
| 让失败容易解释 | 保留首个失败的具体操作、期望和观察；按需要使用工具已有的截图、trace 或日志；依赖前置失败的检查明确未执行 | 所生成应用的检查与工具能力 |

LLD 优先选择已经提供定位、等待、断言和失败记录的现成接口，避免再次由 LLM 临时组合一套 Bash 快照测试工具。
探索用浏览器与最终检查执行方式可以不同；具体选择根据当前固定版本能力、已有依赖与编写成本核实，不预设必须更换现有 agent-browser。
通用 SVC 负责为何这样设计观察和判据，工具专属材料负责怎样准确表达它们。
定位一个元素成功不证明该元素满足要求；需求到判据的漂移仍由 V&V 方法处理。

最终验收产物是可重复执行的应用测试或脚本；browser-operator 的一次性操作报告不替代它，也不新增独立 reviewer 作为本轮必经角色。
不建立 Factory 验收框架、固定验收 schema，或针对 SVC 内容的测试。
浏览器检查不读取隐藏官方用例，也不硬编码本次 GitHub/Sheet 的具体要求。

观察改进是否生效时，除有效发现缺陷外，还要看编写/调试检查的耗时、重复自制工具的负担、环境或脚本自身造成的假失败，以及能否在同一候选版本上直接复跑。
使用运行已有的原始记录判断这些效果，不先建设一套新的测量平台；没有可比证据时只报告实际观察，不宣称成本下降比例。

## 工作与交付

```text
分析、完善产品需求（Issue）
  ├─ 技术方案设计 ──┐
  └─ V&V 方案设计 ─┴─ 相互校正，以需求为依据
  ↓
实现计划与必要排障（PR）
  ↓
实现 ↔ 快速反馈（可使用 browser-operator）
  ↓
自动化测试／脚本执行 V&V → 修复与复验
  ↓
提交、合并与关闭 Issue

多工作项的整合关系：
根 Issue
  ├─ 子 Issue → 子 PR ─┐
  ├─ 子 Issue → 子 PR ─┼─→ develop：持续整合
  └─ …                ┘
根 Issue 的整合 PR：develop → main
  实现计划与必要排障 → 最终候选 → 完整自动化验收 → 修复与复验
  ↓ 验收成立后合并
main：被接受的交付版本
  ↓ 根 Issue 关闭并完成协作收尾
导出 main
```

整合PR是完整产品的验收工作项，不是把子PR通过数相加，也不是关闭根Issue前的一次形式确认。
根Issue负责确定依据；整合PR负责实际执行完整验收，结果回到根Issue，由根负责人完成交付判断。
这里“自行完成”落实到该 PR 的负责人及其原生 session tree，具体编写或运行测试可按工作内容委派，但最终执行载体必须是自动化测试或脚本。
browser-operator 在开发中提供短反馈，不承担最终验收；测试或脚本仍可使用真实浏览器自动化。
验收依据、前置条件、观察与判断应落实到可再次执行的材料，避免每次让 LLM 临场重新理解、操作和判定。
复用已建立的有效检查，在最终候选上运行；不要求重写一套相同测试，也不把子 Issue/PR 的旧 PASS 汇总成整体验收。
Issue与PR仍是不同Braid会话，不能因同一profile就声称是同一个Agent。
不要求根Issue随后重复一遍同样E2E，也不让advisor仅凭意见批准交付。

子任务的结果在develop可用并不意味着整个产品可以交付。
进入最终验收时确定候选提交；候选变化后，按变更影响重新取得有效证据，不能用旧结果支持新提交。
判据以需求为依据，区分违约行为和符合需求的实现差异，不能因当前实现如此而放宽，也不能把偶然实现细节升级为要求。
验收失败先辨别是产品违约、检查失真、环境失败、还是需求冲突，再决定修改代码、检查或设计。
问题没有解决就应保留未完成状态和真实证据，不能把“当前没有可执行会话”当作产品完成。

## 组件边界与已查明的技术缺口

目标边界是 Braid 提供通用的 Issue/PR、comment、任意 Git 分支的 base/head 和 merge；当前 base/head 仍有下述缺口。
选择develop/main、定义验收方法、安排角色属于本variant的工作方法；SVC提供通用V&V方法。
Braid不读取验收脚本、解释得分或判定产品质量；根Issue关闭是Agent报告的工作项状态，而非Braid推断的验收结果。
Factory依据该工作流选定main为交付ref；运行空闲、完成、阻塞的区别应保留到调用方，不能再混用。
若所有会话空闲但根Issue未关闭，可以报告未完成并保留证据；不把它当成功交付，也不以无限等待或自动制造语义事件来掩盖断点。

当前代码缺口：

- `objects::pull_request` 的base直接取单个 `local_run.delivery_ref`。
- `objects::merge`及merge恢复同样固定写此ref；仅增加CLI `--base` 参数不足以落地多目标PR。
- `pr create --head` 当前取源commit另建 `braid/pr-N`，没有让PR持续引用用户指定的head分支。新方案须明确并对齐分支语义，避免develop更新后PR仍展示旧快照。
- `local::drive` 当前以quiescent结束；Factory的 `load_delivery` 不依赖根Issue关闭。需按用户新要求设计明确的完成交接，但不重建产品验收裁决器。

进一步审查发现，`@成员` 不仅缺正文寻址；关闭后的 Issue 成员 sleeping、已合并 PR 成员 retired，普通消息缺少继续执行路径。
建议将工作项完成与成员可联系性分开，显式通信恢复对话但不自动重开工作项。
`pr ready` 还绑定 PR Agent 本地 clone 的干净状态与 HEAD；建议将 draft/ready、已发布版本和调用者验收结论分开，merge 始终以 origin 为边界。
常用 view 应复用已有关系与 Git 事实，提供直接关联项、base/head、当前 SHA 和合并结果，避免依赖 Agent 记忆或另一条隐藏导航路径。
这些建议及暂不补齐的 GitHub 功能见 [审查报告](braid-github-audit.md)，LLD 需要收敛关闭/改派后寻址和分支变化的真实边界。

LLD/预演重点应沿一次实际派工、发布、合并、整合、关闭、导出追踪这些接线，不借机重写整个调度器。
CLI应继续沿GitHub常见交互表达上述能力，命令示例在接口确定后再提供。

原会话整理见 [vv-methods.md](vv-methods.md)：先给出目标、基本前提与知识树，再按规格、证据设计、结果判断、反馈演进四个分支展开方法、反例与适用条件。
该入口还记录与 SVC 的操作化差异；运行时技能按已认可内容方案改进，不照搬整个研究材料。
不把“明确角色、名称、状态不能简化为文字存在”作为新的 SVC 规则；这是原问题的一个实例，通用问题是需求到 oracle 的漂移。

当前需要恢复的执行脉络是：

1. 从产品意图确定行为要求，明确哪些变化影响承诺结果，哪些只是允许的实现变化；再选择观察并形成判断规则。每次转换都解释凭什么能支持上一步，分类或字段本身不是保真保证。
2. 分开处理观察、oracle 和条件选择：观察要取得什么，什么结果算成立，在哪些输入、状态和历史下检验。判据正确不代表选取的条件足够有区分力。
3. 用两个方向挑战检查：需求已被破坏却仍能通过吗；需求仍成立、实现方式改变却会失败吗。必要且便宜时用已缺失行为或有意构造的违约取得判别力证据，不为每条检查强制建设元测试。
4. 行为已清楚时，先表达可执行约束，确认它因预期缺失而失败，再做小实现、取得通过反馈，在行为约束内改善实现。语法、环境或夹具失败不是这个 Red；尚不清楚应该做什么时先探索需求，不冻结猜测。
5. 保持小而连贯的实现与快反馈，同时在集成节点和最终候选上取得更高层证据。技术方案与 V&V 方案共同确定既忠实于产品又有合理成本的观察边界。

用户已同意本轮两个内容变化：在现有 check-design 中用一个贯穿例展示保真转换、观察/判据/条件选择和双向检验；在现有 implementation workflow 中恢复有适用前提的 test-first 循环，并链接检查设计。
用户随后认可较系统的 SVC Corpus 内容与导航改进；测量、选样、可重复执行及跨技能消费已纳入本轮范围。
具体内容归属、目录与导航方案见 [svc-content-design.md](svc-content-design.md)，避免在本文件复制另一套 Corpus 设计。
不用 UI 角色/名字清单代替通用方法，不将长会话整体塞进技能，也不新造强制验收对象或格式。
自动化本身不会防止漂移：错误判据同样能稳定地产生错误的 PASS。它提供重复执行的基础，语义保真仍由检查设计解决。

实现过程中仍要持续得到局部反馈，不能把最终整合验收理解为做完所有代码后首次验证。
根整合PR检验子项组合后的完整结果；它与局部反馈互补，不机械复写每个断言。
对当前检查的修改，若有明确需求依据证明是在修正检查错误或适配观察方式，执行者可直接纠错并留依据；若涉及实质需求解释或设计改变，则回相关Issue协调，不默默与实现一起放宽标准。
无人值守时依据已提供需求作决定，确实缺少必要权威信息才保留阻塞；不假设用户中途介入。
完整来源与认可边界见 [vv-source-review](vv-source-review.md)。

## 验证顺序草案

先用已有冻结应用检验新验收方法是否能区分已知违约与合法实现；检查编写者不接收缺陷清单或测试实现。
再在新variant的真实任务中验证多分支协作、整合PR完整验收和main交付，同时保留模型层级及原生角色证据。
小验证用来筛掉无效方法，不代替完整bench；具体输入、代价、终态判据与实施计划一并供用户复核。
不将当前B与多项变化后的新variant解释成单变量模型对照。
