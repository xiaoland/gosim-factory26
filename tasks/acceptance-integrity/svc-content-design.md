# SVC 内容与导航改进方案

源码入口后继：本文件中的 `variants/pi-team-mixed` 现为 `variants/pi-braid`；历史冻结包与运行身份不变。

状态：2026-09-26，用户已认可较系统的 Corpus 内容改进范围及本文内容架构，同时关注导航与目录性能。
进入具体改写要点、正文样例和实施准备；尚未开工修改技能源码。
原会话知识框架见 [vv-methods.md](vv-methods.md)，本轮协作和运行方案见 [design.md](design.md)。

## 问题与目标

当前 SVC 多数原则与原讨论一致，但将部分因果、适用条件和操作步骤压缩成了提醒。
只增加两段内容难以恢复“需求判断—证据设计—实现反馈—结果解释”的完整联系。
另一方面，将原会话整理全文搬进技能，会增加无关阅读并把研究笔记变成工作负担。

目标是在当前问题发生时，Agent 能找到足以指导下一步判断的方法，保留必要理由和例子，并按需深入。
改变的不仅是篇幅，而是知识归属、路由方式和实际消费路径。
本次以 V&V 为主线审查相关技能；task-packet 的既有规划与协作模型不因这次内容扩充重做。

## 内容归属与拟议目录

保留五个现有技能入口，先不增加第六个总览技能或要求 Agent 预读整套 Corpus。
知识框架用于作者检查关系和遗漏，运行时按任务中的问题分发。

```text
skills/
├─ svc-design/
│  ├─ SKILL.md                         从产品/技术疑问进入
│  └─ references/
│     ├─ workflow.md                   产品、技术与验证设计的关系
│     ├─ product.md                    目标、要求、假设；稳定行为与探索
│     ├─ technical.md                  实现与验证边界共同设计
│     └─ engineering-judgment.md       保留既有职责与复杂度判断
├─ svc-verification/
│  ├─ SKILL.md                         最小理解框架＋按问题直达正文
│  └─ references/
│     ├─ check-design.md               要求到判据、双向判别、贯穿例
│     ├─ evidence-design.md            条件选择、测量、观察边界与成本
│     ├─ repeatable-checks.md           构造条件、执行、观察、重置、复现
│     └─ interpreting-results.md       结论范围、失败解释、判据修订
├─ svc-implementation/
│  └─ references/workflow.md           条件性test-first、快反馈和整体复验
├─ svc-investigation/
│  └─ references/debugging.md          依据具体差异取证，修因并复验
└─ svc-task-packet/
   └─ 现有入口与信息组织                保存判断/材料/下一步，链接方法
```

以上是拟议内容边界，不是承诺必须新建每个文件。
若一项方法不足以形成独立的阅读任务，合回所属正文；保留既有稳定路径，避免无收益改名。

| 承接面 | 改进内容 | 怎样控制负担 |
| --- | --- | --- |
| 最小理解框架 | 说明要求、判断规则、观察与结论的关系；有限证据、实现自由和反馈成本 | 在相关技能入口保留能解释后续方法的短因果，不复制研究中的来源审计 |
| 语义转换 | 从目标提炼有依据的要求，选择观察、形成判断，并双向挑战 | 一个贯穿实例同时展示过弱与过严，避免不断追加禁止事项 |
| 证据设计 | 选择有区分力的状态/历史/边界；明确测量口径；按语义与总成本选择层次 | 按需要解决的不确定性给出方法和盲区，不罗列测试名词目录 |
| 可重复执行 | 设置条件、等待实际结果、记录失败、清理状态与再次运行；适配检查形式 | 提供方法，不规定目录、框架、日志平台、隔离机制或报告 schema |
| 实现反馈 | 行为已清楚时，预期原因 Red→连贯实现→反馈→保持行为改进；按影响回到整体检验 | 保留适用条件，需求探索和无价值的仪式性 Red 不强制 test-first |
| 结果解释 | 保留已有较充分的验收/诊断、共同假设和结论范围；连接判据修改与下一步 | 复用原文，移动重复部分；不再把这些方法复制到每种角色中 |

生产反馈与长期演进应保留适用边界及必要导航，不在本轮扩展部署治理方法。
SVC 持续保持通用；最终必须自动化脚本、browser-operator 分工、根 Issue/整合 PR、模型和比赛规则仍归 variant。
降低浏览器检查编写成本是本轮另一个明确工作项，详见 [主设计](design.md) 的同名章节；具体工具 API、依赖和操作写法归工具材料，SVC 只承载通用方法及按需导航。

## 导航如何服务实际读取

描述使用任务现场的语言，例如“测试通过但行为仍不对”“决定该检查哪些情况”“解释一次失败”，使尚不知道 SVC 术语的 Agent 能判断是否需要技能。
入口先给最小判断方法，再用问题到正文的直接链接指路。
技能入口可直接到目标 reference，不建立“总览→流程总览→方法总览→正文”的必经链。
正文把关键动作及其原因放在当前阅读位置，深入材料链接承担扩展而非隐藏必需前提。

一项方法只保留一个主定义，其他位置给出使用时机和指路。
跨技能引用仍按能力名称组织，不引入安装路径耦合；某个技能独立安装时，不能因未装另一个技能就失去本技能最基本的判断方法。
案例使用通用软件问题；原会话过程、来源争论、已放弃方案留在 task packet，不进入运行时。
按句换行，保持自然因果表达；表格承载比较，树承载关系，不为统一外观制造模板。

这里的导航性能包括：入口是否选对、定位所需方法要绕几次、读到多少无关内容，以及是否因缺关键背景而回读。
不能只以文件更短或目录层数更少判断性能，也不能在没有运行轨迹时声称路由已经改善。

## 必须一起检查的实际接线

当前 `variants/pi-team-mixed/run.py::native_files` 会把 investigation/design/implementation 的 `references/workflow.md` 正文直接追加到 explorer/specialist/executor 提示词。
主会话则通过技能元数据和入口选择材料。
因此仅修改 SKILL.md 的导航不足以让所有消费者受益；重整时需要保持这些 workflow 的核心方法及深读入口有效，核实冻结包中实际分发的材料。
这不要求恢复 AGENTS.md 的大段注入，也不默认将所有新 references 展开到角色提示词。

## 复核与后续验收

下一阶段先给出各文件的改写要点和核心正文样例，按真实读取路径复核，而不是先批量写完再发现组织问题。
受影响的入口、主体与角色实际消费材料一起检查；不增加 SVC Corpus、Factory 或设施测试。
已有冻结包不修改。
后续获授权真实运行中，按明确问题检查是否找到相关方法、形成有效判据、合理修订检查并执行最终验收。
单独读到技能或出现方法名不算采用；脚本全绿也不能自动证明判据保真。
实验分数与方法采用证据分别报告，不把协作机制恢复的收益直接归给 SVC。
