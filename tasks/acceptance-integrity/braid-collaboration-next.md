# 下一阶段：让协作可以持续接手，而不靠偶然读到评论

2026-09-27，讨论稿，尚未授权全面实现。
本次已授权的通知快修与四题本地恢复独立推进，不等本文完成。

## 顶层目标

Agent 沿熟悉的 Issue、PR 和 Git 行为，能够知道当前工作、联系负责者、收到回应，核对具体版本的验证依据并完成集成；上下文重建、短暂离开或运行恢复后，这条链仍可继续。
Braid 提供对象、状态与可达通信，不替 Agent 判断需求、拆分方式、验收充分性或下一步应该做什么。

```text
持续可接手的软件开发协作
├─ 找到工作与责任：需求、负责人、相关任务及当前状态
├─ 讨论与交接：请求可达，回应可追溯，参与者能继续收到更新
├─ 实现与集成：发布分支 → PR → 修订 → 合并，版本身份明确
├─ 验证与反馈：检查结果对应实际提交，失败依据可重读
└─ 重新接手：从对象历史和待处理消息重建当前判断
```

## 独立证据与当前修改

两位独立研究者分别形成 [GitHub事实基准](/Users/lanzhijiang/Documents/Codex/2026-09-26-new-realtime-voice-chat-2/github-collaboration-baseline.md) 与 [Braid实现基准](/Users/lanzhijiang/Documents/Codex/2026-09-26-new-realtime-voice-chat-2/braid-collaboration-current.md)。
前者依据官方材料和只读公开实例，后者依据实际 `factory26/sources/braid` 与 Keep 数据库；不是拿仓库外的 GitHub-runtime Braid 解释 Local。
Braid报告主体是快修前的基线，不能拿其缺口清单声称当前补丁尚未修复。

GitHub 的普通 conversation 订阅不会因另开普通评论而丢失；Braid 把 thread 边界当收件边界是实际错位。
子项关闭会更新父项进度有官方依据，但“父项必有child-closed时间线且所有父订阅者必收通知”未证实，三个公开完整时间线样本也未出现此专用事件。
本次直接父项状态历史及唤醒，是用户认可的 Agent 协作契约，不冒称 GitHub 的完全相同实现。

## 按开发链影响排序的建议范围

| 优先级及归类 | 当前差异与后果 | 建议行为及可验证结果 |
| --- | --- | --- |
| 1，必须补齐：责任与关注分开 | 已有 assignee 和评论作者，但没有持久的创建者订阅；历史发言通过 assignment 找工作项，旧人/新人可能混淆 | 定义创建、参与、明确联系后的默认关注，以及改派、退订、终态后的规则。成员被换掉不能把发给旧人的私信冒投给新人；负责人变更应保留可读历史。先明确语义再定最小数据结构。 |
| 1，必须补齐：交接有可观察结果 | 当前仅明确 @ 有逐地址回执；普通更新保存成功不代表有人接收，忙时排队也不代表已经行动 | 常用评论/状态变更能查看实际收件目标及queued/delivered/unreachable。一次动作同时满足多种理由只投一次；忙时保留输入，恢复后可读。当前跨thread与child状态快修覆盖一部分，尚非完整订阅模型。 |
| 2，必须补齐：可重新找到事实 | 当前状态可查，完整协作历史没有统一入口；父子关系变化、指派、PR反馈分散于内部events和原生会话 | 在已有view/list上提供面向人的活动记录和必要筛选，串起责任变更、讨论、PR及具体commit。不给Agent看调度UUID、reset事件堆栈或完整内部事件表。父子挂接/移除须能回看旧关系，不只查询当前值。 |
| 2，必须补齐的信息能力：验证结果指向版本 | shell检查和评论可用，但没有持久的commit级检查结果；“测试通过”容易被挪用于另一版本或未合入代码 | 让实际运行的检查记录明确commit、命令、结果和日志入口，并从PR/提交可读。Braid只承载通用事实，不生成测试、不判定需求充分满足，不绑定ARC。可先复用已有文件/评论链接与Git SHA，再决定是否需轻量check对象。 |
| 3，可先合理裁减：评审请求与修订 | 缺结构化review/request-changes；现有评论、@及resolve可以协作，但不能冒充审批状态 | 默认通过评论明确请求、反馈及再次联系；若用户需要结构化review，则最小加入对具体head的请求和结论，不自动加强制reviewer或合并门槛。验收不变为“读代码找错”。 |
| 3，可先合理裁减：分工计划 | 缺labels/milestone/priority、blocked-by；这些字段存在于renderer却未接Local写入 | 当前规模用正文表达顺序和依赖、父子关系表达范围，不假装已有自动依赖调度。若引入关系，仅保存/展示阻塞事实并发送约定通知，任务是否可做仍由Agent判断。 |
| 3，保持已有能力：Git服务器与PR | bare origin、独立clone、显式base/head、CAS合并已存在；没有Actions、merge queue等全套平台 | 普通Git负责diff/log/fetch/revert；Braid负责PR对象与发布refs。不要重复包装Git，也不因缺少GitHub所有合并选项推翻现有结构。当前确认缺口是反馈/历史，不是再造Git服务器。 |
| 4，需讨论的Agent适配 | 指派会派生独立成员，工作项关闭后可定向联系；与一个GitHub用户跨多个issue工作不同 | 保留用户已确认的成员/配置分离、关闭不删除联系人及可编辑上下文。明确成员退休/改派与订阅的生命周期；不恢复“增加成员”步骤，不暴露profile/UUID给Agent。 |

## 当前最值得讨论的两个选择

**验证事实先可追溯，是否强制合并门槛另议。**
建议先让当前head的检查及反馈容易读取，不默认要求approval、所有讨论resolve或某类测试通过才能merge。
硬门槛是团队政策，需要明确操作者和例外；把它偷放进Braid会再度让Harness取得语义决定权。

**关注关系应有独立语义，但不必复制GitHub收件箱。**
仅把现有SQL从thread扩大到item不能覆盖创建者、改派、退订、关闭后联系等边界。
建议围绕工作项的成员关注关系定义最小行为，复用现有events/batch/CLI投递路径；不引入仓库级watch、邮件偏好、组织权限或第二套队列。

## 明确保留的差异与未知

普通关联不等于关闭关系；当前merge不自动关闭Issue是可解释的裁减，若以后加入closing link须显式区分。
没有证据要求本场景加入组织ACL、CODEOWNERS、Projects、Milestone、分支保护和merge queue；它们不是本轮要照单实现的清单。
GitHub的取消指派退订、部分元数据通知、父子通知继承尚未知；不阻塞已由用户明确选择的Agent契约，也不借这些未知自行扩展外部测试资源。

现有源码测试含陈旧API，两个研究者都只静态查阅，没有把它们称为已运行通过或失败。
后续验收以实际协作动作、持久记录、provider输入和真实工作接续为证据，仍区分“排队”“收到”“行动”；不依据角色名称或单独quiescent判断完成。
