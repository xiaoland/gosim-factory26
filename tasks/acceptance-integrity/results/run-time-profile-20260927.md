## 按潜在墙钟节省排序的优化

1. **先固定跨 Issue 契约（最高，观察窗口上限约 28 分钟，非保证节省）。** Sheet 将 #5 的验证规则结构与 API 作为单一源，#6 首次移植、提 PR 前就针对最新 develop 做契约检查。13:07–13:35 的主要返工由这里触发；即使前移检查仍须完成正常 rebase，因此可省的是冲突发现过晚和二次重写，不承诺省满 28 分钟。比较未来同类运行的“契约合入→依赖 PR 可合并”间隔。
2. **隔离并明确检查服务身份（高，Sheet 暴露约 29 分钟，GitHub 另有服务误设）。** 每轮检查给独立端口/数据目录、退出清理，失败先报占用 PID/工作树/端口与结果目录。Sheet PR #8 已实现部分防护；需在后续独立运行验证是否消除 11:52–12:21 类型的误判。测试本身仍要执行，节省不能等同 29 分钟。
3. **把 #7 之类的集成契约在并行开发前定义（高但收益未定量）。** GitHub 的 POST `/pulls` 错误形状、页面 host 与路由差异导致 12:11–12:28 手工合并，并延伸到后续检查断言。提前用同一 API 响应和组件边界做一次交叉审查；比较“最后子 PR 就绪→develop 合入→主线浏览器检查首轮通过”的时间，而非代码行数。
4. **用完成事件代替后台检查轮询（中，净墙钟收益未知）。** 把进程退出码、结果路径和失败摘要送回负责人，减少反复 `sleep`/`tail`；检查运行时仍可能是关键路径。验证结果产生到首次处理之间的延迟、轮询 turn 数。
5. **关闭重复通知回环，并修复唯一键忙重试（可靠性/成本优先，墙钟收益未证实）。** 无新相关事件的已关闭 Issue 不再写“状态不变”评论；恢复调度遇不可满足 `member_login` 唯一键时一次记录并等待状态变化。验证重复评论、日志量、turn、队列深度下降且真实事件仍可唤醒 agent。不能把 68 条评论或 21,206 次错误折算为节省分钟。

## 证据边界

两份快照没有最终 main、官网评分或终态成本；`status.json` 的 `run_duration_seconds`、`token_count`、`token_cost_usd` 均为空。检查通过数是各 agent 当时报告或 Pi 可见输出，不代表最终 head 的完整验收。Pi JSONL 与 Braid turn 记录能区分“正在调用工具/等待检查/正在处理消息”，却不能稳定拆出模型推理、provider 排队、后台浏览器执行和 CPU 占用的精确比例。GitHub 的大量 SQLite 错误与重复评论是强相关的系统噪声，未观察到它直接阻断根 agent 的因果证据；Sheet 的检查环境问题和接口冲突则可从检查重试、PR 评论与重写时间线直接对应。要量化净节省，应在修复前后记录每次任务的依赖就绪、首个有效 turn、检查开始/结束、结果消费、PR 合并和 main 交付时间戳。

Token/cost 与墙钟分开：官网在两份 `status.json` 中都未提供 `token_count` 或 `token_cost_usd`；Pi JSONL 中的消息数、重复通知数和 Braid 错误行数均不能换算为官方 token 或美元，也不能作为时间成本的代理。若要评估成本，应另取官网终态账单或 provider 用量记录，与上述事件时间轴关联分析，不用 wall-clock 估算 token。
