## 结论

最高优先级是消除**无行动项的确认链**。Braid 将普通评论交给工作项关注者，冻结 variant 又要求“需要回应时在评论中明确点名”；模型将“收到、无待办”也当成必须回帖的工作。每次回帖再次通知多人，根 Agent 再汇总这批确认，形成新一轮确认。Braid 的送达能力本身在发挥作用；缺失的是「收到通知」与「需要答复」的边界，以及面向单人的根检查评论却广播给所有关注者的范围。

另一个独立问题是根 Agent 用“还没有远端分支/PR/回帖”代理“没有在工作”，五分钟检查连续触发后重派正在工作的负责人。重复检查既耗时，也可能改变任务执行路径。先解决这两处，比压缩一般工具输出或优化模型价格更可能缩短完成时间。

## 可推广性与下一步取舍

全量原生记录中，GitHub 有 635 次 `braid issue/pr view`、363 次 `braid comment view`、479 次 `git fetch`、259 次 Braid `--help` 文本命中；Sheet 分别为 278、81、111、114 次。一次 bash 命令可能包含多个子命令，这些是文本出现次数，不是独立执行次数，也不能把必要的版本核对认作浪费。重复解释相同提交、同一验收证据并回帖的具体链条，才是更可靠的低 ROI 证据。

建议先讨论两条产品规则：

1. 根五分钟检查是发给当前根负责人的提醒：评论仍留在根 Issue 历史，但执行通知只送根成员。其他成员不因这条系统提醒被唤醒。它不替根判断工作是否停滞，也不要求根每次写进度报告；根应核对在工作会话与实际成果后自行决定下一步。
2. 普通评论和回复允许被阅读而无需回执。冻结 variant 中“需要回应时在评论中明确点名”与 Braid 已实现的普通回复通知相冲突，应改成只在请求、提问、纠错或需要行动时回复；`@` 仅用于主动联系特定成员，记录某人的名字不自动等于请求。已完成成员可保持可联系，同时自行退订无关的根工作项更新。

这些是待复核的产品/指引修正，不在本次只读调查中修改 Harness。还须复核第二条对真正交接是否会漏消息：子项完成必须回到约定的父讨论留下结果，父成员仍应自然收到；不能为压制噪声重现之前的交接丢失。验收应比较同类生成中的「无行动回执数、根提醒收件数、重复状态读取、最终集成完成」及原生工具链，而非只看 token 总量。
