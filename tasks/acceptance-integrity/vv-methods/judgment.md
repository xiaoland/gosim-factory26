# 3. 结果判断：观察支持什么结论

[返回框架](../vv-methods.md)。本分支从已取得的观察出发，判断结果的范围、解释的依据和应采取的下一步。
主要依据 [T10–T14](../source/vv-turn-14.md) 与 [T18](../source/vv-turn-18.md)。
下述决策组织是本次归纳，原会话没有规定一个统一的故障分诊算法。

## 3.1 分开观察、解释与完成声明

“请求返回 200”是观察，“业务应已成功”是解释，“功能验收通过”是范围更大的声明。
三者之间需要证据，不能因工具或脚本返回成功便连成结论。

结论应对应实际检查的产物、输入、条件和观察。
旧版本的通过不能直接支持新版本；中断执行不能当作应用失败；没有执行的部分也不能算通过。
明确缺的是哪项观察，并说明不同结果怎样改变判断，比只写“不确定”更有用。

测量也有同样边界：在一种负载、环境下测得分布，不能不加说明地推广到另一种条件。
构建、类型、schema 等检查可以支持它们实际约束的性质，无需贬低这些证据，但不能扩大其范围。

## 3.2 验收与诊断回答不同问题

验收证据回答承诺结果是否成立，诊断证据帮助解释发生了什么、哪里偏离。
两者按所回答的问题区分，不按数据位于系统内部还是外部分组。

原文发票例子中，目标收件人收到正确发票、满足约定时限，接近承诺结果。
Job、SMTP 与事件记录可以定位投递流程的异常，却不能各自保证该结果。
如果某条要求恰好约束内部状态，该状态也可以成为验收对象。

```text
Job 成功，SMTP 接受，目标邮箱未收到
  ├─ 验收：尚未建立“收件人收到”的结论
  └─ 诊断：已缩小调查范围，仍需查明后续环节
```

一个证据来源可能同时服务两个问题，但需要分别说清它支持什么。
增加日志或检查的理由，应是增加相关可信度或诊断分辨力。

## 3.3 限制结论范围，并检查共享假设

Oracle 表达得一般，不意味着执行涵盖所有情况。
一组局部 PASS 不自动覆盖完整组合，多层 PASS 也可能重复同一个错误解释。

检查独立性时，问它们共享了什么：需求解释、预期值、参考实现、替代依赖、输入生成器、观察机制等。
若怀疑共享错误，就选择能够区分该解释的另一个机制或实际结果。
换一个身份、模型或角色表达赞同，本身不是独立证据。

分层结果可以帮助诊断，例如局部规则和真实依赖都通过、产品路径失败，会提示调查连接与流程。
但这只是缩小范围，不能直接断言故障一定在 UI。
归因还需要能区分其他解释的观察。

这也校准了原 T15 过强的表述：不同边界并不天然形成独立证据，后续 T18 已明确共同假设的风险。

## 3.4 根据差异修订判断并选择行动

失败后首先确定差异出在哪里。
下表说明常见方向，不要求先填完所有分类才修一个明显问题。

| 差异 | 下一步应取得或改变什么 |
| --- | --- |
| 观察到明确违约 | 修复实际缺陷，在能暴露它的边界复验；再判断整体验收是否受影响 |
| 检查额外规定了需求没有规定的实现形式 | 指明错误假设，修正观察或判据，确认仍能拒绝真正违约 |
| 环境或前置状态未建立 | 修复执行条件后重跑，避免把无效执行误作产品结果 |
| 观察缺失，多个解释都可能 | 取得能够区分解释的证据，而非重复同一无信息检查 |
| 新证据推翻产品解释或设计假设 | 回到相应判断，修订受影响方案与判据，不累积局部例外 |

检查本身可以合理演进。
修改测试、阈值、输入选择或生成器时，应说明是要求改变、观察方式更新，还是原检查有错。
仅有“现有实现不通过”不能成为放宽依据。
同样，永久冻结有错误假设的测试，会阻止满足需求的实现变化。

例如更换 locator 可能只是观察适配，但若扩展了需求明确规定的接受结果，就改变了判据。
具体判断仍回到 [语义转换与双向检验](semantics.md#14-从两个方向挑战判据)，不能只靠“测试代码变动不大”决定。

最终记录应说明成立的结果、未覆盖或尚未解决的部分，以及下一步需要什么。
证据足以支持当前决定后，不因还能增加检查就无限扩张；发生新变化、失败或重要疑问时再补充。
