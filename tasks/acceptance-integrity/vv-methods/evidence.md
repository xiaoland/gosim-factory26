# 2. 证据设计：怎样取得有判别力的证据

[返回框架](../vv-methods.md)。已明确的要求仍不足以构成一次有效检查，还要设计条件、观察方法和执行边界。
主要依据 [T04](../source/vv-turn-04.md)、[T07–T08](../source/vv-turn-08.md)、[T10–T14](../source/vv-turn-14.md)，并按 T18 校准结论。

## 2.1 判据、条件选择与观察各回答一个问题

| 选择 | 问题 | 发票例子 |
| --- | --- | --- |
| Oracle | 什么观察结果算符合要求？ | 对应收件人收到正确发票，并满足约定时限 |
| Selection | 让系统经历哪些情况？ | 哪个身份、哪张发票、什么初始状态、是否发生重试 |
| Observation | 怎样知道实际发生了什么？ | 读取目标邮箱、邮件内容和到达时间 |

这不是三个独立执行阶段。
例如观察不到最终结果时，需要重新判断观察机制或技术边界；但不能因此把预期结果改成更容易读取的中间信号。
Oracle 正确也不代表 selection 充分：`divide(10,2)==5` 的判断可以正确，单个输入仍远不足以支持广泛结论。

一个关键方法是把最可能改变结论的不确定性说清楚。
若疑问在权限隔离，条件必须包含不同身份与数据归属；若疑问在持久化，观察同一页面的即时提示就没有区分力。
条件的选择服务这个疑问，不以增加案例数量为目标。

## 2.2 有限条件与测量

有限执行依赖对行为和可能失效方式的假设。
选择方法的意义是用较少情况获得有价值的证据，不能保证未运行情况全部成立。

| 方法 | 选择依据 | 应承认的盲区 |
| --- | --- | --- |
| 等价类与边界 | 相同规则区间取代表值，在规则交界两侧增加观察 | 区间内仍可能有未理解的差异 |
| 状态转移与历史 | 同一动作随登录、过期、先前操作而改变含义 | 只覆盖状态不等于覆盖到达它的所有历史 |
| 组合条件 | 重点检查有理由认为会相互影响的变量 | pairwise 不证明更高阶交互正确 |
| 性质加生成输入 | 用一般规则判断大量构造出的输入 | 生成器可能遗漏罕见条件，性质本身也可能过弱 |
| 异常输入或故障构造 | 挑战崩溃、超时、恢复等明确性质 | 不崩溃不等于功能结果正确 |
| 已知反例与重要旅程 | 保留不可替代的真实条件或完整结果路径 | 固定例子可能被过拟合，不能代替行为模型 |

Coverage 必须说明覆盖的是哪个空间：需求、状态、转移、边界、用户旅程或代码分支。
一般性质、覆盖比例和实际执行条件是不同信息。

量化要求还需要先设计测量程序。
“搜索快”至少要明确起止事件、API 响应还是用户首屏可用、数据量、查询分布、硬件和网络条件、冷暖状态、样本与统计量，再判断阈值的依据。
原文出现的 800ms、200ms 只是例子，不能作为普遍门槛。

比较改动前后表现时，需要知道比较对象和测量条件是否具有可比性。
这个要求来自测量定义与条件化证据的关系；原会话未展开完整的实验统计学，本文也不据此补造置信区间或因果推断规程。

## 2.3 验证边界和证据组合

选择边界的依据是它能够保留的语义与能消除的不确定性。
局部计算、真实组件组合、用户入口和生产条件各有可观察的事实，彼此不能凭名称替代。

| 边界 | 常见证据范围 | 不能自动推得 |
| --- | --- | --- |
| 局部性质／组件 | 计算、规则、单个状态转移 | 真实存储、并发、界面接入都正确 |
| 真实集成 | 身份、路由、存储、事务等实际组合 | 用户能从完整产品入口走到结果 |
| E2E | 特定条件下从入口到承诺结果 | 所有边界条件、所有环境和全部需求成立 |
| 生产观察 | 真实负载、长期状态和使用条件 | 错误没有造成后果，或可以完全回滚 |

要求发生在哪个边界，就要保留该边界的重要语义。
OAuth 在具体浏览器中的重定向不能通过抽掉浏览器来证明；局部转账函数守恒也不证明数据库事务与重试下守恒。
E2E 若只判断提示文字，同样可能没有观察承诺结果。

证据组合应增加可信度或诊断能力，不能只把同一个假设重复执行三遍。
不同层甚至不同 Agent 都可能共享错误预期，独立性仍需按具体依据判断，见 [3.3](judgment.md#33-限制结论范围并检查共享假设)。

成本包括环境与资源、设置、等待反馈、维护、失败定位、误报漏报，以及错误限制实现自由的代价。
因此“更便宜”的判断不能只看执行秒数；大量脆弱 mock 的长期成本可能高于真实集成，昂贵而没有新增证据的 E2E 同样不值得。
没有固定层数或比例能代替这个选择。

真实依赖足够便宜且可控时优先使用。
需要控制时间、稀有失败或有代价的外部副作用时，替代品可以有价值，但应表达系统真正依赖的最小契约，并说明哪些假设尚需真实交互验证。
不要通过替代品把待检查的行为直接设为真，也不要无依据地固定 SDK 调用次数或对象协作过程。

## 2.4 可实验性：让重要问题能够低成本反复观察

重复反馈依赖一条实际可执行的链：

```text
设置条件 → 执行目标行为 → 观察结果 → 清理／重置 → 复现
```

从链条上的阻碍推导设计改进，比预先安装一整套测试基础设施更直接。

| 实际阻碍 | 要解决的问题 | 可用动作及其边界 |
| --- | --- | --- |
| 检查过期必须等待一天 | 哪个时间因素决定目标行为？ | 在有意义的边界控制时间；不要求全部依赖都新增接口 |
| 请求已接受，却不知道最终结果 | 在哪里能观察承诺结果？ | 直接观察结果；另用 job、错误和关联日志解释过程 |
| 上一次运行改变权限、额度或数据 | 怎样恢复所需初态？ | 选择可控清理或独立数据范围，不指定通用隔离架构 |
| 一次失败无法重现 | 哪些条件决定这次行为？ | 保留必要输入、seed、版本、配置及相关状态，而非只保存失败标签 |

测试难写时，先问性质是否选在了合适边界。
真实浏览器与外部交互可能本来就是要求的一部分；为降低测试成本而抹掉它们，会失去待验证事实。
确认边界合理后，再考虑显式状态、决策与副作用分离、稳定的语义接口等设计动作。
这些能力需要由具体验证或诊断需求证明价值。

自动化测试或脚本应包含重复执行所需的条件构造、操作、观察与判定。
脚本重放成功仍不代表判据正确；反复失败也可能来自状态污染或失真的等待条件。
原文没有规定框架、目录、报告 schema 或统一脚本协议。
