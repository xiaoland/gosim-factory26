# 4. 反馈与演进：证据怎样改变工作

[返回框架](../vv-methods.md)。前面三个分支分别决定要求、证据与结论；本分支把它们接入设计、实现和持续改进。
主要依据 [T09](../source/vv-turn-09.md)、[T12–T18](../source/vv-turn-15.md)。
这些方法按问题采用，不构成所有改动必走的固定制度。

## 4.1 先判断适用条件，再使用 test-first

当“应该做什么”比“怎样实现”更清楚，且有合理成本的可信反馈时，可以先表达下一小块行为约束，再搜索满足它的实现。
若正在探索产品行为，先原型、比较和反馈，逐步确定稳定部分。
TDD 不能替代需求发现。

```text
明确下一小块稳定行为
  ↓
表达可执行约束
  ↓
确认它因预期缺失或错误而失败（Red）
  ↓
做最小连贯实现 → 取得反馈（Green）
  ↓
保持行为约束，改善实现（Refactor）
```

Red 的作用是取得检查具有判别力的证据，语法错误、环境未启动和任意人为失败不承担这一作用。
若当前实现已经符合要求，不应为了形式完整而强造失败；必要时可用 [语义反例](semantics.md#14-从两个方向挑战判据) 检查重要疑问。
Green 只说明实际执行的约束在这些条件下成立。

先写下什么，也会影响设计被引向何处。
先约束稳定行为，通常保留更多实现自由；先规定 collaborator 调用次数和顺序，则可能冻结预想架构。
若协议本身要求该顺序，它当然可以是行为约束；问题在依据，而不在 mock 或 interaction 的名称。

原会话 T15 提出此方法，T16 明确认可其 SOP 和反例。
本次用户已同意把这条有适用条件的短循环补入 SVC，而非规定所有代码必须 TDD。

## 4.2 快循环与完整判断相互补足

快循环用小变化与及时反馈支持实现搜索和局部诊断。
较慢的循环检查更完整的组合、真实产品路径和现实条件，防止局部优化脱离目标。
划分依据用途和成本，而非工具名；性能优化时，一个局部 benchmark 也可以是快反馈。

局部工作要知道哪些产品约束、系统不变量和设计边界必须保持。
最小连贯变化优于最小代码变化：不能把“先重复扣款、下一步补一致性”当作合理切片。
另一方面，设计是假设，证据推翻它时应重做判断，不把设计选择升级为永久产品要求。

```text
需求理解
  ├─ 技术方案 ─┐
  └─ 验证方案 ─┴─ 确定关键约束、观察边界与反馈方式
           ↓
计划 → 小实现 ↔ 快反馈 → 整合后的高层验证
           ↑                    │
           └── 证据促成修正 ────┘
```

这是基于原会话及当前共识的组织表达，不表示每个框中都要新增角色、文件或阶段交接。
设计和 V&V 需要共同推进，是因为需要观察什么会影响技术边界，而技术边界也影响证据的真实性和成本。

E2E 可以发现组合行为错误，却不能独自保证架构长期一致和易于修改。
原会话 T17 将全局设计视野作为担忧继续探索，尚未实证一种稳定的切片或架构治理方法；这里保留原则，不补造已验证的流程。

## 4.3 从反例完善行为模型

原文 T09 的关键方向是：具体故障的价值不仅在于留下一个永久测试，还在于揭示遗漏的正确性规则。

```text
具体故障 → 可复现反例 → 找到遗漏的性质或条件
         → 修复实现／修正规格 → 取得相应证据
```

排序丢失重复元素可引出保持多重集合的性质；权限故障可能揭示未覆盖的状态或历史，而不一定是缺少一条新规则。
不能预设每个 bug 都只属于“判据遗漏”。

是否保留原案例，取决于替代检查能否可靠保留它的证据价值。
罕见组合、重要产品旅程和暂时不能泛化的失败可能仍值得保留。
回归描述防止已成立能力退化的用途，性质测试同样能承担这一用途。

这样理解，反馈既改变实现，也完善我们对允许行为和有效检查条件的认识。
固定例子可以成为学习材料，不能成为产品正确性的全部定义。

## 4.4 生命周期与自动化边界

设计时明确要求和观察，开发中快速反馈，交付前检查完整结果，生产中再面对实际负载、长期状态和真实使用条件。
生产反例可以回流到开发环境，改善规格、设计与条件选择。

生产证据更真实，也可能意味着错误已经影响用户。
因此自动化决策权需要匹配证据可信度和错误后果；停止、恢复和补偿各有范围，回滚代码不能撤销已发送邮件或扣款。
这属于原会话的通用生命周期讨论，不构成本项目部署或实验的新授权。

值得自动化的通常是需要重复、能形成可信机器判断、结果会影响决策的活动。
暂时无法可靠自动判定的偏好，应如实保留判断方式与局限，不能为了自动化编造一个阈值。

本轮 Factory 另有明确执行政策：最终验收使用可重复自动化测试或脚本，browser-operator 用于开发中的快速反馈。
脚本可以驱动真实浏览器，最终判据仍来自需求。
这是当前用户决定而非原会话对所有场景的普遍规定；具体接线与协作分工见 [本轮设计](../design.md)。

记录留在现有任务和设计材料中。
T14 明确反对凭空创造强制 assurance plan 对象，原讨论也强调应以真实案例检验方法的成本、盲点和效果。
本知识树的用途是组织已有理解和继续学习，不是增加一套流程文件。
