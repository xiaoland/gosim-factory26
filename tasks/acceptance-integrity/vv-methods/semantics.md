# 1. 规格与语义：什么算正确

[返回框架](../vv-methods.md)。本分支先确定判断对象，再解释如何把要求转成判据，以及怎样发现转换失真。
主要依据原会话 [T03](../source/vv-turn-03.md)、[T04–T07](../source/vv-turn-06.md)、[T09](../source/vv-turn-09.md) 与 [T18](../source/vv-turn-18.md)。

## 1.1 区分目标、要求、设计与实现

产品意图表达希望得到的价值，行为要求表达什么必须成立，技术设计提出实现它的方案，实现则是具体程序。
它们的稳定程度和变更依据不同。
“不能重复扣款”约束行为；“使用某种队列”通常是设计假设，可以被更好的方案替换。

相应地，需要分别判断：产物是否符合已陈述的要求，以及我们对要求的理解是否仍服务于原始目标。
前一问题通过，不自动回答后一问题。
这是本整理区分 verification 与 validation 所针对的两类疑问，不要求给每个测试贴互斥标签。

自然语言需求也可能有歧义或冲突。
还不知道“应该做什么”时，先分析旅程、比较方案、做原型或取得可用反馈；把未经检验的猜测写成断言，会让自动化稳定地维护错误解释。
“如何实现已明确行为”才是适合受约束实现搜索的问题。
原文 [T15–T16](../source/vv-turn-15.md) 以 onboarding 的按钮、弹窗顺序说明这一区别。

## 1.2 用性质刻画行为，案例帮助认识边界

一般性质说明一类行为必须满足什么，具体例子说明某组条件下应看到什么。
性质扩大表达能力，例子提供实例、反例和可复现的条件，两者不能互相完全替代。

| 所约束的对象 | 例子 | 设计检查时要保留的含义 |
| --- | --- | --- |
| 状态 | 当前身份不可见无权限数据 | 身份、数据归属与可见范围 |
| 状态转移 | 一次成功转账的余额变化 | 前态、操作、后态，以及失败时的约束 |
| 流程或时间关系 | 付款后收到对应确认 | 中间步骤与最终结果的区别、适用时限 |
| 跨行为不变量 | 成功转账不凭空增减资金 | 哪些状态和并发／重试条件属于约束范围 |
| 带条件的量化表现 | 代表负载下的响应延迟 | 工作负载、测量程序、统计口径及要求阈值 |

这些视角可以交叠；场景、样例、反例是检查它们的方式，不是同层的互斥需求类型。
不要求每个功能填满整张表。

原文 [T09](../source/vv-turn-09.md) 的排序案例展示了泛化价值：从 `[2,2,1]` 丢失一个元素，进一步发现“排序保持输入的多重集合”。
但一般性质的输入生成器未必会重现某个罕见故障。
因此“规则表达得更一般”和“实际检查过更多条件”是两个判断，条件选择见 [2.2](evidence.md#22-有限条件与测量)。

## 1.3 每次转换都要保留理由

一个检查的可执行性，只说明机器能运行它；它与需求之间的关系仍需说明。

```text
产品意图 → 行为要求 → 可观察结果 → 判断规则 → 检查实现
            ↑ 每次转换都可能遗漏、增加或改变约束 ↑
```

下面沿原会话的工作区例子展开。
其中“私有项目不可见”等内容必须确有产品依据，不能仅凭常见产品经验自动添加。

| 转换 | 应回答的问题 | 典型偏移 |
| --- | --- | --- |
| 意图 → 要求 | 登录后究竟要能完成什么，什么必须保持？ | 用自己想象的产品规则替代给定需求 |
| 要求 → 可观察结果 | 什么事实能表明该能力成立？ | 只观察地址跳转或成功提示 |
| 结果 → 判断规则 | 对身份、结果、时限有哪些必要条件？ | 用“出现用户名”代替“可使用自己的工作区” |
| 判据 → 检查实现 | 数据构造、操作、等待和断言真正在检查这些条件吗？ | helper 名称像业务检查，内部只是搜索字符串 |

需求链接回答来源，转换理由回答“为什么这项观察能支持这个要求”。
即使拥有完整的需求编号映射，转换仍可能失真。

还应区分判据依据和观察来源。
业务规则、不变量、明确协议或有依据的比较目标可以支持预期；数据库、页面、文件和邮箱提供实际观察，它们当前呈现的内容不能自行定义预期。
参考实现可以形成差分依据，但其适用范围及共享缺陷仍需判断，不能将任何现有实现当成绝对真理。
这是对早期 [T04](../source/vv-turn-04.md) 将若干“来源”并列后，结合后续语义讨论作出的整理。

## 1.4 从两个方向挑战判据

判据定义了某种接受范围。
它可能过宽而接受违约，也可能过窄而拒绝符合需求的实现。

| 挑战 | 原会话例子 | 暴露的问题 |
| --- | --- | --- |
| 需求被破坏，还会通过吗？ | 私有数据权限判断失效，页面仍跳到 dashboard | 检查观察或判断过弱，或者条件没有触发违约 |
| 需求仍成立，还会失败吗？ | 合法工作区从 `/dashboard` 换到 `/home`，或改变标题标签 | 把未规定的实现表象提升为需求 |

第二种自由以“满足全部已规定要求”为前提。
若 URL、协议顺序或接口本身就是要求，它们的变化就可能是真正违约。
该例外在 [T10](../source/vv-turn-10.md) 与 [T16](../source/vv-turn-16.md) 已明确；无需另建一套 UI 专属规则。

先做具体反例推演；如果仍有重要疑问且成本合理，再用缺失行为、故意构造的语义缺陷或另一种合法实现验证判别力。
语义变异不是每个测试的强制配套工程。
即使故意引入缺陷后仍然 PASS，也要继续区分：条件未触发、结果未观察，还是判断规则过弱。

对测量型要求，这种挑战表现为：有意义的性能变化能否被测量分辨；无关环境变化会不会造成错误结论。
检查的可重复执行并不自动保证这两点。

修改判据的合法依据与失败后的行动见 [3.4](judgment.md#34-根据差异修订判断并选择行动)。
