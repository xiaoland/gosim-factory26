## 能得出的判断

- 23 次已完成重建的事务耗时合计 68.87 秒。它是串行事务时间之和，不是四题 wall time 节省量。
- GLM 13 次配对的旧→新请求中位数：非缓存 input `450 → 2,317`，cacheRead `41,984 → 7,360`。DeepSeek 10 次为 `640 → 3,553`、`97,920 → 8,192`。新会话首次请求均仍有 cacheRead，缓存并未归零；在拥有至少五次请求的会话中，第五次 cacheRead 中位数已到 GLM `15,360`、DeepSeek `17,664`，说明后续逐步恢复。不同请求的工作内容不相同，不能将中位差直接乘次数计算费用。
- GitHub 根成员在 16:35:39 与 16:36:25 的 46 秒内发生两次重建，邻近自追加评论和对象 revision 变化。这是检查“自己的普通评论是否无谓触发完整重建”的窄化候选，尚不是对这两次必要性的判决。
- `materializing` 的四条 GitHub 记录发生在断连/SIGKILL 边界，未形成已完成重建或新请求配对；恢复故障成本另行分析。

## 决策与下一步

保留删除/编辑、权限或指派变化、未知 provider 终态等会使旧上下文不可信的强制 reset。普通追加评论、活动记录或不改变现有事实的 revision 更新可作为候选，但先要查明 Context projector 实际会变化什么，不能只凭事件名豁免。尤其需要区分自己刚写出的内容与他人修改既有内容。

下一步用同一保存状态的两个隔离副本做 A/B：A 保持现行重建；B 只针对已辨明的非破坏性追加候选改为轻通知。两边使用相同输入、模型与工作项起点，记录语义任务是否完成、遗漏/误读、非缓存 input/output、cacheRead、wall time 与实际费用；当 B 出现上下文错判或交接丢失时即否定该候选。先做小样本判别，再决定是否进入完整 benchmark。当前未授权实施该策略，也没有启动实验。
