# 协作通知的时间与 token 效率

阶段：三项最小修正已获授权并写入当前 Braid 与 `pi-braid` 源码；后续真实运行尚未验收，未改正在执行的官网冻结包。证据取自两次旧冻结包的[逐条运行分析](../results/collaboration-loop-analysis.md)，不能把这组数字当作当前恢复运行的成绩。

## 要解决的问题

通知应让负责人获得可行动的新信息，而不是使每位订阅者都重新读取工作项、重复核对同一提交并写“收到、无待办”。Braid 仍保留完整评论历史、普通回复送达、关闭后联系和根检查评论；语义判断仍由 Agent 做。

Sheet 的 10:12–10:33 UTC 窗口产生 55 条评论、248 条逐成员投递、64 个 Braid turn 和 23 次 Context reset。五条明确表示状态不变、没有代码编辑的回执（#45/#52/#61/#64/#67）自身耗费 312 个 Agent 执行秒、51,872 input、9,826 output、682,432 cacheRead tokens；它们又产生 25 条投递记录，其中 13 条显示 delivered、12 条在终态仍 queued。**61,698 非缓存 token 加 682,432 缓存读取是这五条回执的已观测消耗，不是可保证节省量**；并行执行时间也不能直接当作墙钟节省。完整窗口的 33,964,920 processed tokens 包含真实实现，不能整体归因于循环。

GitHub 的根检查评论 #12/#14/#19 每隔约六分钟出现。根 Agent 连续三次以没有远端分支/PR/回帖为停滞证据，约 09:58 UTC 改派了三个仍在执行的负责人；他们当时分别在停止开发服务、等待浏览器任务、读取自检日志。三个检查 turn 合计 205 个 Agent 执行秒、48,777 非缓存和 324,416 cacheRead tokens，但第三次包含真实改派，不能把合计成本当作纯浪费。后续根检查 #30/#39 除根成员之外又向三位活跃成员各 delivered 一次；Sheet 的两个根检查也各向两位非根成员 delivered。通知送达不等于收件人一定行动，因此这 10 条非根 delivered 只证明多余唤醒的机会，不直接换算 token。

## 已实施的最小修正

1. **根检查只唤醒根负责人。** 评论仍写在根 Issue，所有人查看时仍可见；这条面向根负责人的定时提醒只给根成员投递，不经普通关注者广播。普通成员写的评论、回复和 @ 保持原有送达方式。这是有明确对象的系统评论的收件范围，不引入新事件模型。
2. **把通知与回复义务分开。** 在 variant 的通用协作指引中，用既有 GitHub 使用经验表达：收到评论后，仅在需要回答问题、纠正事实、交接成果或采取行动时回复；状态未变不写“收到”回执。普通回复自然通知讨论参与者，@ 用于主动联系具体成员，不要求回复时重复点名。这覆盖当前两份 profile 指引中的“需要回应时在评论中明确点名”。
3. **纠正根检查的判断依据。** 定时提醒仅提示检查，不代表子任务停滞；没有公开分支或 PR 不能单独证明负责人停止工作。准备改派时，根负责人先通过已有讨论取得进度或看到明确失败，再决定是否变更责任。没有新事实或决策时，无需发布重复进度总结。保留根 Agent 自行判断是否拆分、催办或改派的权力。

先做这三项，不改全局评论订阅语义、不缩短五分钟间隔、不自动隐藏评论、不按词面过滤“无待办”。如果三项后普通评论仍持续造成跨线程高扇出，再单独讨论更细的订阅边界；现在没有证据足以承担其交接丢失风险。

实施位置：`sources/braid/src/objects.rs::root_idle_tick` 只向根成员投递 Braid 定时评论；`sources/braid/docs/20-product-tdd/local.md` 记录该可见性与投递区别；`variants/pi-braid/agents/pi-glm-fast/instructions.md` 和 `pi-deepseek-fast/instructions.md` 说明何时回复、如何交接与改派依据。`cargo check --offline -q` 与两仓 `git diff --check` 通过。Braid 现有 `cargo test --offline -q root_idle_tick` 在编译测试目标时因旧测试仍使用已删除的 `ProfileDefaults` 与旧 `SessionFactory` 签名而失败（33 处），未运行到本次行为；全仓 `cargo fmt --check` 也因既有大量未格式化编辑失败。本次未改旧测试或格式化其他人的文件。

隔离复核使用 `runs/acceptance-integrity/20260927/cooperation-operation/braid.sqlite3` 的 SQLite 备份，只在 `/tmp/braid-collab-check.zw9Z2n` 中把根项旧待处理事件标为已消费，并把闲置起点设为六分钟前；原数据库及官网运行未写入。调用当前源码的 `LocalObjects::root_idle_tick()` 后，根 Issue 中可读到 Braid 评论 #12「请检查当前工作进展。」；`local_comment_delivery` 只有 `glm-1: queued`。随后在同一副本用正常 `comment()` 入口写父 Issue 交接评论 #13，投递记录同时包含根负责人 `glm-1: queued` 和订阅者 `deepseek-2: queued`。这验证了收件范围与普通评论扇出仍可用；它不证明真实原生会话已接续，也不代替下一次完整运行验收。

## 验证与节省口径

实施前先记录同一类运行的评论→收件→原生输入→行动链，并按原因标记无行动回执、根检查和必要交接。实施后在独立自费运行中核对：根检查仅根成员入队；子项完成后的父讨论回复仍送达父成员并引发实际接续；无新信息的回执及重复 `git fetch/status` 明显减少；没有因缺少远端分支单独改派正在工作的成员；最终集成与可执行验收没有倒退。

同时分别报告 Agent 执行时间、wall time、非缓存 input/output、cacheRead、Braid turn、Context reset 和最终交付/评分。先比较确定的无效片段，再比较整题总量；模型随机性和任务完成度会影响总 token，不能把不同交付范围的总 token 当作改动净收益。五条回执的 61,698 非缓存与 682,432 缓存读取只是直接成本暴露，不是节省承诺；它们引出的下游成本尚未计量。
