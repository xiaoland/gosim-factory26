其因果链可以写为：产品意图需要转成可观察的行为要求，但每次转换都可能漂移；因此先问判据是否保真，再独立选择能暴露重要不确定性的条件。执行所得证据只支持被观察的产物与范围。廉价局部反馈帮助搜索和诊断，真实组合与产品入口的证据支持整体结果。反例既可能暴露实现错误，也可能暴露规格、检查或环境错误，下一步修改对象必须由这种区别决定。

“正反证据”也有两个不同层次：一是检验 Oracle 本身，要求破坏需求的系统被拒绝、另一种满足需求的实现被接受；二是解释应用结果，保留成功与失败的不同观察来区分原因。它不等于给每个场景机械加一个负例，更不等于把局部通过当成未执行路径也通过。

## 明确接口要求与实现自由的分界

[T10 助手消息](source/vv-turn-10.md) `6ed42cc6-aef2-4a2c-8a55-315c1351e4cb` 在批评 URL 断言后明确补充：“除非 URL 本身就是产品 contract。”[T16 助手消息](source/vv-turn-16.md) `763b652f-af99-4bb5-a009-7713af5074e3` 也指出某些协议确实关心 interaction。原论点从未建立“具体接口永远不算需求”的规则。

因此，角色、精确名称、URL、可见状态、时限或调用顺序若被需求明确约束，就是可观察契约的一部分。它们即使由浏览器、DOM 或协议表达，也不能因“应该保留实现自由”被放宽。实现自由是在满足全部已明确约束之后剩余的空间。

需求只规定用户结果时，检查可以更换观察机制，但必须说明新机制为何仍能区分该结果。例如把一个偶然的 CSS 定位器换成语义定位，通常是观察适配；把需求明确的 `option` 改成 `button|option` 则改变了接受空间，需要需求依据，不能只以当前页面如此为由。这里的具体角色只用来说明通用边界，不应写成 SVC 的比赛专属规则。

判据变更可合理来自三类依据：需求已有获认可的改变；观察机制需要适配但约束未变；原检查含有可指明的错误假设。Oracle 的判断、阈值、输入选择和状态构造都应服从这条规则。永久冻结测试会阻止纠错；无依据地与实现同步放宽则会消除反证。两者都不符合原讨论。

以上比已有总结新增的主要是来源归属、认可强度和操作化判断，而非新的方法论。当前 SVC 16 已覆盖大部分关键原则，但这一事实不足以判断执行细节是否足够好用；A 的 [复核证据](../competition-budget/a-review.md) 只支持在已观察会话中没有显式读取相关材料、判据发生偏移，不能证明所有 Agent 不使用 SVC，也不能证明强制多读一次就能修复。

路由上，SVC 将产品／技术选择放在 design，将局部反馈放在 implementation，将检查设计和完成判断放在 verification。这种职责拆分没有丢掉原方法：check-design 要求观察承诺结果，并用“持久化规则”与“真实用户入口接入它”说明互补；也要求条件可复现、结果可观察、状态可重置。它没有原样复述“高保真 E2E 锚定”，也没有保留完整的 test-first 执行顺序。初轮把这主要解释为消费路径薄弱；本轮用户要求先整理原文执行方法再判断，不能仅凭原则存在就排除内容缺口。若实现后才依据现状构造判据，或者验收材料没有收到上游依据，原则也难以约束完成声明。
