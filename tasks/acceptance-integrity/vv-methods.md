# V&V：框架、方法与原会话依据

本整理回答：怎样在保留合理实现自由的同时，用可信、及时、成本可控的证据推进软件产品？
这是 [原会话 T01–T18](source/README.md) 的分层整理，不是新的强制开发流程，也不等于本轮要把全部内容加入 SVC。
先读本页建立关系，再按当前问题进入一个分支；分支包含具体方法、例子、适用条件与原文入口。

## 目标与基本前提

**目标是改善产品及其迭代决策。**
测试、测量、TDD、生产观察分别提供不同形式的反馈，它们的价值取决于能否帮助决定继续实现、修复、调整设计、接受结果或继续调查。
检查数量、通过率和工具调用成功都不能独自定义产品成功。
这一目标来自 T03、T14、T18；它也说明本文研究的是软件产品的 V&V，而不是评价开发 Agent 本身。

下面四个前提构成这份整理的基础。
它们是对原讨论的归纳，不是原会话正式提出的一套理论名称。

| 前提 | 为什么需要它 | 推导出的工作要求 |
| --- | --- | --- |
| 意图、需求、设计、实现、检查是不同表达，各自可能有误 | 自动执行一个解释，不会让该解释自动正确 | 保留转换依据，能区分该修产品解释、设计、代码还是检查 |
| 正确性总相对于某组要求及条件 | 同一实现可能满足局部规则，却不满足完整用户流程 | 明确要判断的性质和范围，保留满足要求的实现自由 |
| 有限观察通常只形成有条件的证据 | 未执行的状态、共同错误假设、失真的观察都可能藏在 PASS 后面 | 分开设计判据、条件与观察，限定结论，并寻找有区分力的反例 |
| 反馈有成本，也会改变后续搜索方向 | 过弱判据诱导凑测试，过严判据冻结实现，慢反馈减少迭代机会 | 同时优化语义保真、证据增量、反馈延迟和生命周期成本 |

“收拢正确行为空间”因此不是让接受条件越来越苛刻。
目标是更准确地刻画要求：排除违约行为，同时容纳满足要求的不同实现。
发现错误假设时，判据可能需要收紧，也可能需要放宽或更换观察方式。

## 知识树

```text
V&V：为产品迭代提供可信、及时、成本可控的判断依据
├─ 1. 规格与语义：究竟什么算正确？
│  ├─ 1.1 判断对象
│  │  ├─ 产品意图、行为要求、设计假设与实现
│  │  └─ 符合要求，与要求是否服务目标
│  ├─ 1.2 正确行为的表达
│  │  ├─ 状态、转移、流程、不变量与量化约束
│  │  └─ 一般性质与具体案例的互补
│  ├─ 1.3 从要求到可执行判据
│  │  └─ 要求 → 可观察结果 → 判断规则 → 检查实现
│  └─ 1.4 检查判据本身
│     ├─ 违约行为能否被拒绝？
│     └─ 合法实现变化能否被接受？
├─ 2. 证据设计：怎样取得有判别力的证据？
│  ├─ 2.1 三个相互配合的选择
│  │  └─ 判什么（oracle）／经历什么（selection）／怎样观察
│  ├─ 2.2 有限条件与测量
│  │  ├─ 代表值、边界、状态历史、组合、生成输入
│  │  └─ 测量口径、负载、样本、统计量与阈值
│  ├─ 2.3 验证边界及证据组合
│  │  ├─ 局部、真实集成、产品路径与生产条件
│  │  └─ 真实依赖、替代品、互补性与总成本
│  └─ 2.4 可实验性
│     └─ 设置条件 → 执行 → 观察 → 重置 → 复现
├─ 3. 结果判断：这些观察允许得出什么结论？
│  ├─ 3.1 实际观察、解释与完成声明
│  ├─ 3.2 验收证据与诊断证据
│  ├─ 3.3 覆盖边界、共同假设与证据独立性
│  └─ 3.4 失败归因、判据修订与下一步决策
└─ 4. 反馈与演进：证据怎样改变工作？
   ├─ 4.1 需求探索与有条件的 test-first
   ├─ 4.2 快循环、整体验收与全局设计约束
   ├─ 4.3 从反例完善行为模型，保留有价值的具体案例
   └─ 4.4 从开发到生产，以及自动化决策的边界
```

树的第一层按要回答的问题分组，第二层组织判断依据，叶子才是具体方法和例子。
这是一张知识导航图，不是四阶段审批或逐项必做清单。
分组本身也不保证语义保真；原会话 T06 恰好反对用分类代替论证。

| 当前问题 | 阅读入口 |
| --- | --- |
| 要求模糊，或测试为何通过却没有满足需求？ | [1. 规格与语义](vv-methods/semantics.md) |
| 知道要什么，但不知道测哪些情况、怎样测才值得？ | [2. 证据设计](vv-methods/evidence.md) |
| 已有结果，怎样解释失败、通过与未完成？ | [3. 结果判断](vv-methods/judgment.md) |
| 怎样让检查进入日常开发，避免长时间盲目实现？ | [4. 反馈与演进](vv-methods/iteration.md) |

## 分支之间的关系

规格约束证据设计：先知道要区分什么，才能选择输入、观察和判断规则。
证据设计限制结论：例如只观察 API 状态，结论就不能自动扩展为用户能够从界面完成流程。
结果判断决定下一步：差异可能要求修代码，也可能要求修检查、环境或原来的产品解释。
反馈循环把这些判断送回设计与实现，而新反例又可能改变规格和证据设计。

这条关系也解释了为什么技术设计与 V&V 设计需要共同推进。
重要结果若无法观察、状态若无法构造或清理，验证成本会反过来约束技术方案；但验证困难也可能意味着选错了观察边界，不能立即归咎架构。

## 原文、归纳与本轮决定

来源材料保留了完整的 18 turns、36 条消息，以及早期观点被修正的过程。
原文定位见 [材料索引](source/README.md)，认可范围和修正记录见 [来源复核](vv-source-review.md)。
本文的树、分支标题和穿插实例是本次组织方式；没有把这种组织方式倒写成用户曾批准的标准体系。

尤其保留四项校准：一般性质不意味着穷尽检查；不同测试层不天然独立；回归是用途而非只能枚举案例的测试形式；重要接口若由需求规定，就不是任意实现细节。
原会话也没有充分验证一套固定的任务切片或 assurance plan 方法，不能把讨论假设升级为强制制度。

本轮 Factory 的执行政策另有来源：最终验收必须由可重复测试或脚本完成，browser-operator 用于开发快速反馈；Issue/PR 和 develop/main 是当前协作约定。
这些是本轮用户决定，方案见 [design.md](design.md)，不写成通用 V&V 的理论前提。

## 与当前 SVC 的差异及本轮范围

2026-09-26 对照当前源码：这里比较的是 svc-verification 连同 design、implementation、investigation 中相关内容，而非只看 verification 技能。
理论方向基本一致，具体方法与理解支撑尚不等价；已认可的补充目前仍未进入 SVC 正文。
用户随后提出较系统的内容与导航改进，新增范围见 [SVC 内容方案](svc-content-design.md)，下表区分已有认可与新增待复核内容。
主要依据为 [check-design](../../sources/svc/skills/svc-verification/references/check-design.md)、[interpreting-results](../../sources/svc/skills/svc-verification/references/interpreting-results.md) 和 [implementation workflow](../../sources/svc/skills/svc-implementation/references/workflow.md)。

| 框架位置 | 当前指南状态 | 承接决定 |
| --- | --- | --- |
| 目标、基本前提与分支关系 | 原则散见各技能，较少解释为何这些方法彼此关联 | 新方案拟补最小理解框架和按问题直达正文的导航 |

| 2.3、3 证据组合、成本、解释与修订 | 已有较明确的原则和例子 | 复用现有内容，不重复增补 |
| 4.2–4.4 快慢反馈、反例泛化及生命周期 | 有局部反馈、完整验收和不变量提醒；反例如何完善规格、生产证据与决策边界展开较少 | 记录为覆盖深度差异，暂不扩大已同意范围 |
