# GitHub 协作体验对齐：调查综合

2026-09-27。阶段为调查结论与产品范围复核，尚未授权全面实现。

目标是让熟悉 GitHub 的 Agent 能找到工作、联系协作者、读懂变化并继续完成协作，不依赖对 Braid 内部调度的知识。

两份独立材料已经取得：[GitHub 行为基准](github-collaboration-baseline.md) 与 [Braid 当前实现基准](braid-cooperation-current.md)。前者从协调会话目录原样归档；后者是通知局部修复前的调查快照。跨 thread 收件与父项状态通知的后续局部修复见 packet，不能把快照中的缺口全部重新列为待实现。

## 核心结论

1. GitHub 的作者、负责人、评论参与者和有效被提及者可因参与形成整个 conversation 的默认订阅。Braid 按当前 thread 的历史发言人临时推算收件人，会漏掉新 thread 的交接。局部修复缓解已知漏发；完整产品方案仍需明确参与、订阅、退订和改派的关系。
2. 子项关闭更新父项进度，有官方依据；子项关闭必定在父项新增时间线并通知父项参与者，没有充分依据。用户选择通过 Agent 协作完成交接：通用持续指引说明完成子任务后回父 Issue 评论，父 Agent 拆分时可进一步明确交接位置、接收者及所需材料。评论者表达实际结果，Braid 沿普通评论的关注与明确提及规则投递，不将 close 转换成自动父项交接。
3. 可见历史、通知资格、通知入队、原生输入送达和 Agent 采取行动是不同事实。Braid 应提供可导航的协作事实和可靠输入，下一步工作由 Agent 决定。
4. 责任、关注和执行资源独立。改派不是把历史联系人悄悄替换为新负责人；关闭工作项不等于原作者再也不能回答；释放执行资源不依赖取消指派。

## 建议的范围与顺序

| 产品结果 | 下一阶段需要明确的行为 | 边界 |
| --- | --- | --- |
| 参与后能持续收到相关更新 | Issue/PR 级关注关系；作者、负责人、参与者、明确提及的默认行为；退出与改派；重叠收件原因合并 | 不建立强制下一步工作流，不按父子关系广播全部正文 |
| 离开后能重新理解发生了什么 | 常用 view 可读正文、讨论、关系、状态变化及来源；通知回到原对象/评论 | 用户时间线与内部执行日志分开；优先投影现有事实 |
| 找得到人，能继续合作 | 当前负责人、具体成员、配置别名的区别；关闭后联系；不可达时给出明确结果 | 保持只能指派工作来派生成员，不增加成员管理步骤 |
| 已发布变更能正常审阅与集成 | 复核已实现的 base/head、draft/ready、merge 与跨 clone 使用；明确普通关联与 closing link 的区别 | 不把审批、验收或自动关闭策略嵌入 merge；review/check 状态功能是否新增需单独论证 |

父子进度和关系事件保留为可查询事实；完成交接由 Agent 在父 Issue 中发表评论承担。已有的子项关闭/重开自动通知父项适配，列为后续实现时移除的行为；历史记录保留，不在本次方案整理中改源码或运行制品。
建议通用指引为：“拆分工作时约定交接位置。子任务完成后，回到相应讨论中说明结果及相关材料。”普通回复由工作项关注关系投递，@ 用于邀请或特别点名，不是交接成功的前提。父 Agent 可在具体子 Issue 中细化约定，无须 Braid 生成固定交接正文、判定完成或决定下一步。
不先引入依赖调度器、全站通知中心、保护分支或 GitHub Actions。
验收场景应由以上契约推导，覆盖跨 thread、改派、关闭后追问、忙碌时输入保留、再次接手和真实 Git 合并；不能只复刻此前四个运行中的失败序列。

下一步先复核上述产品范围，再形成收件规则、CLI/context 表达、持久化与投递职责的技术方案和验收方案；之后按既有流程完成实施计划、预演与开工确认。
