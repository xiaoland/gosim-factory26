我们最终收敛的目标是：

> **让 AI 在尽量保留实现自由度的情况下，依据可信、及时、成本可控的证据，持续迭代产品。**

自动化测试、TDD、性能测量、生产监控，都是为这个目标服务的手段，而不是各自独立的追求。

## 一、从产品意图出发，约束正确行为，而不是冻结实现

我们采用的基本关系是：

```text
产品意图
   ↓
行为性质 / 约束
   ↓
可观察证据
   ↓
判定准则（Oracle）
```

例如，“登录后能够使用自己的工作区”，不等于“URL 必须是 `/dashboard`，页面必须存在 `<h1>`”。后两者可能只是当前实现的表象。

检验这条链是否发生偏移，可以问两个对称的问题：

**需求被破坏时，检查是否有能力失败？实现改变但需求仍然成立时，检查是否会错误失败？**

必要时，通过故意破坏某个语义性质，检验 Oracle 的辨别能力。

这里没有绝对保证：人脑中的意图、自然语言、规格、测试之间都可能存在解释偏差。我们追求的是**让这些转换及其假设可检查**，而不是假定某一层已经代表了绝对真理。

同样，**产品约束与设计假设不能混为一谈**。“不能重复扣款”是行为约束；“使用某种队列实现付款流程”通常只是可以被证据推翻的设计选择。

## 二、以一般性质为主体，以具体案例帮助发现和检验边界

我们更倾向于：

```text
发现具体问题
   ↓
理解它揭示了什么
   ↓
寻找遗漏的 property / invariant / contract
   ↓
加强对正确行为空间的约束
```

而不是不断堆积：

```text
bug 381 的补丁测试
bug 427 的补丁测试
……
```

但这里需要校准一个术语：**防退化是一种用途，不是一种只能枚举历史错误的测试形式。** 一个持续重跑的 property test，同样可以承担 regression testing 的作用。

所以我们反对的是“机械地永久固化每个历史案例”，不是反对防止已经成立的能力退化。

具体案例也不必急着删除。一个一般性质虽然更有解释力，但它的随机输入生成器未必能再次命中那个罕见情形。只有替代验证能够可靠覆盖其价值时，才值得合并或移除原案例。

此外，自动验证始终有两个不同的问题：

| 问题           | 需要回答什么                                   |
| -------------- | ---------------------------------------------- |
| Oracle         | 什么结果算正确？                               |
| Test selection | 在哪些输入、状态、历史、并发和故障条件下检查？ |

**写出一般性质，不等于验证了所有情况。** 边界分析、状态转移、组合输入、生成式测试等，是让有限验证更有代表性的办法。Coverage 也必须先问：覆盖的到底是什么空间？

## 三、测试分层的依据，是互补证据和生命周期成本

我们保留的分层原则是：

> **在不丢失目标语义的前提下，选择成本最低、反馈最快、定位最清晰的验证边界。**

不同边界承担不同的证明责任——更准确地说，是提供不同范围的证据：

| 验证边界             | 主要消除的不确定性                               |
| -------------------- | ------------------------------------------------ |
| 局部 property / unit | 局部规则、计算、状态转移是否符合约束             |
| Integration          | 真实组件组合后，接口语义、持久化、事务等是否成立 |
| E2E                  | 从产品入口到最终结果，用户是否真的能完成目标     |
| Production           | 在真实流量、数据和运行条件下，产品是否仍然成立   |

例如，局部计算满足资金守恒，并不意味着数据库事务、并发和重试下也满足资金守恒。

因此：

> **分层不是把同一个 assertion 写三遍，而是让组合后的证据比单独一层更有用。**

适度重叠可以有价值；关键是它是否增加了可信度或诊断能力。不同层也不天然独立——如果它们共享同一个错误假设，全部通过仍然可能一起错。

判断一个测试值不值得存在，不能只看运行时间。还要考虑：

**环境和资源成本、反馈延迟、维护成本、失败诊断成本、误报漏报，以及错误约束实现空间的成本。**

一个昂贵但语义稳定的 E2E，可能比一堆廉价但随实现频繁破碎的测试更划算；反过来也一样。没有固定比例可以替代这把尺子。

## 四、偏爱真实结果，但不把 E2E 或 mock 变成信仰

我们对 mock 的核心警惕是：

> 它可能把依赖的行为复制成一个需要长期同步的“影子世界”，并把本来需要验证的假设直接当成前提。

因此，真实依赖足够便宜、可控时，优先使用真实依赖。必须使用替代品时，要清楚它替代了哪些行为、依据什么 contract，以及哪些假设仍需通过真实交互检查。

Mock 仍然可以用于控制时间、构造难触发的失败、隔离昂贵或危险的副作用。问题不在“用了 mock”，而在**它是否把关键不确定性遮住了，或者把非必要的调用过程固化了**。

相应地，E2E 的价值是能把检查放在产品结果上，但这种价值不是自动获得的。一个绑定 DOM 结构的 E2E 仍然脆弱；一个只检查成功提示的 E2E，也可能遗漏真实结果。

我们的倾向可以概括为：

> **用高语义保真的 E2E 锚定产品结果，再用便宜的 property 和 integration 检查提供密集约束与快速诊断。**

## 五、区分“验收证据”和“诊断证据”，并让系统容易产生两者

以发票邮件为例：

**目标邮箱收到对应发票，收件人和内容正确，并满足约定时限**，是接近需求的验收证据。

**Job 状态、SMTP 提交结果、事件和 trace**，帮助解释流程在哪里偏离预期，是诊断证据。

```text
验收证据：产品结果成立了吗？
诊断证据：发生了什么，为什么没有成立？
```

这是按证据回答的问题分类，而不是简单按“内部／外部”分类。内部状态也可以成为某个明确需求的验收对象，但不能拿它替代它所不能证明的外部结果。

为了低成本地获得这些证据，系统应当容易：

```text
设置条件 → 执行行为 → 观察结果 → 清理状态 → 复现实验
```

对应的架构能力包括：显式依赖、可控制的时间与随机性、隔离的测试数据、可查询的重要业务状态、关联日志，以及足够的失败重现信息。

**Testability 不是为了测试而改造几个 class，而是系统能否被可靠实验和持续改进的能力。**

## 六、TDD 的价值在反馈顺序，快循环必须受全局约束

我们保留 TDD 的核心，但不要求所有代码机械地 test-first：

```text
明确一小块稳定行为
   ↓
建立检查，确认它因预期原因失败
   ↓
做一个足够小的实现变化
   ↓
检查通过
   ↓
保持行为约束，改善实现
```

Red 的价值是确认检查对当前缺失或错误的行为敏感，而不是随便制造一个失败。Green 也只说明当前执行的检查通过，不等于完整规格已被证明。

**当“应该做什么”比较明确，而“如何实现”不明确时，这个循环很有帮助。** 当产品本身仍在探索时，应先探索、获取反馈，再逐渐固化稳定部分。

开发节奏则采用快慢循环：

| 循环      | 主要责任                                                     |
| --------- | ------------------------------------------------------------ |
| Fast loop | 小改动、快速检查、缩小问题范围，支持实现搜索                 |
| Slow loop | 更完整的集成、产品验收和现实条件验证，检查局部变化是否组合成整体结果 |

划分不按工具名称机械决定。例如正在优化性能时，一个可重复的局部 benchmark 就应该进入快循环，而不是把性能反馈全部留到最后。

但双循环还需要全局视野：**局部任务要知道必须守住哪些系统不变量、边界和质量约束。** E2E 能检查产品路径，却不能独自保证架构长期一致、易于修改。

所以切分方向是：

> **最小的连贯改动，而不是最小的代码改动。**

每一步都应有可验证的进展，不依赖“先破坏关键约束，下个任务再修回来”。至于如何稳定地切出这样的步骤，我们目前只有原则，还需要真实案例检验。

## 七、上线不是验收终点，自动化也不应拥有无限决策权

整个闭环覆盖：

```text
设计时明确约束
   ↓
开发时快速验证
   ↓
发布前验收
   ↓
受控上线
   ↓
生产中观察真实结果
   ↓
反过来修正规格、设计和验证
```

生产提供开发环境无法完全提供的证据，但代价是用户可能已经受到影响。因此，生产验证必须与限制暴露范围、停止发布、恢复或补偿等机制一起考虑。

**自动化决策权要同时匹配证据可信度与错误后果。** 自动回滚也不能撤销已经发生的发信、扣款或数据泄漏。

对 AI 迭代，还有一条直接的边界：

> **实现可以改变，验收依据也可以合理演进，但不能为了让检查变绿而无审查地同步放宽标准。**

测试、阈值、输入生成器发生变化时，应能说清楚：这是产品要求改变了、观察方式需要更新，还是原来的检查有错。不能用“现在全绿了”代替这个解释。

## 八、第一次应用，先回答这些问题就够了

不必先搭建新平台，也不必规定每个 feature 都有某种新文档。在现有任务说明里记录下面这些内容即可：

| 问题                   | 需要留下的具体内容                                           |
| ---------------------- | ------------------------------------------------------------ |
| 这次为什么改？         | 用户可观察的目标，以及不在本次范围内的事情                   |
| 什么必须保持？         | 关键行为约束、全局不变量；另行标明可修改的设计假设           |
| 怎样验收？             | 场景、条件、直接观察的结果和判定方法；性能改动还要有基线与测量条件 |
| 第一小步是什么？       | 一个连贯改动，以及它对应的快速反馈                           |
| 失败怎样调查？         | 所需状态、日志、复现方式，以及环境清理办法                   |
| 怎样确认整体仍然成立？ | 较慢的产品验收、生产观察和停止／恢复条件                     |

这只是第一次实践的工作记录，不是已经验证过的通用流程。暂时不能自动判定的部分，应明确保留为人工判断，而不是强行制造一个不可信的 Oracle。

**第一次应用的成功标志，不是测试变多了，而是：AI 每次修改后，更快知道是否接近目标；失败时更容易知道原因；实现可以自由变化，但产品约束没有被悄悄放松。**
