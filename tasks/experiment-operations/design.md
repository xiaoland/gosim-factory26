# 实验操作的产品与技术方案

2026-10-02，用户已复核并授权开工的方案。以下是目标行为；调查证据不代表新入口已经完成验收。问题与授权归 [packet](packet.md)，具体事实分别归 [恢复](recovery-findings.md)、[本地与回收](local-findings.md)、[官网与监控](hosted-findings.md)。

## 要解决的操作问题

用户或主 Agent 已决定本次来源、材料、模型、费用和实验范围后，应只需要提供一次这些输入，系统便完成机械核对、实际准备、唯一物理执行的接入和脚本持续跟随。任何环节失败，都能从同一操作目录知道已产生什么效果、哪个事实尚未知、哪些步骤可以继续。中断后继续同一操作，不通过复制脚本或新建 journal 重新开始。

当前基础能力多数已经存在。I13-2 反复手工处理的是来源与新材料的绑定、Linux prepare 的环境和独立读回、短时官网提交、后台跟随接入以及多层退出回收。Mac 进程身份误判与输出链接保全约束是实际缺陷，不能只在它们外面加一层命令包装。

更省事的局部替代是只收进共享 prepare；它可以先减少复制准备脚本，却仍留下启动、监控和重放的人工接线，达不到本任务的完整目标。本方案保留这个实现先后顺序，但最终覆盖整条已授权操作。

## 产品约定

建议使用现有 `python -m lab.arc_bench` 下的一个实验操作入口。暂定三个动作，精确参数在实施准备阶段收敛：

| 动作 | 可见行为 | 成功的准确含义 |
| --- | --- | --- |
| `operation prepare <本次规格> --directory <操作目录>` | 冻结本次执行内容和授权边界；需要恢复时完成来源保全、派生、恢复包及独占环境实际 prepare；输出具体准备结果。 | 对应材料已完成准备和核对，可以进入获授权的启动；不代表来源执行已停止或 provider 已接续，二者分别报告。 |
| `operation run <操作目录>` | 只消费 prepare 的冻结结果，执行已授权的剩余步骤，取得实际 run 身份，交给纯脚本采集与终态跟随。再次调用接续同一操作。 | 短调用若仅派出后台进程，返回 accepted；只有实际身份读回、采集接收，以及本次范围要求的终态/重放跟随接收均成立，才报告持续责任已接通。 |
| `operation status <操作目录>` | 合并展示既有 run/journal 和 observer 的最新事实、时间及原件入口。 | 每项观察带来源和时间，不把操作启动时的快照当当前状态。 |

操作输入引用现有 local recipe 或 hosted 配方，恢复额外引用来源 run/workspace、目标 base/binary、允许材料变更和必要重建依据。prepare 在派生材料就绪后调用现有冻结能力，将实际执行内容和身份固定为 lab experiment 或 Competition inputs，而非仅保存可变文件路径；run 不再重新读取外部 recipe 来决定范围。继续使用 `arc_matrix`、`competition.prepare` 与现有 manifest，不再建立另一套模型矩阵或全局 Harness 配置。机器数据保存私有 key 文件的引用及非敏感身份；凭据不进入输出、命令参数或共享文档。

一个操作目录绑定一次已批准的范围。变更题目、模型、费用、来源或需要新的收费尝试时，新建明确关联的操作；不能改写已有输入以绕过 pending。可变的监控 targets 是观察订阅列表，每项绑定已确认的 journal/run 身份；增添观察不会改变任何操作的冻结执行内容或重放授权。

对于恢复，已运行来源的暂停/停止只在本次维护范围明确覆盖时执行。可先核对并保全暂停检查点，再在实际切换前独立确认旧执行已停止；来源仍运行、停止身份不明或者检查点缺口影响原进度时，返回具体待决定事实。工具整理候选时点，不凭“最新”替用户决定可丢弃进度。

## 组件责任与生命周期

用户在实施中进一步要求“避免打补丁，而是选择长期正确的架构、治理来解决问题；不要盲目遵循 ponytail”。据此，实现必须从组件边界解决重复出现的问题，而不是在每个调用者累加条件。冻结 manifest 界定本次 experiment、job、attempt 和实际包；启动、跟随、重放、监控与完成判断共同消费这一范围，不能扫描共享 runs 目录来扩大授权。恢复 preparation 显式绑定具体 job 或官网输入，未被消费的准备结果属于配置错误；已有冻结 experiment 不允许悄悄替换 agent。

准备成功、来源已停止、执行已启动、观察已接收是四个独立事实。恢复启动必须消费与实际包 SHA 绑定的准备回执及同一来源的停止依据。collector 的确定失败结束当前自动接续，保留失败和已启动执行；显式重入才能重新接管同一 scheduler，不能用高频自动重启隐藏接口或配置错误。Ponytail 不改变这些约束，也不作为缩减职责边界的理由。

新增 ARC 操作入口只承担跨组件接续。它持有冻结输入引用、步骤效果回执与后台责任交接，不保存另一套可写的全局 run 状态，不新增数据库、队列平台或常驻调度服务。

| 组件 | 继续拥有的事实与动作 | 拟补齐的接口 |
| --- | --- | --- |
| `lab.plan/run/control` | 冻结实验、attempt、资源与 controller 生命周期。 | 统一 Mac/Linux 进程身份判断；从真实 controller/attempt 登记确认启动，供 ARC 操作消费。 |
| `package_completed_recovery` / `recover_completed` | 恢复制品、派生材料、包内工作区恢复及调用 Braid。 | 分离来源 journal/旧包与目标 base，接收明确 Git 重建依据，提供可供独立核对的准备输出。 |
| `docker_workspace` / ARC adapter | 源容器/卷所有权、传输、执行边界与归档。 | 共享保全/隔离准备的环境操作，区分输入冻结与输出归档，明确一次 finalization 的所有者。 |
| `competition.Controller` | 官网 inputs/state、pending、远端身份与锁。 | 公开有限的 launch：同一比赛锁内完成 snapshot/create/start，随后释放；复用已有 pending/recover。 |
| `local_monitor` / `hosted_monitor` | 采样、provider 状态、通知去重及 scheduler。 | 接收显式 targets，确认身份和首批采集，保留观察历史，输出可查询的完成/失败回执。 |
| ARC 操作入口 | 以上动作的已批准意图、步骤结果引用和后台交接。 | 自动生成必要输入并调用这些接口；接续本地生成成功后的冻结应用与独立官网重放。 |
| Braid | DB/runtime 所有权、offline-resume 与原生会话生命周期。 | 首期沿用公开接口；不在 Factory 写 SQL 修生命周期，也不接管 Pi 内部子 Agent。 |

本地新执行与恢复仍创建新的 lab run/volume；恢复保持既有 Braid/native 身份和原进度。官网恢复仍创建一次已授权的新平台执行；原源 journal、source ZIP 与派生差异全部保留。这两个层级的 identity 在操作结果中并列，不能互相替代。

## 五项必要改动

### 1. 将保全与准备收进共享恢复操作

来源 journal 的 submission/run/终态/原包校验，与本次目标 base/binary 校验分别成立；允许刷新材料不等于舍弃来源绑定。来源停止证明要引用实际 Docker 身份/状态或官网终态读回，带观察时点和错误。普通 archive SHA、caller-confirmed 或包内 `--offline-resume` 不能自行升级为停止证据。

真实 prepare 由宿主操作创建独占 Linux 环境，固定目标镜像及 Docker endpoint、执行 UID/GID、目录所有权和输入传输；网络关闭，不向其注入运行费用 key。复用现有底层能力的必要部分，不能直接复用会启动生成、重复回收或删除现场的整条退出链。失败保留原始 stdout/stderr、退出事实和本次独占资源身份。

准备读回覆盖源与派生包绑定、应用文件及未提交进度、Git/Braid/native 身份、允许的材料变更和实际二进制。比较依据从源清单与本次变更得到，不把 `786` 等文件数硬编码为门槛。启动只消费绑定最终 ZIP SHA 的准备结果；文件准备、provider resume、最终交付与评分分别报告。

官网缺失私有 `.git` 时，优先消费完整快照；确实缺失时，在现有恢复入口统一应用逐 clone 的明确 ref/commit 及证据引用。DB 登记 branch 不自动等于最后 checkout。保留原工作文件，不能宣称原 staging、reflog 或未发布提交已经找回。维护 comment 作为已批准派生输入一次应用到副本；后续复用最终派生包，避免接续时反复追加。

### 2. 让启动成为可接续的有限操作

本地在 prepare 阶段通过现有 plan 固定实验内容，run 只调用该冻结实验的 start，启动后从 controller/attempt 登记取得 run 列表，自动生成 monitor 和终态跟随所需引用。后台进程派出失败、controller 未就绪、attempt 尚未启动是不同结果，不只返回一个 PID。

官网 `Controller.launch` 封装目前散落在 launch/follow 脚本内的私有锁操作；沿用 journal 和 HTTP 协议。未确认写入只做已有只读 recover；找不到唯一匹配身份就停止并保留 pending，不自动重发，不承诺服务端 exactly-once。确认已有 submission/run 后只继续未完成步骤。

已启动而监控接入失败时保留 run，返回“已启动 + 监控未接入 + 原始错误”。再次 `run` 只补接监控，不创建替代 run，不自动取消原执行。请求错误保留 HTTP 状态、可诊断正文、请求/响应原件及传输阶段；摘要不丢失 `ApiError.detail`。

### 3. 用持久接收取代监控停启接线

保留现有 shared collector/scheduler。让 collector 每轮重读显式 targets，新增 journal 后按其实际 run identity 接收；旧 `next/liveness/notifications/done` 保持。由操作入口在锁保护下原子更新订阅，防止并发添加互相覆盖。已有 target 的身份冲突要报错，不能悄悄替换或移除仍活动的运行。

写入 targets 只表示提出接入；collector 保存接收 identity、采集阶段、首批 outcome 和最近成功时间才构成交接证据。现有最长八分钟的等待可分为较短的本地配置等待，但远端请求仍保持 run 前十分钟三分钟、以后八分钟的节奏；不调用模型，不为了检查配置增加远端轮询。正在下载时如尚未接收，明确显示等待，不虚报即时接入。

后台执行记录 actual argv、源码身份、完整进程身份、stdout/stderr 与最终退出事实，复用现有文件锁排除重复 collector。无存活 collector 时按记录接续同一 scheduler；正常全部完成后的新增订阅可以重新启动同一观察器。collector 的完成、异常退出和运行的终态分别保留；已有进程身份不确定时不得强制接管。若操作进程本身因宿主退出而消失，下次同一命令可据文件和外部状态接续，不承诺尚未安装的系统级开机自恢复。

通知只在有意义状态变化、完成、故障或需人处理时提交；持久回执是事实入口，桌面通知保留 best-effort 语义。PASSED 分类与跨批次错误签名是本次源码发现的候选边界，纳入实现时核对，尚不能声称已发生漏报或重复。

### 4. 把本地成功后的重放接到同一责任链

保留 `runner_exit_code == 0`、生成 result completed、应用已发布三项现行门槛。每题完成立即按本次冻结费用范围处理，不等待同批其它题。

复用 `package_arc_replay` 和同一 Competition journal，以来源 run、冻结应用身份及本次重放范围定位唯一操作。已有包就核对并复用；已有平台 run 就采集；pending 只读核对。原脚本的内存 observed 集合和“目录存在即失败”不再成为恢复依据。重放期间已有 run 的观察与生成继续独立，隐藏评测反馈不注入仍在生成的 Agent。

本次冻结范围包含自动重放时，终态跟随者必须另有持久接收回执，绑定来源 run、重放范围和消费进度。collector 接收不能替代它；若跟随者启动失败，明确报告“生成已启动、采集已接入、终态跟随未接入”，再次 run 只补该交接。它继续使用既有 wait/replay，不建立另一套生成状态。

模型和费用来自冻结输入，不从 `case == flash-root` 等分支重建配方。真实需要第二次评分属于新操作；原失败回执、已生成应用与费用归属不被覆盖。

### 5. 修正进程身份及输出回收的根因

在 `lab.control` 集中判断进程存在性与出生身份，并让 owner、retry、reconcile、cleanup 使用相同语义。同机且确认为不存在可判 lost；存在但旧记录缺出生依据为 unknown；非空且匹配才为 alive。Linux 保留原生依据，Mac 取得系统依据。旧 null 记录不回填；unknown 不放行重试、清理或接管，可从既有 socket/controller_id 单独取证。

输出保全不继续使用严格输入快照规则处理所有链接。保留未展开的原始归档、文件/链接字面清单、已知容器路径映射和缺失目标限制；不跟随外链拷贝宿主内容，也不全局关闭安全解包。数据内容保全与可在目标环境执行恢复分别判定，已保留一个悬空链接不等于其目标已经恢复。原输入 manifest 算法及历史身份保持。

在实际容器退出时立即保存退出事实，再由唯一所有者执行有界 finalization。各层 finally 不重复同一次已失败回收；再次补采是明确可接续操作。生成失败、归档缺失和清理未完成并列，首个原始错误不被后续泛化错误替代。只有本地原件确认保全成功才允许释放远端唯一副本。

## 失败及接续结果

| 观察到的情况 | 持久结果与下一步 |
| --- | --- |
| 包、来源或 prepare 不满足约束 | 已准备的原件/尝试保留，明确差异；不进入收费写请求。修复局部前提后继续本次准备。 |
| POST 结果不明 | 标记具体 pending 动作、已有身份与原响应；只读核对，不能当作未发生。 |
| run 已取得，读回失败 | 保留该 run identity 与“读回未确认”，继续只读确认，不另建 run。 |
| run 已启动，collector 未接收 | 报告观察未接入，继续补交接；不重新启动生成。 |
| 采集已接入，获授权的终态/重放跟随未接入 | 单列跟随接收失败与已有生成身份，重入只补该责任，不宣称整条流程已经接管。 |
| collector 退出但 run 未终态 | 保存原退出/错误及最后成功观察，按完整身份重新接管同一 scheduler；不得伪装 run 失败。 |
| 容器停止，归档失败 | 报执行已结束、归档不完整及保留资源，退出本次自动回收；显式补采接续。 |
| 旧进程身份未知 | 停止会修改或破坏现场的动作，保留未知依据；取得事实后才能接管。 |
| 平台 FAILED 且测试未开始 | 保留生成/部署错误及阶段，评分未发生；不得报有效零分。 |
| 终态已有有效计数，附加证据采集失败 | 保留有效评分，同时显示原件缺口，不用附加采集覆盖结果。 |

操作回执只记录步骤效果和指向权威记录的引用。status 按最近观察读取 run/journal 与 collector，不从 `launched=true` 推导持续健康，也不从 native 活动推导语义进展。

## 验收方案与证据限度

首先以编译、实际文件/进程操作与隔离的真实输入处理取得反馈。不编写或运行 Factory/Braid/SVC 测试、mock、smoke 或改名自检。独立复核直接读取操作产物和原件，不只阅读实现或其布尔结论。

| 必须成立的结果 | 可使用的真实材料与反馈 |
| --- | --- |
| 更新 base 仍保留来源身份，准备不依赖每题脚本 | 本轮已保全的本地/官网来源及现有 r2 冻结材料，在新独占无网络容器执行正式 prepare；独立比对原件、dirty、native、材料与实际环境。 |
| Mac 不再将已消失进程判 alive，未知旧身份不放行破坏动作 | 已保存 PID 98966/15711 的记录和本次 ps 原件；新控制器正向身份从下一次获授权实际启动取得，不构造假进程记录。 |
| 外链不再阻断其余输出保全，且安全边界成立 | 对两种真实链接所在的既有保全副本执行生产归档/恢复操作，独立核对字面值、文件内容和缺口；不触碰原失败卷。 |
| 失败阶段、远端效果与接续动作准确 | 直接读取 I13 的 prepare PermissionError、HTTP500、pending/launch 与归档错误原件；实施后真实出现的失败继续沿该契约记录。现有记录不能证明所有未来崩溃窗口。 |
| 新增目标无需手工停 collector，重入不丢历史 | 下一次获授权监控应用中，以同一共享目录观察已有 run，核对旧 scheduler、接收身份及首批结果；部署前交付具体范围，不创建新收费运行。 |
| 本地完成后独立重放可持续接续 | 下一次已批准实验的真实终态触发。核对同一源应用、journal 与远端 run；无此运行则明确未覆盖，不能用生成脚本存在冒充验收。 |
| 真正恢复和最终结果 | 保留 I13 r2 已有 resume/prefix 证据作为历史基线；新入口的 provider 接续与评分须来自它实际承接的获授权运行。 |
