# 工作项、讨论与上下文的产品设计

状态：设计已复核通过；当前推进状态与授权纠正见 [packet](packet.md)。
技术边界见 [技术方案](technical.md)，验收沿用真实任务与完整 benchmark，见 [验收方案](verification.md)。
本页保留此前易用性设计；“保持既有最终完成条件”和根 Issue 交付职责已被用户批准的 [职责边界](run-boundary.md) 替代。自主工作流程仅用于 [Braid Factory](factory-workflow.md)。

## 要解决的问题

三次实际运行把 Issue/PR 用成一次性派发、实施与复验的阶段容器。
分工和复验可能有效，但不能据此说明 Braid 的持续上下文与协作能力产生了额外收益。
本轮目标是让 Agent 能自然维护当前工作项、就变化交流、按需指派成员，并去掉与这些行为无关的运行协议负担。
不要求更多工作项、更多评论、固定往返或主动调用每一种上下文功能。

## Agent 看到的工作环境

Agent 直接看到当前 Issue 或 PR、关联工作项和成员目录，以 GitHub 式命令查看、编辑、评论、回复和指派。
它不需要知道 profile、writer turn、运行状态目录或 Braid 的重建状态机。
初始说明只解释工作方式与最常见入口，完整参数留在对应 `--help`。

| 载体 | 应承接的信息 | 何时更新或使用 |
| --- | --- | --- |
| Issue description | 当前问题与范围、需求来源，以及已形成的设计和验收依据 | 对问题的理解或已接受方案发生变化，旧正文已不能指导工作时 |
| PR description | 本次实现要交付的变化、关联 Issue、当前实施信息和证据入口 | 实现范围、重要取舍、完成状态或受检提交发生变化时 |
| comment/reply | 具体发现、问题、备选意见、反馈和对另一工作项有用的结果 | 对方需要据此判断或继续工作时，在原问题所在讨论中交流 |
| resolve/hide/delete/reaction | 讨论是否仍有用、是否已处理，以及轻量反馈 | 有事实变化或上下文整理需要时；hide 可说明理由，reaction 不自动解释为批准或完成 |
| task packet 与文件 | 较长的方案、脚本、材料和可复现证据 | 适合放文件的内容按需链接；不另造与 Issue/PR 竞争的状态或重复全文 |

这些是用途，不是强制字段模板。
Issue 仍负责设计，PR 仍负责实施；阶段职责不要求阶段目录，也不要求整个项目只能进行一次设计与实现交接。
原始需求入口保留，description 的修订不能悄悄删除产品义务；PR 引用 Issue 的已有方案，不必再复制整份需求和设计。

建议交付给 Agent 的核心指引如下，具体工作项信息由运行时附带：

> 你负责当前 Issue/PR。description 表达当前工作内容，相关讨论与文件提供依据。
> Issue 承接问题、设计和验收依据，PR 承接对应实现及验证；根据任务需要组织工作，不为使用工具而拆分。
> 把影响其他工作项的发现或问题发到相应讨论，用 reply 接续原问题。决定改变后，更新应持有该决定的工作项，避免让过时说明继续指导工作。
> 需要独立工作项时，从成员目录选择 assignee；当前工作项内部的局部委派使用原生 sub-agent。
> 按需整理已处理或过时的讨论。description 和讨论的可见内容决定后续工作上下文，较长的材料与脚本可以放在 task packet 并链接。
> 自主完成已授权任务；报告验证结论时说明它对应的交付内容与证据。

工作项、角色和交付操作说明归 Braid；V&V 的方法与证据判断指南归 SVC Corpus，Braid 不复制这些内容。
pi-team-vv 只保留提示查阅 SVC 的入口；原生委派配置归 variant。本轮不修改 SVC Corpus。

## 分工由 Agent 决定

Factory 的 variant 只给出成员目录与根 Issue 的启动成员。
创建后续 Issue/PR 时可用 `--assignee LOGIN` 同时指派，也可先创建未指派对象，之后用 edit 指派。
未指派工作项保存内容、显示未指派，不自动挑成员或启动执行。
同一个成员可以承担多个工作项，不要求不同模型或人为区分角色。
允许按现有 edit 接口重新指派；停止旧执行、保存工作树和启动新执行仍由 Braid 负责。
保持既有最终完成条件：有未处置工作不能宣称整项完成；但不自动代替 Agent 关闭、分派或改变计划。

## 上下文维护应是普通操作

Agent 使用 `braid issue view 1`、`braid pr create … --assignee deepseek` 等命令，不传 state 或 writer-turn。
作者和工作项归属自动取得；同一成员的不同工作项不会因共享 login 而串身份。
旧会话失效后不能从当前工作目录取得新会话的写入身份。

保留 description 调整后的完整上下文重建，以及 hide/resolve 对后续可见上下文的影响。
为已观察到的连续 resolve 问题，建议同类评论整理支持一条命令操作多个 ID，例如 `braid comment resolve 4 7` 或 `braid comment hide 8 9 --reason '已由正文更新取代'`。
整条命令一次提交，再进行既有上下文替换，避免第一条处理成功就使同次整理的其余对象失败。
本轮不引入通用事务脚本、显式 refresh 或让 Agent 管理会话的工具。
多 ID 操作解决同类整理，不承诺任意 shell 命令串跨上下文替换继续执行。

## 收敛范围

实现范围为 Braid CLI 与隐式调用身份、默认分派清理、工作项提示与帮助，以及四个现有独立 variant 的接线。
不重做调度架构，不增加语义事件或审批状态机，不管理 Pi 子代理生命周期，不新增固定阶段产物。
旧 run 的验收提交与合并 head 不同记录为风险，本轮通过工作指引与验收观察它；是否修改 merge 接口另按明确需求决定，不附带扩展。

如果真实任务仍只需要一个 Issue 和一个 PR，这个结果可以成立。
若持续工作上下文和讨论在真实运行中仍未承接任何必要信息变化，应报告此设计未证实价值，而不是继续堆指引或制造协作需求。
