# Braid Factory 的自主工作流程与 Issue/PR 协作

本页承接用户要求：将已确立的工作流程应用到 Factory，让 Agent 像团队成员一样使用 Issue/PR。
用户已批准应用，并限定此流程仅用于采用 Braid 的 Factory variant；raw 等其它实现不继承该路线。
“像人类一样协作”保留为一句指引，由 LLM 理解，不展开成交流行为清单。
通用系统边界见 [run-boundary.md](run-boundary.md)。

## 已观察到的缺口

当前 `variants/pi-team-mixed/run.py:117` 的任务正文清楚给出了需求来源、产物布局、执行授权与无人介入条件。
六份 `variants/*/agents/*/instructions.md` 主要说明原生 sub-agent 委派和自主继续，没有把需求理解、方案、验收设计、实施准备、实现和最终验收连接成工作路线。
`sources/braid/src/group/provider.rs:72` 已区分 Issue 设计和 PR 实施，但又把合并决定集中给根 Issue #1，并在通用提示里混入 Factory 的权限和无人介入条件。
已有 SVC Skill 提供探索、产品/技术设计、验收设计、实现、V&V 和 task packet 的按需入口；Factory 已装载该技能，方法可用不等于真实运行已有效采用。

旧 Keep 的 [运行分析](results/keep.md) 显示根 Issue 已写出主要应用，PR 只改少量样式；这支持“职责指引没有形成实际工作分离”的判断。
无法仅据该结果断言缺一段提示就是原因；新的指引是否起效仍需真实轨迹和评分。

## 工作流程如何落到载体

| 工作 | 主要载体与责任 | 下一步所需信息 |
| --- | --- | --- |
| 理解、分析和完善需求 | Issue 的负责人理解原始需求，记录重要假设、范围与未解问题 | 要实现什么、哪些决定仍未形成 |
| 形成产品与技术方案 | Issue 持有当前选择、理由和关键接口；细节按需链接文件 | 实施者能据此工作，重大产品选择没有被隐藏到编码里 |
| 设计最终验收 | Issue 说明哪些观察能支持需求已满足；方法查阅 SVC | 判断对象、条件、标准以及取得证据的办法 |
| 规划与预演实施 | PR 的负责人结合现有实现制定路线，提前核实可能推翻路线的 API、依赖或生命周期假设 | 可以开始的具体改动；若影响既定方案，回原 Issue 讨论并更新决定 |
| 执行与修复 | PR 持有实际改动、取舍与局部反馈；有界工作可用当前会话内的 sub-agent | 可整合的提交和对应反馈 |
| 最终验收与整合 | PR 取得实施结果和验收证据；承担该范围的 Issue 负责人据此判断后续工作与合并 | 对确切提交的结论、尚未满足的需求或可以关闭的工作 |

这些信息依任务复杂度展开；简单改动可以用几句话说明，不固定要求六份文件、六次调用或独立审查者。
阶段可以因新证据回到此前的决定，已经清楚的内容通过引用接续。
一个成员可以承担多个工作项；是否另开 Issue、另指派成员由 Agent 根据独立目标与协作需要判断。

我们开发时的用户复核承担需求和授权决策；Factory 的输入已经授予本任务内的设计、实现与验收权限。
因此 Factory 内由相关工作项的负责人行使该范围的判断，通过 description 和讨论保持决定可追溯。
这不增加 Braid 的审批状态、阶段事件或“获准实施”字段，也不让 Agent 模拟用户批准。
需要修改另一工作项的已接受决定时，向其负责人说明影响；可继续的独立工作照常推进。
缺少不可推断的外部事实或超出任务权限时，留下具体阻塞，不能通过互相评论创造外部授权。

## 指令落点与建议正文

SVC 保持通用方法，不出现 Braid、Factory、比赛、固定 Issue/PR 流程或平台权限。
Braid 解释工作项、设计与实现的职责、讨论和上下文操作，以及成员目录与 Git 操作；它可以作为另一环境中的通用协作工具。
Factory 各独立 variant 的成员指令承接本任务的自主工作路线；`run.py` 继续提供比赛输入、输出与权限。
沿用每个 variant 独立实现的组织，不新建共享流程解释器或配置生成层。

已应用到六份 Braid Factory 成员指令，正文以实际 `variants/*/agents/*/instructions.md` 为准：

> 本 Factory 使用 Braid 的 Issue/PR 组织工作。像人类一样协作、使用 Issue/PR。
> Issue 承接需求理解与完善、产品和技术方案、最终验收设计；PR 承接实施计划与适用的预演、实现及修复、最终验收。按任务复杂度准备足够的信息；新发现改变既定方案时，回到相关 Issue 确定调整，再继续受影响的实施。承担该范围的成员根据实际提交与验收证据判断整合和剩余工作。
> 按当前问题查阅 SVC 的设计、实现与 V&V 方法，用 task packet 保存持续工作所需的方案、计划、材料和证据。

V&V 正文仍只有 SVC 一份，pi-team-vv 保留既有显式入口；本轮不修改模型或工具配方。

## 真实运行中的复核

沿用已批准的完整 Lite 与逐 run 分析方法，观察决定和证据怎样影响后续工作。
重点看验收条件是否在实现前形成、关键未知是否提前解决、实现中的变化是否回到正确决定、最终证据是否对应被整合的提交。
不以文件数、评论数、拆分数或形式上的 Issue→PR 流程作为收益证明。
应用得分、执行故障和协作行为分开报告；只观察到一种行为，不能宣称其它能力已验证。
