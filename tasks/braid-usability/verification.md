# 本轮验收：操作负担与工作项的实际用途

状态：用户已随设计复核通过；延续已批准的真实运行、完整 benchmark 与逐 run 证据分析方法，不重复申请方法批准。
具体实验启动仍需在开工影响中明确，不在设计阶段启动。

## 接口与产品行为

| 要回答的问题 | 使用的证据 | 判定 |
| --- | --- | --- |
| Agent 是否还要搬运身份参数 | 实际输入和 CLI 工具调用 | 正常对象命令不传 state/writer-turn；作者和工作项对应正确；旧执行实例不能取得替换实例身份 |
| 后续工作项由谁指派 | 创建、edit 和 assignment 记录 | 成员由 Agent 选择；未指派对象没有自动选人或执行；同一成员可承担多个工作项 |
| 整理上下文是否可用 | resolve/hide 的工具结果及实际后续 context | 多 ID 整理完整提交，hide 理由可读；后续上下文体现变更，不要求手工更新身份 |
| 工作项有没有承接信息变化 | Issue/PR 正文、讨论、原生会话及交付记录 | 能指出必要信息由谁产生、被谁使用、影响了什么决定或执行；不能仅列操作次数 |
| 设计与实现是否只是名义分离 | 实际编辑、提交与工作项内容 | 不再把根 Issue 已写完代码后创建 PR 当作设计/实现分离的成功证据 |
| 验收结论对应什么 | 受检提交与最终交付提交 | 二者对应；有后续变化就有相应处置依据，不能用旧结论直接宣称新产物通过 |

不强制在题目里制造争议、返工或拆分来展示能力。
没有自然出现的操作场景标为未观察；不能把未观察算通过，也不因此增加模拟脚本或全套测试。
上下文历史不足时只描述现存事实，不能由 revision 数推出正文演化。

## 实验与报告

建议首先选具有多个成员的现有 `pi-team-mixed` 完成一次 ARC-Bench-Lite，而不是先展开四 variant 矩阵。
该轮同时观察分工选择、上下文使用、完成时间和最终得分；控制模型、技能、需求及 runner 身份，避免把其它任务正在进行的配置变动混入本轮。
具体执行环境、可用 runner 和冻结材料在开工前核对，本设计不假定旧平台或本地 runner 当前可用。
已有旧 run 作为机制参照，不因分数差异直接宣称单变量因果；如需严格量化收益再另定对照。

一次 run 的生成故障要在已授权范围内修复并继续，直到完整 benchmark 得分或出现实质阻塞。
完整 benchmark 评分后先汇报，由用户决定下一轮，不以单 task 完成替代整 bench。
沿用一 run 一独立分析 Agent，主 Agent 只综合；重点取证对象及必要的原生片段，不重复扫描完整 trace。
分析应明确区分：操作失败、工作项被形式化使用、实际协作/上下文作用，以及与成绩之间尚未证明的关系。

本轮不编写、维护或运行 Factory、开发基础设施或 SVC Corpus 的测试，不把它们改名为 smoke 或验收探针。
真实生成应用的验收与官方 benchmark 保留；不更改旧冻结 ZIP、旧结果或运行中的其它实验。
