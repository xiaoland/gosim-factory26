## 5. 仅保留证据支持的改进候选

1. **优先：在 Issue→PR及模块验收时处理未承接范围。** 不是再加“全面覆盖”口号；现有根输入已经明确并列对象和原需求优先。让 owner 在排除原需求中的能力时明确记录“谁承接、哪个交付项、对方确认或根裁决”，未确认时保留为根的开放交付问题。落点是根/Issue/PR角色指令与 `svc-task-packet` 的范围/下一步用法；证据强。风险是为普通边界增加文书，可仅触发于发现需求与当前子任务冲突时。零额度核验：用 #231/#235/#305/#308 原文离线逐步填出责任是否闭环，不跑模型。
2. **其次：保留 M1式反例审阅，把“REQ ID出现”与“场景/并列对象覆盖”分开。** 沿现有验收文档建立很小的核对：原始能力涉及什么对象/角色/初始状态，当前观察是否逐一覆盖；不是要求再跑更多已有测试。落点是 `svc-verification` 与根最终整合说明。证据中强：早期有有效对照、末端有覆盖差距；PR23当时为何采用该口径仍缺原始链。零额度核验：人工比较一个正例 M1 与一个跨对象例 REQ-5-3-3 的需求/断言，注明可证与未证，不新增Factory测试。
3. **运行层与提示层分开：按既有I11生命周期审计修复结果/输入交接。** PR13/PR16的已证机制需要运行实现处理；再加“读评论/不要重复测试”不能代替后台作业终态和输入可消费性。此项不作为4分的已证主要原因，也不在本轮重新设计或实施；复用已有设计与原始案例即可。

以上均无提升幅度承诺。已证问题是具体的决策与责任断点；不能以文档数量、调用次数或最终低分推出 SVC / 子 Agent / Issue-PR 架构整体无效。
