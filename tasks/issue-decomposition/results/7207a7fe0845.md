## 验收为什么没有拦住

已有的有效检查集中在 PR #1 的 API、构建和静态服务。它们不等价于最终提交的验证：PR #1 没有合入，最终跑分使用的是根 Agent 的另一套实现。原生轨迹未观察到真正的浏览器页面验收；唯一相关浏览器命令只是查询 Chromium/Playwright 是否安装及版本。

同时，Issue #2 用顺序执行的 shell 把“尝试 merge”和“关闭 Issue”接在一起，没有依据 merge 的成功结果更新状态。该例不是缺少更长的验收清单，而是证据所指向的分支、集成结果和工作项声明没有保持一致。

进一步核对发现，关闭理由在观察 merge 结果前已经写进同一条分号串联命令；最后 close 成功使整条工具调用返回 `isError=false`。
同一原生会话随后明确识别合并失败、Issue 已关闭、根工作区属于另一会话，却没有更正关闭状态或留言协调就代为提交 WIP。
13:11 时检查的两个文件，到 13:14 执行 `git add -A` 时已变成八个文件；提交后它才确认另一个会话仍在活跃编辑。
因此需同时处理依赖操作的反馈、错误完成声明的纠正，以及 PR 合并实现对根 Agent 工作区的不当操作，详见 [定向调查与待复核方案](../../braid-usability/merge-feedback.md)。

入口导出指定集成 ref 的行为符合当前技术说明，Braid 非零退出本身并不禁止导出。此次暴露的产品问题是：**一个用于保全未完成工作的 commit，仍会作为平台要评测的应用离开生成阶段**。是否需要区分故障快照和完成候选，应结合这条真实失败链决策，不能简单把所有非零退出一律判为没有可评测产物。

## 证据边界与下一步建议

官方 API 的 `tests=[]`、`node_states={}`、`result_path=null`；日志只包含生成和部署，没有逐例 Playwright 结果。traceability 返回空数组，commit-history 返回 `workspace_unavailable`；但 workspace 文件树与 template bundle 下载成功，取得了本次 `.factory26` 原生归档。`.arc/playwright-report.json` 和 `.arc/stdout.log` 的 source 请求均为 HTTP 404。这些限制已保留在证据目录，不能把 commit-history 不可用等同于全部产物不可取得。

因此，尚不能回答唯一通过的是哪个场景，以及 99 项各自最早停在哪个断言。主页还存在两个同名 `Sign in` 链接，可能影响未限定范围的定位器，但官方 helper 未取得，不能把这种可能性当成这次 1/100 的已证实原因。

建议下一轮优先解决已经观察到的三个问题：

1. 基础框架由一个明确的工作项交付可共享提交；其它工作项基于该提交实施，根 Agent 负责集成，不再同时重写同一组共享文件。PR 分支由其分配的 worktree 持有。
2. 合并失败保持未完成状态；最终验收针对实际集成 commit，通过真实页面操作覆盖各模块入口，避免只复核未合入的分支/API。
3. 单独调查 Issue #7 的 SIGKILL，并明确发生内部中断时应保存哪些故障产物、什么结果可作为完成候选交付。

这些是待用户决定的改动方向。本次只完成分析与页面复现，未改变指引、运行时或交付策略，也未启动下一轮实验。

## 补充复核：指派含义与协作执行

身份语义修正：用户明确不同工作会话应对应不同 assignee，profile 只是派生配置。
当前源码却将独立 Agent 的负责人统一显示为 profile login，评论作者又使用内部 Agent ID。
因此这里的“相同 assignee”是错误的身份投影，不是产品有意允许多个独立协作者作为同一个人；后续讨论见 [身份方案](../../braid-usability/agent-identity.md)。

用户回传报告后，主会话再次核对对象记录和根会话，发现一个比合并冲突更早的分工矛盾：Issue #2 的 description 写“由根 Issue（#1）自行实现”，却将其 assign 给 `glm`，实际启动独立 Issue #2 会话和 PR #1。根会话仍在原生记录 `native/000-2026-09-25T12-41-22-109Z_01a0d895-a9bd-7248-bc27-5fe76a69f6c3.jsonl` 第 40 行公开声明“现在作为根 Issue 开始实现基础框架（Issue #2）”。这支持“根 Agent 将相同 assignee 下的任务仍视为自己承担，与实际独立执行发生冲突”，尚不能将原因只归给模型能力或工具说明。

Issue #3/#4 的评论已经说明基础框架依赖及等待状态，因此不能简单归因为没有识别依赖。根 Agent 后续又将组织模块的同一段指令投递到 Issue #3/#5/#7（comment 10–12），其中都写组织文件路径与 `pr create --issue 3`；comment 13–14 随后给代码和 PR 模块补充说明。协作对象存在，信息和行为却没有一致对应。

下一步设计应先核实并对齐 Agent 可见的指派、工作项负责人及工作目录语义，再处理共同基础的单一负责人、集成与验证对象。应避免直接增加固定任务图、全量检查表或自动关单条件，把本应由 Agent 决定的产品语义移入 Braid。

WIP 被评分是失败链的最终结果；简单拒绝交付只能改变平台如何显示失败，不能补齐未合入的功能。需分别记录过程故障、可导出的提交和 Agent 的完成声明。SIGKILL 的来源及单会话异常如何终止整个协作仍待定向调查；现有证据不支持直接认定 OOM 或添加重试策略。

本轮新增的 skills/SVC 拆分包只完成材料层面验收，尚未针对上述协作问题修正。后续实验应明确测量哪个改进，不能把新包默认为本次 1/100 的修复版。
