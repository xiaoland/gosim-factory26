# 明确拆分的实验设计

上一轮两题都有生成期自检，却没有用到 Braid 的多工作项协作。
本轮要区分两个问题：Agent 只是未主动采用，还是实际开展协作后也不能改善交付。
先用一轮明确要求拆分的实验，观察采用、执行和整合，再判断分数与耗时；Issue 数量本身不是收益。

## 候选根 Issue 追加文字

> 请先将本任务拆分为多个子 Issue，并 assign 给合适的 Agent 协作完成，再开展实现。
> 按可以相对独立完成、验证的需求组织 Issue；紧密相关、需要连续处理才能形成完整结果的需求，合并为一个 Issue。
> 每个子 Issue 说明要交付的结果、覆盖的需求和必要的依赖，提供所需的需求内容或材料入口。
> 可独立推进的工作并行开展；根 Issue 统筹依赖、整合各项成果并完成整体交付。

这组文字要求实际分工，仍由 Agent 判断具体边界、指派对象和协作方式。
本轮实验要求的是 Braid 子 Issue 的独立负责者，不等于强制 Pi 原生 sub-agent 调用。
“存在先后依赖”本身不足以合并：如果各项有独立结果、只需清楚交接，仍可保留为不同 Issue。

## 拆分粒度的选择依据

需求文件中的编号层级描述产品，并不天然对应工作边界。
Keep 的 REQ-2.3.1 删除、2.3.2 撤销删除、2.3.3 回收站列表，共享同一笔记状态变化，适合放在一起完成。
BookStack 的页面编辑、保存、草稿、阅读入口也存在连续流程，应由 Agent 基于接口和现有实现判断哪些要保持在同一 Issue。
这些例子只用于开发侧复核，不把这两道题的固定划分写入通用任务提示。
逐个叶子 requirement 建 Issue 会放大派发、上下文和共享文件修改成本，首先选择按内聚需求组拆分。

## 技术落点与准备

已认可的拆分要求追加到 `variants/pi-team-mixed/run.py` 中构造根 Issue description 的 prompt。
工作约定写入此 variant 两个成员的 `instructions.md`，具体见下文。
现有路径为 prompt → braid-request.json 的 request.prompt → LocalObjects.initialize；Braid 的通用操作说明、子 Issue 能力和调度保持现有职责。
本轮无需增加解析需求、自动建 Issue、强制状态检查或新的配置层。

已核实 `braid issue create --parent ID --assignee LOGIN` 的现有接口，任务文字可由 Agent 直接执行；WSL 前次打包输入与本机目标文件的差异也已核实为本轮三处文字。
用户已明确批准开工及本轮官网正式 Hackathon 运行。修改后复用现有 Linux runtime 重新打包，保留前一冻结 ZIP 和原始评分作为历史证据。
不为提示词或 Factory 设施编写测试，不在本轮顺带改模型、角色、SVC Corpus 或 Braid 实现。

## 验收

按最新用户指示，直接在官网正式 Hackathon 运行 GitHub 与 Sheet 两题，选择 `official_evaluation` 参加比赛。保留冻结包身份、平台提交与两题 run 身份、评分及可取得的原始过程证据。
候选实验同时加入根 Issue 拆分要求与成员工作流程指引；其余材料沿用上次构建，并明确这不是仅改变拆分指令的单变量实验。

首先看是否创建并指派有真实需求范围的子 Issue，负责人是否实际处理，成果是否进入最终交付，而不只创建几个空对象。
再看各项之间如何协调，以及集成修复是否占去并行带来的时间；PR、评论与原生子 Agent 的使用作为行为证据读取，不凭数量评分。
最终报告两题正式得分、通过数、耗时及可见的失败项。Lite 分数与正式 Hackathon 题目不同，不能直接作分数差分。
若已采用但卡在具体 Braid 操作或运行接线，先按证据定位阻塞；实质实现变化须重新说明范围，不在冻结实验中静默混入修复。
若顺利完成但效果较差，将其作为这一策略的一次负面结果报告，不自动启动下一轮或强化更多硬规则。

## 一般工作流程：实际缺口与补充方案

最新 Keep run be4dde8d43 的 `workspace/official-generation/template/.factory26/20260925-083425-0246dfce/braid-state/physical/01a0d7b3-b4dc-78a1-803a-9ffb16953f08/instructions.md` 仅包括当前 Issue、CLI 使用、成员目录和 SVC 导航。
这与当前 `sources/braid/src/group/provider.rs` 以及 `variants/pi-team-mixed/agents/*/instructions.md` 一致。
Pi Adapter 通过 `--append-system-prompt` 接收该指令，因此渠道存在，缺的是内容。
SVC skill 提供产品/技术设计、验收设计、实现和 V&V 方法入口，但按需目录不等于明确工作流程。
上轮入口修正把具体 variant 的工作约定与 Braid 的通用操作说明一并收敛掉，造成职责缺口。无 PR 只能证明实际未采用，不能证明 Agent 违反了当前明示的工作约定。

拟补充至当前 variant 的成员稳定指令：

> 按产品设计、技术设计、实现计划与必要排障、实现、验收推进工作，各环节深度与任务复杂度相称。
> 在 Issue 中讨论并确定需求、方案及验收依据；创建关联 PR，在 PR 中完成实现计划、排障、代码实现和验收，并根据验收结果整合交付。
> 新发现影响需求或方案时，回到相关 Issue 协作调整。

沿用既有分工，实施计划与预演同样在 PR；需求与方案明确时应在编码前设计验收依据，最终验收则验证实际交付。
这属于当前参赛团队的工作约定，放在 variant 提供的成员指令中，不写入 Braid 通用工具说明，不把 Issue/PR 引入 SVC 的通用方法。
根 Issue 的拆分要求负责本任务的工作划分，成员稳定指令负责每个工作项共享的工作约定。二者通过既有路径分别接入，不增加新的指令层或运行时状态机。
