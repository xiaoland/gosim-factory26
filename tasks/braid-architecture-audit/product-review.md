# Braid 产品需求与机制审查

状态：已完成本轮独立产品审查。只读取源码与既有运行归档，未改实现、未提交、未运行新模型或模拟测试。

最值得调整的是三个默认规则：新增讨论不应仅因完整 Context 哈希变化就替换会话；一次参与不应自动成为整个工作项的持续执行订阅；关闭对象不应天然授予一个额外执行阶段。它们都超出了“可编辑协作记忆”的必要条件。保留 description 编辑后的重建、成员身份、异步回复和 Git 隔离，仍然可以删除这些规则带来的部分复杂度。

第四项需要先作产品决定：本次 `braid local` 执行以什么范围结束。现行规则同时要求关闭后仍可联系、全部对象终态后忽略后续通知；继续补退出条件之前，应先明确本次执行的范围。根负责人空闲五分钟后的进度检查是用户明确要求，本轮保留，不建议因复杂度删除或改成可选能力。

## 按实际影响排序

| 顺序 | 需求选择 → 机制 → 后果 | 证据强度 | 最小方向 |
| --- | --- | --- | --- |

| 3 | close 保证额外 finalization → 对象终态成为执行阶段 → reset、恢复、重新联系都要维护这一特殊身份 | GitHub 8 次，Sheet 7 次 finalization；机制已证实，冗余比例未知 | 普通生命周期通知与当前执行自然收尾，不额外授予一轮 |
| 4 | 本次交付要求全空间终态 → 完成检查与关闭后联系发生例外 → 交付范围与协作空间绑定 | 退出范围是源码事实；开放 backlog 阻断尚未真实发生 | 先定义本次执行的结束信号；保留已要求的根五分钟检查 |
| 5 | CLOSED 等于不再需要完整关联内容 → PR 自动丢弃已关闭 Issue 正文 → 已完成契约可能从工作记忆消失 | 当前 renderer 确定；未证明造成实际错误 | 关联的当前 description 保留；讨论由显式 hide/resolve 管理 |

### 1. 将完整快照相等当作会话有效条件，扩大了 reset 的产品含义

共享对象是当前事实来源，已有 description 被改写时原会话应获知并重建，这是明确需要。但“已有输入失效”不等于“对象有了任何新内容”。历史 [scheduling.md](../../sources/braid/docs/10-prd/scheduling.md) 原本以替换或移除既有事实定义 Hard Invalidation；当前 `LocalObjects::prepare_dispatch`（[objects.rs](../../sources/braid/src/objects.rs)）对每个合法待执行 batch 重新渲染完整 Context，只要与物理会话最初收到的 revision 不等就产生 Invalidate。renderer 的哈希包含完整可见讨论，所以一个普通新评论就足够触发替换。

本轮将每个 applied reset 的 old/new provider ID 配对到归档实际 `physical/*/context.md`，只去除已知历史传输包装并统一末尾空白：

| 归档 | 可配对的 applied reset | 仅严格追加 | 既有内容发生变化 | 内容相同 |
| --- | ---: | ---: | ---: | ---: |
| GitHub | 60 | 40 | 13 | 7 |
| Sheet | 84 | 39 | 37 | 8 |

“严格追加”表示新 Context 以旧 Context 全文为前缀并且更长，未用 LLM 判断追加内容是否重要。内容相同的替换可能承担 unknown 恢复，不能计入无效重建。表中也不声称每个严格追加样本只有一个触发原因；下面两个样本同时有普通新增内容和 generic Invalidate 的完整证据链。

GitHub Issue #4 的 reset `01a0e230-b9b6-74a0-912e-9a805e63b9c1` 于 `09:27:19Z` 应用。旧 Context 为 5,918 字节，新为 6,282 字节，唯一增加的是 comment #7 提醒共享基础已合入、可以开工。其 reset 事件却是“`Issue #4 内容已更新`”。Sheet 根 Issue 的 reset `01a0e209-71fd-7700-a447-1c2c10939fe4` 于 `08:44:24Z` 应用，4,709 → 4,846 字节，唯一增加的是 Braid 自己写的 comment #5“请检查当前工作进展。”。可用的 Wake 最终升级成了会话替换。

最小产品修正是继续使用同一个 reset 协议：已有可见正文、description 或折叠状态被改写时 Invalidate；普通新增 comment、交接和通知使用已有 Wake/引用读取。初次启动和真正 reset 仍渲染完整当前 Context。不能只更新数据库 revision 冒充模型收到了新快照；应改变“什么需要失效”的契约，而不是掩盖差异。也无需让 Braid 判断新内容是否“有意义”，更不需要轻重两套 reset 引擎。

保留强快照相等要求的收益，是每个新 turn 的起点都能展示同一完整投影；代价是普通讨论也反复替换 provider、重送已有内容，并进入通知、自然结束、teardown 和恢复边界。收窄要求后，原生会话保留先前推理，新增事实通过消息和 CLI 到达；不能再声称它的初始 Context 文件永远等于当前全部讨论。实际 token、耗时和质量收益本轮没有测量，40/39 不能直接换算为账单。

可验证标准是：真实会话收到一条新评论后仍保持同一 provider 身份，能读取并处理该 comment；随后修改它已经见过的 description，仍须走原会话通知、自然收尾、fencing、替换，并看到新正文。自身 description 编辑也必须连续工作。关联对象的既有内容失效仍需传播，不能借此取消编辑重建要求。

相同投影必须另行归因。归档的 7/8 次相同 Context 替换不能直接判成多余；unknown 或已失去原生执行句柄时，恢复本来就可能需要相同内容的新会话。只有仍可安全复用原会话、没有恢复义务且没有实际输入失效时，内容相同才应作为不重建的依据。当前契约已经排除同值写入、不可见 HTML 注释和已隐藏正文编辑引起的无效重建，实施应守住这些边界，不能把“新旧字节一样”变成绕过恢复证明的捷径。

主线另已报告：旧 outbox 清理后的 Operational Status 改写为本地 system comment，连续同正文去重且不 emit/notify。因此它没有直接 Wake；但在下一次合法调度时，仍属于完整投影里的新增内容。本项修正应覆盖普通成员评论、根五分钟检查评论和这类状态评论，避免只修某一个来源。本轮未为该新改动扩展取证。

### 2. 关注关系过宽，把讨论参与变成持续执行订阅

普通回复能够到达对方是必要能力；“参与一个 thread 后收到整个工作项未来所有 thread 的更新”是额外产品选择。`subscribe_in` 对创建、comment、有效 @ 都写入 `active=1`，`discussion_changed` 取整个 work item 的关注者和 assignee，`thread_root` 只用于引用而不限制收件人。`deliver_comment_to` 又按收件人负责的对象状态产生 Wake 或关闭后的 direct_contact。因此收件集合直接决定后续模型执行候选，不能把它当作近乎无成本的提示角标。

运行中 GitHub comment #203 只是回复 #180 并点名 `@glm-3` 进行契约终审，却产生 9 个收件目标；#195 回复 #78，正文明确陈述“#5 无行动项”，其回执再次散布到 9 个目标。Sheet comment #123 回复 #120，产生 6 个目标。逐条回执如下，**收件目标数不等于模型执行轮数**：

| 归档 / comment | delivered | queued | unreachable | 总目标 |
| --- | ---: | ---: | ---: | ---: |
| GitHub #195 | 2 | 2 | 5 | 9 |
| GitHub #203 | 1 | 3 | 5 | 9 |
| Sheet #123 | 3 | 3 | 0 | 6 |
| Sheet #145 | 2 | 4 | 0 | 6 |

部分 unreachable 是旧成员已经被改派；保留原身份并明确失败是正确的，不该自动转投新成员。问题是一次历史参与永久扩大了后续收件集合。普通回复、具体 @ 和整个工作项关注在投递上没有足够区分，显式退订也会被后来的 @ 或参与重新置为 active。历史 [publication.md](../../sources/braid/docs/10-prd/publication.md) 已允许 LLM 沉默，所以不应再要求“每次都别回复”来补偿基础层不断分配的阅读工作。

最小产品修正建议为一套结构化收件规则：当前 assignee、同一讨论的参与者、当次显式 @，加显式关注整个 work item 的成员；仍对同一动作去重并跳过作者。评论参与不自动变成全项 watch。显式退订应持续有效，单次 @ 只保证本条到达，不悄悄重开全项 watch；当前 assignee 对本项的责任仍然保留。关闭后的成员依旧能收到这些实际面向自己的讨论，工作项无需重开，具体地址不改变。

收窄会减少跨 thread 的偶然信息暴露；需要全局观察的协调者须显式 watch 或由其它成员 @。这是可见的产品取舍，不能由 Braid 自动分析“谁需要知道”来补齐。无需新增语义分类器、通知代理、优先级系统或另一种隐藏 inbox。

可验证标准是用真实已有讨论关系核对一次普通 reply：同 thread 对方与 assignee 收到，未参与且未 watch 的其它成员不新增执行候选；显式 watch 仍收到全项更新，退订后一次 @ 不重开 watch；已关闭但仍负责原项的成员可以回复实际被寻址的消息。来源空批次回环是另一个已确认实现缺陷，本项只说明有真实输入的通知为何仍可能过宽，不能把数百个历史 terminal_contact 全归到这一产品规则。

### 3. finalization 是历史生命周期承诺，不是关闭对象的必然结果

历史 [workflow.md](../../sources/braid/docs/10-prd/workflow.md) 规定 close/merge 后最多一个 Finalization Turn；当前 Local 契约进一步明确运行中关闭后恰一次 finalization。`prepare_work_item_finalization`、claim 的 `finalization` trigger，以及 terminal 后 sleeping/重新联系路径共同兑现这一承诺。Context reset 还必须保存 finalizing 身份，避免提前退休，于是普通对象关闭与 provider 替换、输入重放发生交叉。

来源 GitHub 有 8 个 completed finalization，Sheet 有 6 个 completed 和 1 个 failed。真实输入已经是普通“请处理 Issue #N”及关闭、评论引用，不是特殊的质量验收操作。例如 GitHub Issue #2 turn `01a0e239-5570-7c23-ac50-6be41d3b4980` 输入只是关闭原因；Sheet 的对应样本还包含其它待处理评论。后者可能有实际价值，所以不能把 15 次全部标成浪费，也不能声称取消特殊身份就会省掉 15 轮。

最小产品修正是让 close/merge 记录状态和普通生命周期事件，当前执行可以自然收尾；真实待处理输入继续按同一投递规则处理，关闭操作本身不额外授予一轮。作者自己已经知道自己关闭了对象，不需要仅因该动作再开启一次执行。外部关闭仍可作为普通通知到达原负责人；完成后有新讨论，仍通过同一成员身份继续联系。

这样保留“关闭后还可以协作”和“关闭不突然杀掉当前工作”，移除的是固定执行机会及其跨 reset 传递的特殊承诺。若用户确实需要关闭后必定再执行一次自检或归档，就应明确该操作的用途；目前 Braid 不得根据 close 推断有新的质量任务。此项收益主要是减少必须维护的组合状态，已有运行不足以证明明显的模型成本收益。

可验证标准是：负责人在真实 turn 末尾关闭自己的项并正常结束，没有新输入便不多出一轮；外部关闭到达时当前执行不被截断；此前接受的实际评论不丢失；关闭后另一个成员的定向回复仍可到达。无论是否采纳产品修正，恢复都必须有旧执行停止证明，不能以删除 finalizing 名称代替安全边界。

### 4. 一次交付的边界与整个协作空间的寿命混在一起

当前 `delivery_complete` 要求根和全部 Issue 关闭、全部 PR 合并或关闭且无 unresolved merge。与此同时，`root_idle_tick` 按用户要求把“根仍开放、无输入与执行、连续空闲五分钟”转成 Braid 评论“请检查当前工作进展。”。Local 一方面不因暂时静止而退出，另一方面全部对象终态后又不让关闭成员的通知延长本次运行。它没有直接理解 benchmark，但已经内置了一套有限执行的结束政策。

两份归档分别有 5、2 条该系统评论；Sheet #5 的完整因果链见第 1 项。GitHub #13 对第一条提醒的答复判断子项处于正常开发周期、没有介入必要。定期检查允许得到“当前无需介入”的结果，这不构成删除该需求的理由；应纠正的是检查评论间接触发 reset 的后果。保留 Braid 身份和可追溯的讨论记录，不伪装成用户消息。

“所有对象都终态”还把未指派的后续想法、暂留 PR 和本次交付放在同一个集合。源码确定它们会阻止该完成分支；本轮未在真实 run 中观察到由开放 backlog 导致的退出阻断。相反，全部对象终态就忽略后续联系，是对持续协作承诺的刻意例外。它可以是合理的单次执行边界，但必须是产品选择，不应继续从队列是否为空反推业务完成。

最小方向是先明确 Local 为调用方执行的一次有限工作：若用户接受根 Issue 表示本次执行范围，可由根负责人明确关闭根来表达结束请求，而不要求清空整个对象空间。停止接受新执行、让已经接受的工作安全收尾、记录确切 delivery commit 后返回；保留对象和 clone 供下一次明确恢复。尚未完成的真实请求如何处置必须公开可见，不能因根关闭静默丢失。`quiescent` 只说明本次执行结束，不代替 LLM 的应用完成判断或宿主验收。这是一项待决定的契约调整，不能仅把现有判断改成 root CLOSED 就宣称完成。

如果保留“所有对象终态”作为本次执行范围，就应明确所有新建对象都属于本次待完成集合，LLM 不应把开放 backlog 放在这个范围内；完成分支之后的新联系留给下一次明确执行。这样也能保持一致，但会限制工作项作为长期协作空间的用途。当前没有证据支持新建通用工作流、阶段机或一套额外服务模式来解决此选择。

辨别证据应来自下一次被授权的真实协作：根负责人已经作出交付决定时，是否有应保留的开放后续项；结束请求之后实际接受的末轮是否自然落盘。根仍开放时五分钟检查继续符合现有要求，已有输入、执行或恢复时不重复提醒。当前已完成快照零调用退出不能证明关闭时正在执行的末轮可以自然结束。交付范围在用户确定边界前不宜直接改动；避免截断已接受执行则是现有 close/merge 契约必须满足的要求。

### 5. 已关闭关联 Issue 的正文不应自动被判为无关

`context::render_pull_request` 根据关联 Issue 是否 CLOSED 决定 `complete`；关闭后只留下引用、状态和关系，description 与讨论均不再完整呈现。这来自历史压缩选择，当前 Local 契约仍保留它。关闭代表工作状态，未必代表需求、接口约定或已接受决定不再对 PR 有用。Braid 在这里用对象状态替 LLM 作了粗略的相关性决定。

建议至少保留直接关联 Issue 的当前 description；可见讨论仍按已有 resolve/hide 决定保留和折叠，不递归展开全部关系，也不添加自动摘要。这样会增加已关闭依赖的输入大小，但描述已是用户/LLM 可编辑的当前契约，移除讨论有显式工具可用。Sheet 实际有 19 个 resolved thread roots 和 1 条带理由的 hidden comment，说明这些能力已被使用，不能为了简单化取消。

本项只有源码边界证据，未从两份运行证明造成实现错误，故优先级最低。辨别标准是关联 Issue 关闭后 PR 的 Context 仍包含当前描述，已 resolve/hide 的旧正文不重新出现；是否改善模型理解需要以后真实任务证据，不能以更长输入自动当作质量提升。

## 应保留的能力与方法边界

| 能力或边界 | 保留理由 |
| --- | --- |
| description、稳定 comment 身份、reply、resolve/hide 理由与历史读取 | 让 LLM 自己维护可恢复的共享记忆；比 Braid 自动总结、自动判断讨论完成更符合职责 |
| 具体人类可读成员名、改派后旧地址明确不可达 | 讨论责任具有历史身份；不能用可复用执行槽代替一个人，或静默把旧消息交给新人 |
| assignee 与执行容量独立 | 负责已关闭工作项的成员仍可回应；空闲不等于解除责任，新任务不必抢父会话容量 |
| 对象与事件同事务、writer fencing、原生 teardown 证明 | 防半次写入和竞争写者；这是跨进程副作用的真实边界，不能当作生命周期“过度设计”删掉 |
| 独立 clone、共享裸 origin、head/base 确认与 merge intent | Git 与 SQLite 无共同事务，成员有未提交工作；保留这些可恢复边界，不强制同步或清理所有 clone |
| provider 适配器拥有各自根进程协议 | Pi 内部子代理及其清理由 Pi 负责；宿主提供离线停止事实，不把进程树管理塞进 Braid |

用户的一般性工作流程包含需求/设计与实现的方法分离，并通过 PR 交付；应保留这一方法，不把角色和人员数量强制写死在运行时。PR 可由当前成员推进，也可明确指派另一成员承担实现或整合责任，不要求每个 PR 都新建 Agent。

当前真实来源中 GitHub 9 个 PR 有 7 个未指派，Sheet 11 个 PR 有 10 个未指派；Issue 成员曾提交代码，个别整合 PR 又有独立负责人。这些观察只证明现状，不能证明工作方法正确，也不能据此推翻用户希望的方法分离。产品文档应分别说明协作方法与运行时能力，是否由同一 LLM 承担前后工作由具体任务决定；本轮不主张取消 PR 指派、PR 交付或设计讨论。

## 待用户决定的最小集合

| 决定 | 本轮建议 | 保留现状意味着什么 |
| --- | --- | --- |
| 是否要求每个 turn 的最初完整 Context 必须等于当前完整投影？ | 只对既有内容失效重建，普通新增信息用 Wake | 接受普通讨论导致额外 provider 替换；不能把这些替换全部视为实现 bug |
| 一次回复是否意味着持续关注整个 work item？ | 默认按讨论收件，全项关注显式操作；尊重退订 | 接受跨 thread 传播及关闭成员的额外阅读，仍不能强制公开回执 |
| close 是否承诺额外执行一次？ | 自然收尾和普通关闭通知即可 | 必须继续维护 finalization 与 reset、恢复、重新联系的组合语义 |
| Local 的结束范围由什么表达？ | 明确一次有限执行；根关闭可作为候选结束请求；保留根五分钟检查 | 全部对象属于本次执行且必须终态，不能留下仍开放的后续项 |

前两项有最强直接运行证据，可以先决定。第三项影响架构复杂度但不宜夸大节省；第四项改变外部执行契约，应先决定再实现。第五项可作为低优先级 Context 规则校准。上述建议均不要求 Braid 理解任务语义、bench 结果或 Pi 内部子代理，也不以新增管理层替代 LLM 自主协作。
