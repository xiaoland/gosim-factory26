# ARC 官方运行观测接入方案

这是用户已认可的公共 ARC 接入设计。当前实施状态、验证范围和原始调查入口见 [packet](packet.md)。本方案接续实验设施已有的 run、制品关系和原始 OTLP 保存能力。

## 用户得到什么

Harness 作者取得一份可随参赛包分发的上报工具和说明，通过自己的命令、工具或 skill 机制交给 Agent。实验操作者使用同一个冻结包在本地和官网运行。诊断者从一次 run 进入，能区分工具是否提供、是否实际调用、官方追溯数据是否收到，以及证据采集是否成功。

需求与实现、测试之间的关系由 Agent 或 Harness 明确上报。实验设施保存这些声明及来源，不从文件名、OTLP 或 Git 提交猜测关联。上报的测试状态是生产者声明，官方评分由评测器产生，两者在查询中分开呈现。

```text
任意 Harness / Agent
  ├─ 自选语义的 OTLP ───────────→ 通用 lab Collector 与原始存储
  └─ ARC 上报命令 → 官方 SDK ──→ Runner 的 .arc 文件
                                      ├─ 官网后端 → Run detail
                                      └─ ARC 采集与查询 → 本次 run 的证据入口

官网运行另经现有 API 采集响应；API 响应与本地文件各自保留来源。
```

通用 lab 不导入 ARC 业务对象，不要求 Harness 使用这份工具，也不把官方图转成一套强制 OTLP 字段。已经直接使用官方 SDK 的包仍可被采集。

## 上报工具与接入方式

ARC 适配层提供 `arc-runtime.pyz`，使用 Python 标准库 zipapp 封装固定版本的官方 SDK、一个薄命令入口、使用说明和来源记录。官方 Runner 已使用 Python；工具无需现场 pip 安装或联网下载，也不依赖 Factory、Pi、Codex 或 Braid。来源记录包含官方获取地址、SDK 版本及源码摘要，导出结果另有内容摘要。

拟定入口为：

```text
python -m lab.arc_bench runtime export --output <arc-runtime.pyz>
python3 <arc-runtime.pyz> guide
python3 <arc-runtime.pyz> traceability <官方方法名> --json-file -
python3 <arc-runtime.pyz> events <官方方法名> --json-file -
```

JSON 通过文件或 stdin 提供官方方法的参数，帮助信息取自所封装 SDK 的实际签名。入口只公开本任务需要的追溯读写和状态事件，不提供任意 Python 方法执行。后续获授权的 `publish-history` 是独立、受限的 Git 历史发布动作：由 Harness 指定源仓库及提交引用，工具导入真实提交祖先并调用官方刷新信号；它不开放任意 Git 操作，也不从提交推断需求关系。需求、接口、测试等字段仍以官方 SDK 为准，不维护第二份业务 schema。

Harness 作者在自己的构建过程中放入该文件，并将其位置和说明交给 Agent；SDK 工具在最终清单和 ZIP 冻结之前纳入。设施不替外部包插入系统提示、不重排依赖和目录，也不复用现有 `instrument_entry` 充当通用安装器。已有本地入口观察包装保持自身职责。

上报能力由最终包内实际材料和调用情况体现，不新增一个可能与包内容脱节的全局“已启用”布尔值。包内工具存在不证明 Agent 收到或遵守了使用说明；没有声明的第三方包，其内部接入状态显示未知。新旧包都可以运行，观测缺口可见。

Competition 当前强制要求 Factory 的 `package-manifest.json`。为使入口能消费其他 Harness 的官方格式包，通用身份采用冻结 ZIP 摘要；仍检查必需入口及安全的归档路径。Factory 清单存在时继续核对，缺少时不再成为额外准入条件；不替外部包生成或改写清单。这里的保证是载荷身份和本地已知的格式约束，不冒充完整的官网资格判定。

## 运行路径、并发与失败

工具使用 Runner 提供的 `ARCBENCH_*` 路径；独立使用时允许显式输出目录。启动时解析绝对路径，没有 Runner 路径也没有显式目录时返回具体配置错误，避免子代理切换 worktree 后把数据写进自己的当前目录。官方单独提供的 events/traceability 路径仍受尊重。

同一次 run 的所有 Agent 共用官方追溯目录；不同 run 使用各自 Runner 工作区。工具对同一追溯目录中的 SDK 调用使用短暂的文件锁，覆盖读、改、写和相应事件，不锁住模型调用或整个 Agent。所有并行写入者需使用同一入口才能得到这项保证；直接绕过它写 SDK 的进程不受该锁保护。同一记录 ID 被不同 Agent 更新的业务冲突仍由生产者协调，工具不建立分支合并机制。

SDK 当前会将读取失败的表当作空表。入口在 SDK 调用前检查已存在的官方表是否可读、是否为 JSON 对象，错误时保留原文件并返回具体路径及原因；不复制业务字段校验，也不自动重建或清空 Runner 已播种的数据。

命令以退出码和结构化结果报告 SDK 成功或具体异常，并把方法、时间、工具身份、实际目标路径及结果写入 `.arc/runtime-reporting/operations.jsonl`，不重复保存提示词或整个业务图。辅助记录写入失败应单独报告；SDK 已完成的写入不能被冒充为未执行。SDK 多文件操作不具备事务保证，失败可能已产生部分效果，因此不自动重试整条操作或回滚应用。

使用说明要求按实际发生的工作更新关联，保留官方需求 ID；子代理通常上报负责节点，整次 run 的生命周期由拥有该生命周期的调用者报告。入口不自动宣布实现完成、测试通过或整次 run 完成。进程被杀或磁盘故障可能使调用记录不完整，没有记录不等于没有调用。

## 采集与用户查询

采集默认工作，不以上报工具是否存在为前提。复用现有 ARC 采集器、运行结果和通用 `artifact_paths`/制品索引，不新增常驻 collector、另一套数据库或通用插件协议。

| 来源 | 保存与观察方式 | 能保证的范围 |
| --- | --- | --- |
| 本地 Runner | 保存 `.arc/traceability` 下原始表、runner events，以及存在的工具调用记录；适配器收尾链接证据，运行中查询直接读取当前文件。 | 保存观察到的文件内容与路径；运行中跨文件读取不承诺事务快照或完整变更历史。 |
| 官网 | 复用现有日志、traceability 和 commit-history 接口；在现有监控周期、终态及显式 collect 时采集。 | 保存 API 实际返回的字段和观察时间；不把整理后的日志摘要当作完整 SDK 事件。 |

官网追溯的每次采集保留成功响应或具体失败记录，包含时间和来源。现有顶层 `traceability.json` 可继续作为最近成功结果的兼容副本，新查询同时显示最近一次采集结果和最近成功时间，避免把旧成功数据冒充为当前状态。沿用现有监控间隔，不增加另一套定时器，也不根据日志摘要推测遗漏的 SDK 事件。

失败保留已有 Client 提供的 HTTP 状态和响应内容，再生成有界摘要，沿用现有凭据脱敏；不能只剩异常类名。单个端点或文件失败不阻止独立证据保存，也不抹掉运行结果。未确认官网有自定义文件下载接口，因此不承诺能取回托管工作区内的工具日志；无法取得时明确显示不可取得。

统一的 ARC 查询拟为 `python -m lab.arc_bench traceability <run或官网task记录目录>`，支持节点筛选和 JSON 输出。默认只读保存的证据，网络刷新沿用显式 collect。通用 run 查看通过已有制品链接到该查询所用的证据，不新增一套必须启动的 Web UI。

查询分开回答三个问题：

1. **提供了什么？** 冻结包及工具身份；可验证存在、声明存在或未知，不推断 Agent 一定使用。
2. **收到了什么？** 实际表、事件和可取得的调用结果，列出需求关联和原始来源；空表是事实，不能直接归因为未接入。
3. **采集到了哪里？** 最近尝试、最近成功、错误、缺失来源和观察时间；HTTP 成功但返回空数据与接口失败明确区分。

仅评测旧应用时，追溯入口指向原生成 run；本次评测拥有自己的评测证据。复制进来的旧图不得呈现为回放 Agent 新产生的开发过程。没有已保存来源关系的历史记录不补造关系。

## 维护归属

公共工具源码、使用说明、官方 SDK 副本及其来源记录放在 `lab/arc_bench/agent_runtime/`。SDK 保留上游布局与已有版权/许可文件，入口通过公开高层 API 调用；导出器排除 starter 中的应用模板、参考实现及测试内容。新建的 ARC `traceability.py` 负责证据汇总与查询，采集接线留在现有本地和官网适配代码中。

运行后文件留在各自 Runner workspace 或现有托管 task 目录，仍由该次 run 的证据索引连接。工具不在每个 variant 下复制实现，也不新建全仓库共享的追溯数据库。公共说明随工具分发；实际 Harness 的接线说明属于其自身材料。

## 完成条件与阶段边界

方案的接口和职责已收敛，公共能力已按授权落地。具体 Harness 的接入仍是消费者工作，需明确纳入其实施范围；公共工具本身不会使旧参赛包自动上报关联。

设施验收先使用已存在的真实记录：所查五份官网成功空响应必须呈现为“采集成功、关联为空”；本地嵌套原始表应可找到；历史来源与本次评测必须可区分。这些可以证明读取和诊断行为，不能证明新工具已在官网显示成功。

完整接入验收需要另行确定并授权真实运行：固定工具和 Agent 包，观察实际 Agent 上报、并行子代理共享写入，以及官网 Run detail 与保存响应的对应关系。官网没有提供的细节只能保持未知；实际验证一个 Harness 不证明所有 Harness 已适配。若要求两种 Harness 的实证互通，应在实验矩阵中明确第二个消费者，不顺带恢复已停用的基线矩阵。

不以伪造需求关联、修改历史运行或自动重新生成应用补齐验收。本次只构建 WSL 隔离目录中的工具产物，并读取既有记录；没有运行新模型、评测、上传官网或提交代码。
