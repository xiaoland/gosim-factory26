# ARC 公共接入接口技术方案

本文记录已获授权并落地到工作区的接口设计。当前代码、静态验收与剩余运行证据见 [packet.md](packet.md)。

## 职责与生命周期

variant 自己实现薄接线，选择如何装入工具、把能力交给 Agent、何时上报、选哪个仓库及引用，以及如何重试或保留工作区。轮询、线程和原生事件回调属于消费者选择。公共组件不接管 Harness 进程，不解释 Braid、Pi 或 Codex 私有状态。

ARC 公共组件负责一次明确操作：解析 Runner 路径，调用固定 SDK，发布指定 Git 历史或发送通知，返回完成状态与诊断。通用 lab 保存外部执行和自选语义的 OTLP；ARC 采集器负责官方文件及接口响应。需求、实现和测试关系来自实际工作者，不从 Git 或 OTLP 推断。

接口中立性取决于不同 Harness 能否独立通过相同接口接线，不以 variant 内代码行数或是否使用线程判断。

## 分发与稳定入口

继续分发自包含 `arc-runtime.pyz`，复用固定官方 SDK，不增加服务或安装器。跨 Harness 的稳定边界是 CLI；内部 Python 模块和 `__main__` 不属于承诺接口。variant 通过公开导出命令取得工具并纳入最终包，自行决定原生指令和工具暴露方式。

```text
python -m lab.arc_bench runtime export --output <文件>
python <工具> guide
python <工具> version --json
python <工具> methods --json
python <工具> traceability <方法> --json-file <文件或-> --json
python <工具> events <方法> --json-file <文件或-> --json
python <工具> notify-history [--preview] --json
python <工具> publish-history --source-repo <仓库> --ref <引用或OID> [--preview] --json
```

保留现有命令、参数及默认输出；新消费者通过 `--json` 获取 v1 结果协议，旧消费者可按原方式调用。`version --json` 分开报告包装接口版本与 SDK 来源版本；`methods --json` 报告公开方法及签名。SDK 升级时显式核对公开方法，不因上游新增 public 方法自动扩展入口。业务参数沿用固定 SDK 的字段，不创建第二套需求/接口/测试模型。

同一接口主版本只作兼容扩展。方法删除、参数含义改变或结果类型改变需要新的主版本；冻结包保留原工具，不被设施现场替换。

所有运行操作接受现有 `--output-dir`。优先级为显式目录、SDK 支持的 ARCBENCH 输出/project/template 环境变量；无配置时明确失败，不默认为 Agent 当前 worktree。events 与 traceability 路径尊重各自官方变量，并在结果中返回解析后的绝对路径。公共工具不搜索 `.factory26`；工具自身路径由消费者提供。

## Traceability 与状态事件

`traceability` 接收官方参数并调用固定 SDK；`events` 提供明确列出的状态及刷新方法。节点 ID、关系及证据由调用者提供，工具不自动宣布测试通过、实现完成或整次运行结束。

同一 store 的读改写仍受文件锁保护，写前检查已有表的可读性，避免上游将损坏数据当作空表覆盖。业务校验复用 SDK，不复制大套 schema。锁只覆盖通过本工具的调用，不能承诺与直接 SDK 写入者共同串行。

Git 和追溯操作可能写入同一事件文件或操作日志。实施时按实际目标路径共享短暂追加锁；SDK 写调用还保留 store 锁，统一采用 store/目标仓库锁在前、共享追加锁在后的顺序。Git 对象传输不占用事件追加锁。多文件 SDK 操作没有事务保证，失败后不自动重放整个方法。

## 两种 Git 使用方式

| 操作 | 适用布局 | 行为与所有权 |
| --- | --- | --- |
| `notify-history` | Harness 直接在 Runner 项目目录维护仓库 | 读取该目录仓库当前 HEAD，发送官方刷新信号；不初始化仓库、不修改 refs、HEAD、索引或应用文件。 |
| `publish-history` | Harness 在内部仓库开发 | 将指定提交及祖先导入 Runner 项目目录的受管仓库，设置展示引用和 HEAD，再发送刷新信号；保留真实 OID。 |

原地通知要求项目目录确实是仓库的工作树根，不能误读上级仓库；合法 Git worktree 形式也应支持。缺少仓库或尚无提交时返回具体错误，由调用者决定何时再调用。原地模式展示当前 HEAD，不承诺让官网展示另一个未被选中的分支。

跨目录发布在开始时把 `--ref` 解析为一个 commit OID，后续传输、引用更新和结果都使用这个 OID。最终应用已冻结时，variant 应直接传该 OID，避免交付和观测分别解析活动分支。导入不依赖源工作区当前文件；源仓库被清理后，目标应能独立读取已发布历史。

目标不存在仓库时创建受管仓库；已由工具管理时更新展示引用。已有由 Harness 管理的仓库不被隐式接管，应由消费者选择原地通知或调整目的地。只发布选定提交的祖先，不同步全部 refs、未合并分支或未提交文件，不合成提交。

发布仅修改受管 Git 元数据，不 checkout 应用或修改索引。移除现有 `--preview` 分支里的 `read-tree`；该标志只要求官方刷新预览，调用者负责确保应用已就位。提交历史与应用文件的发布时间可以不同，一次历史通知不意味着源码文件已实时交付。

每次显式调用都尝试发送刷新信号，包括目标已经是相同 OID 的情况；结果分别报告历史是否改变和通知是否写入。这样前一次 refs 更新成功、通知失败时，可以重试通知。是否减少重复调用由 variant 决定，公共组件不建立定时器。

目标仓库操作串行；外部源仓库由 Harness 管理，不被公共组件长时间锁住。源引用在解析后变化不改变已选 OID；对象在传输前不可用则返回 Git 错误，不自动改选提交。

## 结果、失败与诊断

v1 机器输出为一个 JSON 结果，包含 `api_version`、`operation`、`status`、实际 `paths`、操作 `result`，以及存在时的 `error` 和 `diagnostic_error`。有效操作成功或执行失败都输出该结果；命令语法错误使用退出码 2 和 CLI 错误说明。退出码 0 表示所请求的操作与通知已完成，1 表示失败或部分完成。辅助日志失败单独呈现，不把已完成的主操作改判为未完成。

Git 的 result 至少给出选定 OID、模式、历史是否改变、历史更新是否完成、刷新信号是否写入。结果与诊断应足以定位当时来源和目标。Traceability 出错时若 SDK 已开始写入而无法精确判定副作用，应标明可能部分完成；不能声称没有写入。客户端未取得成功返回也不证明工具没有执行。

“通知已写入”只表示 SDK 文件操作完成，不代表官网收到、渲染或保留数据。官网 HTTP 200 与 `workspace_unavailable` 分别表达请求成功和内容不可用。

沿用 `.arc/runtime-reporting/operations.jsonl` 记录操作、时间、版本、路径、阶段和结果。保留 Git 退出码、stderr 及可诊断输出后再生成摘要，不只保存末尾 2000 字符。日志和 stdout 使用同一结果含义。SDK 可能先写表再发信号，公共组件不自行回滚。重试、现场保留和工作区删除由消费者决定。

## 官网采集与证据查询

沿用 Competition、Playground 的监控周期和采集入口，与包内是否提供工具无关。每次采集保留来源、时间、原始值或 HTTP 错误；终态不可用不能抹掉运行中取得的提交列表。

查询同时呈现最近观察及最近可用值的时间和来源，避免旧列表被误认为当前终态读取结果。没有成功历史时呈现未知或不可用，不通过空列表推断没有提交。API 响应与本地 SDK 日志保持各自来源，不伪装成端到端确认。

## 实施范围与顺序

1. 在现有公共入口和随包说明中固定 v1 CLI、公开方法及结果契约，保留旧调用形式。SDK 原始文件继续保留来源，不为包装逻辑修改上游文件。
2. 实现原地通知与跨目录发布的分工，统一部分完成、刷新重试、锁和原始诊断行为。必要时把 Git 操作抽到同目录局部模块，不建立插件框架。
3. 由 mixed 自己迁移薄接线：构建使用公共导出命令，运行读取 v1 结果，最终传冻结 OID，保留原始失败信息。轮询与清理策略仍由它持有；不批量修改停用 variant。
4. 核对官网最近观察与保留值的查询表达，更新现有运行/技术说明，明确新契约的实现状态。通用 lab 和独立 Braid/SVC 源码不承担这次 ARC 接口调整。

本轮规划不把需求/实现/测试的具体 Agent 上报工作流一并实装。该消费者工作需明确谁在何时提供哪些真实关系；公共接口先保证它可以独立完成接线。

## 验收与尚未证实的事项

实施后的静态审查核对公开命令、结果、路径和调用依赖，重点审查两种仓库布局、重复发布、通知失败后的再次调用，以及最终 OID 与交付身份一致的控制流。依项目规则，不新增或运行 Factory 测试、模拟集成、包 smoke 或换名探针。

真实验证使用后续获授权的官方运行，冻结包、需求、凭据模式和实验终点。mixed 可以提供跨目录模式的实际证据，不能据此宣称原地模式或所有 Harness 已运行验证；原地模式应结合实际采用该布局的消费者验证，不为验收恢复停用矩阵或伪造 Agent。

验收区分工具成功、本地文件存在、官网 API 取得数据及 Run detail 实际展示。历史 `workspace_unavailable` 无法回答终态保留问题，保持这一限制。官方接口、真实实验范围或消费者需求变化时再调整方案，不用未经证实的后台行为补齐设计。
