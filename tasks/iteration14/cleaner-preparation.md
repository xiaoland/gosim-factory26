# I14 cleaner 实施准备预演

2026-10-02。本页细化已认可的[机制方案](mechanisms.md)，只涉及 cleaner，不扩展 reviewer、浏览器工具或实验设施的范围。本次只读核对生产代码和已安装 Pi 0.85.1，未修改源码、运行测试或发起模型调用。以下是实施建议及尚待取得的真实反馈，不是能力已经完成的声明。

结论是可以按已批准边界实施，采用按需的一次独立模型请求，返回声明式维护批次，并在父工具返回前短事务提交。这与已认可机制一致。正常结束后一次提交有必要：它让 description 与讨论整理作为完整结果生效，避免清理过程触发自身的 Context 重建，也避免失败后留下半份整理。它不要求跨模型执行的数据库事务、第二个常驻 runtime 或通用 fork 框架。主线已取得实现、基础验收与 I14-0 的授权；本页不代替该轮冻结配方，也不据此执行模型运行。

## 调用、继承与正常结束

提交发生在 cleaner 已结束、父方 cleaner 工具尚未返回时。此时父方 Braid turn 仍应处于运行中，可以沿现有 writer 校验提交。不能在工具内部等待父方的 agent_settled，也不能等父方工作 turn 结束后再借原 writer 提交：前者会自等，后者不满足当前写入条件。cleaner 的完成、父方工具返回与父方会话结束是三个不同事件。

原生入口应记录本次 toolCallId、父会话身份和当前有效分支。Pi 在执行工具前已保存产生该批工具调用的 assistant 消息，因此 getBranch() 此时包含 cleaner 自身尚未结清的 toolCall；同批较早工具的结果也可能已经保存。不能把这个尾部直接交给新的模型执行。

建议按本次 toolCallId 定位发起调用的 assistant entry，以它之前的 branch leaf 为继承截点，调用纯 parseSessionEntries/buildSessionContext 投影完整前缀。这样继承的是父模型发起这批调用时已经拥有的有效历史，保留此前压缩后的工作记忆，不包含本批仍未结清的调用。当前维护请求及最新对象快照另行加入 cleaner 输入，并说明它们晚于历史快照；不伪造“cleaner 已完成”的父方 toolResult。若不能找到本次调用或完整截点，返回具体错误，不静默换成无上下文模式。

使用工具的原生 executionMode: sequential 可让包含 cleaner 的当前工具批串行执行，避免为了这次调用另建全局锁。它不能阻止外部成员或原生后台工作的修改，因此提交前提仍必要。后续合法写入仍可改变对象，cleaner 不持有返回之后的独占编辑权。

共同要求、cleaner 职责和历史材料应分开装配。不能将父方 getSystemPrompt() 原封不动当成 cleaner 的 system，其中包含实施角色、工具能力和配方中的执行任务；也不能只删掉 system 就丢失语言、模型通道等共同约束。共同材料应沿已有独立文件和配置提供，cleaner 职责只说明维护操作与资料优先级，不解析或内联 SVC 技能。

首版使用一次独立模型请求返回声明式维护结果。负责人只触发维护，不给出具体 edit plan。已有继承历史和本次完整维护快照时，不给 cleaner 提供 shell、代码修改、Braid 写命令或后台工具；无需第二个 Pi AgentSession、工具写入拦截或多轮暂存协议。“一轮”就是该独立请求的完整响应。

实际 Pi 0.85.1 已有 ctx.modelRegistry.complete(model, context, options)，直接委托当前 model runtime；扩展上下文还提供 model、thinkingLevel 和 AbortSignal。首选已配置可用的 GLM-5.3-Flash，由 variant 显式选定注册模型，不能绕过 registry 自行拼 API 或读取凭据。调用保持同一 gateway 和所属 Braid session 的预算归属，保存 AssistantMessage 返回的 usage、stopReason 和实际模型身份；缺失使用量时如实记缺口，不填零。模型不可用时保留具体错误，不静默切换供应商。本轮使用自有 API、不使用 ARC 的费用选择归主线冻结配方。

只有完整响应的 stopReason 为 stop、不含工具调用、结果通过结构校验且取消尚未生效，才能进入提交。pending、length、toolUse、error、aborted、deferred 和只有部分文本均不提交。“已有工具结果结清”约束继承前缀，不要求尚在运行的父方 cleaner 工具先返回结果。该实现没有第二个 AgentSession，因此不等待独立 agent_settled；既有 agent_settled 事实只用于辨别父方生命周期，不能另建一套结束信号。

继承来源是原生生效历史，不宣称等于经过所有 context 扩展变换后的最终模型 payload。禁止对 live 来源调用 SessionManager.open/forkFrom，也不调用会替换主 runtime 的 fork/clone。来源文件和主会话身份必须保持不变。

## 维护结果、来源前提与提交

结果模型不负责选择执行身份、目标工作项或来源版本。原生入口取得这些事实，Braid 从当前 writer 确定本次拥有的 Issue/PR；cleaner 只决定整理内容。建议一次调用保留下列事实。

| 部分 | 最小内容与来源 |
| --- | --- |
| 来源 | 原生入口生成的维护操作 ID、父 session/turn 和 native 截点；Braid 返回的工作项、成员及指派身份、完整 description、参与整理的讨论和生效需求背景。 |
| 待应用结果 | 可选的最终 description，以及 hide 的 Comment ID/理由、resolve 的讨论根 ID。缺省 description 表示不改，显式空字符串仍按现有正文契约处理。 |
| 提交回执 | 操作 ID、结果内容摘要、来源前提摘要、发起成员、实际 changed/no-op、受影响对象/讨论与事件身份。它和对象/事件同一事务提交。 |

维护范围仅为当前工作项的 description、hide 和 resolve；不顺带加入删除、指派、关闭、合并或源代码修改。ID 必须属于该项，resolve 仍只接受讨论根。结构校验应拒绝未知动作与矛盾结果，不用 shell 命令文本表示待执行动作。模型给出的“完成”字段不证明正常结束，正常结束由执行入口判断。

来源前提应覆盖实际供给 cleaner 的维护资料，不能只验证将要写入的记录。例子是 PR 的关联 Issue description 在调用期间改变：即使 cleaner 只准备 resolve PR 讨论，它的判断依据也可能过时。最新对象快照应明确优先于继承历史中的旧对象内容。

首版可对固定维护快照作一次稳定摘要比较，内容包括原始 description、供给的评论正文与身份、线程关系、可见性、resolved_through，以及实际供给的关联需求版本。新回复、编辑、删除、hide、resolve 或相关需求改变均应使来源前提失效。复用已有记录计算摘要，不新增第二份可编辑正文或持续维护的修订权威。正文必须保留未投影的原文，不能对 details 折叠后的文本计算覆写前提；普通 context_revision 也不能未经核对就作为完整维护快照的替代。

这比让模型声明精确读集合、逐字段合并或自动重试简单，代价是无关讨论变化也可能使整批作废。首版接受这一可见代价；只有真实拒绝频率影响收益时，再考虑缩小前提范围。过时结果保留待应用产物及具体冲突原因，本次不提交，后续显式调用重新取材。

resolve 不能直接拿提交时的新 max(comment_id) 代替已观察截止。若整个讨论快照前提仍成立，可调用现有事务内规则得到同一截止；否则整批拒绝。hide 保持原有“隐藏本条及现有、未来后代”的语义，快照校验只能防止误吃掉提交前未观察的新回复，不能把未来后代排除在 hide 之外。不要承诺“所有 hide 永远只影响已观察内容”。

一次短 SQLite immediate transaction 应按下列顺序完成：

1. 查询操作 ID 是否已有提交回执；相同结果返回原回执，不重复效果或事件，同 ID 的不同内容拒绝。
2. 沿现有 writer 检查运行、session、turn、assignment 和 reset 屏障；另外确认 writer 的工作项与本次维护目标相同，且仍属于捕获的来源执行和指派。
3. 重读并比较来源前提，校验整批操作，再计算最终对象状态与实际差异。
4. 更新正文和讨论，按现有规则写入活动、失效及投递义务，最后保存提交回执并 commit。

不从模型推理开始持有 SQL 事务或写锁，不由扩展逐个调用 edit/hide/resolve 来模拟原子提交。现有对象方法可以抽出被普通 CLI 与维护批次共用的事务内函数；不需要通用事务语言或可执行操作编排层。

正文按提交前原文与最终原文比较。纯 HTML 注释变化继续采用现有不触发重建的规则；普通重排、折叠区正文修改等仍按现有有效正文比较处理，不增加模型判断“语义相同所以免 reset”。一次维护中的 A→B→A 最终无有效正文差异，就不发 Invalidate；最终有差异，每个应受影响的对象/当前责任只产生该次净变化所需的失效。Issue 变化仍须传播到实际展开它的 PR，不能把“一次提交”误解为全系统最多一条 Invalidate。

hide/resolve 各自的对象事实、讨论根、截止和作者仍须保留，不能为了减少通知而丢失语义事件。合并输入继续使用既有队列和去重规则，不增加维护专用通知队列。事件与对象一同提交后才允许被派发；无需再建立一个“等模型结束才发通知”的外部 outbox，因为提交本来已经发生在 cleaner 结束后。负责人通过工具回执取得整理结果，不额外创建一条会再次唤醒协作者的完成评论。

writer 校验不能复用“某成员仍是负责人”这样的宽条件。来源执行进入 teardown、改派或取消责任后，旧身份不得提交；Context 失效等待期是否仍有写权限，沿现有 writer 契约处理，来源变化另由快照前提阻止。无需增加新的公开 cleaner 成员或安全权限平台。活动记录可以保留发起成员并明确 origin 为该维护操作，避免把自动整理记成没有来源的 external 写入。

失败、取消、中断、Unknown 或无效结果均不进入提交。父方 AbortSignal 要传入独立请求，进入提交前再次检查。提交事务是效果的确定边界：若取消先被观察，就不开始提交；若事务已提交后才取消或丢失输出，事实是“已提交”或“提交结果未知”，不能报告“已取消且未修改”。没有必要为这条边界添加反向补偿。

提交命令失败或回执丢失时，按操作 ID 查询持久回执，不自动重跑模型或重新应用一批操作。查不到回执但原提交进程仍可能运行时，仍然是未知；不能据此启动竞争提交。待应用结果和具体错误作为不可编辑的本次证据保留，不建立自动接续的 cleaner 待办。

## 实施切分与判别性反馈

| 有界实施面 | 具体工作与交接物 |
| --- | --- |
| Braid 对象提交 | 在 objects/CLI 边界加入固定工作项维护快照与原子 apply；复用事务内正文/讨论事件逻辑，保存最小操作回执。先冻结输入、结果和错误回包契约。 |
| Pi 原生扩展 | 定位完整历史截点，装配独立职责与快照，执行选定的一次调用，保存待应用结果，正常结束后调用 Braid apply，再给父方返回回执。它只消费前一项接口，不接管 assignment 或 reset 调度。 |
| I14 variant 与材料 | 只在相应 I14 variant 接线入口、职责和模型材料，保留预算归属与 usage；I13 冻结包不变。共同基线不加载 cleaner。 |
| 主线集成 | 核对投递、重建和 writer 撤销仍沿既有契约，并将确认的产品约定回归 Braid PRD/TDD。主线决定最终源码切分和开工范围。 |

反馈应区分静态可行、无模型实际操作和真实模型集成，不建立测试、模拟 session 或包 smoke。当前没有执行以下检查。

| 要关闭的不确定性 | 最低成本且真实的反馈 | 何时需要修订 |
| --- | --- | --- |
| 投影会不会带入悬空调用或改写父历史 | 对保全的真实 Pi 会话，通过生产投影入口导出选定调用前缀，保存 leaf、消息身份及来源文件前后摘要；只读检查工具配对和最近压缩被正确采用。编译扩展与 Braid。 | 若只能补造成功 toolResult、遗漏必要的压缩上下文或写回 live 文件，应先修正截点/读取实现。编译通过本身不证明继承正确。 |
| 正常 cleaner 能否在父工具返回前完成原子提交 | 第一项单独批准的有限 Pi 实验只需一个工作项和一次有实际正文/讨论整理的调用，核对来源截点、独立结束、apply 回执、父方 toolResult、对象及事件顺序。 | 父方提前结束导致 writer 无效、清理期间对象已写入、无实际净变化却触发重建，均说明边界实现需要修订。 |
| 过时结果、取消与旧身份是否留下半份效果 | 在获授权的实际调用中，取得快照后通过正常对象入口加入新回复或改变正文，再观察 stale 回执和原始对象；对已有真实身份取得的结果，可在责任撤销后用旧身份执行实际拒绝路径。取消反馈同时检查是否已越过提交边界。 | 新回复被折叠、正文被覆盖、旧身份仍修改数据，或已有回执却报告未提交，应停止扩大模型实验。 |
| 净收益是否值得下一轮 | 在既定 cleaner 对照中汇总负责人整理量、cleaner 使用量、reset 和重读成本，并定向检查被改写决定/讨论。使用已有原件，不新建遥测平台。 | 整理成本转移后总成本或错误率更高，则调整触发/作用域；不能先靠增加重试、后台运行或免 reset 特例弥补。 |

无模型阶段不能为制造成功证据而伪造 running turn、assignment 或 provider identity，也不应新增 --external 提交旁路。有效负责人提交的正路径和父方取消交互，必须留到明确授权的真实 Pi 集成运行；检查旧身份被拒绝不能冒充正路径已验收。

当前还需落实的是单次 registry 调用所需消息转换与 options、模型预算/usage 归属，以及共享要求与 cleaner 职责如何从现有材料装配。已有调用接口无需另行发明。其余边界可据以上建议直接形成接口，不需要额外用户选择或全平台设计。
