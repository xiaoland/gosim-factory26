## 接线收敛与可执行解除路径

冻结的 `budgeted-pi` wrapper 会先注入 `native-managed.mjs`，再注入 timing、model-budget，随后才是 `pi-subagents`、`pi-background-bash`、observer、FFF、Context7、Exa；I14-e2e 的显式顺序没有第二个注册同名 `bash` 的扩展。`pi-subagents`、native-managed、model-budget 均未注册 `bash`，所以普通调用的实际 handler 是 PBB 的 `pi.registerTool({name:"bash"})`，PBB 在加载顺序上覆盖 Pi 内置 bash；这与 ZIP 中 `bg019/bg020` 的返回格式相互印证。

native-managed 只在 PBB 的 `runPbbBash` 内包裹 `spawn("bash","-lc",...)`。`spawnManaged` 发布 start receipt 的同步等待有明确 10 秒上限；它发生在 `runPbbBash` 建立之后、PBB 的 30 秒 `Promise.race` 之前，资源准入失败会立刻 resolve error。因此静态链路不能支持“resource helper 无限等待把 30 秒 timer 卡住”的解释。PBB 的 timer 本身是普通 Node `setTimeout`（仅 `unref`），没有同步资源调用包住它。

本冻结接缝存在一个更窄的可疑点：managed patch 将 child 的 `close` listener 改为 `async`，先 `await managedRuntime.finishManagedProcess(child, ...)`，然后才调用 PBB 的 `finish(...)`。也就是说，进程收到 `timeout`/信号后，PBB 不会先交付 tool result，而要等待 native ownership 的终止核验完成；若 `records()`、`/proc` 扫描、进程组核验或资源证据进程在压力/退出竞态下不返回，原始 tool call 可以保持 pending。当前源码中的核验循环有秒级上限，但 ZIP 没有这次 close 的 terminal receipt，不能证明它是否进入或卡在此处。这比“扩展未加载”或“timer 被普通资源等待卡住”更具体，但仍是待现场验证的竞争根因。

因此可行的现场解除步骤不是重试网络请求，而是由 root 读取现有 PBB 事件/job 与 native terminal receipt，确认 pending call 对应的 managed start record 是否已有 `terminal`；若已有 close/terminal 而 Pi 仍 pending，则是 tool-result/会话投递层；若没有 terminal 且 child 已结束，则优先查 native finalization/collector。若现场无法执行读取，下一次冻结的最小定义层修复应把 `finishManagedProcess` 设为有界、可诊断的收尾：先保存原始 close（exit code/signal），再以短时限等待 ownership 核验；核验超时记录 `terminal.status=unknown` 后仍完成 PBB 的 `finish`，不让进程归属证明阻塞 agent 的工具结果。该修复保留原始错误并把 native evidence 缺口显式化，不能用 HTTP timeout 代替它。
