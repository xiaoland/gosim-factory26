# Variant 与实验命名整理

## 当前范围与授权

用户已认可 variant、实验、运行三个层次，进一步要求：“variant 的命名可能也还要有一个规则；你可以去进行整理，规划，然后给我一个完整的方案。”

当前已完成本轮实现与已有记录核对，未提交：用户在实施计划与两项独立预演完成后明确要求“你可以开工。并且我要确认一下，你会相应地更新或者添加文档，对吗？”，随后再次指示“开工”。授权覆盖三个 variant 与 Lite 配方迁移、标签和包/应用来源接线、报告批次隔离，以及配套文档；模型实验、官网写入与提交不在本轮范围内。

## 调查中的关键约束

三层分别解释稳定实现、一次研究问题和具体执行，不能靠名字替代冻结输入与真实运行身份。原样重放必须关联来源应用，重新生成与重新评分需要明确区分。

现有技术说明要求 variant 独立维护流程、角色和材料，不通过共同配置生成器装配不同实现。因此“模型不放入 variant 名称”不自动授权合并实现或恢复通用配方系统。方案须根据实际差异说明哪些是命名整理、哪些另有行为重构成本。

工作树有其他任务的大量未提交修改；本轮只编辑本任务文件及必要的任务导航。正在运行或已冻结的制品、journal、应用和官网 ID 保持原身份。

## 当前结论与下一步

只读调查与方案已完成，见 [完整设计](design.md)。建议 variant 使用 `<engine>-<coordination>[-<workflow>]`；活动/实验三目录拟为 `pi-braid`、`pi-braid-coordinator`、`pi-braid-review`，其余保留历史路径并明确家族归属。模型与配置变更用实验快照表达，不恢复统一生成器，也不把已分化的历史实现当成等价别名。

实验使用 `eYYYYMMDD-NN` 加问题标题，配置行为 case；运行区分生成 g 与固定应用重评 r，保留所有现有机器 ID。官网 submission 名称不是单 run 名称，Competition 的恢复与单 task/run 约束均保留。来源与报告应沿已有记录接通，不能把同名 variant 的不同配置、应用或独立评测批次混计。

挂起前的两项有界只读调查分别核对了 variant 实际 diff 和实验身份消费者，并对草案作针对性复核。已纳入职责可由指令表达、coordinator 指派边界、跨 venue/task 唯一性、case 全链路透传、submission 重跑限制和评测批次隔离等修正；当时完成的是设计调查，恢复后的实施预演另见下文。

2026-09-26 用户确认“这个方案很好，我接受”，并因正在修改 variant 而挂起任务。随后用户要求恢复，并在澄清时选定本任务。本轮以当前工作树为迁移对象重新核对；Git HEAD 为 `ad0a627`，但三个目标 variant 与通用实验设施仍含其他任务的未提交或未跟踪改动，不能用 HEAD 文件覆盖工作树。

恢复后的 [实施计划](plan.md) 与 [预演结论](preplay.md) 已完成。两项独立只读预演分别覆盖路径/内容迁移和命名/来源字段链。关键修正是：稳定实验标签随冻结 job，run_name 随本次执行；真实包 variant 与实验 case 分离；报告先选择真实批次，再处理显式 retry 和来源应用。root-only 的未跟踪目录与 mixed 的新材料须完整保留，三个名称不代表同版本基线的单变量对照。

本轮实现与文档已完成，证据及限制见 [交付核对](verification.md)。目录保全确认三个 variant 只有身份常量变化；WSL 已用真实历史记录完成只读查询、不同 suite 的报告隔离及两份 replay 包来源读取。未运行新模型、评测、官网写入或设施测试，未提交。新执行标签与官网写路径等待下一次另行授权的真实实验观察，不以历史读取代替该证据。
