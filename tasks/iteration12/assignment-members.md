# 指派直接选择成员名

2026-09-30。用户产品提案：“deepseek、glm不是可以直接委派的对象，要委派给deepseek-1，glm-1；当委派了glm-1给PR3，那么委派PR4时自然会看到glm-2、deepseek-1可选。”
用户随后明确授权“这点不需要分析了，直接修改”，并进一步澄清：“按配方，委派一个后，按序号递增，虚拟下一个assignee”。源码、指引与实际 CLI 核对已完成，随后按从零启动的新授权进入 [当前运行](restart.md)；已存在身份、旧冻结制品和暂停现场不改动。

## 修改前的问题

当前 `sources/braid/src/objects.rs::assignee_directory` 列出profile的裸别名，`profile_for_login`也仅接受这些别名；实际负责人随后由 `reserve_member_for_profile` 生成带后缀的成员名。
CLI回执和帮助明确禁止将返回的实际成员名再次用于指派，并要求以裸别名派生新负责人。
因此“选择谁”和“实际由谁负责”采用两套名字，仍需要LLM理解配置与具体成员的内部差别。
编号当前来自 `local_run.next_member_sequence` 的全局序列，与用户示例中每种成员分别递增的体验不符。

## 已批准并实现的产品行为

每个配方提供按序号递增的下一位虚拟assignee；候选查询直接显示该成员名及能力说明，裸配方别名不再是指派参数。
例如候选为 `glm-1` 和 `deepseek-1`，`braid pr edit 3 --add-assignee glm-1` 成功后，PR #3负责人就是 `glm-1`；下一次候选为 `glm-2` 和 `deepseek-1`。
虚拟候选不是已存在的空闲成员。查询不会创建成员、占号或启动会话；成功指派才认领候选名字，使实际成员身份成立，并将该配方推进到下一序号。其它配方的下一位候选保持不变。原生会话随后沿既有调度创建，不增加“创建成员”操作或预启动成员池。
同一成员在指派回执、对象负责人、当前身份、评论和通知中使用同一个名字；重建和恢复保持它，已有成员不重命名、不回收名字。
下一个新名字按各自命名前缀的已用名字生成；实现要保留现有历史序号，不借此重编号旧成员。
候选被另一操作先指派时，明确提示该名字已不可用并返回当前候选，不悄悄换成别的人；不凭解析字符串后缀接受任意不存在的成员。
成员名与配方的映射仅由宿主维护，不向Agent暴露profile内部ID或UUID。
责任关系与执行容量保持解耦；这个目录不是worker槽位表，不要求为腾容量取消指派。

本次不引入同一成员跨工作项复用或多个负责人；这些行为若有需要应独立明确，不能由名字修改悄悄带入。
对既有当前负责人的重复指派保留同一身份；新工作项选择尚未被认领的候选，不把指派当作复制当前人的上下文。
