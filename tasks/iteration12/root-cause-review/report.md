## I11：验收为什么没有约束最终交付

### 需求排除没有成为被接收的工作

既有 I12-G01/G02 已成立：REQ-5-3-3 包括 Issue **或 PR** 的里程碑；最终 `PullDetailPage` 只提供 Reviewers 与 ReviewsSummary，PR 端缺里程碑链路。M6a 明知缺项而排出自身范围；M6b 明知 M5 没做 PR，仍以其属于 M5 的范围排除；根负责人读到这一说明，没有建立被明确接收的后续工作。对应验收只检查 Issue，却在总表中按 REQ 编号算覆盖并给出 152 PASS。

这里有两个互相支撑的缺口。任务边界没有保证“别人负责”最终对应一位已接受责任的人；验收又把同一需求编号的一部分当成全部，使遗漏不影响完成判断。通知投递、代码能构建、各模块负责人确实做了工作，都不能反驳这个链条。权限 Write 的例外在最终应用已修，不应继续混入未修清单。

最小修复不是让 Braid 解析业务需求或新增强制状态机。Agent 在现有任务记录中保留每个实质排除项的原要求及去向，由接收者确认；未被接收的缺项仍属于整合者的未决义务。验收负责人从原始承诺核对每个不同对象及跨任务结果，而不是汇总子任务的自报编号。这个约束应进入通用交接方法；GitHub 里程碑的具体实现仍由生成 Agent 决定。

I12 实际 `svc-verification/references/check-design.md` 已明确要求逐个检查并列对象、保留场景初始条件、走完整跨组件路径。**G02 的方法修复已送达，尚无最终交付样本证明有效采用。** 不建议再加一轮近义句。G01 的“排除项被另一方接收”不能由已存在的“候选包含依赖实现”规则完全替代：前者决定谁负责完成，后者检查已声称完成的依赖是否真的进入候选。

### 补证：组织 seed 的内部约定取代了原场景

公开需求 ROOT 第 8–15 行规定已有对象是应用必须提供的预置数据，允许生成名称带唯一后缀，但对象的角色、所有权、可见性与关系须保持原规定。REQ-2-1-1 第 533–553 行用 `Acme Demo` / `acme-docs` 描述组织列表、完整名称过滤、进入 `organization name/repository name` 的路径。

最终应用将 `acme-docs` 放在 `alice-dev` 个人名下；`acme-demo` 只有 `org-handbook` 与 `org-private`。这不只是静态命名推断：隔离操作从首页登录，经账户菜单、Your organizations 进入 Acme Demo，显示这两个仓库；过滤 `acme-docs` 后出现 No results，匹配链接为 0。该结果保存在 [组织操作原始观察](i11-organization-operation.json)。

决策链也可追溯。生成期根评论 #73（2026-09-29 06:46:17 UTC）以两个 seed 幂等共存为依据，明确裁决沿用 `acme-demo/org-handbook` / `org-private`；#77 接受。最终 `orgs.spec.ts` 也直接进入组织地址、过滤 `org-handbook`。因此，“seed 没冲突”“内部契约一致”“验收通过”都是真的，但没有验证原场景中的仓库关系。原文、真实裁决、最终代码与浏览器观察形成了独立于 PR 里程碑的证据链。

这一结论的边界是：已证原组织场景指定的对象不可从该路径取得，不是组织列表整体失效，也没有证据给它分配官网失败数量。公开场景若被正式更正为另一对象，判断会改变；当前没有这种更正。允许唯一后缀也不支持把公开示例对象及其归属任意替换为另一套内部 seed。

最小修复是让原始场景成为共享契约的约束，必要时在不同 owner 下保留同名仓库，并从未被验收脚本补造数据的初始状态走原路径。不要让自建 seed 文档取代公开要求。它与 PR 里程碑漏项同属“需求转换与验收共享同一错误前提”，但前者是错误替换，后者是无人承接，修复点不能只剩泛泛的“加强 review”。

### 广泛失败：公共入口假设有区分力，但未取得官网原因

最终首页确有两个 accessible name 精确为 Sign in 的链接，分别在 navigation 与 main；Sign up 也有两个。隔离浏览器用无范围 `getByRole('link', {name:'Sign in', exact:true}).click()`，真实得到 strict mode violation。这个结构从基础 PR 原生快照到最终冻结应用仍存在；生成 Agent 当时通过具体引用点击，后续自验收主要直接进入 `/login`，部分入口调用用 `.first()` 消除歧义。

这足以提出一个能解释大量共同前置失败的假设：**若官网公共登录步骤使用不带容器范围的严格选择器，许多功能在进入各自路径前就可能失败。** 但我们没有其逐例报错或执行轨迹；公开需求仅明确 Create an account 是唯一链接，没有规定首页 Sign in 唯一。重复合法入口不能仅因某种猜测的选择器失败而定为产品缺陷。

竞争解释通过真实操作已缩小：从首页选择实际导航链接，以指定账号密码登录得到 HTTP 200；刷新仍保持会话；搜索 `acme-docs`、点击结果并进入个人仓库均成功，没有浏览器脚本错误。因此“认证整体不可用”“所有初始账号密码无效”“仓库公共访问完全断裂”不受本次证据支持。官网保全 DB 没有登录会话、业务数据仍似初始态，与早期 setup 失败相容，但也可能来自评测清理或失败回滚，不能单独作证。

这条线真正已证的验收限制是：直接进入登录页的检查没有覆盖公开场景要求的首页起点；`.first()` 的成功也没有证明不加范围的定位唯一。应保留这两个检查各自的条件，按真实用户路径检验产品。只有官网公开提供的逐例错误或执行轨迹，才能把共同 setup 假设升格为该评分的原因。本次不应为取此信息再启动评分，也不读取隐藏评测器。

## I12：自然完成与新输入已形成行为闭环，未发生的分支仍保持未验证

I11 的已见反例是 reset 开始时看到工作还在 running，便把“需要继续”固化；稍后原工作自然完成，仍创建 reset_continuation，恢复通知又被读成新任务，导致再次检查与回执。I12 冻结实现改为在重建提交时读取旧 session 最近一个非 reset-notice 工作 turn 的持久终态，仅 interrupted / failed / unknown 需要继续。这一机制变化有下面的真实行为支持，非编译或代码阅读代替验收。

以下时间均为 2026-09-30 UTC；原始记录见 [暂停现场表](i12-paused-evidence.json) 和 [原生会话](i12-native-selected.json)。

四次根 reset 都没有产生 reset_continuation 事件；第一次重建后的根 session 在真正评论到达前保持 idle。两题各两次外部评论都引发对应工作 turn，原生记录显示读取指定评论并处理其含义。故“自然结束后虚假续跑”这个原问题在已触发的场景中得到解决，重建也没有吞掉后续真实输入。

此外，Sheet PR #2 于 04:07:04 进入 cross-surface reset 的 interrupting 阶段；04:07:08 收到重建通知；根评论 #2 随后到达，原生于 04:07:23 收到具体评论入口，04:07:24 调用 `braid comment view 2`。这至少反驳了“进入 reset 就必然把新评论搁置到新 session”的判断。不过该 PR 在暂停前仍是原工作 turn，reset 尚未 applied，不能把它当作重建提交瞬间事件保全的完整验证。

剩余不确定性明确收窄为：真正 interrupted / failed / unknown 后的继续工作、失败过程中封存原结果、以及真实输入恰与重建提交交错时是否无丢失且不重复。两题 PR #2 的 interrupting 与 running 是暂停时的持久事实，不是失败或卡死证据；Docker pause 也不会自动把业务 turn 写为 interrupted。没有必要为缺少这些样本先增加新机制，更不能发明一个反例。下一次获授权实际运行若发生这些分支，再核同一输入的事件、batch、旧终态、新 session 和原生处理；没有触发就继续标为未验证。

## 重复验收与全局镜像：两个诱因不能合并处理

实际两题的 `interpreting-results.md` SHA 为 `c5719eab7702d6de5d2ef0f9fddc9e19f2866b985da3b689abf5700234128566`。其中已经没有专门 SHA 规则，取而代之的是比较候选差异、检查实现、构建产物、输入、持久数据、依赖和环境；复用仍适用的证据，只补受影响或未覆盖的承诺，并在证据足够时交回结束。实际角色材料还明确没有相关变化或待办时不用重新核代码、哈希、检查，也不发“无动作”回执。不能把当前机制描述为仍要求每次换 head 一律全量重验。

尚存的是另一条资料职责问题：冻结 Braid `docs/20-product-tdd/local.md:60` 写了“本项正文不维护其他工作项或分支不断变化的全局状态镜像；整合任务维护当前集成状态并链接历史成果”，但本次实际物理指令没有这一完整区分。它只说当前任务与稳定决定、不要反复复制日常进度；SVC 的通用任务材料也不会自动建立“历史 PR 的交付证据”和“整合者当前状态”的具体职责。这是已批准想法到实际接收材料之间的交付缺口。

其因果关系是：把已完成 PR 当作最新集成看板，其他任务的变动也会变成本 PR 的正文修订；正文确实属于上下文投影，相关 session 重建便有合理触发。这些额外修订又容易让 Agent 误以为自身交付或证据失效。I12 根正文编辑已在关联 PR 上产生 cross-surface reset，说明传播路径存在；但新运行还没有完成一批历史 PR，因此没有 I12 全局镜像循环或重验复发实证。

最小处理是把已经确定的资料职责放到真正投递的共享角色约定，继续以现有整合任务和证据链接承载，不建立另一张状态表。不建议让 Braid 猜测正文改动“只是进度”而过滤通知，也不建议恢复 SHA 特判。证据适用性是 Agent 对改动与条件的判断；对象变化与订阅投递仍是 Braid 的职责。下一次整合发生后，观察历史正文是否只保留自身成果、整合者是否说明复用条件，才能判断方法是否被采用。

## resolve：讨论级语义适合结束讨论，局部整理已有另一条正确路径

I11 的错误是把整理一条旧信息当成 resolve 整个讨论，评论 #324–327 随后需要 unresolve。I12 冻结 CLI help 已明确通过评论 ID 选择整段讨论，回执给出 thread root、resolved-through 截止和影响数量；对象语义仍是折叠该截止前的已结束讨论，后续新回复保持可见。这与保留决定后结束讨论的需要一致。

对“只有一条过期，其余讨论仍有效”，已有 hide + reason。I12 GitHub 根在外部整理请求后实际执行 `braid comment hide 1 --reason …`，理由是创建期进展已并入当前正文及 packet、下一步已过期；SQLite 确认该条 hidden，原内容与理由保留。Sheet 对仍有引用价值的评论保持可见。局部整理没有再误用 resolve，这是采用层面的正例。

仍缺的是新版讨论级 resolve 回执在真实使用中的效果，不是已发现了新的语义缺陷。下一次有真正结束的讨论时，核范围是否被操作者理解、需保留的结论是否有入口、截止后的新回复是否继续可见。当前没有依据改成“resolve 只隐藏指定评论”，也不应把已投递通知回收列为整理的隐含要求：编辑投影与擦除别人已收到的信息是不同能力。

## 监控与 Console：缺回传消费者和暂停依赖分别处理

`lab.analysis.factory watch` 已按约定 3/8 分钟读取状态、保留结构化原因，并在 blocked 或终态退出。真正的断点在 `runs/iteration12/fresh/start-watches.py`：`Popen(..., start_new_session=True)` 后只存 PID、stdout/stderr 路径，启动者没有保留 wait，也没有回调或负责最终报告的监控任务。文件继续增长可以证明在采集，不能满足“终态/异常主动返回主线”的约定。

这是部署编排缺陷，修复优先级 P1。最小做法是在下次授权运行的启动链上明确一个持续存在的结果消费者，等待现有 watch 的完成并带原始原因报告，或使用已规定配置的授权 run-monitor。正常状态保持安静。无需更多轮询、不需让 Braid 实现语义监工，也不需新的通用告警平台。本次暂停时最后 watch 行仍写 running / clear，只是持久业务状态；它不证明容器实际执行或语义推进。

Console 则为保证原 Git 路径命名空间，实际注册的 CLI 桥通过 `docker exec` 在生成容器中执行。容器 pause 后不能执行 CLI 是这一依赖的直接结果。已有服务器日志持续出现对象端点 HTTP 400；本次仅 GET 不触发 CLI 的 `/api/runs`，得到两项 `writable:true`，并读取原日志，没有为了验收执行暂停容器。`writable` 当前表示配置允许写入，不能视为实时可操作状态。

因此“pause 后 Console 不能查询”不是数据库丢失或 Braid 对象查询失效的证据；在当前依赖设计下是预期边界。若产品需要暂停后继续浏览和审议，这是一个明确的能力缺口，宜提供标注时间与运行身份的只读快照/宿主读取路径，并把实时可用性与配置写权限分别显示。实现前需确认这一产品需求，不应为了显示页面偷偷恢复容器或改写原 DB 的工作区路径。即使先只修界面可用状态和具体错误，也比用 writable 掩盖暂停依赖更准确。
