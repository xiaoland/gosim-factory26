## 主要失分嫌疑：评测可能访问了旧服务

证据链如下，以下过程时间均为北京时间：

1. **09:44:16，PR #3 的 GLM Agent 启动旧分支服务。** 命令是 `cd backend && (node src/app.js > /tmp/backend.log 2>&1 &)`，没有显式指定端口；源码默认 3000。工具返回 `Listening on http://127.0.0.1:3000`。[原生会话，行 32–33](../../../runs/k3-root-experiment/20260926/analysis/final/template/.factory26/20260926-002531-ca958b35/native/014-2026-09-26T01-41-31-842Z_01a0db5f-ec42-7104-a6a6-2b6cbf7dfc6b.jsonl)
2. **09:46，另一 Agent 已遇到端口冲突并查出服务身份。** 当时进程 PID 为 25764，`/proc/25764/cwd` 指向 `braid-state/worktrees/pr-3/pi-glm-fast-g1/backend`；它改用 3101 验收自己的模块。说明各工作项的服务并未隔离。[原生会话，行 19–31](../../../runs/k3-root-experiment/20260926/analysis/final/template/.factory26/20260926-002531-ca958b35/native/016-2026-09-26T01-45-09-225Z_01a0db63-3d69-73de-b9ef-95666a139b37.jsonl)
3. **旧服务的代码远不等于最终交付。** 最终工作区包里，PR #3 的 `orgs.js`、`issues.js`、`pulls.js` 仍是空路由，Issue/PR 页面仍显示 `This page is provided by a feature module.`；最终导出的对应文件则已有完整实现。[旧工作区](../../../runs/k3-root-experiment/20260926/analysis/final/template/.factory26/20260926-002531-ca958b35/braid-state/worktrees/pr-3/pi-glm-fast-g1/)
4. **Factory 清理范围漏掉了这些服务。** 冻结 `run.py` 调用 `cleanup_workspace(work)`，它只按进程 cwd 是否位于 `run/work/` 内选取进程。但 Agent 的代码及服务在同级 `run/braid-state/worktrees/`。本次 `cleanup_pids=[]`，与这一范围缺口一致。[冻结调用](../../../runs/k3-root-experiment/20260926/stage/run.py:260)、[进程选择逻辑](../../../runs/k3-root-experiment/20260926/stage/support/agent_support.py:90)
5. **12:22:31，官方正式服务启动失败。** 平台安装、构建成功后运行 `node src/app.js`，报 3000 被占用；约 16 分钟后记录 11/100。[平台 stdout](../../../runs/k3-root-experiment/20260926/analysis/platform-stdout.log)

**确定的事实**是正式服务启动失败、生成期间存在旧的 3000 服务，以及收尾清理没有覆盖其工作区。**高可信推断**是官方评测访问了残留旧服务，旧分支的多个模块为空，因而可能解释大面积失败。没有评测时刻的监听 PID、逐例错误或 HTTP 访问记录，尚不能证明当时一定还是 PID 25764，也不能把全部 89 项失败精确归因于它。

另一个 Agent 最后执行过按命令文本匹配的 `pkill`，但没有随后核验端口或进程身份；工具仅返回 `(no output)`。因此这不构成清理成功的证据。这里的问题应在一次运行所拥有的进程生命周期边界解决，而不是依赖各 Agent 临时编写全局 `pkill`。

## 根 Agent 的最终验收没有发生

Braid 数据库中，四个子 Issue 已关闭、四个 PR 均已合并，四条合并记录都是 `applied`。最终交付确实包含 PR #4，并非仍在导出未合并的 WIP。但根 Issue #1 仍为 OPEN。

根 K3 只有一段原生会话，08:25:40 开始、09:01:25 结束。它实现共享基础、分派其余模块，并承诺“各模块完成并合入后，根 Issue 将做整体集成验收”。此后没有第二个根回合；根对象的事件记录也没有子任务完成后的唤醒。直到 12:22，Factory 直接导出集成 ref。[数据库查询结果](../../../runs/k3-root-experiment/20260926/analysis/verified-facts.json)、[会话摘要](../../../runs/k3-root-experiment/20260926/analysis/final/session-summary.json)

这说明，最终集成验收责任在实际执行中没有闭合。当前交付约定允许导出已有集成提交，导出本身不是错误；但“有可导出的提交”和“根负责人已验收完整需求”是两件事。本次只发生了前者。应补齐子任务完成后的明确交接与根任务继续执行，并单独记录是否完成最终验收，不能把 quiescent 当作产品完成证明。

## 耗时增加的直接原因：实现重复，验收也重复

Issue #5 的 K3 在 09:00–10:38 实现并验证 Issue/PR 模块，提交 `16a6ada` 含约 3,100 行新增代码，并推到 `braid-agent/issue-5/pi-kimi-k3-g1`。但随后 `braid pr create --issue 5 ... --assignee kimi` 建立的 PR #4，其分支从当时集成提交 `a271031` 起步，未承接 Issue 工作分支。

PR #4 的 K3 在 10:29 打开分支时，`issues.js`、`pulls.js` 各只有 8 行占位代码；它重新写出整套模块并再次验收，到 12:17 才结束，约 1 小时 48 分。Git 祖先关系确认：Issue 的 `16a6ada` 及整合提交 `6a61b93` 不在最终交付历史中，最终纳入的是 PR 重新实现的 `d7f6d6e`。[PR 开始时的原生记录](../../../runs/k3-root-experiment/20260926/analysis/final/template/.factory26/20260926-002531-ca958b35/native/032-2026-09-26T02-29-08-436Z_01a0db8b-82d4-70e3-ad50-8295a0fbb17c.jsonl)、[Git 查询结果](../../../runs/k3-root-experiment/20260926/analysis/verified-facts.json)

PR #4 的浏览器验收并非虚构：12:14 的工具返回确有 `ALL E2E PASSED`、`PASS count: 156`。之前经历了多轮浏览器会话、定位及脚本调整。它证明 Agent 在自己启动的 4102 服务上完成了该模块的自编检查；不证明全部 100 个官方场景，更不证明随后官方 3000 端口运行的是这份代码。这里不能沿用上一轮“只跑 API、不用浏览器”的诊断。

更直接的效率改进是统一 Issue 与 PR 的实施责任：若由 PR 实施，Issue 不先完整写一遍；若由 Issue 实施再交 PR 复核，PR 必须明确承接已实现的分支/提交。当前轮的角色理解与分支创建语义不一致，消耗了实质时间。

## 与上一轮及后台执行改动的关系

相较 [mixed 4/100](../../braid-collaboration/results/b77e4357a4e1.md)，官网记录增加 7 个通过项，但本轮同时有评测服务身份不确定、K3 参与子 Issue 与 PR、重复实现等变量，不能据此判断根 K3 的稳定收益。

冻结 runtime 的 [package.json](../../../runs/k3-root-experiment/20260926/stage/runtime/package.json) **没有 `pi-background-bash`**，冻结 `run.py` 也没有加载它。这轮沿用的是旧对照包，不能用它判断此前 `a0fa047` 后台执行接入的效果。插件能改善长命令交还控制权及受管任务清理，但不自动解决上述分支交接、根验收继续执行或所有进程的归属问题。

官网 `token_count=102868119` 与归档的 996 条模型响应 usage 汇总一致，其中约 97.2% 是 cache-read token，不能把它解释为生成了 1.03 亿新 token。金额字段虽名为 `token_cost_usd`，同时返回 `token_cost_currency=CNY`，值 151.03771；仅保留平台账面记录，不据字段名写成美元。请求模式 `official_evaluation` 与返回 `billing_mode=self_funded` 的不一致仍未核清。

## 建议的处理顺序与证据边界

1. 先修复运行所拥有进程的收尾范围，并在正式部署边界确认新进程成功绑定、提供服务；避免旧自验收服务代替最终应用被评分。
2. 补齐子任务结束后的根任务交接和最终集成验收；同时明确 Issue/PR 的实施与分支交接语义，消除重复实现。
3. 在干净环境中仅重评冻结的 `4c17843` 应用，不重新调用生成模型，以区分部署污染与应用本身的缺陷；复评属于单独实验授权，本次未执行。

官方 `tests=[]`、`result_path=null`、traceability `tests=[]`，下载包也未包含逐例评测记录。因此当前不能列出哪 11 项通过，也不能给出 89 项失败的精确分类。
官方不提供隐藏测试的逐例步骤，后续调查不以取得这些数据为前提。
下一份最有价值的证据是同一交付提交在干净部署后的官方评分，以及我们依据公开需求自行复现的页面行为；不能继续用自编通过数代替这些证据。
