## 为什么 Agent 的 156 PASS 没有拦住这些问题

PR #4 的自编浏览器检查是真实执行的：原生会话行 204 返回 `ALL E2E PASSED`、`PASS count: 156`。但它的文件头明确只负责 REQ-5/6，不能代表全部 47 条原子需求。

其证据弱点是可定位的：

1. `hasctl()` 只在快照中查找名称字符串，不验证对应角色；`has()` 主要检查全页包含文本。角色错了、文字出现在其它位置，都可能继续通过。
2. 多数场景直接打开 `/issues/...`、`/pulls/...` 等内部路径。Checks 用例直接打开 `/pulls/9/checks`，因此不会发现默认 PR 页没有状态区。
3. 遇到选择器失败后，行 199 将 `option` 匹配改成 `button|option`，并以用户名尾部匹配接受 `✓ username`。部分调整确实是在适配 agent-browser 的快照表示，不能一概说成掩盖产品错误；但调整后没有另行核实公开要求的 DOM role 和精确名称，原有契约缺口留了下来。
4. 原运行最终根 Issue 仍 OPEN，子任务没有向根明确交接，承诺过的最终集成验收没有执行。局部模块脚本通过后，没有另一轮从公开需求核对最终交付。

这里的原因是验收依据发生了偏移：实现者验证了自己选择的页面、种子和定位方式，缺少对公开契约的独立核对。单纯增加断言数量、执行时间或根模型能力，都不能保证修复这个问题。

## 对下一步的判断

优先级应转向需求契约到验收的对应关系，先修复共享入口和选项控件，再验证默认页面状态与种子前提。在生成阶段设计验收时固定期望角色、精确名称、操作入口、前置数据和刷新结果；验收失败后先区分应用违约、需求歧义、工具表示与测试自身错误，避免只把脚本改到能通过。

已有运行隔离、分支交接、最终集成验收闭环的修复仍然有价值，但干净重放已证明：它们本身不足以使这份应用获得高分。后台执行插件改善长命令管理，也不会自动补齐这些功能契约。当前证据足以定位真实缺陷与验收失真，尚不足以给 86 个官方失败逐项分配原因或预测修复后的分数。
