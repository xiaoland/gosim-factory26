## 问题与目标

用户要求缩短打包、启动运行、热修复恢复的耗时，并强调运行定义与运行数据分离。开发者的目标是修改Harness、配置实验、取得可解释的结果和接续故障；现在还必须选择Python、制作runtime、组装driver、找回执、处理物理路径、复制材料和判断失败是否产生副作用。底层身份已经较完整，组件间的组合规则仍经常由Agent补齐。

## 职责模型

推荐保留controller/runner，同时明确材料生产、制品存储和执行资源域的责任。它们是现有组件需要承载的逻辑边界，不预设新的常驻服务或独立部署。

```mermaid
flowchart LR
    D["实验定义与维护的环境配置"] --> C["Controller：编译、绑定、控制与投影"]
    C -->|"声明构建或恢复输入"| P["材料生产者 / Harness"]
    P -->|"发布内容与语义事实"| A["制品存储：身份、组成与位置"]
    C -->|"固定输入与动作请求"| E["执行资源域 / Backend"]
    A -->|"引用、同域装配或跨域输运"| E
    E --> R["Runner：单attempt执行与运行服务"]
    R -->|"封口产物与保全证据"| A
    E -->|"准入与动作效果"| C
    A -->|"发布与可用性事实"| C
```

| 责任 | 拥有的决定与事实 | 边界 |
| --- | --- | --- |
| 实验定义与compiler | 比较条件、允许源码/材料、模型及费用、预算、目标约束；编译选择依据与依赖关系。 | 高层定义不要求全部物理材料先存在；不能隐式扩大授权或改变供应商。 |
| Controller | 为本次运行绑定配方版本，安排缺失工作、分配attempt、发动作请求、接续阶段，聚合monitor/analyze。 | 消费生产者事实，不成为执行、产物或停止效果的第二写者；不要求payload经控制宿主中转。 |
| 材料生产者与制品存储 | 生产runtime、Harness材料、checkpoint/prepared/application；记录输入、内容、语义覆盖与发布；维护资产位置、保留及有效复用关系。 | 生产成功、字节相同和可在目标消费分别成立；同一内容不抹去不同生产来源。 |
| 执行资源域 / Backend | 实际host/daemon/平台、存储位置、准入权威、物化和输运、资源出生身份、相应动作效果。 | 持有跨attempt的域事实；Local、Docker、托管如实暴露能力，不把未知容量当空闲。 |
| Runner | 单attempt入口、限额、stdout/stderr、资源证据、遥测接收、工作区保全及产物发布责任。 | 服务在入口前齐备，controller断开后继续；不理解Braid私有协作，不因更换OTLP接收丢失资源采样。 |
| Harness | 自身材料选择、检查点组成、一致切点、恢复兼容性、native路径/历史语义、应用交付。 | 通过公开命令和产物合同提供能力，通用设施不读取私有SQL补恢复语义。 |

计算与数据所有权分开，不意味着删除必要物理核对。域内共享准入仍需能解释全部持有对象和在途物化；停止生成容器不自动关闭可写accessor。Console保留服务与访问环境生命周期，但实际绑定来自上述公开事实，不要求开发者传递state/binary/container/mount清单。Analyze只消费固定证据范围，不决定生成是否允许启动。

## 定义、配方、资产与运行的生命周期

可编辑实验定义描述目标和条件；Frozen execution recipe是这次选择的不可变版本；资产是有生产来源的内容；run/attempt保存实际发生的绑定与效果。定义与数据分离必须覆盖这些生命周期，目录分开只是落点。

编译先表达明确的依赖和政策，尚未生产的输入可绑定特定producer及输出合同。输入产物发布后，分配attempt前绑定确切artifact引用，不从“最新输出”持续改绑已经执行的消费者。原始输入需要冻结；生成结果没有预先可知的内容哈希，不能据此要求开发者先跑一次生成再手工写执行计划。

高层配置可以使用维护的环境名与能力约束，编译/绑定保存最终选定的OS、架构、runtime和后端身份。域内资产位置由实际观察给出，不替代内容身份；实际进程/容器出生身份产生后绑定attempt。更换目标或配置不改已有attempt的记录，等待期间不能静默换环境解决阻塞。

改变模型政策不自然使runtime或Harness字节失效；改变Harness代码不自然使checkpoint原件失效，但可能改变恢复兼容性。依赖生产配方应明确源码/lock/补丁、builder版本、参数及目标条件。已有成功产物可在这些条件有效时复用，不能从相同文件名或单一hash推断构建可重用，也不能假定所有外部构建均可重复。未声明的依赖使相应复用依据不足，不增加泛化“总是安全”的缓存。

Runtime按依赖与平台存在，不以每次run作为安装生命周期。Controller与runner继续有不同的角色绑定和限额职责，依赖相同不必强制复制两套物理安装；它们的代码版本仍分别冻结。开发侧SVC CLI与参赛SVC技能继续独立，不能通过共享资源偷换来源或用途。

推荐保持“一个run消费一个固定配方”的原则。阶段重入沿同动作请求接续；同配方重新执行是明确的新attempt。热修复改变执行材料时产生新配方及派生运行，显式关联来源attempt/checkpoint与允许变更，不改原run的冻结输入。原Braid/native会话可以按Harness恢复合同延续，它们与新attempt/平台run并不合并身份。是否将受干预结果纳入比较由实验条件决定。

生产身份继续由artifact_id/producer relation表示；底层可以共享相同内容的存储字节，但不能把两个生产行为合成一个事实。运行记录主要持有引用、输入绑定、效果与证据索引，不为每次运行复制全部既有资产。资产跨运行保留须有明确消费者和恢复承诺，GC不能因生产attempt退出就删除下游仍需要的named output。

## 构建、装配与传输

构建从声明输入产生可复用材料；装配使材料能在指定目标被消费；传输把材料移到缺少它的资源域。三个动作有不同的输入、失效条件和效果，不能由“打包一次”代替所有阶段。

ZIP是后端交付格式。Local/Docker应能直接消费冻结资产；平台仅支持完整包时仍生成并上传完整包，不承诺增量API。只改变配方不必重建所有资产，同一个物理包被多次使用也不代表平台允许复用submission或收费授权。

Artifact的身份和逻辑组成稳定，位置另由资源域提供与核验。目标已有相同发布资产时同域装配；目标缺资产时输运，并核对接收字节。控制器保存引用和回执即可，移到另一控制宿主不自然导致worker数据迁移。Prepared仍可能要求特定OS/runtime/native布局；同域并不免除这些约束，改变环境需要由Harness判断是否重新prepare。

发布资产与可写执行工作区必须隔离。只读复用、文件系统快照或独立复制都是可能机制，尚不选择；不能用指向原恢复现场的共享可写链接换取速度。发布存储如何排除后续修改、检测失效及维持保留，是证明复用的前提，当前源码的原子发布和约定不可变尚不足以宣称此架构已经成立。

资源域首次建立、旧writer接管和日常新运行也有不同生命周期。维护好的域配置与权威交接可复用其覆盖事实，日常请求沿原权威执行；不能每次运行都让Agent重新调查完整退役范围。旧来源的写入关闭和当前停止仍在其适用边界核实，域覆盖改变、来源重启或旧writer重新进入时失效，不以一次导入永久授予控制权。

空间计划分别处理控制宿主、资产存储和执行工作区所在的实际文件系统。材料与阶段已有清单可用于估计峰值；缓存未命中、复制、解包和归档并存都进入估计，不只看最终包大小。预估不等于容量预约，实际物化仍重核；检查应在大复制前给出可操作阻塞，不能按 `/Users` 前缀推断磁盘。

## 产物就绪、校验与信任边界

消费者依赖明确的产物合同与必要成功事实。Prepared complete与sealed output、完整恢复来源、目标兼容性、来源停止分别成立；最终application还需满足其最终或阶段快照合同。不能从artifact存在推出producer整体成功，也不能要求所有产物消费都等待terminal archive和遥测全部收尾。

终态归档、telemetry排空和后台输运保留明确owner、回执及保留责任，不因移出下游关键路径而丢失。只有该消费者不需要的收尾可以并行；需要终态应用的评价仍等待相应交付事实，不提前评分一个未经明确冻结的工作区。

| 事实 | 可复用范围 | 重新取得的条件 |
| --- | --- | --- |
| 发布内容与组成 | 指定artifact及受管理存储中的相同发布版本。 | 从可变来源导入、跨存储传输、完整性失效或消费未受管理字节。 |
| 恢复语义 | 指定内容、producer/validator版本、恢复政策及目标条件。 | 内容或上述条件改变；缺口不降格为complete。 |
| 实际装配 | 指定artifact引用、目标资源身份和布局。 | 新目标、新可写工作区、布局变化或原装配不可确认。 |
| 来源停止与writer关闭 | 绑定来源出生身份的历史依据可保留。 | 启动边界还要确认来源未重启、相关写入入口没有恢复。 |
| 容量、资源样本与凭据可用性 | 只支持各自观察时点与覆盖范围。 | 实际准入、入口服务就绪或对应调用时；不能当永久许可。 |

正确的显式性落在最终冻结记录和选择依据上，不等于要求开发者每次逐字段输入。兼容解释器、现存runtime、后端参数和工具来源可从维护的环境配置解析；无法满足时给出具体缺项。模型/费用、需求版本、恢复损失和未知效果的处置则仍消费已有授权与实验定义，不从ambient environment静默补政策。

重复校验的根源应通过阶段合同消除。原始包验证不重新用于合法派生的prepared；装配读回不重新解释已经固定的原始解压过程；checkpoint的链接与外部依赖由生产者处理并保存依据。接收边界继续核对真实字节，普通未受管理目录不能靠mtime或旧回执跳过完整检查。技术机制尚待论证，不新增一层回执后仍让每个消费者重做全部证明。

## 动作效果与接续

受理请求、取得容量、物化资产/资源、runner就绪、启动Harness、执行退出和保全各自有不同效果。为这些具体动作保存稳定请求及执行者回执；unknown只影响其实际覆盖范围，不作为所有阶段共用的“可能已经生成”。

只读环境查询失败可有界重试，不因此分配新attempt。已取得reservation但物化未完成时，接续依据域内权威与现场资源对账；create/entry响应丢失则先查绑定出生身份与请求效果，不以文件缺失推断没有执行。材料输运失败保留partial并接续同一内容，不能触发已完成的prepare或收费main。不可消除的启动窗口仍保留unknown，不承诺通用exactly-once。

执行域负责数据搬运和资源观察的协调。全域physical查询不能因一个对象超时就推断全部容量为空，也不能只靠增加超时化解复制与准入耦合。持有记录与物理观察如何同时保证容量正确、以及输运压力怎样不扩大查询故障范围，属于待论证接口；本设计没有授权跳过未知对象或放松容量合同。

Runner的入口前就绪包含Harness声明必需的服务。OTLP接收和ResourceEvidence是不同能力，遥测关闭不应关闭运行所需资源样本；Docker cgroup限额与Local进程约束分别解释。模型逻辑身份、预算归属、供应商wire ID和凭据绑定分别记录，子Agent不能通过改变身份层级绕过父Braid session预算。

## 开发者与Agent的控制面

默认入口以实验目标、比较条件和实际运行呈现，显示复用/构建/装配/等待原因及真实效果。开发者不先选择记录生产者、不寻找receipt、不计算输入hash，也不手写prepare/generate driver。底层身份和原错仍可钻取，不能用一个万能trace ID替代它们。

查询使用保存事实，展示观察时点和缺口；昂贵核验及实时准入属于相应动作边界。环境诊断能消费同一依赖与能力模型，在缺少runtime或尚未产生输入时解释将做什么，不要求先完整build才有可读状态。维护的环境默认配置和推导出处可见，涉及用户决策的阻塞与设施可接续的阶段失败分开显示。

Monitor、Console和分析订阅实际运行与数据引用；控制器断开后原执行和必要采集继续，控制器重连不重新启动入口或复制工作区。订阅回执、模型成功响应和最终应用交付各自成立。对新的模型、平台、来源停止或迁移动作继续遵循任务授权，不从一条高层命令扩大权限。

## 方案取舍与待定问题

| 方案 | 收益 | 局限与判断 |
| --- | --- | --- |
| 把现有步骤全部包装进controller | 减少命令和临时driver。 | 数据生命周期、全量复制及副作用边界仍不变，不能作为架构收敛。 |
| 明确上述逻辑责任，在现有组件中实现 | 同时处理变更传播、数据位置、产物消费与效果接续。 | 需要收敛真实合同；推荐作为讨论方向，不预设服务拆分或文件组织。 |
| 新建中心构建/资产/调度服务 | 可集中跨团队、跨宿主管理。 | 当前证据未证明需要额外服务生命周期与分布式协调；暂不选。 |

尚待决定的机制有三个。第一，发布资产的不可变性与独立可写工作区用什么存储边界保证，以及存储损坏如何失效。第二，域内资产位置和保留事实采用哪些公开记录与查询，如何让控制宿主变化不丢引用。第三，准入权威、物理观察和动作效果怎样划分，既保留容量/防重复合同，也不让只读失败成为无边界unknown。这些问题要先按各后端能力论证，再决定接口及实现范围。

独立advisor本轮因agent thread limit reached未受理，当前建议是主Agent依据源码与原件形成的讨论稿，未取得新的独立复核。现有硬切、历史只读、生产者身份及平台pending保护继续作为约束；不把本文当作新字段或当前能力的说明。

以下反例限定提案的适用范围。字节不变但目标OS/native布局改变，内容证明仍成立，恢复兼容性可能失效；只改模型但Harness将wire ID嵌入材料时，不能忽略这条真实依赖。Producer退出非零却留下artifact，日志可供分析，prepared是否可执行仍依其覆盖与发布合同；不默认提升为成功。控制器失联或归档pending时，可消费产物仍须有独立保留责任；源仍可能有writer时，消费可恢复字节不等于可以开始生成。平台只能整包上传时，资产复用不能消除该上传成本。这些限制影响三类流程的验收，不能通过泛化“增量”“不可变”或“就绪”掩盖。

## 三类流程的架构检验

| 流程 | 变化与复用应如何表现 | 必须保留的结果与边界 |
| --- | --- | --- |
| 打包 | 首次缺资产时构建；源码局部改变仅使实际依赖失效；无变化再次交付复用既有材料，按后端需要封装。 | 完整生产来源、实际消费字节和权限；不能只记录ZIP压缩耗时。 |
| 启动 | 已有资产按目标位置装配；环境缺项或容量不足在昂贵工作前可解释；新运行不自然触发runtime安装和全部输运。 | 新attempt、实际入口确认、运行服务就绪；模型首成功及排队/输运等待单独计时。 |
| 热修复恢复 | 明确checkpoint与修复材料独立引用，兼容判断只覆盖变更条件；同域不绕控制宿主，未成功输运接续而不重跑prepare。 | 来源/writer关闭、需求身份、原Git/native/DB进度及新运行关系；未知执行不被猜成安全重启。 |

三类流程并列用于检验架构，不指定首条实施路径。每类分别记录完整操作到制品发布/入口确认的端到端区间，以及人工接线、构建、扫描、复制、输运和等待的实际工作。输入规模、代码/runtime版本、物理环境与缓存条件明确；局部命令时间和移出的归档债务不能冒充总成本下降。机制未实现前不承诺倍率，设施测试/fixture/probe/smoke不作为反馈路径，真实执行另按具体实验范围授权。
