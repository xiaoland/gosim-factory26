## 关键发现

### 1. 用户把“可自主重验”与“新修复须复核”明确拆开，随后又补充提交/推送授权

**观察。** 用户在 `01a08e3a-12e1-7510-9ff6-3878d03b9210` 说“重新验收，无需我的授权，只是修复方案需要和我确认”。Agent 仍因仓库规则请求提交/推送确认；用户在 `01a08e3c-64d6-7f42-98ba-923ce8723d6a` 明确“提交和推送也不需要我额外授权了”。之后每轮保持“已确认的改动→Preview 重验→如实报告；发现新问题不追加修复”的节奏，例如 `01a08ec5…` 和 `01a09519…`。

**推断。** 授权接口需要表达动作类别：诊断/重验、已批准修复、提交推送、合并发布并非同一权限。显式持久化这些类别能减少既有全局规则与当前用户授权冲突时的多余停顿。

**限制。** 该证据只说明此会话的授权演进，不能推断其他仓库的 commit 规则。

### 2. 提示词应说明认知条件，而非把工具动作变成必经步骤

**观察。** 用户在 `01a0900d-2218-7f32-8061-3f424faf40e7` 提出“最小限度地引导，而不是约束 LLM 行为”。Agent 将其收敛为：“提示词描述需要达到的认知条件，不把获得它的动作规定成必经步骤”；例如完整内容可能已来自输入、邻域或其他工具，只有信息不足才补读。随后 `01a094b7…` 的回溯也区分了写前重复读取与写后确认：没有发现回执要求读回，10/11 有写入执行在最后写入后直接结束。

**推断。** 对 LLM 工作流，提示词与工具描述应约束判断的依据、边界和可见合同，而不预设读取顺序或用“禁止 X”堆砌流程。这样既保留在真正缺信息时的工具选择，也能减少已有上下文却强制读一次的诱导。

**限制。** 这不是免除语义合同或验收；是否有足够信息仍需由具体行为和结果判断，不能固化为一份通用 SOP。

### 3. 诊断把“耗尽预算”拆为不同的行为失效模式，避免用统一加预算或单一提示词补丁遮蔽差异

**观察。** 用户要求诊断 rumination、evidence stance、anchoring 耗尽根因（`01a08fe2-e831-7ad2-9d2f-ed6b2362adce`）。Agent 以实际轨迹区分：rumination 已有图修改、evidence stance 卡在可比较对象前、anchoring 目标发现不收敛；同时指出真实为词法检索而模型提交语义式长查询，且 `null` 可掩盖实体类型误用。用户进一步质疑 rumination 是否应检索（`01a08fed…`），Agent 回溯到焦点 Block 职责偏移，而不是继续只谈效率。

**推断。** “预算耗尽”是观测症状，需要验收记录能同时保存：是否有产出、终止方式、工具错误/语义误用、输入与检索通道。否则改动会错误地针对预算或调度，而非目标形成/接口契约。

**反例/限制。** 对模型为何这样行动的解释仍是基于轨迹的推断；Agent 多次明确不能据此断言模型内部动机。并非每个行为都能用同一套指标做因果比较。

### 4. 接口设计和最小提示词指导都能修复局部摩擦，但必须由真实运行区分“调用成功”“自然结束”“语义正确”

**观察链 A（接口）。** `01a08e26-b5c4-7aa3-95b2-661a9dd7f67d` 将读取接口升级为批量/随机 `get_entities`；复测发现指定 ID 数组被模型传成字符串（`01a08e3c…`），于是用户拒绝“返回更多内容”并要求逐项 `{type,id}[]`（`01a08ec3-5bd2-79d0-a3a2-cc67ef38f1c0`）。随后的重验记录 12 次新格式读取成功，却仍有 rumination/evidence stance/anchoring 耗尽（`01a08ec5…`）。

**观察链 B（提示词）。** 对“结束不等于证明没有遗漏”的方案，`01a09519-7ac3-76c2-bde1-8e92c69a7e97` 实施后 19/20 次自然结束，但 evidence stance 把同源重述写为 supports，refinement 仍有无产出耗尽；Agent 明确不把较低调用数当整体成功。后续针对 evidence stance 的语义合同修复，三次真实运行仍复现两次同源 supports（`01a09563-0130-7582-954b-e4b48815ae87`）。

**推断。** 高价值验收载体应把三个结果轴分开呈现：接口/运行是否可用、执行是否收敛、写入语义是否满足合同。只强化 prompt 或 schema 不能替代其中任一轴。

**限制。** 每次真实模型运行的 seed/前序图可能变化，Agent 自己也标注不能当严格单变量实验；不能以这些轮次计算修复成功率。

### 5. 用户的产品语义纠正有效阻止了“把迁移任务演化为新产品行为”

**观察。** 用户在 `01a0900d-2218-7f32-8061-3f424faf40e7` 指出 rumination 原先已实现，本 unit 应迁移执行载体而非改变产品行为。Agent 承认此前把问题当探索效率、诊断层级错误，回到 focal-Block rumination。随后用户进一步要求恢复专用工具组合（`01a094b7-f776-7751-a756-5f409c67046a`）；Agent 查迁移前实现，确认本 unit 给 rumination 加了通用检索、图查询和 candidate 工具，采纳为只保留 draft/submit 的专用组合。

**推断。** 对“迁移”类工作，方案模板需要一个显式的行为保真对照：旧入口提供什么上下文、旧工具面、旧可见结果，哪些变化只属载体而非产品。此载体比泛化的“不要超范围”提醒更可检查。

**限制。** 历史运行时允许不同定义，Agent 也承认不能断言所有历史部署的工具组合相同；对照应引用具体旧集成，而不虚构全局不变量。

### 6. 本 unit 的完成边界被用户定义为生产交付；收尾 packet 还暴露了工作树携带记忆的设施缺口

**观察。** 用户在 `01a096be-62c5-7b32-b2e7-725090bc5d66` 要求“生产发布完成才算 unit 完成”。Agent 区分 #100 合并、Release PR #101、版本实际变化、部署、探针和 `stable` 接纳；特别指出一次绿色 workflow 只是“版本未变，跳过部署”，不计为发布。最终记录 Core 0.2.0、生产探针/独立健康检查/`stable` 接纳成功，且新 organization 行为没有默认启用。`01a09691…` 的用户还拒绝为 SQL 性能问题扩大节点规模或跳过读取验收，Agent 用三节点完整/截断/闭环及并行健康响应验证并保留性能延期。最后 `01a09867-eff5-75b1-8c17-18f5995a3aef` 更新 parent packet，分开下一 session 必须恢复的现状与 Hub 文档、语义误判、SQL 性能等候选残余，并警告本地未提交的 packet 收尾不会自动带入新 worktree。

**推断。** 当用户把 unit 完成定义为生产交付时，发布验收需要能查询 release commit、部署版本、活性/readiness、稳定渠道接纳及默认配置状态的交付回执；unit close 还需把已知残余放到可见的后续入口，避免“发布成功”覆盖未解决语义风险。未提交 packet 无法随新 worktree 自动继承，说明任务记忆需要显式携带/交接接口。

**限制。** 生产回执和外部 workflow 仍未由本分析独立核验；完成边界取决于用户目标，不能从本 unit 推导所有 unit 必须发布；发布模型的可迁移性主要适用于存在 release PR/渠道接纳的项目。

## 可迁移正例

“不在运行中改方案”：各轮隔离已批准改动、保留实际运行条件和轨迹，先记录结果、清理临时数据，再将新缺陷带回方案复核。例如 `01a09519…` 在发现语义残余后停止追加修复；`01a09563…` 在失败复测后登记“未解决”而非继续叠加 prompt。Agent 也明确 seed/前序图变化使轮次不能当严格单变量实验。这样失败结果仍可审查，而非被下一次即时改动污染。

## 高价值候选改进（最多三项）

1. **在迁移方案中提供旧行为的因果对照和反例。** 说明旧入口/工具/可见结果与拟议载体的关系，并写清什么变化会构成产品扩张。证据是 rumination 被无意扩展后才通过历史实现纠正。限制：这是评审材料，不应硬化为固定文档模板。

2. **将真实 Agent 验收输出稳定呈现为运行、收敛、语义三轴。** 证据是新 schema 调用成功仍有耗尽，19/20 自然结束仍有同源 supports。限制：语义判断仍需人或产品合同，不可用自动状态替代。

3. **提供未提交 task packet 的显式 worktree 交接动作。** 证据是 `01a09867…` 明说本地收尾记录不会自动进入新 worktree。限制：只在 packet/证据确实未提交且会创建新 worktree 时触发，避免对普通切换增加流程负担。
