# 从长会话提炼协作交互与工作模式

本页替代上一轮以设施缺陷为主的总结。仅分析用户指定的 InKCre 核心能力升级会话，按日期分六段，覆盖 720 个有可见消息的 turn。explorer 负责前三段，主 Agent 负责后三段；遍历用户请求/纠正骨架，深读关键往返，不宣称重放全部工具执行。原始材料、脚本与边界见 [packet](packet.md)，证据分见 [1](segments/part-1.md)、[2](segments/part-2.md)、[3](segments/part-3.md)、[4](segments/part-4.md)、[5](segments/part-5.md)、[6](segments/part-6.md)。

## 核心：共同推进对问题和系统的理解

这段会话的中心是人与 Agent 共同形成、校准和落实一个当前可用的产品/系统理解。Agent 自主调查、思考并提出有根据的方案；人类补充目标、领域知识、偏好和约束，质疑前提、作实质取舍；Agent 将反馈传播到当前设计，推导自然后果，再找尚未收敛的问题。问题、图、task packet、spike 都服务于这个过程。

最直接的证据是 019ff424…：Agent 承认把“一次尽可能只问一个问题”误读成“每轮制造一个问题”。修正后的推进方式是：更新模型、推导已定结论的后果、检查一致性、识别真实未知，再决定有没有值得向用户提出的问题。用户将其标成 experimental、task-wide，而非不可修改的 law。不能从此机械推导“必须有两个选项才能发问”；缺失的用户事实本来也需要提问。

## 人与 Agent 怎样互动

| 场景 | Agent 应形成什么 | 人类参与什么 | 怎样继续 |
| --- | --- | --- | --- |
| 进入大任务或新领域 | 原始目标、项目语言、对象关系、既有实现与文档冲突；有依据的讨论拆分 | 补领域事实，纠正目标和错误前提 | 形成能解释范围、依赖与顺序的共同模型，再选切片 |
| 讨论一个设计问题 | 自己的具体方案、因果依据、关键例子和有意义的取舍 | 审查方案、挑战依据、选择有实质差异的方向 | 更新受影响的设计，直接推出自然后果，不把每个字段都重新提交审批 |
| 用户提出纠正 | 找到纠正背后的判断标准及其适用范围 | 确认理解是否准确，补充例外 | 沿依赖传播到技术方案、验收和计划；保留无关的已定内容 |
| 长讨论变得难以审查 | 当前模型、已定结论、剩余分歧与下一步 | 调整节奏、范围或优先级 | 先整理再继续；批次大小随信息密度变化 |
| 进入源码实施 | 已复核设计与验收、近线性的实施计划、关键预演结果和影响说明 | 复核可理解的实施边界并授权 | 在授权内持续实现和验证；发生实质设计变化再回到讨论 |
| 实验或交付结束 | 实际结果、证据、残余和对目标的影响 | 判断接受结果、下一轮方向或 scope | 关闭当前交付或开启下一轮，不用后续补丁抹掉本轮失败 |

这里的“方案先行”很重要。019feec1… 中用户直接指出，Agent 缺少自己的产品/技术思考，导致讨论退化成让用户提供方案。随后 Agent 带着具体行为、技术拓扑与验收旅程再讨论，才恢复协作价值。可查事实通常由 Agent 去查；人类不应被当成搜索接口，也不只是最后点击批准的人。

提问需要足够展开，让用户能修正前提，而不是只在候选项间选。通常只聚焦当前一个实质问题；mail unit 曾短暂扩大批次，随后因信息不足又缩小，且用户禁止把这个局部节奏升级为全任务 SOP。共享理解已稳定的自然结论不需要重复确认。

## Agent 的工作模式/SOP

一般主线是理解并完善需求，形成产品与技术设计，设计最终验收，规划并预演实施，执行，最终验收。这些工作回答不同问题，不能合并成一份“计划”后立即写代码；也不是 harness 必须强制执行一次的不可逆阶段机。

**先维护任务全貌，再选择可实现 unit。** 从总目标与当前能力缺口选择有完整用户价值的纵向切片。方向有价值但太宽时，缩小本次增量，不撤回方向。unit 设计暴露的公共机制、接口和文档变化横向传播；确实拥有独立目的和交付的纠正任务另立 packet，保留回到主线的入口。unit 不等于 release，也不等于研究子任务。

**设计依据来自真实对象、边界和调用关系。** 先理解现有系统，再用产品场景、调用链、拓扑、时序或反例检验方案。表示方法按疑问选择，不要求每个问题都画图。文档与用户判断都可能有误，应核验；同时不能把“当前代码这样写”当作合理性的证明。讨论接口时引用已有业务合同，避免重复规定另一层的规则。

**验收先回答怎样知道需求成立。** 从产品性质、真实旅程和判定依据选择证据；不把任意实现细节冻成 Oracle。自动化测试、临时脚本、真实环境操作按剩余不确定性和复用价值选择。预期图或一次 successful call 不能替代产品结果。历史中强烈偏好静态分析/真实黑盒的具体政策属于该项目，不能抄成所有项目禁止局部测试。

**计划和预演要把实施分支提前收敛。** 计划按真实依赖安排；预演去获得协议可用性、外部条件、边界行为、环境状态和操作材料。019ff495… 与 01a09db0… 展示了具体未知如何通过多模态 spike、取消清理、独立安装和数据库准备解决。不能在关键设计和环境未知尚多时说“都准备好了”，再在实施中反复改方案；预演也不追求穷尽所有意外。

**实施在明确边界内持续推进。** 使用已确认的设计与计划获得局部反馈，自行解决可查问题；只有目标、设计、验收依据或授权有实质变化才返回相应讨论。设计变化会使受影响的计划/预演过期，不会自动使全部旧结论失效。先形成可审查的 baseline，再开始落地，是为了让改变清楚，不是为了制造更多审批。

**收尾重新对齐真实状态。** 验收结果、已知残余、交付身份和后续入口写回 packet；将成熟的合同或方法提升到正确 owner 的长期文档。活跃父任务不能因某个 unit 完成而被清理。规范归有权改变该合同的语义 owner；消费者引用，避免每个任务留下独立可修改的第二份规范。

## 对 SVC、Factory 和 profile 的含义

SVC 应帮助 Agent 建立上述问题意识和判断能力：何时需要调查、怎样形成可复核方案、怎样预演、怎样知道交付成立。会话对 use-inkcre Skill 的纠正尤其明确：Skill 传达何时有价值、必要的心智模型，工具 schema/CLI help 承担操作发现。不能把这条观察泛化为所有 skill 禁止操作示例，但应避免重复工具帮助或用固定调用步骤代替判断。

Factory 无人中途参与，因此不能照搬“每个问题等待用户同意”。需求约束仍是权威；协调 Agent 在其范围内维护产品理解、评估方案、作日常取舍和组织交付，不能凭空补造需求。Issue 承接需求、技术与最终验收设计；PR 承接实施计划/预演、实现与最终验收。需要讨论或修订时通过 Braid work-item/comment 进行，不建立固定往返次数，不强制把所有 requirement 拆成子 Issue。

Braid profile 定义谁以怎样的核心、模型、技能、工具和方法承接 work-item。Pi subagent 只是该 profile 内部可用的有界调查、实施和审阅能力。Braid 多 Agent 的分工围绕产品与责任；不能把 explorer/executor 子代理清单误当作完整的 Braid 团队。

上一轮推荐的强制 owner 表、统一行为卡等没有成为本轮结论。值得移植的是这些载体背后的判断职责和必要信息；字段、文件、提问批次、并行方式都应按真实问题安排。下一步可据此审阅 SVC 具体正文和 Factory profile 指引，但本轮没有修改它们或声明改进已生效。
