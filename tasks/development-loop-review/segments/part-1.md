## 工作模式

### 1. 先让拆分依据可推导，再讨论第一个功能

**触发→材料→互动→继续。** 用户觉得“讨论主线没有源”（`019fada2…`, raw L271；`019fada5…`, L302）。Agent 先把交付物、横切机制、业务动作和纵向切片混在一张初始计划里的问题说清，再提出“权威状态迁移”主轴（回复 raw L352）；用户接受（`019fada8…`, L358）。该方案随后因把动作实体化为状态而撤回，改为“对象×动作×职责”（`019fadb0…`, L406；回复 L438）。继续条件不是继续罗列 unit，而是取得一套能同时解释层级、顺序和拆分的项目语言。

**结论。** 稳定原则是拆分必须能由已知业务/依赖推导；“唯一主轴”只是可撤回的讨论工具，不能压过已有概念。

### 2. 调查的目的，是把可查事实与必须由用户决定的语义分开

**触发→材料→互动→继续。** 用户要求“继续，直到你认为可以开始和我讨论”为止（`019fadb7…`, L444）。Agent 做术语审计，区分 Hub 冲突、当前代码的 `SubGraphForm` 持久化、`storage` 的专门含义和未统一概念（回复 L749）；用户则补充 collection/organization 的产品关系，并警告 Hub 与本人判断都需核验（`019fadd2…`, L765）。Agent 以一个实际术语问题——是否沿用 block 为基本持久单元——再进入讨论（L749）。

**结论。** 稳定原则是先查项目事实，后把无法从代码或旧文档推出的产品语义交给用户；历史文档和用户陈述都是高价值证据，不是不可质疑的 authority。

### 3. 一次只推进一个有因果的决策；解释要足以让用户修正前提

**触发→材料→互动→继续。** 用户明确“一次尽可能只问一个问题，而且要展开解释”（`019fada2…`, L271）。初始 Agent 同时抛出五个 D0 问题（L265），违反了此偏好；修正后只问 memo-like 的产品含义（L296），再在具体实现选择中只拿 deployment-scoped single-user backend 及 O-015 供审查（`019fb939…`, L3433；`019fb94b…`, L3595）。用户会指出自然可推导事项无需占用讨论带宽，并要求解释真正例外。

**结论。** 可变 SOP 是“一个问题”的粒度由其是否要求人类语义判断决定，不是机械的一条字段或一个文件。正例是先说明选择改变何种行为；反例是拿未存在的“审计、重放”替虚构对象背书（`019fadb0…`, L406；Agent 承认于 L438）。

### 4. 产品讨论沿切片进行，同时让上游发现横向传播，但不抢先造公共层

**触发→材料→互动→继续。** memo-like 从具体用户旅程开始：Memos/Flowmo backend 与 collector、block/graph 表达、附件关系和 canonical memo（`019fae3b…`, L1194；`019fae41…`, L1285；`019faeb4…`, L1363）。在 schema version、identity 和 source binding 处，用户明确希望上游讨论“传导出”对 info-base/collection/use 的调整（`019fb192…`, L1776），但也要求 resolver 尽力做 provenance/reconciliation、剩余副作用交 organization（`019fb8d9…`, L2436）。

**结论。** 稳定原则是 unit 从可感知的纵向行为开始；横向机制只有被多个切片的同一压力实际暴露时才提升。项目特例：首个 memo unit 同时承担 Memos backend 的 MVP，名称被用户从 `memos-backend` 校正为 `memos-extension`（`019fb961…`, L3666）。

### 5. 产品设计、技术设计、计划和预演是有门槛的连续链，不是一次性规格书

**触发→材料→互动→继续。** 在是否实施前，用户反问 task packet 是否支撑“产品设计、技术设计→计划+最后探索→实现”（`019fb91f…`, L3052），授权重构和整理 packet（`019fb927…`, L3109）。当 Agent 从公共 registry 假设出发时，用户要求先列计划以暴露仍缺的产品/技术设计（`019fb96b…`, L3767）。最终用户要求全面复审、脑内预演、提前排障和分支遍历（`019fbbdc…`, L5579）；Agent 以配置、路由、认证、存储和 fixture 的具体分支回应，用户只对真正有判断负担的点纠偏（如 L6198），随后明确“批准，开始”（`019fbc48…`, L6546）。

**结论。** 稳定原则是计划/预演用于暴露设计缺口和实施分支，不能被当成事后文档。可变 SOP 是预演深度随外部 API、生命周期和部署依赖而变。

### 6. LLM 的开放性保留在判断与动作选择，持久化和边界由领域合同收紧

**触发→材料→互动→继续。** 用户把 memo 的外部稳定 identity、best-effort exact identity 与无法低成本一致化的残余划界（`019fb8f8…`, L2631；`019fb8d9…`, L2436）。对 extension 热启停，用户明确按小项目的真实风险选择直接增删 routes（`019fb9c3…`, L4680），拒绝因理论低概率风险过度复杂化。与此同时，用户拒绝把 raw PAT 视为不能进入数据库的绝对安全边界，要求基于实际 config 角色判断（`019fbbcd…`, L5507）。

**结论。** 稳定原则是明确 ownership、持久字段和安全/外部协议边界；可开放给 LLM/实现判断的是未穷尽的内容解释、best-effort reconciliation 与具体动作路径。后来撤回的做法是把通用架构范式和假设收益先行固化为项目状态机。

## 正反案例与可迁移指导

正例：术语审计后再问一个真实冲突；用户可用项目语义纠正 Agent，而 Agent 把纠正回写为下一轮调查边界。反例：初始“source-first”和“observation/审计/重放”把外来范式包装成选项，迫使用户在虚构前提中选择。

1. harness 应让 Agent 在方案前标出“已查事实、用户需裁决的语义、仍待调查”，并允许用户否定其拆分依据。
2. 提问界面应支持一个展开的决策问题，携带因果与最小实例；自然可推导项不默认升格为审批。
3. 设计推进状态应保留“产品→技术→计划/预演→实现”的实际门槛，但不要把每个项目固定成同样的阶段长度。
