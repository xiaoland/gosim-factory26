## 为何最终验收没有使用浏览器

冻结包已经注册 `svc-verification`，包含 `agent-browser` 技能与浏览器可执行文件，也定义了 Pi 的 `browser-operator` 角色；能力本身并未缺失。不过冻结 `run.py` 只把 `svc-verification` 等主技能传给主 Pi 会话，`agent-browser` 留给内部角色使用，这降低了根会话对浏览器工具的直接可见度。原生会话中，Issue #4 的 Agent 实际用 `agent-browser` 做了仓库/代码模块的浏览器检查，Issue #5 的 Agent 用 Playwright 检查 Issue 模块。根 Issue Agent 的两段会话没有浏览器命令，也没有调用原生 `browser-operator`；其他模块的 Issue/PR 会话没有浏览器检查。现有证据不支持“Agent 不知道浏览器存在”，更准确是浏览器验证停留在局部工作项，没有被组织成最终交付的共同验收。

决策证据尤其明确：根 Agent 在完成最终构建、首页 HTTP 200 和 API 脚本后，原生思考写道：`Now run the full E2E suite ... Then check frontend pages render key content (can't easily test JS; trust subagents' work + API checks).` 它随后运行的所谓“full E2E”仍是 71 项 `curl` API 检查，并用构建产物的字符串搜索代替页面交互，接着关闭根 Issue。这里的 `subagents' work` 在实际工作流中主要是其他 Braid Issue 负责人所交付的局部成果，不能等同于对最终集成提交的独立浏览器验收。

这个选择在工作分解时已有先兆：根 Agent 写给 Issue #3（身份/组织）的交付标准是“`curl / 简单 UI 流程检查`”；对应 PR #2 只预留 `curl` 自检。Issue #6（PR/合并）的验收称“端到端脚本”，但其原生会话没有浏览器命令。根 Issue description 强调平台构建、启动、首页可访问，未把最终集成应用的实际用户旅程列为交付判据。通用用户指引只说“验收”，SVC V&V 正文虽然区分 API 隔离检查与用户路径检查、要求观察最终产物，但没有在这次根会话里转化为可见的最终验收决策。根会话没有显式读取 `svc-verification` 正文的工具记录；这不能证明它未看到技能索引，但可证明技能未改变其最终检查选择。

因此，当前较强的过程根因是**验收责任和证据范围没有在任务设计时闭合**：局部负责人可各自选择检查，根负责人把局部通过与 API 通过累加成全局完成，却没有检查最终集成应用的跨模块浏览器旅程。修正应围绕最终产物的用户可见判据与责任归属，而不是简单增加浏览器工具或规定每个子任务都运行大量 UI 脚本。
