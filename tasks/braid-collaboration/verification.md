## 要回答的事实

| 观察对象 | 支持本轮修正的证据 | 不能据此声称的结论 |
| --- | --- | --- |
| 指派 | 同一配置的不同工作项得到不同名字；assign 返回名字与最终会话、assignee、评论一致。 | 工作项数量多就代表协作有效。 |
| 会话接续 | 实际发生的重建/恢复仍对应同一成员和本地仓库；实际改派产生新成员且保留工作项成果。 | 未发生改派/恢复时已验证全部生命周期。 |
| Git 边界 | origin 与客户端有各自 refs；本地提交通过 push 发布，PR ready/merge 指向准确的已发布提交。 | 本地 build 或 ready 就等于整体交付。 |
| 合并 | 真正的 PR merge 更新共同分支，操作本身没有更改其他客户端的 HEAD/index/文件；冲突结果与 PR 状态符合原始 Git 结果。 | 无冲突的一次运行已经验证冲突恢复。 |
| 操作反馈 | Agent 实际收到的 CLI/上下文/通知使用可读身份，操作成功与失败说明准确。 | 本轮已经改善了 SVC 方法或保证 Agent 永不提前关单。 |
| 交付 | origin 的确切集成 commit、导出文件与实际送评应用一致；生成过程错误与评分原文分别保留。 | 有可导出的 commit 就代表 Agent 完成了承诺。 |
| 产品效果 | 两题完整官方评分、通过数/总数、耗时及可取得的逐例报告；沿原生轨迹定位关键行为。 | 所有分数差异都由其中一项修改单独造成。 |

使用既有对象、session manifest、原生记录、Git 历史、归档与官方结果进行定向核对，不为了覆盖表格强行触发改派或上下文重建。
某项没有实际发生或缺原始材料时明确写“未观察/证据不足”；不由当前源码或计划补造该运行的行为。
原生会话实际系统输入仍需在新归档中核实可取得；旧 run 的该材料有缺口，不将旧记录的缺失解释成 Agent 从未看到指引。
