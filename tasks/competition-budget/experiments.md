## A：回放必须保持什么

从归档 Git 仓库导出精确 commit，不直接上传经过自检或评测的工作目录。
已核实该提交没有数据库文件、node_modules 或前端构建产物；后端默认在首次启动时创建数据库，并在空库执行 seed。
因此新官网工作区能通过应用本身的正常启动恢复初始数据，无需修改代码、清洗数据或添加特殊评测逻辑。
沿用现有产物回放入口，保留需求摘要、commit 与导出文件摘要；仅做官方入口需要的包装。

依据官方部署日志确认新服务启动成功，无 EADDRINUSE；若平台能提供进程身份，再记录监听者。
不以 HTTP 200 单独证明新服务成功，也不虚构官网未提供的进程或逐例测试证据。
报告通过数、功能覆盖指标与部署状态；回放耗时和零生成 token 不用于比较原 Harness 的速度与成本。

如果得分明显上升，说明部署污染对原结果有实质影响，仍不能把差值逐项归因。
如果得分仍低，说明清洁部署后的应用本身也有较大缺口，依据公开需求和自身行为复现继续分析。
如果新服务再次未成功启动，先解决部署问题，这轮不用于判断应用功能质量。

## B：冻结内容与过程验收

沿用 K3 作为根 Braid session；后续 Issue/PR 使用 DeepSeek V4 Flash、GLM 5.3 Flash，视觉角色使用既有 DeepSeek 视觉模型。
原生角色仍属于 Pi 配置，不能拿其数量代替昂贵 Braid session 数。
本轮不继续换模型；根模型效果需以后在相同修复基线上另做对照。

新包要纳入已经批准但旧 K3 包缺失的完整工作流程（包括设计最终验收方案）及当前后台工具依赖。
冻结时明确每项来源，使用同一份 runtime、技能和需求版本完成两题；不得把旧包拼接造成的依赖缺失当作模型能力问题。
原生 specialist 目前源码为 DeepSeek Flash，此项在实验前明确记录为固定配方，不把它解释为 Braid session 限制的要求。

环境约定写入 Factory task prompt，并进入根 Issue description：

> 生成、自检与后续评测共用环境。3000 端口留给官方评测，自检时显式设置其它空闲端口，并为并行服务分别选端口。自检数据库、缓存、上传文件和浏览器状态使用临时位置，不改变交付应用的初始状态。交付应用仍按平台提供的 HOST/PORT 启动，并通过正常启动准备需求所需初始数据。完成自检后停止自己启动的服务，交接时告知后续负责人这些约定。

不禁止常见工具默认使用的全部端口，不另造沙箱；只处理与后续阶段共享的服务和数据。
现有进程收尾覆盖本次运行的 Braid 工作区，作为任务指引之外的保障。

| 要验证的改进 | 来自真实运行的证据 |
| --- | --- |
| 昂贵模型只用于一个 Braid session | Braid 会话身份与模型配置；原生会话到 Braid 的归属，不按 Pi 文件数量判断 |
| 自检不占评测端口或污染初始数据 | 自检命令中的端口和数据位置、收尾记录、官方启动日志 |
| 实现没有在 Issue→PR 时丢失或重做 | PR 的 head/base 与 Git 祖先关系；有已有代码时明确承接，没有时从 base 实施 |
| 完成或阻塞结果交回根 Issue | 实际 comment、递送后根会话的后续行为，不只看 Issue 关闭状态 |
| 最终验收覆盖最终交付 | 事先设计的验收方案、执行记录、所验 commit、最后交付 commit；后续改动需有对应复验 |
| 用户需求实现情况 | 两题官方总分和功能指标；公开需求驱动的复现，不依赖不可取得的隐藏逐例步骤 |

根负责人可委派浏览器或验收执行，最后依据结果决定是否完成；Braid 不裁决验收合格。
不强制出现某种 PR 数量或指定命令，不把自编断言数当成官方覆盖率。
过程证据从已有 Git、Braid、Pi 和平台记录取得，不要求 Agent 为实验单独填表。

## 报告与监控

复用现有脚本与监控 Agent，每 15 分钟读取一次官网状态，终态或明确故障时报告。
需要工作区快照时允许 2–3 分钟打包；判断轨迹新鲜度以包内会话时间为准。
完整报告分别列出分数、生成/部署/评分是否有效、墙钟耗时、模型用量和实际费用，以及上述改进是否发生。
一次完整实验只提供本次表现的证据；不承诺任意分数阈值，也不据一次运行宣称模型收益或稳定性。
