2026-09-26 用户要求复核 A 的分析并寻找改进方向。
本文件是调查与方案讨论，不构成新源码修改或实验授权；B 沿用原冻结包。

## 结论与边界

A 的 73 个应用文件与旧交付一致，官网正常构建并打印 Listening，零生成 token，最终 14/100。
这些证据支持下调旧服务污染作为主要失分解释的权重。
11→14 是两次总数变化，不代表恰好修好三个场景；无逐例数据，不能量化污染造成的全部影响。
已复现的需求偏差足以说明验收存在真实缺口，但不能将 86 个官方失败全部归为可访问性或选择器问题。
本地七项失败在首个不满足条件处停止，后续业务行为仍未被检验。

报告的应用修复建议可以指导复现，不应直接抄进通用 Harness。
报告所称旧问题修复不足以高分，应解释为清洁部署本身不足；A 没有运行 B，不能说它已证明 B 的交接、验收设计等修复无效。

## 比原报告进一步收敛的原因

**信息可得，但没有保持为判据。** PR #4 的输入 context 明确列出 Search assignees 的 textbox、option 精确用户名、Checks 到达即显示等约束。
它在原生记录 32/34/36 行又实际读取了 REQ-5/6 全段原始需求。
至少这些已知缺口不是单纯漏传需求，也不是只有根 Agent 知道约束。
原子需求读取返回从 offset 2125 连续到文末，没有发现这些读取因截断跳过指定区段。

**诊断能力存在，验收精度不足。** 记录 160–163 行通过浏览器 console 找到 r.id.slice 崩溃并修复；不能把整个过程说成不会调试或没做真实反馈。
但 hasctl 只判断快照中的名字字符串，has 只判断页面文字，默认内部 URL 绕过入口。
程序能够通过这些检查而不满足已知需求。
记录 199 的一部分改动在修正脚本和种子矛盾，另一部分把 option 限定改成 button|option；后者没有同步核对需求允许的角色。
修改测试本身不是问题，缺少证据证明修改后的判据仍代表需求才是问题。

**浏览器自动化脚本也消耗了注意力并引入错误。** 会话读取 agent-browser core 的前 120 行后，手写 Bash 的快照解析、等待和会话管理；记录 144–146 行一度把 openp 改成递归调用自身，再修正。
这能证明额外工具摩擦，尚不能证明 agent-browser 本身比其它工具差。
已安装的 core 文档另有语义定位接口，但当前工具读取截在该节之前。
交互浏览器和可重复验收有不同需求：前者关注如何操作页面，后者还需稳定表达判据、定位、等待及失败。

**扩大模型不是充分解释。** 该 PR 由 K3 执行，仍发生上述偏移。
这不排除模型影响，但反驳把问题直接归因于廉价实现模型。
现有冻结 SVC 已有判据来源、不能为通过而放宽、独立机制、结果范围等原则；检索该 PR 原生工具调用未见显式读取 svc-verification/check-design/interpreting-results。
只能说该会话未观察到这些材料被读取，不能推广成所有 Agent 都不用 SVC，或推断增加阅读就能修复。

## 下一轮的三个方向（待复核）

1. 将设计验收方案落实为实施前可执行的判断依据。
   在现有 Issue 或 task packet 中，从需求确定重要的前置状态、用户操作、可观察结果，以及哪些接口性质被明确约束。
   每个关键检查能回指依据；无需逐句复制需求或固定新表格。
   约束明确时保留其语义，需求留白时允许不同正确实现。
   验收失败后先辨别应用、检查、环境、需求矛盾，再决定改哪一个；判据更新保留依据。
   通用方法归 SVC，Braid 只承载讨论与交接，不引入比赛专属的 UI 规则。

2. 使浏览器角色易于执行有判别力的检查。
   页面探索继续使用现有浏览器；重复验收优先使用工具已有的语义定位、条件等待、断言和结构化失败能力。
   根据具体工具能力选择执行方式，不预设必须换浏览器，也不重新制造 Factory 验收框架。
   工具操作层可以适配页面；它应继续核对需求明确约束的角色、名称、作用域与可见状态，不能把适配成功当成产品合格。
   原始错误应可见；入口或登录失败后，依赖它的检查应记为未执行，避免大量无关 FAIL/PASS 掩盖第一处故障。
   这是原生角色和工具材料的接线问题，不让 Braid 管理浏览器或原生子会话。

3. 以独立依据完成最终应用验收。
   根负责人根据最终 commit、部署状态和需求范围决定验收是否完成；局部 PR 的通过数不能替代完整范围。
   独立 reviewer 是候选对照，不强制每轮增加；先收齐已有本地对照。
   若采用，应基于公开需求和实际应用复现，不以代码阅读或重复实现者测试充当独立证据。
   即便由同一 Agent 执行，也需让判据来源独立于实现细节。

## 最短的验证办法（仅建议，未启动）

B 继续运行，从它的证据区分：没有形成验收方案、方案已有但执行弱、可靠检查发现问题却未修复、局部通过但最终交接缺失。
不要把这些不同结果统一处理为加 reviewer 或加提示词。

若决定改验收方法，先用当前冻结应用检验新方法是否能发现已经复现的缺口，无需完整重新生成。
生成检查的 Agent 只接收原始公开需求和应用入口，不接收这份缺陷清单、本地测试实现或官方失败信息；分析者事后对照已知缺陷。
选少量有区分力的正反例，同时检查未规定的实现自由是否被错误限制。
这仅是应用验收方法的低成本筛选，不是 Factory/SVC 内容测试，也不能换算官网分数。
再依结果决定下一次完整生成对照；本轮不启动额外实验或修改 SVC。
