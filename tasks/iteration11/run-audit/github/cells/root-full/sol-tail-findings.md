## 1. PR #13 首次独立 Vitest 结论被管道退出码掩盖

- **原文位置**：U23 R17–18 启动干净 archive 的 `platform-path.sh` 与 `cd backend && npm test 2>&1 | tail -15; echo "VITEST_EXIT=$?"`；R67–69 读取 bg001 结果。平台检查 `exit 0`、Playwright 51/51，但后台 `npm test` 显示 75 failed / 20 passed，最后却打印 `VITEST_EXIT=0`。U23 R70–73 随后发现工具 Node v24 与交付 Node v20 不一致，用正确 PATH 复跑得 94/95，唯一失败是 `auth.test.js`「keeps the session and the data across a restart」5 秒超时；R74–77 单文件两次仍超时，R78–81 指出另两个并行安装/构建任务使同文件其他用例也接近 5 秒。U23 R82 后台完成消息保留了最初失败全文，R83–85 明确尚待机器空闲复跑。
- **动作与后果**：根侧没有把 75 failed 直接判成业务故障，但最初的 `VITEST_EXIT=0` 是 `tail` 的成功状态，掩盖了 `npm test` 真实失败。改 PATH 后仍有一次真实超时，冻结点未见空闲环境复验，因此「负载性偶发」只是合理假设，尚不是证实结论；PR #13 的平台路径 51/51 则确实通过。
- **根因与竞争解释**：第一层确认为命令退出码/Node 版本选择错误；第二层超时可能由并行负载导致，也可能是重启流程本身在该机器条件下不稳定。判别证据是固定 Node v20、无并行构建时复跑同一 auth 用例及完整 Vitest，并保留原始输出与命令退出码。修复层在验证编排：明确应用 Node，使用 `set -o pipefail` 或保存测试进程状态，不从 `tail` 推断通过。
