# I11-07：检查输出先被过滤，环境推测随后成为已确认结论

## 已确认的动作与结果

原生会话 `2026-09-29T07-01-58-325Z_01a0ebf8-5fb5-70da-a773-18a0d10a7f4d`，snapshot-02 record385（08:10:26）主动构造 `pnpm --dir backend run test 2>&1 | grep -E "Test Files|Tests |FAIL" && ...`，后续typecheck/build/e2e也接tail。没有先保存原始stdout/stderr，也没有保留Vitest独立退出码。实际PBB `pbb_18638_a75b9eac:bg025` 结束于08:13:30.544，duration184319ms、exitCode=0，但完整bg025.log只有19行，包括5 failed /98 passed与后续58个e2e通过。日志和job身份见 `pbb-evidence/pbb/sessions/598f70d105a825cd190b1969/instances/pbb_18638_a75b9eac/`。

这不是PBB将已捕获堆栈裁掉：过滤发生在shell向PBB输出之前。grep匹配到FAIL行也会成功，后面的&&因而继续；PBB保存的是整个shell链的0。不能从job的exitCode推断Vitest通过。record398–401试图用`pbb tail --full`追回堆栈仍只有同一过滤结果，record402才明确承认自己的grep使错误细节从未捕获。首轮具体错误类型不可从现有证据恢复，不能补写为timeout。

record395在检查完成后才读取uptime=33.01（08:13:41）；它并非失败发生时的连续负载记录。record397第一轮重跑PASS时负载31.32→26.93；record403第二轮PASS时24.61→22.10。这支持“同提交随后两次通过，负载较高”，不证明无并发或环境是唯一原因。record396/398/402却将同提交重跑通过当作环境根因证明。record404发布PR15评论#138时披露了grep丢失，但仍判定非代码问题。

## 根因层与最小修复方向

第一层在检查命令构造：复用已经提供的 `agent-browser/scripts/with-service.py --check-only`，直接包裹未过滤的原检查命令。让完整输出和原进程退出结果先写入证据目录，再由后续独立读取命令生成摘要。多项检查分别取得结果，或由已有runner传播失败。只加pipefail能修复退出传播，不能恢复被grep丢掉的堆栈；只加保留日志原则也没有改变实际执行路径。

第二层在验收解释与交接：当首轮错误细节缺失，只能记“原因未确定；同候选后两次通过”，消费方不得将它升级为“已排除代码问题”。这里需要补的是失败类型与可区分原因的对照，不是机械再跑第三次PASS。若后续运行再次失败，先读取保存的原始错误，再决定是否需要控制并发或修应用；已通过本身可作为重跑结果接受，但须与首轮原因分开陈述。

上述为审计建议，未修改运行源码或应用、未补跑检查。PBB原始工具对过滤后输出忠实记录，因此不建议以扩大PBB输出缓存作为本例修复。

## 可发现性补证

`braid-request.json`共同指令提到agent-browser的检查包装和首轮退出保留。基础PR2会话01a0eb6f…record39已全文读取agent-browser技能，明确API/build也适用、已有runner使用--check-only。PR15会话01a0ebf8…全源检索没有with-service/check-only文本，未建立M5实际消费该技能的证据，不能以其他成员读过替代。PR15 record385的直接动机是认为重跑便宜、能免去docs-only等价性讨论，随后自行组合grep/tail命令。后续设计应优先让现有项目检查入口天然保存/传播原结果，而非只向提示词再添加一条原则；具体入口归属需结合既有runner核实。

## 实施边界收敛

Harness不预制或修改生成应用的package/scripts/src。应用Agent自行让其现有runner保存结果属于应用实现层建议，不能当作Harness设施补丁。

Bash/PBB执行边界可忠实保存收到的stdout/stderr、实际shell退出状态和job身份；本例已如此工作。它看不到shell内部被grep丢弃的Vitest堆栈，也不能从shell整体exit0还原任意管道中每一子进程的退出值。禁止猜测拆分、改写任意shell来制造“原命令”证据；增加输出缓存不解决本例。

Harness最小候选方向是改善现有外部检查工具的可发现性：在现有能力提示中直接给出`with-service.py --check-only -- <未过滤检查命令>`的用途与入口，说明它同样适用于无需自起服务的Vitest/build；原始结果保存后再读取日志摘要。现有skill说明已充分，但藏在以agent-browser命名的技能中，而PR15没有读取它的证据。将已存在能力移到检查/后台执行决策点可消除这一发现路径依赖，是否改善采用率需后续授权运行反馈；不能声称多写提示必然有效。工具反馈只能指出它实际捕获的shell结果范围，不能将子命令通过情况自行推断填入。
