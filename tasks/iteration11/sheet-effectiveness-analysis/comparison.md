# I11 Sheet 与 GitHub：工作模式差异的有界对照

> 适用范围更正（用户后续指示）：本文是既有局部报告的切片对照，不足以解释两题完整工作模式。下文把接续阶段差异列为主要解释的表述已撤回；它只是一项待检验因素。新的分析贯通最初需求至最终交付的完整I10→I11 lineage，覆盖原生会话、对象正文/关系、评论及hide/resolve/状态演变；见[Sheet全阶段报告](full-lineage.md)及其明确区分索引/语义阅读的覆盖账。本文保留历史写作及事实引用，不作为完整比较结论。

2026-09-30。复用两题已完成的正向过程分析，比较原需求、当时状态、选择及后续动作；未重做全量调查，未扩查 GitHub 最终源码断点，未运行应用、测试、模型或评测。下文 Issue/PR 均指 **Braid 的开发协作对象**；“应用 PR 里程碑”才指题目功能。

**最有证据的解释是：观察窗口和剩余工作不同。Sheet 的 I11 接续已接近验收收尾，GitHub 的 I11 历次接续还包含业务模块设计与实现。Sheet“本阶段没有新 spawn”属实，但其交付继承了前期 advisor、vision、explorer 和完整 Issue/PR 分工的成果。现有材料没有建立同阶段、同剩余任务量的协作频率比较，不能把它描述成“少协作的方案战胜多协作的方案”。**

Sheet 59/100、GitHub 4/100 是两个不同题目的最终结果。两题没有逐例官方失败详情，也没有控制任务、继承进度及恢复环境的对照，故**为什么差55分尚不能回答**。能回答的是工作模式为何看起来不同，以及哪些机制在各自链路中实际改变了决定。

- **未形成新责任的范围排除，是GitHub已证的区别性样本。** #231/#235 → #305/#308中，原文的issue或PR范围被看见，M6b `a3ff1bd7` L68仍按模块编号排除；根 `10a5036c` L27读到后处理了A/B/C，却没有可见的新承接闭环。同一#308里的seed争议反而获裁决并实施。因此问题不能简化成“咨询少/多”或“根没收到”。Sheet有成功的跨域承接反例，但本次没有证明它完整lineage不存在类似遗漏。来源：G §6、GC §3；S §2。

重复验证和状态回执也会使工作模式显得不同，但**并非GitHub独有的失败模式**：Sheet #567/#568/#569维护“无待办”模块的全局候选镜像，PR13在已有同树结果后重验；GitHub M5 `d9f3ae68` L345在交接后为了packet自洽再次改变候选。两题均支持改进证据适用性与文档职责，均不支持把这些成本直接兑换成失分。

对后续机制设计，现有证据支持保留“具体反例→改判→落实”的协作，同时在**范围排除**处补接手闭环、在**交付声明**处核对对象/角色/初态的实际证据、在**候选变化**处判断旧证据是否仍适用。它没有给出减少或增加Agent数量的依据。恢复binary、模型路由和后台/通知连续性应各自按运行机制证据处理，不混成提示词效果。

本次新增结论的边界：没有完整、同口径的两题角色调用/成本对照；GitHub末段原生决策链在所复用报告中仍有缺口；官方私有验收不可见。GitHub最终源码断点由另会话调查，本报告不重复、不预取其结论。原两份报告事实未改动，所有机制改进仍为候选，未实施，也不承诺提分。
