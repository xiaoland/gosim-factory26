## 仅保留证据支持的改进候选

1. **给最终验收明确双重职责，而非再加“严格、完整、读文档”的泛化要求。** 保留已有效的 head/diff/平台检查；额外把“原需求场景的角色、对象、状态、允许/拒绝结果是否均有独立断言”作为覆盖复核结果，ID 引用只能当导航。尤其跨模块排除须指向接手 owner/证据。提示/verification skill 可改；证据强度高（A:L48/71/86/110/154）。风险是又造一份庞大矩阵或重复全套检查；可以只审查边界与排除，不重跑。零额度验证：对现有原需求和现有 spec 人工/静态标出一个 ID 多对象的场景，比较旧“引用全覆盖”结论与实际断言范围，不执行应用或模型。
2. **一次执行一个不可变证据身份；报告引用具体 attempt、head、结果文件。** 原始失败与中断另存，不用同名 `>` 重写后称“前一版”；成功/失败表行从相同执行结果提取。运行机制优先，skill 明确要求可补；证据强度高（A:L215–218 vs L297/304、L279）。风险是日志数量膨胀；只保留失败、中断及最终成功并有小索引即可。零额度验证：对现有目录做只读关联核验，检查表格 exit 与文件 exit/head 是否一致。本段不要求新增 Factory/Braid 测试。
3. **明确“证据适用性”与“文档提交”的收敛规则。** 把已验 head 与最终候选的相关文件差异交由已指定的核实者一次判断；证据存档不会要求无限递归重跑。提示与 packet 模板可改，必要时运行元数据承载 evidence head；证据强度高（大量可见 A/B 反复、最终 root 实际接受）。风险是把“docs-only”机械豁免扩展过宽；必须保留路径/可执行影响比较。零额度验证：用本次 `0e57fd0→0c73f4a→f628045` 已有 diff 检查能否写出一次性、不循环的交接。
4. **通知先展示目标变化及动作责任；展示 thread 折叠范围。** 先读目标 comment 再按需展开；已完成后的自操作 resolve、纯 housekeeping 不应再次诱发全面重查；多步 merge/update/close 用进行中与完成状态区分，完成回执在动作后产生。属于运行机制与角色操作方法共同问题；证据强度高（B:L27–33、DB #716–724、C:L28–29、D:L4），但仅支持降低协作成本，**不支持承诺提高评分**。零额度验证：用本次保存的事件及渲染输入人工重放可见性/时间线，检查目标内容是否被截断、已完成项是否无动作仍被唤醒，不跑模型。

本段能明确支持的是“现有检查及协作流程真实执行，但最终覆盖判断依赖了既有 spec 代理指标；证据身份与上下文选择另有可修复缺陷”。它不能单独解释官方 4/100 的所有丢分，也不能证明加更多 Agent、缩短全部文档或笼统加强提示就会提高成绩。整体低分因果须与前段需求→规划→实现链和官方末端结果分开拼接。
