## 新增结论

这里不是简单的“没有 owner 机制”或“没让 advisor 看”。可观察到的是三次信息变换：

1. **按 REQ 章节拆分时，完整对象集合没有进入同样完整的交付/验收条目。** 原文的 `issue or pull request` 已经给根和 M5 看过；根把 REQ-5 整组交给题名“Issue 管理”的 M5，交付与验收写成 Issue 页面路径。随后根确实再次把 PR 里程碑提给 M6a/M6b，但形式是“复用权限谓词”的跨模块约束，没有把“谁新增 PR 端行为、谁证明已存在”明确化。
2. **M6a 把尚未证实的外部承接从疑问写成既定边界，M6b 再把边界当作可继承依据。** M6a 原生记录先说“可能 M6b/Issues 泛型处理”，定稿 #235 却写“既有 issues 模块路径”。M6b 后来明确知道 M5 只做 Issues，仍以 REQ-5 归属及 M6a 决定排除。此时 M5 和 M6a 都已关闭；并非另一个仍在实现中的成员已经接下这项需求。
3. **独立审阅和根裁决实际处理的是经过筛选的问题包。** M6b 发给 advisor 的材料自称汇总根 #305 约束，却省去其中 PR 元数据条，也未给 REQ-5-3-3。advisor 不可用后的 explorer 任务同样只指定 REQ-6 原文与六问。根收到完整 #308，因而不能说根“没读到排除”；其后原生记录明确选择核实 A/B/C 三个请求，未把边界排除列为第四个裁决项。

证据支持的近因是：**“不属于我实现”被当成“已有他处负责/已满足”的充分理由；继承契约与独立审阅都没有要求为这个等号提供证据。** 角色指令本来要求保留未决、核实依赖行为，也给出联系/改派/重新打开工作项的能力，所以不能归结为指令禁止跨范围上报。Issue #8 的成功义务转移进一步排除了这种解释。

## 8. 只针对已证实断点的优先候选
