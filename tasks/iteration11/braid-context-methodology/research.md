# Braid 内容与生命周期方法：一手研究参照

日期：2026-09-30。范围：为 GitHub / Sheet 完整 lineage 调查提供有限标杆；本分线不读取或重新归因运行日志，不实施任何改动，不运行测试、模型或评测。

**这些来源支持调查方法和协议候选，不证明 Braid 已发生某种缺陷，也不证明压缩上下文会提分。** 正向调查仍须从当时需求、可见信息、选择与动作出发，最后核对产物。实际 Braid 的 description、relationship、comment、hide、resolve 语义须由源码及历史版本核实；以下词语是内容职责建议，不假设产品已有对应字段。

## 1. 共同理解：送达、理解、赞同、承接是不同证据

Clark 与 Brennan（1991）将对话贡献区分为呈现与建立理解证据；理解须达到当前目的所需程度，手段受媒介影响。“acceptance”在此指对理解的确认，不能译作赞同方案或承担实施。其成本视角关注双方从发言到相互理解的总工作，不能简化成最短消息。原文：pp. 128–133、135–136、140–143。[作者托管论文](https://web.stanford.edu/~clark/1990s/Clark%2C%20H.H.%20_%20Brennan%2C%20S.E.%20_Grounding%20in%20communication_%201991.pdf)

- **支持**：检查接收方的回应是否表达了正确范围、约束和下一步；区分通知已送达与协作已经完成。
- **不支持**：要求每条通知都回复、要求逐字复述，或从一句“明白”推出内部理解正确。论文研究人类沟通，不能直接推断模型的内部认知。
- **Braid 假说**：涉及责任或接口的交接若只有发布方陈述，没有接收方对内容和行动的可观察回应，可能留下未闭合责任。证据应是“提出交接 → 对方所见内容 → 回应或行动 → 上游是否据此更新状态”，而不是评论数。
- **可否证处**：对方已按正确约束实施并交付，即使没有形式确认，也说明本次缺少确认没有阻断协作。独立出现同样结论不等于消费了那条评论。

## 2. 协调：关系必须说明依赖如何被满足

Malone 与 Crowston（1994）以活动间依赖组织协调问题。生产者/消费者关系至少涉及先后条件、交付以及产出是否适合下游使用；任务分解与共享资源又是不同关系。它是一套分析框架，并不指定唯一组织形式。原文 §2.2.2，pp. 93–95；表 1，p. 91；§2.2.4，pp. 95–96。[作者托管正式论文](https://crowston.syr.edu/sites/default/files/acmcs94.pdf)

- **支持**：不仅记录“相关 Issue”，还问谁需要什么、何时可用、什么条件算满足；区分“父任务拆分”与“消费另一个任务的输出”。
- **不支持**：关系越多越好、任何依赖都必须阻塞执行，或集中控制必然优于成员自主协商。
- **Braid 假说**：一个范围排除若只指向另一个 work item，没有该项实际接手范围和完成条件，关系可能仅提供导航。证据应追到消费者能否取得并使用正确版本的输出。
- **可否证处**：关系未显式建模，但共享合同与后续调用已经使依赖正确满足；这属于机制形式不统一，不应自动算交接失败。

## 3. 软件工程：需求、决策、配置与验收要可追溯

NASA Systems Engineering Handbook 的四段公开正文提供可裁剪的工程标杆：需求须有来源、分配与双向追溯，分解后合起来仍需覆盖上层需求；变更须评估接口及上下游影响；配置管理区分当前基线、历史和待决变更；验证/确认须基于明确要求及预期使用环境。

- **定位**：[§6.2.1.2.3–4 需求追溯与变更](https://www.nasa.gov/reference/6-2-requirements-management/)，[§6.5.1.2.2–4 基线、变更与状态记录](https://www.nasa.gov/reference/6-5-configuration-management/)，[§5.4 产品确认](https://www.nasa.gov/reference/5-4-product-validation/)。这些是同一本官方手册的章节，不是独立实验。
- **支持**：当前工作说明与历史讨论有不同职责；模块完成不能直接证明上层需求完成；证据应带所针对的版本和条件，变更后判断哪些结论仍适用。
- **不支持**：将 NASA 的审批委员会、所有阶段门或文档规模照搬到 Braid；也不要求任何文档修改都重跑全部验收。
- **Braid 假说**：若 PR 的验收只回指局部拆解，没有反查原始需求中的并列对象、否定约束与跨模块路径，局部完成可能被提升成总体完成。需要原始需求→分配→实现→具体验收行为的逐项链条，而非只比较 requirement ID 数量。
- **替代解释**：链条齐全仍可能因验收实现错误、环境差异或交付版本偏离失败；不能把所有末端失败归因于文档或责任管理。

## 4. 信息负载：长度和压缩率都不是语义质量

Nematzadeh 等（2019）分析 Twitch 公开聊天，结合消息流速、个人参与和文本特征观察交流变化。高负载阶段反而出现更短、更重复的消息；作者明确指出缺少真实回复线程等限制。这是人类实时聊天的观察研究，不能搬用其阈值解释 Agent 上下文。原文 §2.1–2.3、§3、§4.5。[论文全文](https://pmc.ncbi.nlm.nih.gov/articles/PMC6837236/)；[作者页面](https://glciampaglia.com/publication/from-conversation-to-cacophony/)

- **支持**：长度只能作描述量；必须结合处理任务、交互和具体信息内容才能讨论负载。
- **不支持**：从 description 长、token 多或文本可压缩直接认定语义过载；从短摘要推定任务信息保存完整。该论文没有验证 LLM 摘要或 Braid 注入策略。
- **Braid 假说**：历史讨论反复注入可能增加查找当前结论的工作，但删减也可能移除例外与未决项。需要核对“实际注入内容 → 正确可用信息所在位置 → 读取/引用 → 选择”，同时观察有效长消息和无效短消息作对照。
- **不能推出的因果**：后期消息增长、重启、失败可能共同由任务难度、外部故障或反复修复造成。时间先后和长度相关不足以证明负载导致错误；本次不新跑模型做因果实验。

## 5. 待本地证据裁决的方法草案

以下是本分析提出的工程化候选，不是上述论文对 Braid 的结论；不预设现有机制缺失，不改写现有 work items。

| 内容位置 | 建议职责 | 何时更新或结束 | 原始记录应检查什么 |
| --- | --- | --- | --- |
| Issue description | 当前问题、原始需求出处、范围、约束、可判定结果；列出仍待决定的点及负责人 | 责任人明确确认的新决定改变范围或约束时修订；保留变更出处 | 旧范围是否被悄悄保留/删除；新读者是否能辨认当前事实与提案 |
| PR description | 本候选解决哪些问题、具体行为变化、所基于的合同版本、验证证据及剩余限制 | 候选内容或适用前提变化后同步；不能用旧结论自动覆盖新候选 | 所述内容是否与实际候选一致；局部验收是否被当成整体完成 |
| Comment | 有时间和作者的提案、问题、证据、异议、审阅结果与响应 | 得到决定或新证据后用可追溯响应说明处理结果；无须把整段历史复制进 description | 每项关键异议是否得到对应回应；“已读/同意/已做/验收通过”是否混用 |
| Relationship | 导航加可解释的责任/依赖：谁产出什么、谁消费、满足条件在哪里 | 依赖满足、替代或责任变动时更新状态/说明；保留出处 | “相关”是否被误当“已承接”；排除事项是否仍有端到端负责人 |
| 稳定共享文档 | 跨任务复用的已采纳定义、合同、领域规则与理由，带来源/适用版本 | 经负责者裁定后上移；下游引用唯一入口，局部讨论保留证据链 | 是否有多个冲突副本；上移后的结论是否被目标成员消费 |

需要把三个动作分开：**作出决定、更新当前说明、保留历史出处**。一条评论可以完成第一个，不能据此假定另外两个已经完成。上移稳定信息的前提是其已被裁定且需要复用；尚未解决的争议留在当前未决项中，不能只留在历史附件。

**hide / resolve 候选前提**：先明确这两个实际命令对存储、默认注入、按需检索、通知和状态的影响。内容被替代可从默认视野移开，但应留下替代指针；问题已解决须有处理结论和相应证据。隐藏不等于解决，关闭工作项也不应吞掉已转交但尚未接手的义务。若原机制没有“决议/证据/替代”字段，可先用固定写法和现有链接表达，不据此立即新建状态机。

**上下文候选**：默认提供当前职责、适用合同入口、本次增量、未决问题及关键依赖；旧日志、已替代方案和大块原始证据按需取。该候选只有在检索入口真实可用、关键例外与未决责任不被删去时才成立。已经有限额注入或分层检索的版本，应先检验实际消费，而不是再添同类策略。

**变更候选**：每项变更说明“替代哪个决定/候选、影响哪些消费者、哪些验收结论仍可沿用、哪些需重新核实”。内容相同的文档整理不应自动使行为证据失效；反过来，代码未变但需求解释改变也可能使旧验收结论不再充分。这是待用历史案例检查的规则，不授权新增测试。

## 6. 提示/Skill 与运行机制的分界

| 优先用现有机制规范 | 只有出现对应证据才考虑运行机制改动 |
| --- | --- |
| 给写作者说明每类内容的读者和用途；要求责任排除附承接出处；稳定结论引用来源；隐藏前安置未决项；审阅回查需求原文 | 现有默认上下文确实丢失未决项、隐藏后不可找回、缺少版本/替代身份、通知语义让关键增量不可见，或无法查明本轮收到哪个版本 |
| 接收方只对影响自己范围的交接作出明确处置：接手、提出条件或拒绝并交回协调 | 系统若需要可保证的交接，应使请求与回应有可追踪身份；仅有任意文本不足以提供强保证。但是否值得实施须由本地失败证据和成本决定 |
| 先做少量历史人工核对，比较正例与反例，避免强制所有通知多一轮确认 | 不直接引入全文自动摘要、全局硬字数限制、自动隐藏或“全部接收回执”；这些会增加协调成本或误删信息 |

最小取证单位建议为：**需求/问题 → 当时可见的版本 → 选择 → 责任与依赖 → 动作 → 审阅响应 → 当前信息更新 → 验收及交付**。只有到关键分叉出现可观察偏离，才讨论原因，并并列记录替代解释与缺口。文献不给本次运行补造任何未记录的理解、动机或内部思维。
