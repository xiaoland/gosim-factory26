## 4. 现成方法为何没有阻止这一选择

### 实际指令已经要求什么

P 与 P-root 是这两位当时的指令，不是当前 variant 源码。P:L8/L10 要求需求→方案→验收、根先理解完整需求、共享文档与任务 packet；P:L14 要依赖实际行为成立才算满足；P:L16 要最终候选覆盖完整需求，并消费未解除的验收前提；P:L20 要根据原需求设计/解释检查；**P:L37 明写“不以通过数量代替覆盖说明”**。这些都已存在。

P:L12 的 advisor 触发条件也不是单纯建议：

> “确定仍有关键假设的验收判据之前，先向 advisor 咨询”

它要求提供原始目标、约束、相关材料、待决问题，寻求反例和能改变选择的事实；不能因已通过自检而不咨询。但它**没有明确要求每个最终 PR 一律再调用一位独立语义 auditor**，且日常明确决定可直接推进。A 的实质完整记录未发现原生子 Agent 调用；更窄而有据的判断是：A:L48 将 mapping 视为既定事实，使这一决策没有被当成“仍有关键假设的验收判据”。这是对可观察选择和条件规则的机制解释；日志未直接写“我故意绕过 advisor”，不能这么归因。也未见本段 advisor 工具报错，不能借早期其它会话的 401/额度故障解释这里没有调用。

## 6. 只据本链收窄的优化候选

1. **在最终交接明确两项不同的返回义务。** 既有 suite 在本候选上的结果，以及这些判据足以支持哪些原始要求、仍有哪些未知。落点是根创建整合 PR 的角色说明及 `svc-verification` 验收解释方法。不是增加“完整/认真”的口号，而是让“沿用 mapping”必须说明可追溯的原需求与断言依据；跨对象、显式拒绝角色、未承接排除可作为重点审阅入口。证据强：R26→A14/16→A48/71。风险是变成全量冗长矩阵或重复旧检查；可保留有效模块证据，只审其证明边界及已出现的排除。零额度核验：用本次原始材料人工区分“ID被引用”与“对象/角色/状态断言已证”，无需执行应用。
2. **让“既有映射足够”的决定进入现有 advisor/独立审阅条件。** 当最终覆盖依赖他人完成声明、scope有排除未承接或 count/场景与交接不一致时，把这些当成待消除的验收假设；输入原文、既有断言和具体反例问题。不是无条件要求每轮咨询；更不是因本例未调用就宣布角色失效。落点是已有 P:L12 类规则与 verification 方法的条件说明。证据中强：条件已经存在，A48把假设当事实；M1 提供有效输入形式的对照。风险是 advisor 只读同一摘要再背书；需要回到原始场景和独立反例，不承诺提升分数。
3. **packet 分开“业务依据”与“当前工作分配”，不把二者排成一个总序。** 工作项决定谁做什么、先后和交付门；原始需求决定产品允许什么。派生判据需要指出解释/裁决的来源和适用范围。落点是 task-packet 的现有方法用法与交接示例；不是新增强制大模板。证据中等：L56/57→L154为明确模仿链，但它晚于最初选择，只能改善固化/传播，不能单独解决 A48。零额度核验：对同一 packet 两种写法人工判断下一 owner 是否能辨别“任务当前如此”与“原始功能已证明如此”。

这三项属于提示、Skill与任务内容的具体决策规则；本链没有证明必须改变 Braid 调度或增加运行层 gate。若要求系统自动保证原始场景语义覆盖，那已超出本次证据支持的提示修改范围。最终官网分数没有逐项失败明细，不能把这条链换算为 96 分损失或预测任何提分幅度。
