## 3. 现有方法与实际运行语义

从04:24实际instructions开始，已有：description承载当前任务/稳定决定；comment承载讨论/证据/增量；相关回复在thread；更正联系受影响者；hide失效整条；resolve前安置仍使用的结论/证据，未决/风险/验收前提保持可见。父Issue正文不会自动成为子项上下文，子项需自包含。[历史指令与代码核对](runtime-semantics.md)

实际投影有版本变化：早期PR先完整展开关联Issue及讨论，后期先PR自身、只展开OPEN关联Issue正文、不带其讨论。普通Issue默认自身正文和可见讨论；关系不是递归加载。预算full档仍可能注入本项全部可见讨论，超预算逐级变索引/截短，但没有本次实际降档触发证据。故“每次把全部历史全部塞入”不成立，“局部重复内容会被重新带入”有实物依据。

hide仅改该条可见性并保留正文/理由；resolve回复ID实际折叠整thread截至当时最大ID，新的回复仍可见；直接读单条可取得resolved正文，`--thread`默认仍折叠，`--include-hidden`才展开。hide/resolve会使后继上下文失效，但不能撤销在途已读信息。旧CLI没有明确root/cutoff影响回执；当前源码已增加部分回执结构，不能把历史缺口直接开成重复修复。

SVC/角色的作用也分层：task-packet实际读取、创建、接续；durable docs共享定义被读取与实施；部分methods通过角色内嵌而非显式read。advisor、vision、explorer均有具体有效消费案例；晚期advisor实际gpt HTTP401后由explorer补复核，主未盲从。executor虽有配置，本调查未发现原生调用，不能说它“调用后失效”。Braid的Issue设计者/PR实施者是协作工作项角色，不等于Pi executor。[SVC与角色证据](../../pi-minimal/github-score-analysis/i11-mechanisms-forward.md)

## 5. 可操作的一般方法草案

以下是候选写作/协作规则，未创建新字段或改变Braid语义。评价标准是后继能据此作出正确决定，非字数短。人类沟通研究区分呈现与建立理解证据，协调研究区分生产/消费中的先后、传递和可用性；它们支持按接收方行动判断交接，而不支持要求每条通知都回复。[Clark与Brennan原文](https://web.stanford.edu/~clark/1990s/Clark%2C%20H.H.%20_%20Brennan%2C%20S.E.%20_Grounding%20in%20communication_%201991.pdf)、[Malone与Crowston原文](https://crowston.syr.edu/sites/default/files/acmcs94.pdf)

| 载体 | 应回答的问题及维护责任 | 何时更新/按需取 |
|---|---|---|
| Issue description | 本负责人要解决什么、原需求/当前合同在哪里、完成要证什么、尚未解决/尚未接手的义务是什么 | 范围、决定、责任或完成门变化才修。根保全局义务；已关闭模块保自己的交付记录，不镜像所有后续head。 |
| PR description | 当前候选解决哪些行为、基于哪个合同、验证入口和限制、谁审阅/合并 | 候选或适用前提变化时更新。具体head及一次执行证据在PR维护，根只引用PR及影响上层门的变化。 |
| Comment / thread | 一次提案、待决问题、反例、裁定或交回；说明影响谁、需要其做什么、依据是什么 | 一个thread围绕可独立结束的问题；背景用链接，引用关键例外，原始长日志按需读取。新问题即使相关也不一定共用关闭条件。 |
| Relationship | 结构关系与导航；正文/评论补清谁提供什么、谁消费及依赖满足条件 | `parent`、关联PR不自动意味着继承所有需求/讨论或自动承接。只有相关责任变化才通知相应消费者。 |
| 稳定共享文档 | 多任务需复用且已采纳的领域定义/接口/决策理由，保留来源与适用版本 | 决定成立且需复用时上移；评论留原裁决，description指权威入口。未决争议不伪装成稳定合同。 |
| task packet | 跨会话恢复本任务所需的当前决定、下一行动、未决及证据入口 | 与Issue正文先选一个当前状态维护点，另一个只放职责不同的内容或引用；不为自洽复制所有状态。 |
| 证据文件 | 哪次执行、哪份候选/环境/判据、原始失败与退出码 | 每次执行独立身份，复跑新增文件而不覆盖；摘要链接到实际结果。文件名不能继续标成另一轮成功。 |

生命周期建议：

1. **理解与分工**：原始义务可以拆开，但被某项排除后仍由原owner/根保留，直到新owner明确承接或以实际行动证明接手。边界不清可问一个具体裁决，不让每个owner越界实现。这是对M6与Issue8正反例的归纳，详细树映射另行规划。
2. **实施与审阅**：普通评论按“新事实→影响→请求/结论→来源”组织；不把无动作确认写成又一项需处理的消息。独立审阅分别判断需求解释、实现是否满足、证据是否有效；只复跑同一解释的检查不算重新审查解释。
3. **决定上移**：一次已采纳决定在共享文档有唯一当前表达，description保指针和未决影响；历史评论不改造成无时间的权威全文。消费者给接手、条件或反例即可，不要求逐个抄回决定。
4. **变更控制**：说明替代哪个决定/候选，受影响的消费者和未决义务，哪些验收结论仍适用。代码没变但需求解释变了也可能使验收不足；docs变了则不必当然全重跑。这个区别符合需求追溯和配置身份的工程原则，但无需照搬大型审批流程。[NASA需求管理](https://www.nasa.gov/reference/6-2-requirements-management/)、[配置管理](https://www.nasa.gov/reference/6-5-configuration-management/)
5. **hide / resolve**：hide用于明确无效/被替代整条，先留替代出处并安置仍有用部分；resolve前按真实root/cutoff检查整串都能结束，未决留当前入口。有独立未决的混合thread暂不整体折叠。整理已完成提醒不应被当作新的业务交付。
6. **按需上下文**：默认优先当前职责、有效合同入口、未决责任和本次实质变化；相关历史/原始证据按ID取。先单条读目标评论，再按需展开thread；不要先全thread再`head`导致新目标被截掉。要求运行时自动实现这一默认投影属于机制改动，不是已有事实。
7. **验收与关闭**：“候选已验、记录真实、原需求覆盖、最终交付一致”分开判断；写完成结论时引用对应证据。状态动作实际成功后再宣告closed，避免文字先走一步引发额外协调。关闭模块不表示其他未承接义务消失。

信息负载研究不支持越短越好，观察到的高负载退化也可呈现为更短、更重复的信息；不能把其人类聊天阈值搬给LLM，或用Shannon熵推导本次语义丢失。[一手研究及限制](research.md)

## 7. Sheet的同维度参照及剩余未知

参照独立会话的 [完整协作lineage](../sheet-effectiveness-analysis/full-lineage/coordination/report.md)、[根主线](../sheet-effectiveness-analysis/full-lineage/root/report.md)、[D/E主线](../sheet-effectiveness-analysis/full-lineage/de/report.md)，不是按接续点判断工作模式：

- 两题都有“具体反例→裁定→消费者→实现/验收”成功链。Sheet的tail paste、pivot sentinel、排序值层/rowMap，和GitHub的M1、M5、#281合同传递，都说明协作基础设施有用。
- 两题都有旧owner或根镜像全局状态、自编辑重建与重复核对，也都有停止无动作或按证据继承结束的正例。共同候选是内容维护责任和事件意义，而不是“Sheet协作少所以好”。
- GitHub已证跨对象排除无人接手；Sheet本次整理得到多条跨域承接正例，不据此断言其完整应用没有漏项。Sheet的blocked reset、旧assignee unreachable与GitHub最终完成后的自回声是不同可观察条件，须分别归因。
- 分数不构成两种方法的对照实验，题目难度、验收尺度、需求形态和版本不等价。本文不据2/4/40或其他分差排序模型与Harness。

尚不能确定：上述成本占全部运行消耗多少；减少维护后是否会改善业务理解；某条范围遗漏对应多少官方失分；SVC、独立角色或特定模型的净贡献。没有新评测或模型干预，因此不报告预测增分。可用的产出是完整来源与可反驳的过程解释、能被现有反例检查的候选方法。
