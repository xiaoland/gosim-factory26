2026-09-30。此文是设计候选，不是已创建的 Braid Issue/PR，也不表示应用已经满足需求。工作范围仅为阅读两份原始树、复用既有调查、形成映射；未改 runtime、variant、Braid 工作项或其它报告，未运行应用、测试、评测或生成。

## 3. 依赖不是同一种边，场景也不是另一份需求

**事实：** G 的 `dependencies` 既引用 ATOMIC，也引用 FOLDER，例如 REQ-6、REQ-6-2 指向 REQ-4-3（G:2805、2940 附近）；REQ-4-3-3 还明确要求默认分支改变不影响已存在 PR。S 的 REQ-2-1-2（切表）依赖 REQ-5-1-2（筛选）及 REQ-5-2-1（验证），REQ-2-1-4（删表）依赖 REQ-5-3-1（透视），S:533–536、754–756。这些首先是完整行为与验收的依赖，不能推导成“做完所有数据工具之前不许实现切表”。

**建议：** 保留原边原名，协作层另外解释当前义务，不重写原树的 dependencies：

| 依赖含义 | 具体例子 | 协作处理候选 |
| --- | --- | --- |
| 入口/既有上下文 | G REQ-6 需要可读仓库、分支；S 修改依赖已打开 workbook | 实现可先接约定接口；完整旅程证据必须从规定入口到达，不把直接 URL 当作入口证明。 |
| 共享事实/模型 | G 当前 session、有效仓库角色、current compare commit；S sheet identity、range/reference/operation | 每项一个主责任者，消费者引用其当前契约和版本；不要各域另存同名权威。 |
| 变更一致性 | G 授权改变→搜索/直链；S 行列变动→公式/验证/筛选/pivot | 下游交付后重新触发需要的集成观察；记录哪些观察因该行为变化失效，而非全部重跑。 |
| 验收前提 | S 切表需带不同 filter/validation 状态；删表需已有 pivot 关系 | 可以先实现基础切表，但关闭其完整需求义务前必须有这些状态下的证据。 |
| 真正实施阻塞 | 未决定共享操作输入、身份、原子边界，无法安全接入 | 只对具体未定接口/决定设 blocked；不要把整个上游 FOLDER 未关闭当统一阻塞。 |

**场景处理：** G ROOT 要求原子操作和 seed 隔离，REQ-6 父层要求唯一首页入口；它们随场景一起生效。S 原场景中存在 `the requested workflow` 等损坏占位语，例如 S:2798–2822；既有 Sheet 报告已识别这一点。不能按残缺 WHEN 猜测隐藏评测，也不能删除该场景义务。候选取法是：保留原 description、祖先、scenario 的来源位置，将可读步骤、冲突、缺失分别列出；以未冲突的明确文本形成暂行判据，把影响行为的歧义交主责任者决定。`REQ-x/scenarios[0]` 若用于定位，只是零起始源数组地址，不新造“权威需求 ID”。

计数复核：FOLDER 1+4+2+4+3+3+1=18；ATOMIC 0+5+4+7+4+3+1=24。S3 跨树的第 2/3 分支聚合，是围绕同一次用户操作的候选边界；可在 owner 下拆 UI 与持久化 PR，但验收不随代码目录分裂。

## 5. 六个可落实为 Issue/子 Issue/PR 的片段

以下 `G-*`、`S-*` 是示例标签，不是实际 Braid 编号。每个 PR 的具体代码边界应在接口/变更影响清楚后决定；“一个需求必须一个 PR”不成立。若多个 PR 共同满足某节点，主 Issue 保留尚未满足的义务，不能按合入 PR 数自动结案。

### G-A：首页到认证动作的入口旅程

**源事实。** REQ-1/REQ-1-1 定义公共访问页、session 和错误留存（G:28、46）；REQ-6 父层明确首页 **唯一** `Sign in` link、登录字段/button、登录后 username（G:2837–2839）；REQ-4/REQ-5 也要求首页登录和 active page 控件唯一。REQ-1-1-2 的成功 session 还要服务组织、仓库、工作项（G:152）。历史断点报告已确认最终 shell/body 各一个 Sign in，而自验从 /login 开始；这里复用该事实，不推断官方所有失败均由此造成。

**候选映射。** G1 上位 Issue“首页→账号访问→有效 session”引用 REQ-1 整棵子树，引用 G4/G5/G6 父契约中的入口条款。只有注册/恢复足够独立时才开子 Issue；一个 PR 可同时收敛 shell/home/login 组合，另一个 PR 实现 session 状态改变。G6 保留“从首页以非作者 reviewer 身份进入 PR”的消费义务。

**责任及未决。** G1 是唯一首页入口实现 owner；G6 是其 PR 旅程消费验收者。若 G1 PR 声称“不包括导航”，主 Issue 的未决条款不能被一并排除，需在 G1 内接回或显式转交并确认新 owner。父层约束不因为 G1 的祖先路径不是 REQ-6 就失效。

**应交证据。** 给定新匿名浏览器，从首页可见唯一 link 开始，进入表单、登录、显示 username、通过可见仓库/PR 入口到达；刷新仍是同用户。登录 API 成功或直接打开 /login 只能作为局部证据。关联 PR 描述引用源需求与当前合成页面的证据，不能仅列“实现 Sign in”。

### G-B：组织授权到操作级权限，而不是角色等级比较

**源事实。** ROOT 说角色不是自动累进梯级（G:18–20）；REQ-2/REQ-2-2/REQ-3 规定成员/团队、撤销和私库访问（G:485、697、1130）；REQ-2-3 声明从有效 Owner/direct/team grants 取最高有效角色，团队层级不传权（G:1048–1078）；REQ-5 明定 Write 不可分派/改 metadata/status（G:2148–2153）；REQ-6-3 要非作者且指定角色、Open PR 才能 review（G:3273），merge 只有 Maintain/Admin/Owner（G:3658）。

**候选映射。** G2“组织成员与有效授权”主 Issue 持有授权事实和撤销传播；G3 子义务“搜索/列表/直链消费同一可读规则”；G5/G6 各持本域操作权限，引用同一授权事实。实现可以是“授权关系与查询”“Issue 操作矩阵”“PR 操作矩阵”多个 PR，不是每种角色一个 Issue。共享契约以角色/主体/仓库/操作/当前状态为边界，不用一个 `role >= Write` 条件概括。

**责任及未决。** G2 不替 G5/G6定义内容操作规则；G5/G6 不另写另一套私库授权。REQ-2-3 的“最高有效角色”与非累进操作集要一起解释：候选为先确定有效角色，再按操作枚举判定；同时有 Write 与 Triage grant 时是否按这一规则导致只保留 Write 操作，需要留下精确解释决定，不擅自改成权限集合并集。该边界是源文潜在歧义，不是本次已经发现运行缺陷。

**应交证据。** 组织同名 team 分别属于不同组织时选择授权正确；撤销成员后搜索/直链/受保护操作同时反映新事实；Write 能评论但不能改 milestone；PR 作者不能 review，非作者 Write 可 review 但不可 merge。成功与拒绝都从规定角色/对象初态开始，失败不改状态。权限页面“不显示”和 API“拒绝”分别满足各自条款，不能互相替代。

### G-C：PR 当前版本链与跨分支 milestone 不能掉在接口之间

**源事实。** REQ-6 的 current compare commit 变化使 review stale、inline comment Outdated（G:2826–2829）；REQ-6-1 绑定 checks/审批/保护（G:2855）；REQ-6-3-4 的最新 review 决定及 Request changes（G:3523）；REQ-6-5 合并前重读 head/current commit/保护并原子创建 merge commit（G:3658–3688）。另一个不沿树父子闭合的具体节点是 REQ-5-3-3：标题和正文同时要求 **Issue 与 PR** milestone（G:2696、2702），虽然它位于 REQ-5 且只显式依赖 Issue detail。

**候选映射。** G6 主 Issue“比较→PR→审阅/check→合并状态链”下可拆“创建与详情”“审阅/inline comment”“资格与合并”子 Issue；G4 提供 branch/commit 实现边界。关联 PR 需要说明改变的是哪一版 compare commit 的证据。G5 的 milestone 主 Issue 列两个可验收面：Issue 及 PR；PR 面由 G6 的具体 PR 交付，G5 收证据，绝不因树位置属于 Issue 而默认为 G6 范围外。

**责任及未决。** G6 是 review/check 改变后同页资格更新的主责任者；G4 新 commit 写入完成不等于 G6 已消费。若一个 PR 排除 checks→资格刷新、另一个排除 UI integration，主 Issue 中该义务保持 open 并指定 owner。milestone 是否在 PR 面沿用 REQ-5-3-3 中的 Triage/Maintain/Admin 权限集合，应保留源条款并明确解释，不借“PR 通常 Write 可改”覆盖它。

**应交证据。** 同一可见 PR，从 pending 到 success、从 Request changes 到当前有效决定、从 compare 旧版本到新版本，资格与旧记录标记正确；merge 后 base head/PR 状态同时持久，拒绝二者不变。milestone 的 Issue 和 PR 两面各有当前仓库选项、即时保存/None、刷新、允许和拒绝角色证据。单次正常合并不能证明整条版本失效规则。

### S-A：workbook 子树可直接聚合，但 editor/CSV 必须使用同一身份

**源事实。** REQ-1 是稳定 workbook 状态及统一 editor 的父契约（S:18–35）；REQ-1-3 规定完整导入和只读导出（S:215–220）。REQ-1-3-1 导入失败不能留下列表记录，导入保留原文、空格/引号/换行等 CSV 语义（S:227–241）。REQ-1-3-2 导出当前 active sheet，公式导出计算结果，并保持 filter/grid/formula bar（S:342–352）。REQ-5-1-2 另规定 export 包含被隐藏的行（S:2449 附近）。

**候选映射。** S1 可较直接镜像 REQ-1：上位 Issue“workbook 入口与持久状态”，子 Issue“创建/打开/重命名”与“CSV exchange”，关联若干内聚 PR。S2/S3/S4/S5 作为共享消费者/提供者，以 workbook/active sheet/显示值/过滤视图接口连接；不复制 REQ-1 的另一份“editor 要求”。

**责任及未决。** S1 对首页→打开/创建/导入→editor→刷新/重开负责，S3 实现 grid 的 ARIA 也不使 S1 免于父层验收。CSV 格式解析可独立，但“export 包含隐藏行且使用公式结果”仍是同一 CSV Issue 未决条款；不能只验独立 CSV 编码函数即关闭。

**应交证据。** 首页导入→Sheet1→显示全部文本→刷新/返回/重开同一 workbook；失败无半 workbook。修改公式并筛掉某行后导出 active sheet，下载内容使用当前计算值且含隐藏行，前后 UI 状态不变。相同 workbook name 不是稳定身份的充分证据，需保留可见打开位置/产物身份。

### S-B：编辑、结构、公式、验证、撤销应围绕一次完整操作交接

**源事实。** REQ-2-2、REQ-3、REQ-3-2、REQ-4/4-2、REQ-5-2 是跨分支共同契约。行列变更移动完整记录/验证/公式引用，pivot 旧结果保留直到刷新（S:887–891、1013–1017）；range move 的源/目标/受影响公式要整体成功或保留（S:1498–1502）；undo 恢复值、表达式、结构、规则范围、pivot validity、结果，历史只需当前 session、撤销后的状态仍持久（S:1609–1621）；验证覆盖 grid/formula bar/paste/move 并拒绝整个 bulk operation（S:2600–2620）。

**候选映射。** S3 上位 Issue“原子编辑和可恢复操作”跨 REQ-2-2 与 REQ-3 聚合；子 Issue 可按“grid/range 入口”“结构变化”“undo/redo”分工。S4 提供引用调整/结果，S5 提供验证/筛选规则，S6 提供源范围/有效性变化。关联 PR 必须各自说明对完整操作状态的输入/输出义务；不要求预先造通用插件总线，先选足够实现这些动作的共享调用边界。

**责任及未决。** S3 是完整操作原子性的责任者，S4/S5/S6 是具体状态语义责任者。单个 contributor 可以先交局部实现，但不能把“等待公式/验证/透视”从描述中删掉后宣告对应 requirement 完成。数值验证一般错误 `between <min> and <max>` 与特殊 0–100 场景 `from 0 to 100` 都在源文，须按场景例外保留，不能“统一文案”抹掉特殊要求。

**应交证据。** 选择包含公式和受约束单元格的范围，执行一次会被某个目标拒绝的 bulk move，源/目标/公式/规则立即及刷新后全部未改；结构成功后引用、验证位置、filter 范围正确，undo 恢复同一整体状态。每个 state 字段不是独立 Issue，证据是用户动作的整体结果。

### S-C：透视可以相对独立，源关系、筛选及删表不能独立结案

**源事实。** REQ-5 的 sort/filter/pivot 含义不同（S:2242–2251）；REQ-5-1-2 filter 只隐藏、不删不重排，CSV/pivot 仍包含隐藏行（S:2435–2452）。REQ-5-3-1 创建独立 pivot worksheet，显式刷新替换结果；删去源字段后报确切错误、保留最后成功结果（S:2793–2796）。REQ-2-1-4 要求删结果表后释放源表约束；源表仍被依赖时拒绝删除并保留双方（S:757–772）。

**候选映射。** S6“pivot 结果及源依赖生命期”可保留 REQ-5-3 子树形状；“聚合/布局”“source change/refresh”“删除依赖释放”可以按真实代码边界进入一个或多个 PR。S2 持有删表旅程，S5 持有过滤语义，S3 持有源结构改变；三者只引用同一个 source→result 关系。

**责任及未决。** S6 对依赖关系创建、重建、删除释放负责；S2 对用户确认及拒绝后页面/数据状态负责。REQ-2-1-4 指向 REQ-5-3-1 是完整删表验收条件，不强制删表功能等待整个 pivot 编辑器写完才动工。按源表头文本找字段还是稳定字段身份，是实现待选；必须能够区分移动字段仍有效与删除字段无效，不能由“header name 还在”猜定。

**应交证据。** 先过滤隐藏部分源行，再创建 COUNT/SUM 等 pivot，结果包含隐藏源；行列移动后旧结果暂留、刷新按调整后源重算；删除源字段时报错保留旧结果；删除 pivot 结果后源表能按生命期规则删除。验收关系是双向的，单独透视渲染正确或单独删普通表成功都不足。

## 6. 直接镜像树与按实现单元组织的适用边界

| 候选 | 优点 | 适用条件 | 本题反例 / 代价 |
| --- | --- | --- | --- |
| 每 FOLDER 做上位 Issue、每 ATOMIC 做子 Issue | 身份与树一一对应，源文位置容易找；初始覆盖清楚 | 每叶确有独立动作、可明确独立 owner，父 owner 持续承担共同契约；工作量足以分开 | G 登录入口落在多个父层；G milestone 横跨 Issue/PR；S 单次结构变化横跨 2/3/4/5。若每个 owner 只验自己叶子，树仍会全绿而完整行为失败。维护 47/24 个叶级工作项还会产生无新增事实同步，但数量本身不是判失败理由。 |
| FOLDER 为责任与上下文、内聚叶子聚合为实现 Issue/PR | 保留用户指出的天然分域，同时减少同界面/同事务的拆分开销 | G 身份访问、组织对象、S workbook lifecycle 等子树内部共同对象/入口强；父约束有具名 owner | 大的 REQ-6、REQ-3 仍需按实际实现与验收分成子义务，不能用“聚合”遮蔽失踪的 leaf/scenario。 |
| 原树作唯一需求源，Issue 按完整实现/验收单元组织 | 可用一次用户动作收敛跨域状态，减少“不是我范围” | S 操作原子性、G 授权传播/PR commit 失效等横切行为；覆盖映射可反查每个源节点 | 需要维护稀疏的 source→owner/PR/evidence 映射；若从树完全脱离，容易重新退化为 UI/API 分工后无人负责旅程。 |

**推荐是第二种为起点、第三种处理有证据的跨域单元，而不是预先否定镜像。** 保持树的 ROOT/FOLDER/ATOMIC 身份；对每个非叶先读自身契约，再决定它是上位责任、共享契约还是仅导航索引。只有可以指出独立交付/审阅/阻塞/未决义务时才增加 Issue，不按每个名词/字段/场景自动开项。

## 7. 主规划需要保留的可检查义务与未决选择

1. **全节点责任，而非叶子计数。** 当前表给出 107 个源节点的主责任候选；实施前核实每个实际工作包都能反查源身份，FOLDER 自身 description 不能由“所有子 Issue 已关闭”自动满足。主 Issue 的关闭依据是本域源义务及其证据，PR merge 只是候选实现进入集成。
2. **消费义务不能通过排除范围消失。** 共享能力被某个 PR 排除时，保留源节点/具体条款/承接 owner/缺什么证据。只有接受转交的 owner 或仍明确开放的原 owner，才算有承接；“通知过别的 agent”不算。
3. **上下文需要祖先与相关边，不需要整树重复全文。** 实现者最小入口为当前工作包、完整源叶、其自身祖先、所引用共享契约的定位，以及当前未决依赖。G6 的首页条款消费者不在其后代，应通过共享义务显式连接；S 的全部跨状态语义不能只靠 ancestor closure 得到。
4. **需求版本/源定位与证据条件。** 证据绑定源条款、应用候选及具体初态/角色/旅程/结果。父层约束变更应找到相关消费者并重判对应观察；不能只检查叶子 hash，也不能把无行为差异的新 commit 等同全部证据失效。
5. **不要把树依赖强制成串行排程。** 先标清是对象入口、语义依赖、验收依赖还是真实施阻塞；对先交付的基础功能保留具体集成义务。S 切表/删表的反向领域依赖是现成反例。
6. **源内部歧义仍需 owner 决定。** G 多来源 highest role 与非累进矩阵、milestone 的 PR 角色适用；S 损坏 scenario、特定数字错误例外、sort/引用语义应按原文保留具体问题，不用“最佳实践”自动覆盖。

本报告只建立可复核的映射设计，没有观察它在新 run 中是否改善行为、减少上下文或提高成绩。可先由主规划用现有记录检视上述映射能否暴露已知遗漏；任何新模型生成/官网重放/有预算实验仍需另一轮具体授权。
