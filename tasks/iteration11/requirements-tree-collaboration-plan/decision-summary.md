# 决策摘要：把需求树变成有责任、有证据的协作骨架

2026-09-30；规划完成，未实施。详见 [完整方案](plan.md)。

**建议采纳这个方向：从 Requirements 树开始拆分，用 Issue 管原要求、决定和验收责任，用 PR 管候选实现与证据。默认按内聚子树分域；对跨分支的完整操作明确聚合与总责任，保留原树全部身份。** 不需要预先规定每节点一个 Issue，也不能因实现按模块分工就丢掉父层约束。

两题原树共 107 个节点，包含 36 个 FOLDER；父节点不是空目录。GitHub REQ-6 的首页唯一 Sign in，Sheet 的稳定 workbook 状态、原子编辑、公式/验证/透视一致性，都必须进入工作包及验收。已给出 [全节点责任表和六个实例](mapping-review.md)，它们是候选映射，尚未创建工作项或证明行为覆盖。

需要改变的是几个具体决定条件：

1. **分配不等于覆盖。** 原节点 ID 出现在 Issue/spec 只证明可追溯；验收须能区分原文要求的对象、角色、初态、入口、结果和例外。GitHub Milestone 的 Issue 面通过，不能证明 PR 面完成。
2. **排除不等于交接。** 某项不做的原要求，必须由具体 owner 接手或仍由原 owner 保持开放；不能写“应属另一组”就从两边消失。
3. **共享事实各有归属。** 原树是要求权威，稳定合同进现有项目文档，Issue 保当前义务，PR 保候选与证据；完成模块不再镜像所有全局 head。
4. **关闭须有证据，维护须有停止点。** 一次执行一个证据身份；hide/resolve 前保护整串未决事实；只有自己的已完成整理、没有新事实和待办时就结束。

Braid 已有这些方法的一部分，不能归因成“以前没教”。实际边界是父子 Issue 不继承正文，PR 只自动展开直接关联且 OPEN 的 Issue 正文，ready/merge/close 不替代显式交回；resolve 折叠整 thread 历史前缀。当前已有范围回执，两处文档与实现差异已记录。细节见 [能力边界](context-boundary-review.md)。Skill 能规范操作，自动传播、阻止误折叠或消除 self-wake 则需另外设计 runtime，当前不把它们列为开工范围。

**下一步先用既有记录做桌面回放及静态语义核对。** 比较直接镜像与推荐组织，检查父约束可见/消费、无人承接比例、证据对应、无新事实重复工作及上下文冗余，同时保留正确协作与停止的正例。不能用字数、Issue 数、ID 引用数或全部 CLOSED 作为质量指标。该阶段不运行 Factory/Braid 测试，也不跑模型生成。

随后才细化材料差分、独立预演和开工复核。要验证模型采纳及评分，另申请冻结输入/材料/预算的 `self_funded` 实验；初步可用两题×现行/候选四次生成作探索，不足证明稳定收益。费用、受限模型 session 配置及重复次数尚未授权。

完整 GitHub 与 Sheet lineage 已纳入；PR23 原始缺口已补齐，不沿用旧说法，也不拿 I11 收尾切片或 4/59 分差解释全程。现有证据支持研究这个方向，不支持承诺提分或节省多少 token。无资料访问阻塞；未改 runtime、variant、应用、Braid 工作项或他人报告，未运行测试、生成、评测、部署或提交。
