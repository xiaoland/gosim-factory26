## 主线与判断依据

本项目只有 Coding Agent 开发代码；用户参与目标、设计和授权。设计应使一次变更沿着“定位责任与消费者 → 准备必要依赖 → 修改并取得反馈 → 验证跨组件行为 → 同步合同与说明”完成。Harness、实验系统和共同开发的上游仓库都是这条开发路径中的对象。

组件边界按它拥有的输入、行为与输出确定。开发设施把组件边界连接到环境和检查入口，使局部修改只承担实际依赖的成本。判断方案时观察取得首次有效反馈的时间、定位影响所需的额外搜索、检查结论是否覆盖实际行为、恢复任务需要重新调查什么。暂不建立评分平台。

更大的问题是当前开发单元与实际想改变的对象不一致。
Agent 想改一个 Harness，却要理解共享配方、二次物化、共同执行器、特定实验清单和包内默认配置；想验证一个入口，又被迫带入完整 benchmark 或历史 ZIP。
这种额外负担来自责任与依赖，不会仅靠更多导航、规则或测试消失。
因此先让独立变化的对象拥有自己的行为，再为它连接必要工具与反馈；不以统一配置或统一生成核心作为架构前提。

## 责任划分：先确定谁决定什么

下表是依据现有消费者推导的维护责任，不要求每行成为独立仓库、服务或目录。

| 责任及现有落点 | 自己决定的事实与输出 | 消费者以及依赖边界 |
| --- | --- | --- |
| 原生工具及依赖准备：scripts/runtime.py、submission 的 Docker 构建 | 可执行工具、协议适配与运行库的取得和构建结果。 | 各 Harness 直接取得实际需要的依赖，不通过另一种 Harness 的 ZIP 提取；不规定所有 variant 必须使用同一个全量 runtime。依赖准备不读取实验题目或 Agent 角色。 |
| 各 variant 的完整 Harness：variants/<name>，通用文件与证据操作归 scripts | 本实现的指令、模型、原生角色、技能选择、上下文接入、协作方式，以及如何产生并交付应用。 | variant 自己使用 Pi/Codex/Braid 的实际接口；不以共同 Factory 配方或生成核心作为必经层。每份内部可以复用自己的本地/参赛执行逻辑。 |
| 边界适配：submission 入口、raw 入口、ARC adapter | 将各自一侧的公开输入、过程终态和交付约束转换到另一侧。 | 平台入口不反向成为生成核心的依赖；ARC adapter 不解析任意 Harness 的私有会话布局。 |
| 实验执行与原始观测：local_experiment、otlp_store | 对明确任务执行 argv，管理 run 工作区、进程终态、输入和产物索引、OTLP 批次。 | 消费 Agent/bench 组合的公开命令和结果；过程数据的业务语义与分析归使用者。 |
| 证据查询：inspect_runs、run_feedback、viewer、analysis 接入 | 识别已声明的生产者/格式，导航原始证据，提供有条件的摘要。 | 查询依赖证据合同；历史读取支持不构成保留旧执行器的理由。 |

Braid/SVC 的内部开发仍属于各自仓库。消费它们的 Harness 持有接线选择，项目维护依赖取得方式和跨仓库检查入口。
共享可以发生在稳定的外部接口、工具资源或文件操作上，不要求共同生成流程。
若一次局部实验必须先给共享 schema 增加字段、修改所有 Harness 都会经过的分支，应先检查行为是否放错了位置。
原生工具与上游工作树的绝对位置由开发入口解析。共享环境、密钥或 Docker 选择在调用入口注入，不由底层组件自行搜索其他入口的默认配置。

模型 API 的能力事实、兼容参数与实测记录有独立归属；Harness/raw 配方选择本次模型与推理方式，原生接入负责正确转换。相同 API 事实避免手工维护多份副本，不同配方的选择允许不同。真实支持结论必须带端点和请求条件，不能由 native metadata 推导。

## 分开描述构建依赖和运行调用

构建关系如下；箭头表示产物供右侧消费：

```text
Pi/Codex、浏览器及协议适配的构建输入 → 可直接取得的工具资源
                                                ↓ 按需使用
某个 variant 的源码 + 它选用的 Braid/skills → 该 variant 的可执行目录/制品
                                                ↓ 公开 Agent 入口
需求 + 官方 Runner/bench 适配 + 实验选择     → 一次实验及其证据
```

团队 Harness 与 raw 的构建入口可以复用已有 Docker 构建机制，同时直接取得自己所需的工具资源。
raw 制品不需要先构建完整团队 Harness；任何 Harness 的构建都不经由实验清单取得依赖。
共享缓存按真实安装或编译输入复用，指令与模型选择调整不应导致无关原生二进制重建。

运行时由调用入口选择 Agent 制品、题目、bench 适配器、模型连接和执行参数，组成一次调用。通用实验执行器运行该调用；bench 适配器调用选定 Agent，并负责其边界上的冻结与评测约束。各 Harness 自己负责内部行为。
开发侧应能直接运行所选 Harness 的源码入口，传入一份小需求和已准备依赖；不要求先打 ZIP、取得整个 benchmark 或形成实验矩阵。
正式实验才冻结本次源码、依赖、需求和参数，产生独立实验身份；打包是否通过与生成质量是否合格是两项不同判断。

跨进程结果先复用已有公开终态。若 Runner 缺少可独立消费的生成结果，才在它与 Agent 入口之间定义最小共享结果合同；具体字段需核实实际 Runner API。文件存在或 exit 0 不能单独替代既有的完整终态检查；native 终态解释属于对应接入边界。

## 来源、构建输入与运行身份

三个事实分别处理：来源声明说明依赖从哪里取得；构建输入说明哪些材料影响这次构建；运行身份说明实际执行了什么。完整工作树快照可以保留为证据，构建有效性只依赖实际构建输入。优先让 Cargo/npm/Docker 处理增量准备，不在外层以整仓文档变化拒绝生成。

默认来源应能从仓库声明重新取得，固定 revision 表示要取得的具体版本。共同开发可以显式选择现有工作树，记录真实内容与来源；此选择不伪装成固定 revision，也不要求先提交或自动重置工作树。开发侧 SVC CLI 与被装入 Agent 的 SVC Corpus 是不同依赖，分别说明取得方式和消费者。

准备顺序是：读取不依赖完整环境的最小来源声明，取得当前目标必需的依赖，然后解析其能力材料。普通检查不触发 benchmark 安装、模型请求或完整包构建。已有来源或工具不符合声明时，指出具体差异和相应准备动作。

本次使用的代码和工具路径在调用入口明确传入，底层不再次依据当前 ROOT 或个人环境猜默认值。
这不要求发明一份所有 Harness 共用的“有效能力对象”；记录和传递实际依赖足够。
开发调试允许直接消费显式选定的工作树，记录本次观察条件；修改后重跑取得新反馈。
正式运行消费冻结资源；开发工作树可以继续变化，但不原地改写其他执行正在使用的产物。
本地开发和参赛包应使用同一份 Harness 行为源码，允许平台路径与启动适配不同，不维护两套行为逻辑。

来源证据、实际原生配置与运行制品可以有各自摘要。单个共用 lock 是否拆分，需在 LLD 核实 npm 安装关系；不能只为追求较小摘要复制依赖算法或增加多套手工同步的锁。
variant 独立意味着可以自己选择依赖，不意味着现在就要创建四套工具安装系统。
首先解除对未选行为的语义依赖，再根据实际版本选择与构建成本决定缓存范围。

凭据保留单一配置来源，按调用边界注入；生效摘要保留来源标识和非敏感参数。临时转换文件由创建它的调用负责清理，不生成另一份要求用户维护的长期配置。协议失败先保留原始状态、响应与上下文，再作原因判断。

## 信息归属与历史退出

信息按成立依据区分：产品要求与合同说明应当成立什么；源码和有效配置说明实际机制；运行证据说明特定条件下观察到了什么；packet 保存提案、决定和未决判断。恢复任务时不以 packet 代替进程状态，也不以历史成功代替当前兼容性。

| 归属 | 持续维护的内容 |
| --- | --- |
| AGENTS | Coding Agent 常驻约束、组件与语义导航；局部约束按需靠近组件。 |
| CONTRIBUTING | 开发准备、改动到检查的对应关系、跨仓库集成与收尾。 |
| README | 项目用户所需的用途、能力和使用入口。 |
| PRD / 跨组件技术说明 | 稳定目标、范围与共享合同；源码/schema 已充分表达的字段不重复抄写。 |
| Deployment | 运行、打包、证据定位和故障恢复；开发环境准备由开发说明导航。 |
| packet / reports / runs | 当前任务控制与设计 / 特定条件的历史结论 / 原始运行证据。 |

模型列表、工具版本、默认值和参数集合优先由执行入口及声明读取，文档解释意义与选择方法。开发说明维护少量“改动什么，读哪里，准备什么，查什么”的导航，不另建一份自动依赖图数据库。选定目标的生效条件应可解释，不能让文档预览与执行分别推导默认。

历史内容按消费者处置：活动入口迁到当前合同；仍有用途的受控探针明确其范围；历史证据保留必要读取；无活动消费者的旧执行分支退出当前入口并在获准实施时删除。旧报告保持原始条件，长期文档同步撤下旧默认。没有消费者不等于没有保留价值，但不再据历史材料指挥新运行。

变更完成时同步实际改变的合同及操作说明；没有外部行为变化的内部重构不强制修改所有文档。当前配置或入口替换必须同时处理旧入口，避免“新功能完成、旧默认继续生效”。
