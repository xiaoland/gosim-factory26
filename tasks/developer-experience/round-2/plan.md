# 第二轮实施顺序与效果判断

用户已确认方案并明确要求开始，长期文档与代码注释的限定实施已获授权。
本轮不使用子 Agent，不运行 Factory/基础设施测试或新 benchmark。
本轮按约定范围实施与汇报；用户随后授权提交，提交边界见本任务 packet。

## 实施顺序

1. 整理当前事实与历史决定。
   从本轮 inquiry 和现行源码提取成立的约定；将 DX 旧 design 中过期测试建议、首轮实施状态与第二轮提案分清。
   只将确定已转交的任务改为后继入口，未完成或证据不足的任务保持开放；不重写历史运行记录。
2. 建立跨组件技术说明，整理产品与运行说明。
   先写 Product TDD 中的职责/调用链/终态语义，再从 PRD、Deployment 移除重复或过期叙述。
   所有“当前支持”都对照实际入口；当前实现缺口直接说明并链接已有任务，不扩展本轮实现。
3. 按已核实知识补局部注释和 docstring。
   只修改方案列出的边界；不得改变控制流、参数、提示词、模型、材料选择或运行数据。
   注释只能支持当前行为，不能凭预期把 best-effort 归档称为完整证据。
4. 最后更新导航与开发使用方式。
   AGENTS 目录地图、CONTRIBUTING 的角色/技能修改路径、docs/index 的当前说明与任务/历史分区应指向已存在的内容。
   task 状态只在各 packet 维护，索引不复制详细进度、PID、分数、凭据或授权。
5. 对本次实际文档改稿作编辑审阅并汇报。
   核对链接、删除的旧推荐及注释与实现的一致性；不保存或运行自动化测试脚本。
   说明实际改了什么、哪些运行能力尚未改善，不以文档完成声称实验效果提升。

## 验收方式

这是对本次文档与注释交付的人工阅读复核，不是 Factory 设施测试，也不新增可执行验收框架。
使用本轮调查的五个真实维护问题，记录最终实际阅读路径与仍需猜测的内容：

- 调整 mixed 的 executor 模型或技能：能区分 Braid 主会话、Pi 子代理、材料打包各自的位置及影响，不需要阅读旧 presets 任务。
- 修改 Runner 接入：能解释入口退出、部署失败、评分和诊断状态为何不同，并找到对应代码及旁注。
- 接手既有 run：能根据记录生产者选择现有查询入口，知道其限制，不把 lack of viewer discovery 当成没运行。
- 恢复任务：能辨认当前设计、授权、未完成验收和已转交事项；旧 task 的开工许可不被误用于当前任务。
- 准备另一机器开发：能区分共享工具、开发 SVC、参赛 Corpus 和本地上游修改，知道哪些可取得、哪些恢复条件尚缺。

通过条件是答案能由当前文档和相邻实现说明支持，历史上下文不是理解现行约定的必备输入。
阅读中遇到尚未实现的功能可以明确答“不支持/待处理”，不得为了让场景看起来通过而修改产品行为。
不以文档篇数、注释数量或固定跳转次数判定质量；优先删除无消费者的重复信息。
