## 样本 A：实验基建改进

### 事实链

调查阶段用户要求继续分析既有实验及其子 Agent，判断哪些工作应由确定性实验设施承接（turn `01a0fab1-6d86-7312-b311-63a778e5084c`）。Agent 随后把问题收敛为“设施之间的交接仍需主会话反复解释和拼装”，并列出失败阶段接续、统一状态/阻塞解释、完整检查点和启动后登记等缺口；该消息称主会话读取了 26 个 turn 和 8 个实验相关会话，这是会话中的报告，不能替代独立全量审计。

中段出现多次从调查转实施的边界变化。真实离线材料显示约 1.4 GiB 材料复用后更快，但恢复来源因缺少连续停写证明、Git 历史曾重建而只能标为 `partial`。同一时期主线还需要人工拼接 task、experiment、case、variant、job、attempt、run、Braid session、hosted submission 等对象，用户明确指出底层身份无需合并，真正缺的是统一查询入口、状态投影和下一步动作（线程中的用户 turn `01a0fb4a-dd05-7343-973c-77c142086730`）。

后段用户授权开工（turn `01a0fd6b-16f0-7b41-8539-2d141e26d4c3`）。实施中连续暴露边界问题：Docker 监督者与 Harness 共用容器/UID，入口可能写发布存储；新 I14 `main.py` 原先不能调用 `--execute-prepared`；容器逻辑路径和 Mac 导出路径混淆；同一 artifact 的入口、runtime、技能和 Braid 角色重复做整份 payload 校验。最终提交 `302878bc`（监控临时载体释放）和 `83e723d0`（定义/派生配置/运行状态分离、checkpoint/prepared v3、恢复入口和 Docker 导出映射），20 个 Python 源码和生成入口编译、离线读回通过，但完整打包、启动、热恢复耗时仍未验收，原因是缺少新的 I14 冻结 runtime/material（最终 Agent 消息 `msg_0d455cdf...4c6f734`）。

### 对恢复成本的解释

**观察。** 同一次任务中，主 Agent 需要反复确认“哪个身份、哪个路径、哪份状态、是否完整恢复”，并在实际接线后才发现准备入口、路径映射、容器权限和重复校验问题。定义资产、派生输入、可写运行状态的边界是在用户补充后才贯穿到 variant 内部。

**推断。** 恢复昂贵的核心原因不是单纯目录大，而是跨层合同没有在一个可消费的投影中表达：接续者必须从多份 packet、JSON、容器路径和子 Agent 回报重建状态。缺少真实冻结材料时，编译/离线读回只能证明局部能力，不能证明端到端恢复；如果入口没有显式记录这一限制，下一 session 很容易把“已实现”误读为“已验收”。

**候选优化。** 先复用现有 Lab projection/status、stages 和 available_actions，检查它们能否覆盖来源身份、定义资产引用、派生输入、可写状态位置、当前阶段、阻塞原因、缺失证据和下一合法动作。只有现有投影无法表达具体缺口时，才由 advisor 判断是否需要最小字段或代码调整；不预设新增 handoff schema、expiry 或另一套权威状态。把“局部验证”和“端到端未验证”作为不同状态，避免继续考古。对路径和权限优先复用已有规范映射。

## 样本 B：整理项目数据、代码与文档

### 事实链

开头用户要求整理近期频繁迭代留下的数据、代码和文档（turn `01a0fcde-ac1c-7f33-b677-a386925a4520`）。Agent 发现入口文档与近期任务状态漂移，工作区混有多项任务未提交改动，并盘点约 2,400 个未跟踪 task 文件、约 402 MiB；还发现文档中的 `gc-plan` 与当前 CLI 的关系需要区分历史冻结协议和现行入口。

中段 Agent 自行把工作称为“首轮”，先交付文档入口、代码归属和数据保留清单，并向用户请求按该范围推进。用户随后纠正：“为什么又是首轮，难道还有第二轮吗？为什么不全部做完呢？”（turn `01a0fd0c-70d1-7fb3-84b4-ad92c7929d6b`）。Agent 承认这是自行收窄范围，继续落实代码职责、版本归属、数据证据导航、Git 忽略边界和剩余文档入口。

尾部报告称 465 个链接、语法和差异检查通过；有实际消费者或恢复价值的材料保留原位，没有强行删除（`msg_05fe37c...3f5f91487d29d22ec4ea17226fd`）。

### 对恢复成本的解释

**观察。** 仓库整理会话的主要返工来自“当前/历史”混写、工作区多任务修改未分界、未跟踪文件不等于可删除，以及 Agent 自行增加“首轮”边界。用户需要再次纠正完成定义，才能让已盘点的材料进入实际整理。

**推断。** 累积叙述会掩盖当前入口、完成标准、待决对象和证据限制。新 session 即使找到 packet，也要重新判断哪些是事实、历史或建议；维护一个准确的当前答案可以减少这种工作，尚不能据此要求机器可读协议。

**可实施优化。** 在每个长期任务 packet 顶部维护短小的当前状态块：目标、已授权范围、已完成证据、未完成/阻塞、下一动作、最近更新时间和权威证据入口；历史叙述下沉。对于工作区混合修改，保存一次基线清单和任务增量清单，恢复时直接读取差异。完成定义必须由用户目标或 packet 中明确的验收条件产生，Agent 不得自行引入“首轮/下一轮”。

## 样本 C：factory26 main 的协调型长会话

### 事实链

既有 `experiment-dx-review` 复盘统计该主线自 2026-10-01 起 26 个 turn、551 个命令，并引用 8 个实验相关子会话。其早期主线把问题归纳为“准备、传输、启动、接续、监控和 Console 登记各有回执，但主会话仍反复拼路径、版本和依赖”。后续用户要求把人的认知入口统一，而不是合并底层 producer identity；Agent 因此提出 Intent → Compiler → Controller → Projection 四层，默认视图只展示“实验—执行尝试—证据”。

本次定向读取的末段 `01a0fbcc-ffd9-7872-85f6-e4a35872416b` 暴露了具体交接错误：主线把 I14 的 GLM-5.3/K3 配方增量混入 I13 恢复会话，用户指出不应让 I13 恢复 owner 处理 I14；Agent 承认并撤回附带要求。该事实说明即使已有多份 packet 和 owner，交接消息仍可能携带越界范围。

本轮修订前的实验 DX packet 还存在恢复歧义：顶部保留“待开工/尚未实施”，文末却记录 2026-10-03 已完成并合并，接续者必须自行裁决。本轮已改写当前入口，原文保留在[历史页](../../experiment-dx-review/history-20261003.md)。

### 对恢复成本的解释

**观察。** 命令数量很高，主线同时协调多个 owner、供应商、运行身份和恢复路径；错误不是缺少更多身份字段，而是人要把多个身份和局部回执投影成一个下一步判断。交接消息没有稳定的范围与 owner 校验时，I13/I14 会串线。

**推断。** 这类长 session 需要把保存事实与当前决定连起来。早期投影缺口已有设施改进覆盖，但 packet 只按时间追加仍会产生顶部旧状态、底部新状态的冲突；长交接文本也可能混入相邻任务。

**候选优化。** packet 采用“当前状态块 + 追加审计日志”双层结构，当前块只保留一个权威版本，旧状态必须显式标为历史。先用现有 Lab projection/status 和任务 owner 入口表达 owner、scope、来源、允许动作、阻塞和证据；发送前做 scope/owner 校验，拒绝把 I14 动作交给 I13 owner。只有现有入口无法承载具体交接约束时，才由 advisor 判断是否需要最小 schema 或代码调整。保留底层 identity 分离，但提供单一当前答案和下一步命令。

## 跨样本结论

1. **最常见的重复成本是重建状态，不是缺少更多文档。** A 中要拼路径、资产和状态；B 中要辨别当前/历史和工作区归属；C 中要把多个 producer 回执还原成下一动作。优先交付短的当前投影与规范 handoff，而不是继续扩充总说明。
2. **局部“完成”经常被误读为端到端完成。** A 已编译和离线读回但热恢复未验收；B 已盘点后被误称“首轮完成”；C 的 packet 顶部/末尾状态冲突。状态模型必须区分实现、局部验证、真实运行、交付和未验证。
3. **跨任务消息必须保持负责人和范围清楚。** C 的 I13/I14 串线是直接证据；但这一错误不足以证明需要新建机器可读交接协议。先采用现有 packet 与会话负责人，核对本条增量属于哪项任务；是否还缺设施能力须由实际无法完成的操作证明。
4. **恢复材料要以“下一步可执行”组织。** 每个 packet/run 应让接续者回答：已有产物能否消费、阻塞在哪里、缺什么证据、下一合法动作是什么。否则即使保留所有原始 JSON，也只是在保留更多考古材料。
