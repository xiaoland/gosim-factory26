# Hackathon 本地模拟测试集：覆盖与验收预演

## 核验目标与结论

本预演只读取任务包、实施计划和 WSL 的两份公开 `requirements.yaml`，未读取或运行被测应用、模型、Runner 或现有测试。核验的是已认可方案能否把公开合同转成独立、本地 UI 场景，而不把本地结果说成官方评分或服务端实现证明。

**允许进入开工复核：是。** 47 条 GitHub ATOMIC 加 24 条 Sheet ATOMIC 的固定分母与“每场景独立 app copy、场景内连续操作”的设计可实现。进入复核前应把下列最小约定写入实施材料和覆盖清单；它们不需要私有 API、参考应用或额外运行时。

两份 YAML 的结构统计为 GitHub 47 条 ATOMIC / 100 个 scenarios，Sheet 24 条 ATOMIC / 100 个 scenarios。依赖图当前没有环，但这不改变场景独立运行的结论。

## 影响实施的最小处理

### 1. ATOMIC 是计数单位，ROOT/FOLDER 是继承合同

不能只将 71 条 ATOMIC 的正文映射到用例。GitHub `ROOT` 规定精确英文可访问名称、种子/隔离会话、非单调角色矩阵与服务端原子写入；`REQ-1` 定义当前浏览器 session，`REQ-2` 至 `REQ-5` 补充可见性、权限和跨账户观察，`REQ-6` 规定直接导航、同页控件唯一性及 PR 导航链接。Sheet `REQ-1` 规定稳定的编辑器地址、ARIA tab/grid/gridcell 和选择状态，`REQ-2` 至 `REQ-5` 继续约束菜单角色、当前工作表边界、公式栏和数据操作。

最小处理是在每个覆盖项保留 `atomicId` 之外的 `inheritedContractIds`、选择器作用域和“该断言观察的祖先条款”。祖先条款不新增分母，也不单独作为通过项；它们进入对应 ATOMIC 的必需检查。例如 `REQ-6-3-3` 的重复 `Add comment` 需按 `REQ-6` 的已变更行作用域定位，不能只按同名控件全页匹配。

### 2. Sheet 的同名种子不能做成一个全局“Q3 Sales 已验收”

下列公开 GIVEN 使用同名 `Q3 Sales`，但状态彼此不相容：

| 场景组 | 要求的初始状态 |
| --- | --- |
| `REQ-1-1-1`、`REQ-1-2-*`、`REQ-1-3-*` | `Sheet1` 的 `A1=Region` |
| `REQ-2-1-*`、`REQ-2-2-*` | `Sheet1`、`Sheet2` 与 `East/1200`、`North/800` |
| `REQ-3-1-*`、`REQ-3-2-*` | `A1:B2=Item/Qty, Pen/4`，目标 `D1:E2` |
| `REQ-4-1-*`、`REQ-4-2-*` | `A1=2`、`B1=3` 及指定公式 |
| `REQ-5-1-*`、`REQ-5-2-1`、`REQ-5-3-1` | `A1:C6=Region/Sales/Status` 与销售数据 |

每个覆盖场景须绑定一个明确的 `seedProfile`。交付种子检查在 UI 准备前、针对该 profile 记录；UI 准备随后在该场景独立副本中通过公开控件建立固定状态。两者分开报告：UI 准备成功不能把交付种子缺失改写成成功，交付种子不匹配也不应让其余可观察功能被误报为业务失败。

### 3. GitHub 角色与状态分成可公开构造和只能交付的两类

可由预先写定的公开 UI 步骤建立的前提包括：新账户、组织 Owner、团队、成员和仓库角色（`REQ-1-1-1`、`REQ-2-1-2`、`REQ-2-2-1`、`REQ-2-2-3`、`REQ-2-3`）；分支/PR 的普通前提以及 Admin 通过 `REQ-6-1` 的 `test status` 控件设置检查状态也有公开入口。此类准备使用固定后缀和固定步骤，不从 codex-base 的页面或源码反推值；准备本身失败时，依赖它的目标检查为 `blocked`，不改成目标需求 `failed`。

以下状态没有可替代的公开构造路径，缺少交付值时只能记录材料缺口：

- `REQ-1-1-2` 的“unavailable account”分支；可注册账户、未知账户和错误密码不等于可用性被撤销的账户。
- `REQ-5-3-2` 的仓库既有 label，以及 `REQ-5-3-3` 的既有 milestone。`REQ-5` 明确本产品不提供创建、编辑或删除 label/milestone 的界面。
- `REQ-4`、`REQ-5`、`REQ-6` 中仅以 Write/Maintain/Admin/Read 等角色描述、却没有可登录凭据或无法由上述公开准备建立的指定账户、私有记录、PR/分支状态。`REQ-6` 只要求每个 role account 有用户名、验证邮箱和密码，并没有授予测试从被测实现提取这些值的权限。

覆盖清单应对每个 actor/状态标注 `ui-prepared`、`delivery-seed` 或 `undefined`。`undefined` 保持在 71 条分母中，场景报告为 `blocked` 或 `unexecuted`，不能套用通用 `alice-dev` 登录或读取旧应用来补值。

### 4. clipboard、多会话和可见地址是场景合同的一部分

一个场景可有多个隔离 `BrowserContext`，但它们必须连接同一个场景 app copy，才能观察同一服务端状态；不同场景才使用不同 copy。至少应覆盖：

- `REQ-1-2`：当前 context 登出后，Back 和此前受保护地址恢复未认证状态，同时“只影响当前 browser session”不能被单 context 断言取代。
- `REQ-2-2-3`：Owner 写入成员关系后，独立新成员 context 看见组织、却仍对未授权私有仓库得到 `Access denied`；`REQ-5` 和 `REQ-6` 的作者、审查者、维护者也依此分 context。
- Sheet `REQ-1-1-1`：从页面实际获得的稳定编辑器地址可在同一或后续浏览器 session 直接重开。可复用已访问的可见地址，不能猜测路由格式。
- Sheet `REQ-3-1-2` 与 GitHub `REQ-3-2-3`：clipboard 权限和外部内容是浏览器前提。应显式授予并读取/写入浏览器 clipboard，分别核对 Ctrl+V、`Paste` 和 `Copy clone value` 的公开效果；浏览器拒绝权限是 `blocked`，不是应用业务失败。

### 5. UI 只能验证外部效果，不能证明全部服务端语义

GitHub `ROOT` 要求服务端持久化、当前 session/目标对象权限检查和原子写入；`REQ-6-5` 还要求合并时重读分支头、当前 compare commit 与保护条件并创建特定父提交。Sheet `REQ-3` 也要求一次操作全量改变或保留旧状态。UI 可以通过失败后可见状态、刷新和另一 context 观察“无部分记录/状态一致”的外部代理，不能证实数据库事务、并发原子性、服务器端鉴权位置或 merge commit 父关系。

每个结果应标明 `ui-observed` 的证据范围。需求级“通过”只能表示定义的本地可观察检查全部通过，不能表述为已验证内部实现；不新增第五种场景状态。

### 6. `dependencies` 不能成为场景调度 DAG

两份依赖图虽无环，依赖仍表达产品上下文而不是一次本地运行的前序作业。例如 Sheet `REQ-2-1-2` 依赖后面的过滤与验证需求，GitHub `REQ-6-5` 依赖 `REQ-6-1`/`REQ-6-3-4`，但它自己的合同又要求独立恢复的可合并和拒绝 PR 状态。若据此串行调度，会把上一场景的可写状态错误地带到下一场景。

保留 dependencies 供覆盖追溯和准备阻断说明即可。Runner 只按独立场景派发；每个场景的公开 UI 准备自己验证前提，不能因依赖场景没有运行而自动跳过或标为通过。

### 7. 部分 suite 和正例证据需要分开命名

报告至少同时给出：目录中定义的 71 条、coverage 清单已映射数、当前选择/实际注册数、已执行的 pass/failed/blocked 数以及未执行数；并核对官方报告恰好返回选择的 `scenario_id`。未注册的场景是 `unexecuted`，不是 skipped/pass，也不能从 47/24 分母移除。

因此“71 条完整覆盖”只能指 **71 条均有覆盖映射和解释**。只有所有必需场景已定义并取得结果时，才可称完整评测；存在 `blocked`、`unexecuted` 或未定义角色/种子时，不可称 71 条均已验证。

当前不引入参考应用，且本预演未运行 codex-base，不能证明每个新断言都有独立正例。历史失败与后续冻结应用的失败只能说明诊断路径，不能证明期望正确。覆盖项应保留正例证据字段；已有 GitHub 浏览器证据仅为登录失败反例，API 200 不能充当 UI 登录成功正例；Sheet 的打开、公式、刷新成功可记录为有限正例，其他项目明确保留证据缺口，不因应用失败而修正需求解释。

## 已执行的只读核验

- 读取 `AGENTS.md`、`tasks/hackathon-local-bench/packet.md` 与 `plan.md`。
- 通过 WSL 上既有 Node/YAML 解析器遍历两份 `requirements.yaml`，核对 ROOT/FOLDER/ATOMIC 数量、全量依赖和关键描述；未安装依赖，未改动官方材料。
- 未运行 Playwright、Runner、应用、模型、基础设施探针或任何测试，因此本报告没有产品通过/失败结论。

## 覆盖缺口与下一步

当前缺口是角色凭据、不可用账户、既有 label/milestone 等公开材料未定义时的可执行性，以及各断言的独立正例证据；它们应在 coverage 清单中逐项显式化，而不是用实现观察补齐。

建议下一步：**accept，进入开工复核**。呈现实施范围时把本报告的七项约定并入 coverage/报告口径；用户对具体源码范围开工后，再实现用例和执行已批准的冻结应用验收。
