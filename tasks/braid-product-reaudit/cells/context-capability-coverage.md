# Braid 产品价值的运行审查

用户指出官网根 Issue 未使用 hide/resolve，而之前没有收到对应报告。这暴露出审查方法缺口：围绕已知通知、调度、工具故障取证，未对照 Braid 的核心产品承诺检查实际采用与效果。工具存在、提示词提到、接口通过都不能替代模型在运行中有效使用。

## 顶层问题与分工

用户进一步纠正：不是只审查“Agent是否使用可编辑上下文”，而是“Braid到底提供什么价值，有没有被应用”。功能采用不是顶层目标，工作结果与成本才是。

官网两题的全对象审查、三项价值的正反链条与证据边界见[官网 Braid 价值审查](braid-value-official.md)。

| 产品价值 | 应观察的结果 | 失效或负收益的表现 |
| --- | --- | --- |
| 可管理的工作记忆 | 当前判断、需求和初始条件可取得；过时信息不持续干扰；接续后少遗忘和重做 | 重复读取与重建、旧决定混杂、依据丢失、形式化记账却不被消费 |
| 多 Agent 协作 | 独立工作有效并行；依赖与决定及时交接；成果能可靠整合 | 等待和通知增加、职责重叠、基础重复实现、共享冲突、交付无人负责 |
| 设计与实现分离 | 需求/技术/验收依据先澄清，独立实施者可消费并反馈，完成声明对应最终证据 | Issue直接实现、PR仅为事后记录、设计材料不被消费、实现倒逼验收判据 |

官网调查归 live_deep_diagnosis，本地08/09保留状态调查归 vision_root_cause；复用现成报告并补关键证据，主Agent综合判断。工作继续按09接续计划推进。各机制的采用审查只是下表证据层，不以更多调用当改善。
每个结论按期望→实际收益/代价→机制解释→证据强度→改进决定组织。区分能力缺失、不易用、不采用、采用无效，以及该任务本不需要。没有对照实验时不声称移除Braid会更好；可提出能区分解释的消融实验，但不自动启动。

## 机制证据层

| 产品能力 | 之前证据 | 本次补查与判据 |
| --- | --- | --- |
| description 保存当前任务说明 | 有重写触发reset及重复复制评论的样本 | 正文是否反映当前权威需求/决定，编辑是否必要，旧内容是否真被替换 |
| comment/reply 支持异步讨论 | 已检查部分投递与读取 | 是否形成有效thread，是否重复创建平行讨论，交接是否被消费 |
| hide 与理由移除过时内容 | 缺少运行采用审查 | 历史调用、理由、原始与投影内容；是否有明确过时内容一直保留 |
| resolve 整理已有讨论 | 缺少运行采用审查 | 历史动作与当前折叠范围、后续回复是否可见，解决事实是否保留 |
| delete 移除不需保留内容 | 缺少运行采用审查 | 是否实际需要删除，删除和hide语义是否准确；零使用不自动算失败 |
| reset 更新会话上下文 | 有性能、重复投递等证据 | 重建后的正文/评论是否消费上述变化，决定及初始条件是否仍可见 |
| Issue / PR 独立协作 | 之前只看对象/成员数量，覆盖不足 | 已确认多数历史PR未指派；需观察独立PR成员实施与Issue消费交接 |

## 分析规则

按“机会与输入 → 可发现能力 → 实际调用 → 工具反馈 → 后续上下文 → 决策影响”建立具体链条。
当前快照没有隐藏或折叠内容，不等于历史从未调用；反过来活动日志有调用，也不代表新的LLM输入已使用整理结果。
保留尚有价值的历史证据是合理行为，不以删除量或压缩率最大化为目标。
只有明确的无效重复、过时决定持续注入、整理调用失败、投影不生效等证据才能支持对应修复；无法从归档取到投影时记录缺口。
修复分别归通用Braid能力与返回反馈、使用能力的指引、或SVC整理工作记忆的方法，避免把一切归因于模型不遵守提示词。

## 补充：交接时点与责任内容

用户指出官网 GitHub PR #8 的独立成员可能在 Issue 成员已经完成实现后才出现。审查不能把“独立 PR 会话/复验存在”升级为“设计与实现分离成立”。必须区分功能实现、修改修复、独立验收、最终整合；各自可以有价值，但不能替代另一个承诺。核对实现提交时间/来源、PR 创建与指派、首次 PR 会话及实际产物。
当前09指引要求实施前创建并指派，是否生效须观察真正的实现前交接，不能凭现有代码完成后的补指派验收。当前半成品接续用于挽救交付和检查后续行为；不能倒推此前功能已按新方法生成。如果实验目标是证明新完整工作流，需要有尚未实施的工作或明确的实现前恢复起点，不自动授权清空当前成果/重跑。
