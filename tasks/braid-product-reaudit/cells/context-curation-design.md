# 工作记忆整理：保留当前依据，收束已结束的讨论

状态：基于官网归档和当前 Braid 源码的设计预演；未修改源码或运行，尚未在新运行验收。证据与覆盖范围见[官网价值审查](braid-value-official.md)及[共享契约因果核查](../../experiment-infrastructure/cells/shared-contract-braid-causality.md)。

## 决定

整理的目标是让下一步能直接找到当前有效的依据和未决问题，而不是压缩历史。触发点包括旧判断已被推翻、问题已经解决、稳定决定形成，以及交接时暴露当前说明与实际工作脱节；不是评论数或字节数。负责该判断的 Issue/PR 成员依据业务语义选择动作；Braid 只负责准确保存、投递、投影和恢复，不自动给评论分类。收到跨任务契约更正的成员还应在自己的任务中确认采用或说明未采用的理由。无需新摘要对象、后台清理器或固定周期。

### 完整的动作选择

| 需要解决的问题 | Agent 选择的动作 | 保留下来的依据 |
| --- | --- | --- |
| 旧判断已被推翻且会误导后续行动 | 先回复更正并通知受影响者，再窄改旧句；整条失效才 hide 并附理由 | 更正依据、旧原句要点和新结论之间的链接 |
| 一个问题已经解决，过程不再需要默认展开 | 保留可用结论与证据入口，再 resolve 这个单主题线程 | 当前正文中仍需要的决定，或折叠后新发布的简短结论回复；不能让唯一结论一起消失 |
| 讨论形成会约束后续工作的稳定决定 | 更新负责该决定的工作项 description，链接讨论；相关成员按当前决定继续 | 当前规则及来源，不把全部需求改写成容易漏项的摘要 |
| 交接或恢复时当前说明不再能指导下一步 | 修订失准部分并整理已结束的讨论，保留未决分歧、风险、验收前提和失败证据 | 接手者无需从相互矛盾的历史里重建当前任务，不要求固定模板/条数 |

问题未解决、证据互相冲突或仍在争论时保留可见，不因为文件变长就折叠。
resolve 是折叠讨论过程，不是判定软件正确；必须与 Issue/PR 的完成状态及验收证据区分。
每个成员维护其负责工作项的当前可读性，根负责跨项稳定决定；后续成员发现过时依据时同样可以提出更正。不存在一个额外的固定“记忆管理员”角色。

具体顺序：

1. 先在原讨论串用 `braid issue comment ID --reply-to COMMENT_ID`（PR 用 `braid pr comment`）写短更正，明确旧断言、当前结论、依据和受影响的工作项；需要在途成员立刻注意时直接 @ 具体负责人。新增评论走 Wake/引用投递，比等待整份 Context 重建更适合正在运行的会话。送达不等于已读或采纳，应看其后实际动作。
2. 再修正**默认投影**。若工作项的任务定义或长期共享契约真的变了，把当前版本写入该 Issue/PR description，并链接决策评论；短期进展仍留评论。混合了有效信息和错误句的评论，只窄改旧句为“此处已废止，见更正 #ID”，保留仍有效的部分及更正链；若历史原句尚未被更正评论引用，先在回复中记录原句要点，避免编辑后失去原貌。整条损坏或完全失效的评论用 `comment hide ID --reason '由 #ID 更正：…'`，而非删除。单主题讨论在结论已落实且无未决问题时用 `comment resolve ID` 折叠；多主题根评论不能为隐藏一个错误子句而整串 resolve。
3. 重要受影响者在其 Issue/PR 中引用当前契约及具体检查结果；根负责人以代码、验收或新评论确认其采用。整理动作与采用动作分别核验，不能把一次 hide、edit 或送达计为成功。

这些动作按语义选择，并非每次更正都要全套执行。对尚无后续消费者、只留档的旧讨论，追加更正即可；对会误导下一步的旧内容，单独追加更正不够，因为旧正文仍会进入以后完整 Context。

## 机制边界与反向诱因

`objects.rs` 当前对新增回复发 Wake；可见评论的 edit、工作项 description edit、hide、resolve 发 Invalidate。`group/provider.rs::render_context_reset_notice` 明说**当前会话结束后**用最新内容重新打开；进行中的模型回合仍可能使用旧快照。`context.rs::render_complete` 在新物理会话投影完整当前对象，隐藏评论只显示 `minimized (reason)`，已解决旧回复只显示折叠标记；`comment view ID --thread --include-hidden` 可追溯未删除的原文，新回复在 resolve 截止点之后仍可见。直接关联 PR 也接收相关 Issue 内容变化的 Invalidate，但不递归穿透任意依赖图。

这带来真实的取舍：只追加更正成本较低、可通知在途成员，却留下未来 Context 的互相矛盾段落；改旧内容可清理下一次输入，但会触发重建及重读，且不会瞬间改写正在执行的模型上下文。最小做法是**紧急纠偏先回复/定向通知，默认投影修订在结论稳定的决策节点做一次窄操作**，再根据 reset/读取证据确认生效。不能为节省 reset 永远不清理，也不应为少几个字反复改 description。隐藏理由必须指向更正，避免历史证据凭空消失。删除会丢正文，不适合这类可追溯纠错；静默重写旧评论同样不合适，因为当前评论表只保留最新版正文。

现有产品能力没有阻挡这套做法的必缺 API。主要缺口是操作指引虽列出 hide/resolve 与重建，却未给“**被推翻且影响后续行动**”的判断规则，也没有要求核对受影响成员是否采用。具体落点为 Braid 的成员用法说明：说明整理职责、语义时机、操作选择与生效时机。SVC 只保留通用的当前依据和外置工作记忆方法，不承担 Issue/PR 操作协议；adapter/wrapper 不拥有此工作方法。不要增设新的自动分类、摘要层或清理服务。`ContextPressure` 只报告容量压力，不应取代语义判断。

## 真实接续验收

在下一个自然出现的“旧判断被新证据推翻、且有下游在途”的工作项上，记录原评论 ID、新决策 ID、负责成员、关联 Issue/PR 和产生的 Braid activity。先核对更正回复实际进入目标成员的输入或其按引用读取；若对旧内容作 edit/hide/resolve，再核对 Invalidate、reset 后物理 `context.md` 的默认投影不再把旧断言当当前指导，并确认 `comment view --include-hidden` 可还原历史。最后检查下游成员的后续评论、代码或验收是否使用新契约；若仍用旧口径，判为采用失败并区分未送达、已读但拒绝、或实现未改。对无自然纠错机会的运行记录“未触发”，不用制造 Factory 试验。

不以 hide 次数、评论缩减率或 Context 字节下降验收。官网样本只证明旧错误与更正共同投影，不能证明特定错误由旧评论导致，也没有逐请求 token 可给出节省量。将来若要衡量收益，应比较同类真实接续中决策正确性、重复解释/重做与 reset 成本；缺少对照时只报告观察链，不推断净收益。

## 被否决的捷径

- 自动按评论数量、时间或关键词 hide/resolve：无法判断旧说法是否仍有效，可能抹掉任务证据。
- 一律把整串讨论压成摘要或裁短 Context：会把语义权威从负责成员转给不可靠的转换器，并削弱可追溯性。
- 只追加“更正”而永不处理旧默认投影：本例的晚期完整 Context 已证明两种口径会并存。
- 对每条进展都编辑 description：把普通协作消息变成重复 reset，增加重读成本。
- 把所有历史都 hide、或将 hide/resolve 使用量当目标：会丢失有效进展，且与多主题根评论不匹配。

## 落地计划与验收设计

第一步只修改 Braid 现有成员指引的工作记忆段落，替换目前纯命令清单式的介绍，保持命令示例可发现；不在多个profile重复注入。具体内容包含上面的语义时机、操作选择、结论保留、在途通知/默认投影区别。用当前Braid的系统/用户指引承载，不塞入要求Agent处理工作的单次user message。
第二步在既有view输出与原生投影上核实方法是否可执行。现有API足够表达，暂不增加自动摘要、审查gate或新“curation”对象；若真实使用显示操作成本/回显阻断，再针对已证缺口改CLI。
第三步在真实运行观察两类机会：一个被推翻且影响下游的判断，以及一个已经解决的讨论。分别验证当前结论仍可取得、旧内容不再冒充当前指导、未决问题和依据没有丢失、接手者确实采用。没有自然机会标未触发；不安排为刷hide次数的任务。
通过标准是工作依据变得准确且可消费，不是减少多少字符、调用多少次工具。只有指引改变而无相应行为证据时仍记为未验证。
本方案尚未进入当前03：当前03仅装入前次用户已复核的09材料。完成具体指引差异后应与问题、影响、验收一起提交部署复核。
