# Braid 在本地 attempt-08 的实际价值与采用边界

本页评估 2026-09-28 本地 attempt-08 的 GitHub、Sheet 两题，不把“提供了命令”当成“工作方式已经生效”，也不把使用次数当成收益。证据来自停止后的 Braid SQLite、根 Pi 重建输入、原生会话和现有定向报告；09 的指令、CLI 与对象层修正尚未在本页所查轨迹中生效。本页不据此估算评分增益、净时间节省，或声称删掉 Braid 会更好。

| 价值与期望 | 08 实际收益或代价 | 机制解释、采用分类 | 证据强度与下一步决策 |
| --- | --- | --- | --- |
| **工作记忆**：Issue 保存需求、决定、进度和来源；会话更替后新成员能接续，并可整理不再适用的上下文。 | 两题根 Issue 有持续的评论与回复，新根会话确实收到先前交接；Sheet 的坏消息曾被 hide 后重发。代价是根正文未更新、根评论未 hide/resolve，已经被后续结论取代的进度仍进入新 Context；Sheet Issue #3 把短期进度写入正文后多次自行触发重建。 | **承载与重建已采用，根历史整理未采用，子项 hide 采用但用途是纠错。** Braid 默认保留历史；hide/resolve 的投影代码会折叠正文并留下引用，功能并非缺失或已用却无效。 | 对“信息带到新会话”和“旧信息也带入”是强证据；对其影响判断质量、减少/增加总成本则缺对照。保留审计来源，在已形成新结论的真实线程中明确收束旧催办，再查下一次 Context；不设 hide/resolve 数量指标。详见[上下文编辑核对](local-context-editing-adoption.md)。 |
| **多 Agent 协作**：可把相对独立的需求交给不同成员，在各自工作区推进，由根消费交接并整合。 | GitHub、Sheet 均出现多个 Issue 负责人、分支/PR 与根集成；GitHub 根实际读取 PR #6/#7 并复验，多个功能得以并行推进。代价是共享入口和页面的正常重叠要求根串行 rebase/回归；GitHub PR #5 先由 Git 合入，随后 Braid 合并命令拒绝，留下 Git 已合入而 PR 为 `CLOSED` 的状态差异。根还有低信息的 PBB 睡眠式轮询。 | **协作已采用且产生可见交付；整合与状态同步不是自动完成。** #6/#7 的交接已投递、唤醒已消费，不支持“成员完成但根根本没收到”的解释。GitHub #8 的 Pi `vision` 子代理另属原生工具委派，不能充作 Braid Issue/PR 分工证据。 | 对分派、交付、消费、合并行为是强证据；对并行相较单人是否更快、更稳没有同条件对照。继续保留独立负责人和可审计交接，检查关键依赖满足后的派发时点、共享文件的集成责任，以及 Git 与 Braid 合并状态一致性；不要以 Agent 数量代替完成质量。详见[GitHub 进展与关键路径](attempt08-progress.md)和[成本因果](../../experiment-infrastructure/cells/hotfix09-cost-causes.md)。 |
| **设计与实施分离**：Issue 成员形成需求、技术和验收依据；把实施交给独立 PR 成员在自己的会话与工作区验证，Issue 成员审阅。 | Issue 分派广泛，PR 对象也大量创建，但独立 PR 会话少得多：08 GitHub 的 12 个 PR 中只有 #12 有 PR 指派，且两个接续负责人会话均已退休；Sheet 的 19 个 PR 中 7 个有指派，其中只有 #4/#8/#13/#18 查到实际 provider 会话，#15/#17 仍阻塞、#19 仍在实例化。旧官网归档亦有 Issue 成员直接创建、合并 PR 的例子。 | **Braid 能力存在，Factory 方法在 08 只部分采用。** 未指派 PR 是关联和 Git 对象，不会自动建立独立负责人、会话或 PR 工作区；指派本身也不证明独立实施已经发生。原指引及创建回执没有把“创建对象”和“交给独立成员”说清。 | 对 PR assignment 与物理会话边界是强证据；对每行代码的实际作者、独立成员的净验收价值是有限证据。09 已补“实施前创建并指派 PR”的指引与真实 assignee 回执，但需要从**新 PR 创建→指派→独立会话/工作区→实施验收→Issue 消费**核验实际采用，不能把修复文本当成运行结果。详见[会话边界](issue-pr-session-boundary.md)。 |

这些现象不宜合并成“Braid 没价值”或“Braid 已充分发挥价值”。工作记忆和成员交接有直接可见的作用；历史整理与 PR 角色边界没有稳定采用；集成、重建和轮询又确实带来成本。某些根集成、审阅、很小的修改可能由同一负责人完成得更直接，但本次没有逐项证明它们不需要独立交接，也没有理由为 Factory 目标预设“轻量 PR 例外”。同样，需求图由 Pi `vision` 解读的成功接续支持一种清晰的角色分工，不证明 Braid 的 PR 分工已经落实。

若要做消融或对照，问题应分别落在可观察结果上：同任务、模型和验收条件下，持久 Issue Context 与普通对话记录相比，是否减少遗漏、错误重复决策或恢复耗时，同时保持可追溯性？多个 Braid 负责人相较较少负责人，是否缩短关键路径且不增加冲突、返工和缺陷？独立 PR 成员相较 Issue 成员直接实施，是否提升验收证据、设计约束的兑现与问题定位，其交接成本是多少？目前单条 08 轨迹无法回答这些反事实。09 可先验证已修正的交接方式是否真实出现，再决定是否值得做受控对照；评分单独记录，不能代替机制证据。
