# 独立复审结论

本轮按产品目标、用户 local 约定、既有观测与当前源代码交叉复审。没有修改产品源码、原应用或原始证据，没有运行测试、探针、应用、实验或评分。148 个目录快照文件与审查时内容一致，见 source-drift.json。本报告不是全部原生轨迹的第二次全量审查；GitHub/Sheet 的既有报告及其证据入口用于定向追溯，Sheet 仍由另一条审查继续。每项的独立核查深度和剩余证据见 coverage.md。

主要结论：回执歧义、输入遗漏、改派缺首轮输入、上下文重复、失效成员输入、离线孤儿等修复都有对应机制；SVC 方法改动放在通用方法层，Braid 对象与生命周期改动大体守住语义权威边界。没有依据把整个修复树回退。最明确的新问题是 observer 与原生同身份恢复的组合没有保持既有子任务索引；另有旧子任务通知的存活条件未闭合。PBB 的原生 pending-work 接线方向正确，但它的新等待时序尚不能称为完成验收。

## F1：同 native-home 恢复会清空子任务索引（R11、R15、R16，P2，确定的源码机制）

产品需要父恢复后知道先前由谁执行、结果在哪里，避免因不可见而重复派写；同时不能让 Braid 接管 Pi 子任务。旧运行确有父重建后重复 executor 的链，入口为 `tasks/factory-subagents/cells/iteration10-role-audit.md` 的官网 g01 恢复案例及其原生索引。

当前 `factory-subagent-observer.ts` 的 `createSubagentObserver` 总从空 `children` 开始；`session_start` 先执行 `current().observe({})`，将当前 native-home 的 `.factory/session-tree.json` 原子替换成空列表，然后 `previousRuns` 跳过 `home === nativeHome`。Braid `provider/factory.rs::resume` 明确查找并复用旧 native-home，`provider/pi.rs::spawn` 将它再次传为 `PI_CODING_AGENT_DIR`。新增 sleeping resume 正会经过该组合。

因此，有子任务记录的父同身份 resume 时，已持久化的索引被覆盖；随后若发生 fresh 重建，扫描旧 home 也不再得到那些条目。这里不需要假定原生子任务仍活着，已完成产物的归属也会丢失。它还使空列表被标为 `diagnostic_status: complete`，把“没有恢复记录”投影成“已完整观察且无子项”。

反证与限制：原生父 transcript、子 transcript 和 artifacts 没有被该代码删除；Pi 自己可能从原生历史恢复部分工具状态。因此不能由此断言所有结果丢失或新运行必然重复写；确定的是 Factory 自己承诺持久化的观察索引不保留。此前“08 有首轮交接”仅证明 fresh-home 读取其它 home 的路径，不能排除同-home 问题。

最小修复方向是在 observer 初始化时保留并校验当前父的已有清单，再合并新事件；不能用读取所有旧历史或将原生状态搬入 Braid 代替。消费方应通过真实恢复后的清单、原生身份和产物入口核对前后连续性；不重建被禁止的测试或探针。两个活动 variant 的同文件都在范围内。

## F2：旧子任务终态转送只在新父进程仍存活时有效（R11，P2，条件性完整性缺口）

observer 对旧 run 用 `fs.watch(..., {persistent:false})` 监听，终态时 `pi.sendMessage(...,{triggerTurn:true})`。它没有把被承接的旧任务注册为当前 session 的 pending-work；`session_shutdown` 又立即关闭所有 watcher。Braid 的 `sleep_closed_idle_agent` 在工作项 CLOSED/MERGED、没有运行 turn/reset 等条件下即可休眠原生会话，并不理解旧子任务。这个边界本身是正确的：Braid 不应查看原生 job。

可达顺序是：fresh 父发现旧在途 run → 父结束当前回应且对象已关闭 → Pi settled → 原生进程收尾，watcher 关闭 → 旧 run 才达到终态。当前实现不能保证最后一跳唤醒新父。A01 给 PBB 注册的 pending-work 不会自动覆盖 observer 的旧 run。与“错误终态已保存但父没读取”相比，这里是订阅寿命没有覆盖承诺的消息时刻。

反证与限制：OPEN 工作项的父可能长期保持可接收输入，旧 run 也可能先完成；这些情况下转送可以成功。用户没有要求任何关闭对象永不结束，因此不能简单增加永久等待。没有本轮真实在途完成收据，当前结论是承诺的适用条件未闭合，不是声称历史某条通知确已丢失。

最小处理是明确需要承接的旧任务是否仍属于当前工作的待完成责任；若需要自动转送，使用原生已有 background-work 契约保留必要的原生存活条件，并定义原生状态缺失/旧任务失联如何收尾。也可以缩小能力声明为“存活期间转送、恢复时提供持久结果入口”，但不能仍宣称无条件终态唤醒。不建议 Braid 解析子任务状态或自动 adopt/rebind。

## F3：PBB 修复在正确层面，但把未分类/不退出的命令转为无界结束等待（A01、R12，P1 补证项，未证运行缺陷）

产品不应把“模型结束回应”当作其有限检查已经完成。锁定包接口和 `native-idle-spike.md` 确认旧 PBB 作业可能早于结果发送就遇到 Pi settled/关闭，现有 provider 注册正好填补这个技术事实；没有必要在 Braid 加 job 状态机。`service:true` 是语义分类由调用者提供、执行等待由原生扩展保证的合理边界。

当前补丁除注册 provider 外，还在所有无 UI `agent_end` 中 `await Promise.all(pendingCompletionJobs().map(job => job.completion))`。这是为了 child 没加载 pi-subagents 的路径，也会越过主 pi-subagents 30 分钟 drain 边界。bash timeout 可省略，没有扩展自身上限。一个未标 service 的 watcher，或确实挂住的有限任务，会令本回合无法 settled；新提示词降低误用概率，却不是执行上的有界保证。

反证：主动等待必要有限检查是正确行为，不能拿固定短超时截断真实长任务。任务仍可经既有取消/宿主终止停止，故目前没有证据称其不可取消或必然死锁。加载成功、provider 可列出、schema 有 service 都没有覆盖执行顺序。

本项不建议立即加入任意超时或回退为早退。新批准实际运行应记录有限作业完成、结果进入 follow-up、模型消费、最终 settled 的顺序，以及停止操作是否结束等待；同时观察 service 不阻止 settled。若原生取消不能中断 await，再在 PBB 所属层修复取消传播。没有这些观测前，应写“接线完成、时序待验”，不能以本轮编译/加载证据宣布闭环。

## F4：方法修复解决错误决策条件，不等于消除全部性能或失分根因（R04–R09、R22、A08–A11，结论边界）

GitHub 原生 session04 的 L25–32 是评论 delivered 被归成业务交付的直接链；R01 的 CLI 分区是工具本身能消除的歧义，R22 的接管方法是不同层的补充，不能只教育模型。当前树确实两层都有修正。相反，原文/派生权威、用途迁移后的豁免、截图反证等属于 Agent 的语义判断，SVC 不自动裁决业务，当前做法合适。

根共享基础经独立 PR、Issue 设计与 PR 实施分开，是当前用户选定的协作流程。它不是由旧运行分数推出的唯一根因修法。`provider.rs` 保留对象职责，`run.py` 才规定根基础/业务分批/develop-main；未发现将具体赛题答案移入 Braid。SVC 新增条款使用用途、状态、入口、前提等通用概念，没有两题具体业务值。无需为“方法不能机器保证”再加语义调度器或硬审批门。

下一轮应看真实决定和交接是否变好，而非仅统计角色调用、规则条数或测试通过数量。原始材料内部冲突允许有据裁决；最终 seed/session bug 已修的反证仍须保留，不能把过程错误重复计入终态失分。

## F5：预打包与共同输入总体合边界，Node 版本差异仍限制自检结论（R02、R28、A06、A07，P2 观察项）

四个带 bash 的 fresh 角色获得共同环境/原需求来源边界；vision 仍只读明确材料，未拷贝整套 Braid 协作身份。开头明确共同环境不扩大委派范围，所以 explorer/advisor 收到安装约定不等于获得改码授权。共同正文较长且对只读角色有无关实施条款，是维护成本，未证它导致错误；优先维持一个权威正文，不建议另建角色模板系统。

Linux runtime 的 Node24 与 pnpm/portless 包装器独立，交付协议仍是平台 Node20.19.3 下逐目录 npm 安装/启动；当前提示已提醒版本兼容和独立安装。实际生成自检用的 PATH/工具仍可能在 Node24 上运行，因此不能用该自检通过证明 Node20 下 ABI、API 和依赖引擎兼容。pnpm-lock 也不会让 npm 安装自动遵循相同解析；当前要求只保留 npm 兼容，未承诺两套安装完全一致，不能误列为确定缺陷。

新环境没有预写应用源码、固定 TS/Vue、强制离线或增加沙箱。最小后续观察是记录生成检查实际 Node 与安装器版本，再以正式平台部署反馈确认兼容；失败时依据具体安装/启动错误修，不为假想差异增加第二套通用构建框架。预打包减少下载和路径猜测，不能替代 A08 的前置成功再启动依赖动作。

## 交付判定

41 个目录 ID 均已给核查状态，重叠项仅重复映射不重复计为多个根因。确定需要修复的是 F1；F2 应收敛承诺与存活边界；F3/F5 是下次获授权真实执行的关键观察条件。其它项目的“方向成立”表示机制/职责对应，不表示模型采用或评分收益已经被验证。无需为本报告再运行任何被禁止的测试。
