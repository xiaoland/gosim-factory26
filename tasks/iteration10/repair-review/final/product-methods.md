# 最终独立修复审查：方法与协作产品

本次从原始表现和产品义务重新判断，不以旧报告的“无新增阻断”、目录覆盖或提示词存在作为结论。建议保留当前以原需求、实际调用链和同属性证据为中心的方法修正；替换“缺文档／基础责任放错位置／未用子代理导致失败”的过宽归因；停止继续按历史实例增加同义规则。没有发现必须推翻用户指定 Issue 设计、独立 PR 实施、根负责共享基础这一工作流的证据。也没有证据支持把所有返工消除归功于这套工作流。

只读审查当前装配、七技能入口及相关正文、角色、Braid责任介绍和已审运行证据；定向重读 GitHub 原生 L23、Sheet 最终父会话 L27/L46及原工作项用途/豁免记录。未修改源码、运行测试、探针、应用或模型、提交。运行实证与静态路径沿用原审查的证据等级，未重做两题终态归因。本文是方法侧取舍，不代替运行时或 analytics 的产品交付结论。

## 让需求、判据与交付保持对应

### 保留 R04/R05；将问题定位从“压缩丢失”改成“派生权威取代原要求”

GitHub `run-audit/github/evidence/session-03.txt` 原生 L23明确知道原始场景要求 `acme-docs`、`secret-research` 及 owner，知道派生 Issue #2另写了对象，甚至预测搜索会失败；仍决定“Issue #2 … my authority”。这排除了该实例只是没有读取原文的解释。根后续也以局部自测和场景起点解释全局搜索范围，详 `run-audit/github/report.md` session13/14/24。真实输入歧义与后期种子修正均存在，因此不能把所有差异都判为违约，更不能将该轨迹直接分配给隐藏评分失败。

**反事实。** 即使子项完整附上原文、先写所有设计、基础 PR 顺利合并，仍会发生这类偏差：原文已经在眼前，错误发生在选择哪份材料有权改变承诺。多建文档、强制引用、增加总检查数都不能独自解决。

当前 `svc-design/references/product.md` 明确派生材料不是新权威，冲突需对照原句、交负责者裁决、更新消费者；`check-design.md` 再从原场景检查判据，保留被 setup 绕过的初态、并列对象和非单调规则。这个组合针对的是实际决策错误，而非形式完整性。若严格执行，旧例中不能再靠“父 Issue 写得详细”静默取消对象；对原输入真实矛盾则仍允许有据选择并限定结论。应保留，不需增加题目专属规则或程序化需求裁决器。

**长期方案。** 原始要求保持唯一承诺来源；共享设计记选择及理由；子项引用对其有影响的原句和当前决定；最终检查独立对照原要求，不能仅证明根裁决。现有材料已经表达这一责任链。后续观察应区分“没取得原文”“取得但未比较”“发现冲突却以实施便利覆盖原文”，不要把三者再合并成导航不足。最小判别证据是一条真实冲突从发现到负责者裁决、消费者更新和最终判据的消费链，不能用 advisor 调用次数替代。

### 保留 R06 与 M01 的组合，但共享规则的一处实现优先于两份文档一致

Sheet `items.md:2999` 附近将工作簿级 PATCH 说明为跨表 undo/redo；PR15又将普通编辑迁到该入口。PR19（`items.md:7203`起）补 move 守卫时仍以历史恢复理由排除工作簿入口。最终调用链与前后端重叠规则差异见 `run-audit/sheet/report.md:35–57`。这证明契约存在、协调存在、检查存在，遗漏的是用途和规则相交状态。新 pivot 写入口绕过公式缓存同步的静态发现也属于同一类：局部功能成立，不代表所有写入口保持共同不变量；它不是新的“再加一条 Sheet 规则”理由。

**反事实。** 即使所有人使用同一文档路径、交接及时，若文档仍称端点仅供恢复、parity仍仅覆盖互不重叠样例，问题照样出现。即使扩大全量验收，只复跑旧样例也不能发现它。相反，一处共同判定/写入边界能够消除相当一部分策略漂移，但仍需正确表示普通写入与恢复的不同语义，不能粗暴给所有写入统一加守卫。

当前 technical/workflow要求用途变化也算契约变化、追真实调用者和旧豁免；documentation优先共享实现并记录消费者/版本；check-design要求可达交叠和实际跨组件交接。它们一起满足根因修复需要。M01作为共享知识能力应保留，但不能单独宣称修复 R06；不应把复杂的前后端一致性长期维持成“文档 + 更多 parity”这一默认产品要求。

**具体取舍。** 生成时优先让同一业务裁决和持久化不变量由一个可复用实现拥有，必要的边缘验证只承担自身责任；确需多端实现，定义相同可达状态的共同判据。该决定仍由生成 LLM作出，Harness不预置应用实现。最小判别是实际消费者变更用途时，旧例外是否重新裁决，以及一个能区别两种规则解释的状态是否经过真正写入/读取路径；不是文件数或 parity 条数。

### 保留 R07；A04只提高观察质量，不能修复父会话偷换待证属性

Sheet最终父原生 `evidence/native/469-unparsed-…01a0e7be-98d2-7048-8fae-4bb61ef09772.jsonl` L27/L46已明确读懂 vision指出公式栏为空、选中位置与脚本意图不一致，也考虑了未进入编辑模式；最终以其它 formula suite通过认定截图只是 capture artifact。原生反证否定“没调用视觉角色／没收到结果”这一解释。截图不足不等同公式功能失败，参考图与文字的真实冲突也不能被忽略。

**反事实。** 更详细的vision角色、更多截图或更强视觉模型都不能替父决策者回答：这个截图中的交互为何没有进入预期状态。即使完美提取，父仍能用另一层 PASS把异常排除。R07结果解释要求同属性证据、修正观察或缩小声明，才是根因措施；A04保持为用户批准的观察能力增强，不能写成该失败的已证修复。

当前解释方法已足够。保留事实／推断／未知、图像来源、相关图集中读取和观察复用；删除“看过图即视觉验收完成”的完成标准。遇到同类反证只补能判别该交互的一次观察，或保留未证范围，不再泛增一整套验收。

## 让协作减少返工，而不以更多角色和工序证明协作

### 保留 R03/R08/R22 的用户工作流；修正它们能解决什么的陈述

GitHub基础曾先合入再派业务，仍因错误接管在制代码和窄自测传播 session缺陷（`github/report.md:62–68`）；Sheet则提前指派消费者、迟发布契约，同时存在真实环境排障和恢复故障（`sheet/report.md:59–71`）。两者不能归成一个“没有基础先行”的原因。

把基础责任留在根、通过关联独立 PR实施，改善整体责任与原需求到共享设计的交接，并兑现用户明确指定的策略；它不能天然保证基础正确，也不能消除接管误判、接口晚发布或消费者错用旧版本。R03只有一个根完成判断者，R22按当前负责人事实决定接管、消费当前候选证据与未解除前提，分别补不同问题。应共同保留，避免把组织图当作质量机制。

实际组合没有要求所有人停到基础全部完成：run.py允许独立工作并行，planning明确依赖只延迟消费者，主指令要求尽早发布最小可消费契约，局部有效证据可复用，根不再重跑有效整合验收。因此没有充分依据主张现在强迫全串行或每位负责人都重跑完整套件。不要为进一步“提速”撤掉独立 PR、advisor或最终可重复验收，这会反转用户要求。

更合适的并行边界是已决契约允许哪些工作独立推进，哪些实现仍依赖基础。基础作者完整验收未结束时，稳定定义和真实进度可以先发布，但未验证实现不可冒充就绪。下一运行观察消费者是否少猜字段、接管是否依据实际失败、同候选检查是否仍有多个无独立问题的负责人；不用总并发数评价。

### 保留前置 advisor 与有界委派，不将零调用改成配额缺陷

R09修复了独立咨询与普通执行委派ROI混淆：advisor在多个任务依赖的解释、责任边界和未知判据定案前介入，日常明确决定直接推进。当前角色拿原始目标、证据与待决问题，返回反例和替代，而非泛读代码盖章；这能挑战共享错误前提，属于必要的方法边界。

**反事实。** 就算每次准时调用，父子也可能共享错误前提；advisor一致赞成不是验收证据。所以不增加角色数量门槛，不要求每阶段另一个Agent。R10区分已经指派的Braid成果与当前成员的局部工作，executor先查重叠，比只修角色名更根本。R11恢复身份/产物入口是避免重复委派的技术前提，方法必须消费这些事实；仅持久索引不等于被采用，当前机制由运行时审查另核。R13工具路由直接进入explorer角色合理，零调用本身不构成缺陷。

R02共享运行条件需要传给fresh有bash角色，不能因输入变长便删掉；fresh隔离任务历史与继承共同环境可以同时成立。vision仍只读给定材料，不需要获得写入/进程约定。当前没有可兑现收益证据支持按字数机械裁掉输入。

### 保留 packet 与 documentation 两种能力；限制双份“当前真相”是表达澄清，不是删除技能

M01项目文档保存共享规则，packet保存任务恢复状态、执行路线、分cell材料及证据；两者服务不同消费者，用户明确要求独立。M02金字塔是观察边界模型而非各层配额；M03例子均有适用条件；M04规划负责路线、packet负责保存。当前组合没有七技能逐项执行的门槛，嵌入角色的只是相关workflow。这些应保留，不再添加总流程或统一模板。

唯一值得收敛的文字是 `svc-task-packet/SKILL.md:35`：只要多于一个明显动作就必须建文件，与Braid要求Issue/PR维护当前要求、决定、问题并列时，读者可能重复维护同一状态。但现有源码并没有强制复制全文，历史材料也未确证该新句已造成双写。因此它是可消除的表达歧义，不是已证运行缺陷或阻断。

建议保留任务包创建和独立技能，明确稳定当前决定只在一处拥有：Issue/PR可链接任务包中的详细计划/材料，packet可链接协作对象中的当前约定；有独立恢复或分工价值才保存额外状态，不要求把同一决定再抄一份。无需新映射机制，也不把packet退化成PR摘要。若主线不改这句，不能据此宣称当前必然过度文书化；后续应只看是否存在真实双写和漂移，再定成本。

## 让反馈及时可用，而不把技术欠缺转成模型义务

A08前置执行成功后再消费、A09保留原操作首错/退出码、A10只清理自有资源、A11写入已受理或结果不明先读回，均对应已见原生行为；它们没有禁止独立并行，也不需要语义调度器。就算预装完美，安装与rebuild同时写一目录、reset与观察并行、把queued当写入失败仍会发生，因此A06/A07不是这些根因的替代方案。

A06的pnpm/portless/Vitest/组件库/图标/UnoCSS是用户选择，不能倒推为旧分数不足的已证原因。当前约定兼容平台Node20与逐目录npm入口，要求真实控件语义、正式构建路径和初态保持，未预写应用；保留这些约束。增加领域选库不能解决权威反转和实际调用链遗漏，用户已排除的题目专属建议不应恢复。A12错误示例纠正保留，属于具体API知识缺陷，不能扩大成所有公式失分原因。

R17让稳定正文与讨论/证据分责、修正旧结论并联系在途消费者，长期方向正确。单靠hide/resolve只改变未来上下文，不能召回旧输入；当前介绍已说清这个限制。不要新增自动语义整理器；也不要把应由回执准确说明的accepted/delivered、后台结果可达、原生恢复身份归成“模型再认真些”。相关实现是否兑现，需运行时侧实核。

M05保留结果因果与全过程发现两条路径，以及唯一账本、精确原文位置、局部取证与跨链判断分工。全过程阅读来自用户本次明确要求，不能以热点采样替代；后续定向修复审查也不能自动重启全量阅读。模型分工的收益仍是可检验选择。该SOP本身不等于低认知成本analytics已交付：工具还须使来源定位、连续补读和跨链事实连接可用，由主线结合正在实施的analytics单独判断，不能让分析Agent永远手工拼链作为产品完成条件。

## 跨域回传补充

运行时审查者已核回执共用分区与具体assignee反馈，支持A11不是只靠教育模型；其提出R22仍有协作可见性缺口：原生failed详情主要在tracing/日志，工作项status未必给当前协作者提供停止/失败正证。该实现结论由运行时报告收口；方法侧据此不能把“联系owner或核实失败”当已经拥有全部可用事实。最小补齐方向是向工作项提供实际执行失败/不可恢复状态及原错入口，保留LLM是否接管的决定，不增加语义自动改派。

终态普通回复仍可能唤醒负责人，合批不能消除跨批串行确认环。当前主指令已明确纯回执不必回复、没有新事实或决定不发重复进度；这是保持可联系性同时控制成本的合理分工。不能把通知合批/退订的收益表述成消除全部无行动轮，也不能据此让工具猜语义并丢弃普通消息。
