# SVC 方法视图审查与应用

用户授权增加检查金字塔，并审查整个SVC系列中缺少直观、高内聚案例或视图的元思想。
两个独立技能svc-task-packet与svc-documentation保持分开；实验仍暂停，不提交、不运行内容测试或探针。

| 技能 | 审查判断 | 本次处理 |
| --- | --- | --- |
| verification | 已有完整的保存设置后重新登录判据案例，层次分工不直观 | evidence-design增加检查金字塔，并沿用原案例说明各层观察和盲区；入口直接链接 |
| investigation | 有竞争解释与停止原则，但缺观察如何改变下一步的例子 | 保存设置丢失的四条候选路径，逐项对应区分观察和后续动作 |
| design | 产品/技术/验收视角清楚，复杂化后回到需求较抽象 | engineering-judgment加入多标签同步案例，区分真实需求与方案额外承诺；入口链接 |
| sub-agents | 有查询孤儿记录的短例，但没有完整委派到采用的链 | 替换旧短例，补决定、上下文与效果边界、返回、消费动作；不额外堆一个案例 |
| task-packet | 拓扑术语和结构树已有，缺为什么要从单计划长成多工作单元 | 共享格式/编辑器/导入器依赖图；有真实协调成本才引入Cell，非固定模板 |
| documentation | 归属、变更传播有原则，缺规则到消费者视图 | 同一共享规则的权威定义、版本、两消费者与任务包引用图；重叠例不预设通用优先级 |
| implementation | 已有有条件test-first、前置成功再消费和具体执行反馈，无需重复画流程 | 沿用现有到technical/verification/documentation的导航；本次不新增案例或重复金字塔 |

审查涉及七个入口及其工作流、设计、调试、委派、规划、增长与V&V正文；没有将每个历史模板都当作缺少案例的问题。
案例只解释方法，不规定题目行为、技术栈、角色派发顺序、检查比例或必经层级。
新增内容留在原本方法所在位置，入口直接导航；不另造跨技能案例目录或总览技能。
已直接复核正文、路径和例子的前提/结论边界；实际采用效果待获授权实验。

## 用户批准的规划方法补齐

在svc-implementation新增references/planning.md，包含起点、路线改变型未知、预演、依赖与并行、可集成产出及反馈、动态重规划。
使用已有共享配置格式案例，展示共同边界→消费者→完整路径，而不是新增业务主题或必经阶段。
原workflow中的未知收敛方法迁入planning正文，原位置变直接导航，避免两个权威定义。
Task packet入口和planning topology按需指向制定方法，模板只增加每个产出的前提/反馈/消费者提示；计划存储与制定仍分开，没有新增第八个技能。
未构建、提交、运行测试或实验；直接复核正文、导航及相对引用，行为效果留待后续授权实验。

## Issue 工作流中的使用责任

用户确认补齐常驻指令，并强调根 Issue 建立文档入口与先理解完整需求、搭建整体框架的责任相呼应。
当前 pi-braid 与 pi-braid-flash-team 的五份成员指令已明确：根先形成整体设计和共享契约并建立或接续项目文档入口；各 Issue 使用本任务的 packet，关联 PR 接续同一 packet，跨任务定义保持单一权威位置。
共享框架的代码实施仍由关联的独立基础 PR 承接；Braid 机制与通用 SVC 技能未增加角色或比赛策略。
已核对五份指令及既有技能装载路径，技术说明同步更新；仅完成源码文字与接线核对，未部署、未运行实验，实际采用效果仍待运行证据。
