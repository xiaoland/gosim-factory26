hotfix-02 的 Sheet run `pi-braid--hackathon--sheet-d105b86431cdc7` 于 2026-09-29 16:13:31（北京时间）以 exit 1 结束。真正的 Braid 错误保存在原 run 的 `continuation-1790663455870289442-braid.log`：08:10:35 UTC，idle Context reset 报 `SQLite operation failed: database is locked`；08:12:28 UTC，主循环报 `local run failed: database is locked: Error code 5: database is locked`，并写入失败的 `braid-state/result.json`。最后一次成功更新 `status.json` 是 08:11:57 UTC，此后原生会话仍有工具调用，数据库在 08:12:24–27 UTC 仍能写入 operational-status 评论。因此没有数据库损坏或永久不可写的证据；进程退出后无法唯一指认当时的持锁连接。

Braid `store::configure_connection` 原先在每次数据库操作时执行 `PRAGMA journal_mode=WAL`，而运行中 StoreActor、各 Agent CLI、主循环并发使用 SQLite。WAL 是数据库级持久设置，重复执行会增加锁争用。源码提交 `8ad15898d13f9802361b1a866c4885edf1c9224e` 将 WAL 设置移到启动 `apply()`，只在持迁移租约、workers 启动前执行；普通连接仍设置外键与同步模式。store 与 object 连接的 SQLite busy timeout 统一为 30 秒：锁若提前释放立即继续，超过期限仍报原错误。这是有界等待，不重放可能已产生外部副作用的调度轮次，也不将 `SQLITE_LOCKED` 偷换为可重试的 `SQLITE_BUSY`。它修正已确认的争用放大器，不能证明已消除所有长事务。`cargo check` 通过；按运行约束未新增或运行测试。
