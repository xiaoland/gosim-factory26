## 决策结论

最值得改进的不是再增加一次全量验收，而是让**契约的用途变化、例外的适用前提、验收实际经过的入口**在跨角色交接时保持一致。此次运行中，校验临时适配器长期保留，两个规则选择算法相反；为 undo 创建的免校验工作簿端点后来承担普通编辑，而后续守卫审查仍把它只当恢复入口。工作项讨论非常充分、多个独立检查也通过，却没有覆盖这条调用链。这是已确定的静态实现不一致和检查盲区，不能直接等同官方失分原因。

第二个改进方向是把“结果可信”与“每个角色必须重新取得结果”分开。运行出现同树全量重跑、重复 PR 关闭后仍跑旧候选、不同评审同时复验同一范围。适当复用证据必须以树、运行条件、被测行为和退出状态为边界；单纯减少检查次数会误删此次真正发现缺陷的独立复核。

第三个方向是约束解释和证据的替代关系：根裁决能统一实现，不能证明已消除输入歧义；函数/API检查通过，也不能解释一张真实交互截图为何没有待证状态。需要保留剩余不确定性，而不是把“全需求覆盖”当成完成度证明。

## 发现二：两个规则选择算法相反，parity检查只证明了非重叠样例

**可达性推导。** 先对B2:B3创建0–100规则，再选A1:C3（左上角A1不受旧规则覆盖）创建0–200规则，可形成重叠。重新选B2单格，BE fallback找到新规则；FE写150按旧规则拒绝，而BE按新规则允许。范围设置优先级正文未明确规定，但同一持久化状态在读回/普通写/move中得出不同有效规则，属于确定的实现契约不一致。以上为静态路径推导，尚未实际浏览器复现。

**根因解释与反证。** 临时实现被保留可解释漂移，parity样本过窄可解释自测为何没有提示；不能据此证明所有双实现都会错，也不能把第三方库或模型能力当根因。旧讨论曾主动要求统一接口和错误文案，说明一致性目标存在，但一致性的观察面局限于常见字面值。

**最小通用杠杆。** 审查共享策略时，覆盖状态的竞争关系和边界组合，而不只比较消息文案：多个规则同时适用、规则更新后已有状态、批量中的一个非法值、公式与普通值。优先消除重复策略；确需双端实现时，复用同一组行为样例，且样例由公共语义和状态变化生成。判别效果是两端对相同可达状态作同一裁决，不是测试字符串完全相同。
