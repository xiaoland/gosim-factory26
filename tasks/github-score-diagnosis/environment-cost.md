### 非重叠成本与可省动作的界限

这四链横跨不重叠的时段，但缺少后台进程完成事件，故没有可信的“环境净耗时”单一数字。能确认的最低成本包括：端口 0 和 `/tmp` 第二轮各一个 30 秒失败就绪轮询，合计**至少 60 秒互不重叠的无效就绪等待**；cookie 手工探针两次从 401 到正确业务响应的命令跨度为 12:30:59–12:32:15；双重 JSON 探针的两次 401 响应各在约 1 秒内返回；`BASE_URL` 修复后的有效浏览器执行为 37.6 秒。后三项的调用跨度包含读结果、编辑及未解释的消息间隔，不能再与 60 秒机械相加。`/tmp` 第一轮可能另有至少一次 30 秒就绪等待，但 stderr 被过滤，只知 12:55:11 后台化、12:57:03 前退出；不纳入下界。

可省动作的因果依据是**提前暴露已经存在的判别信息**，不是宣称一个模型对照收益：固定端口预检可阻止 `CHECK_PORT=0`；结构化登录工具可把 401 连同前置 400/空 cookie 返回；保留 stderr 与子进程路径可在第一次 `/tmp` 失败时给出 `/server.js`；后台完成事件与日志首行可免 110 秒式轮询。它们也不能消除后续 62/66 的业务断言差异或浏览器页面失败。Pi 只给调用/结果和若干自报时长，不能细分这些观察窗里的模型推理、排队、后台运行或空闲。

## 判定和可改进对象

本段最明确的**外部工具/提示词可消除障碍**是检查命令构造和运行隔离：外部 runner 在执行前确认仓库根目录、脚本目录、正整数空闲端口、独立临时数据目录与所有必需浏览器环境变量；启动后同时记录子进程 PID/工作树、实际监听端口、`/api/health` 与登录状态；每次检查结构化返回命令、环境摘要、起止、退出码、失败摘要和清理结果。这样可直接预防 `CHECK_PORT=0`、`/tmp` 副本相对路径、遗漏 `BASE_URL`、漏带 cookie 后把 401 误判为产品失败。端口检查应识别监听者身份，不能只看 health 200。这个能力应在 **Harness 提供的外部检查工具及给 Agent 的运行指引**中实现，不预先写入或修改生成应用及其检查脚本。

真正的 PR 校验优先级、403 权限语义、UI 文案/可访问性，以及断言随现有实现漂移，均不属于环境成本。指引应要求 Agent 将“启动/配置错误”“无效探针请求”“有效请求的产品不符”“需求与断言不符”分别记录，只有后两者进入需求修复决策。官方逐例失败不可见，无法证明上述某项占 96 个失败多少；现有材料也不能把环境排障时窗换算为纯模型耗时或官网分数损失。

此前报告如给人“直接修这份冻结的生成应用并再评分”的方向，应撤回：本任务的改进对象是 Harness 的**外部工具和提示词**。冻结应用只用于诊断，不作为可由 Harness 预制、打补丁或重评的对象。若未来评估改进效果，应在另行授权的同口径生成中比较环境故障次数、首次有效检查时间和需求独立验收质量；本页未启动新实验。
