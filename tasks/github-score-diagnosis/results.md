# 结果

**决策级判断**：`595ab74c90a9` 的 4/100 是有效完成评分后的应用低分，不是生成、部署或评分未启动。来源 `435b79927a47` 的 58/58 是真实的自建检查通过，却不能外推到官方 100 场景：自检一方面按错误可访问性角色定位，另一方面把认证多字段校验主要放在 API 层验证，漏过了真实浏览器会阻断提交的路径。两类缺陷均违反公开需求并在独立副本复现，足以说明自检与低分并存；它们影响官方多少场景未知。

最强因果链：需求明确 `link` → 交付 Header 覆写 `menuitem` → 自检按 `menuitem` 通过组织/仓库场景 → 同一应用中按需求定位 `link` 的独立检查在入口超时，业务逻辑未执行。另一条独立链：需求要求同次呈现多字段错误 → 后端返回全部错误 → 浏览器因 `<input type="email">` 原生校验不调用提交处理器 → UI 无错误；API 自检仍通过。具体命令、路径与反例见[证据索引](evidence.md)。

**可控根因**是验收流程允许失败检查被改为匹配当前 DOM，却没有回到公开需求复核判断规则。原生轨迹中 @glm-4 的组织检查先按正确 `link` 失败，随后被改为 `menuitem`，这个过程比“模型不懂需求”的笼统结论更有操作价值。冻结包提供 SVC/V&V，实际主线未显式读取它；另有成员读过浏览器指南仍偏离。根在成员活动期间因缺回执重复实现基础，选中的版本漏了被弃候选已有的注册 UI 检查；该分支也有组织角色错误，所以协作问题不是万能解释。完整时间线、证据和反证见[生成流程归因](process.md)。

下一轮改进应先修正验收依据：每个原子需求从权威文本抽取可访问性角色、名称和公共入口；检查失败后改断言须引用需求依据，不能以页面实际角色为理由。对认证和跨模块入口保留少量从首页完整操作的独立检查，让浏览器、服务端和持久化一起被观察。冻结最终 `main` 后按同一产物做检查；若未来获得官网逐例失败，再按首个阻断点分组，而不是根据总分倒推。公开代理的 `Sign out` 选择器也须校准，不能把它的全部失败直接算到应用头上。

未解：官网 96 个失败的逐例位置、4 个通过场景身份、是否存在特定 fixture 缺失或状态污染、隐藏测试对上述角色和表单问题的权重。现有证据足以决定优先修验收 oracle 与 UI 合同，不能证明它们解释全部 96 个失败；不启动新的官网生成或收费重评。
