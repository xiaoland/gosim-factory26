# 发现

| 候选解释 | 结论 | 依据与界限 |
| --- | --- | --- |
| 部署、构建或后端启动失败 | 基本排除为本次低分的总因 | 官网构建和 3000 端口启动成功，评测执行至终态；本机同一产物可完成登录、搜索、仓库、Issue、PR 入口。官方个别场景的运行时异常仍未知。 |
| PR 集成把验收过的代码换掉 | 未见证据 | 来源 issue-1 验收工作树与交付 `main` 的共有应用/检查文件字节一致；最终多出预置 JSON 数据。58/58 仍是在子工作树运行，流程上不是最终 `main` 的独立浏览器验收。 |
| 总体没有种子数据 | 基本排除 | 交付包内有 4/4/4/4 用户/仓库/Issue/PR，独立浏览器可读取预置仓库和工作项。特定前置 fixture 是否缺失需官方逐例或更多场景复现。 |
| 需求理解和实现 | 已证实至少两类缺陷 | 账号菜单的组织/新仓库入口覆写成 `menuitem`，违背明确 `link` 合同；注册页 HTML 原生 email 校验截断多字段反馈。二者均在独立浏览器中复现。 |
| 自检 oracle 与需求脱节 | 已证实 | 自检用 `menuitem` 通过相应组织/仓库创建场景，按需求用 `link` 的代理在入口失败；最终 58 个浏览器检查没有认证 `REQ-1-*`，API 检查掩盖 UI 提交边界。 |
| V&V 材料未提供 | 排除 | 冻结包有 `svc-verification` 与参考，成员指令明确要求验收方案；@deepseek-2 曾显式读取技能。 |
| V&V 材料未被最终主线采用 | 有直接过程证据，但因果贡献未量化 | 根编写基础的原生会话未显式读该技能；@glm-4 读 `browser-checks` 后仍把正确 link 检查改成 menuitem，@deepseek-5 读参考后初写 menuitem。见[流程归因](process.md)。 |
| 单一模型能力不足 | 不能成立为现有结论 | 错误横跨 GLM/DeepSeek 成员；同轮 @glm-3 又能依需求修正 Sign out 的 link 角色。任务、状态和检查反馈不同，未做同口径模型对照。 |
| 官方隐藏测试与公开需求代理的差异 | 范围未知 | 官网 `tests` 为空，没有失败选择器/DOM；公开代理本身在 `Sign out` 上违反需求。不能给官方 96 个失败逐项归因，更不能把代理通过率解释成官方分数。 |

失效机制不是业务 API 全面缺失，而是可访问性角色和表单提交边界使多个场景在公共入口提前停止。源头自检在这些边界复用了实现假设，成功计数因此高估了对用户路径的覆盖。
