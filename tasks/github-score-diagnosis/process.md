## 我们能改变什么、怎样区分

1. **优先修验收修复规则**：当浏览器检查与 DOM 的角色/名称不符，要求在改断言前引用原子需求中的角色和名称；若需求明确，修页面并保持检查。最小区分实验已由冻结应用完成：同一实例中实现导向的两项自检通过，需求导向的两项检查在入口失败。反证条件是需求允许 `menuitem` 或独立浏览器能以 `link` 定位当前 DOM；两者均不成立。若未来官网逐例不经过这些入口，这条机制对官网 96 项失败的贡献仍待量化。
2. **把认证 UI 放进最终候选的检查范围**：根所选基础的 API 自检有多字段错误，但最终 58 项浏览器 suite 没有 `REQ-1-*`；被弃候选有精确 UI 检查。最小区分实验是仅在冻结主线运行这一条无效注册的浏览器路径，观察网络 POST 和字段错误；本次已测出 `posts=0, fieldErrors=0`，直接 API 反而返回所有错误。反证是官方环境自动禁用 HTML 校验或实际注册页用不同入口；当前交付源码与本机浏览器均不支持。
3. **在接管协作项前确认活动，而非以无评论等同无工作**：根自行实现时 @glm-3 原生会话仍在写代码。可在未来一次已授权运行中对照工作项消息与原生活动时间，要求根在重派/接管前检查是否有活跃会话并给明确交接。被弃分支的 `noValidate` 说明这次选择影响注册边界，但其组织入口也错，且未独立评分；不能宣称改进协作状态就能提高官网分数。若在根判断时成员实际上已停工或另一分支同样缺失该 UI 检查，这个流程假设会减弱；本次轨迹反驳了前半项。
4. **技能提供与效果分开看**：SVC 已提供，实际主线未显式读；`browser-checks` 被读后仍发生判据偏移。可以在不重生成的条件下对现有检查做一次“需求→角色/状态→断言”的只读审计，列出所有有争议断言并用公开需求复核；本次发现两条。要判断强制读技能或增加独立 reviewer 是否改善生成质量，仍需用户另行批准的同口径生成对照，不能从单 run 推断模型能力或指引单句的因果效果。

模型因素目前仅能定位行为归属：@glm-1 写出两个缺陷，@glm-4 将正确检查改错，@deepseek-5 起初写错检查；@glm-3 又曾修正另一个 link 合同。不同成员都出现过正确和错误判断，模型差异与任务分配、所见状态、检查反馈纠缠，现有材料不足以把 4/100 归因于某个模型。
