# SVC 路由调查与拆分提案

## 当前事实

`sources/svc/SKILL.md` 为 31 行，`references/` 下当前方法正文合计约 417 行。
入口短，正文也不庞大；目前没有证据说明文件长度是采用不稳定的主要原因。
根入口的 description 同时覆盖规划、记忆、需求、技术选择、调试和完成判断，消费者需要先想到 SVC，再从表中找到具体方法。
拆分的可检验假设是：让具体需要直接匹配技能描述，可以降低这层发现成本；技能数量增加本身不等于更好的路由。

实际消费有两条路径：

- Braid 成员的 Pi 主会话通过 `variants/pi-team-mixed/run.py:native_files` 显式注册 `svc` 等技能。
- fresh 子角色独立声明技能；explorer、executor、specialist 还分别预装 Explore、Implementation、Design 入口正文，以及 exploration-tools。

第二条路径是已批准的角色 SOP 接线，并非必然重复或错误。
子角色可能已直接得到方法，却仍有 `svc` 技能作为深读入口；本次设计不能简单删除所有直接正文，重新制造“角色只有边界、没有方法”的缺口。
打包和运行分别选择材料，`scripts/agent_support.py:copy_skill` 复制每个技能的 SKILL.md、references/assets/scripts 与许可；`build.py`、run.py 和角色技能列表都必须一起考虑。

## 候选边界

建议先按五类真实需要组织；名字是提案，不是已经存在的技能。
每项用自足的短入口描述问题、核心方法和按需资料，不要求先理解 SVC 专有名词。

| 技能 | 触发的真实需要 | 收入的现有内容 |
| --- | --- | --- |
| `svc-task-packet` | 多步骤任务需要保留判断、材料、负责人、依赖与恢复点 | task-packet 正文与模板；协作规划及委派材料入口 |
| `svc-investigation` | 决策缺信息，或具体错误需要区分原因 | Explore；打转识别；可区分假设、复现与诊断反馈 |
| `svc-design` | 需求或实现路径存在重要选择，职责与状态设计需要确定 | Product/Technical Design、Engineering Judgment |
| `svc-implementation` | 已选定改动，需要排除会推翻路线的未知并取得快速反馈 | Implementation；按收益做文档核实与小 spike；执行与反馈 |
| `svc-verification` | 实施前决定怎样检查，或观察后决定修复、复验和完成范围 | Test Design 与 V&V 合并为同一入口的前后两部分 |

这不是逐章节拆分：Test Design 与 V&V 必须在一个能力内连起来；调试是调查能力的一种使用情景；产品与技术设计保留在同一设计能力下。
委派方法仍描述当前 Agent 的子代理，不接管 Braid 的 Issue/PR 工作项或规定固定角色流水线。
不额外做 `svc` 总路由技能与五个新入口并行生效，避免两套竞争的导航。

拆分后的 SVC 仍是通用软件工作方法，不包含 Hackathon、浏览器工具品牌、模型名或比赛专用流程。
本轮独立库技能、工具指引与能力选择属于 Factory 的材料，不归入通用 SVC。

## 消费方式与成本

主会话可看到五项简短元数据，根据问题选读正文。
子角色保留 fresh 历史和已有 SOP：只将职责所需的方法来源换到新技能，其它完整技能按需暴露，不再同时追加和主动读取相同正文。
浏览器角色以浏览器操作和观察为核心，不为了技能数量强制加载设计、委派和任务规划全套方法。

实现前需用当前 Pi 与 pi-subagents 的实际接口核实五项元数据如何暴露、显式 skills 对正文是否 eager load、路径引用如何解析。
当前源码能证明材料选择与追加，但不能仅凭配置证明模型看到了哪些元数据、如何选读。
跨 skill 的相对路径、独立分发完整性和已有子角色 SOP 来源要在 LLD 中明确；不要靠复制同一方法正文维持多份入口。

## 外部方法的处理

`verification-before-completion` 的长处是将完成声明和实际证据直接连接；现有 V&V 已包含制品身份、证据范围、复用已有结果与独立观察。
值得借鉴的是直接可发现的触发描述及简短的“结论—证据—范围”表达，不是重新加入重复正文。
其要求每条消息内重跑完整命令、部分检查不提供证据等规则不适合采用：针对未改变制品的相关证据仍然有价值，局部检查也能支持边界明确的局部结论。

`systematic-debugging` 中读原始错误、追踪数据流、形成可区分假设和修复后重现原路径可用于审视调查入口。
固定四阶段、三次失败阈值、永久红测前置及等待人类的流程不进入无人值守 SVC。
现有 `harness/skills/diagnosing-bugs` 已有类似改编，但并未被活动 variant 选择；实施时决定迁移其可复用方法，避免再提供三个重叠的调试入口。
