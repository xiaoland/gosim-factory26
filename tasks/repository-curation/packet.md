# 仓库整理

## 目标、授权与当前结果

2026-10-02，用户希望整理过去几天密集迭代留下的数据、代码和文档，原话：“现在我想来进行整理。”随后明确：“开始处理”。Agent 起初自行把实际应用限于文档，把代码和数据只交付为清单。用户纠正：“为什么又是首轮，难道还有第二轮吗？为什么不全部做完呢？”本任务据此继续完成必要的代码说明、版本归属、数据索引与 Git 边界，不预设第二轮。

整理完成的依据是：工程师可以找到当前实现、有效决定与原始证据；已发现的组织问题实际修正；主要材料的用途、入口与处置明确。清空 dirty、删除有消费者的历史实现、结束其它任务的功能验收不是本任务的完成条件。模型运行、官网写入、暂停解除和现场清理没有从其它任务引入新的授权。

## 基线与工作区边界

起点为 `61e0f5f6c53cca8d81dc629e45a54ae974d6538a`。早期调查观察到 83 个已跟踪变化；实际开工基线是 85 个（84 修改、1 删除）及 2,458 个未跟踪文件，清单按开工基线覆盖。其用途包括有效源码、任务说明、历史快照、派生索引和分析脚本，未跟踪不代表可删。

开工文档、状态、既有 diff 与 index 保存在 `runs/repository-curation-20261002/baseline/`。新增编辑范围的原件同样留基线；文档相对基线的对照存入 `verification/task.diff`；共享文档存在同期更新时，该对照是审阅证据，不是可整体提交的任务补丁。源码仅提取本任务顶部说明增量。同期模型提供商文档与 Lab/DX 有原负责人的更新，保留并从本轮增量排除。当前 Lab 已演进为 schema 2，按其权威说明对齐入口，不代替原负责人的实现验收。没有暂存或提交既有 dirty，没有恢复已删除的旧 viewer packet。

## 数据结论及证据边界

主要本地簇的用途和保留决定已在数据清单记录。定向占用核对包括 third_party 约 17G、.adapter 约 470M、.bootstrap 约 5.5M、runs/iteration14 约 85G、runs/experiment-operations 约 7.3G；这些不相加外推全部 runs。I11 snapshot.tar 为 47,554,560 bytes，records.jsonl 为 34,391,986 bytes。

检索范围中的 14 份 archive.json 全部为 decision 且回收 blocked，原文仍有部分保存或恢复承诺。它们不能代表全部 runs，但足以要求保留各自材料。runs 全树总量、远端消费者与每个历史目录的实时状态没有完整核实；本任务没有具体可回收对象，因此这些未知不转化成物理清理计划，也不妨碍完成本地索引、归属和 Git 边界整理。没有证据充分的源码删除或原始数据回收候选。
