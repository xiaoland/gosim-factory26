# 补齐一般工作流程，并比较独立 reviewer

## 问题定位

用户此前确定的一般工作流程是：产品设计 → 技术设计 → 设计最终验收方案 → 实现计划与必要排障 → 实现 → 最终验收。前三步属于 Issue，后三步属于关联 PR。这不是本轮发明的验收机制。[产品说明](../../docs/prd/index.md)已经写明“Issue 承载需求理解、技术方案与最终验收设计；PR 承载实施计划、执行与最终验收”；开发侧 [AGENTS.md](../../AGENTS.md)也把方案和验收设计置于实施准备之前。

当前 `pi-team-mixed` 的成员指引却只枚举“产品设计、技术设计、实现计划与必要排障、实现、验收”。虽然下句提到 Issue 中确定“验收依据”，这一阶段没有进入顺序，容易被理解成实施之后补充的检查。修正应是把既有流程完整地表达给参赛 Agent，不为“验收方案”再定义格式、清单、工具或审批状态。无人中途介入时，相关 Agent 自行按需求作判断；SVC 的 verification skill 提供可选的具体方法。

GitHub run `b77e4357a4e1` 中，最终提交的 API 检查与局部 PR 分支的 UI 检查被用来支持整个产品完成；这说明验收过程存在问题，但单次轨迹不能证明缺少一句流程指引就是全部原因。本轮要观察流程修正后 Agent 的实际行为与本地结果，不以文案存在作为成功。

## 两个运行 variant

| Variant | 一般工作流程 | 独立 reviewer | 实验意义 |
| --- | --- | --- | --- |
| 更新后的 `pi-team-mixed` | 补齐已确定的六步流程 | 无 | 作为当前正确的基础 Harness，观察单靠完整流程的表现。 |
| `pi-team-reviewer` | 与更新后的 `pi-team-mixed` 完全一致 | 新上下文 Pi 内部 reviewer | 观察额外独立验收是否改善整体交付。 |

此前冻结的 `pi-team-mixed` 包保留为历史参照，不把缺少既定流程的旧版本作为应长期维护的“验收方案关闭”variant。K3 根 Agent 官网运行也继续保留原冻结条件，不能与本地两组作同条件因果比较。

基础 variant 只修正现有两种可指派 Agent 的原生用户指引，明确六步顺序及 Issue/PR 分工；不改根 Issue description、Braid、SVC Corpus 或参赛需求 prompt。指引不照搬开发侧的“交给用户复核/等待授权”，因为 Factory 运行无人中途介入。

Reviewer variant 在同样的指引之外增加一个 Pi 原生角色，由负责最终整合的 Agent 在完成声明前委派。它以新上下文取得需求、Issue 中的验收方案、最终交付产物及已有检查证据，按任务选择能辨别完成与否的实际观察；不靠泛读代码或重复其他 Agent 的结论。它报告观察与缺口，不修改代码，也不代替负责人决定修复、交付和关单。Reviewer 可先使用 GLM 5.3 Flash，与根 Agent 相同模型，以隔离新上下文与独立观察的作用；模型选择可在复核时调整。它是 Pi 内部 sub-agent，不是 Braid assignee。

## 本地验收

两组使用相同公开 Hackathon GitHub、Sheet 需求、模型 API、Runner 镜像与生成环境，各自独立生成应用，生成阶段不向 Agent 传模拟测试。生成后冻结应用，使用现有本地套件评估 GitHub 47 项、Sheet 24 项。测试由官方本地 Runner 执行，但内容是本项目依据公开需求编写的模拟检查，不是官方隐藏测试；本地通过数不能称作官网得分。

报告同时分析过程：Agent 是否在 Issue 中于实现前设计验收方案，PR 是否依据它实施并验收，最终整合产物是否受到相称的检查，完成声明与证据是否一致。Reviewer 组另核对原生调用、上下文独立性、实际操作和负责人如何处理反馈。分数分别保留 `passed`、`failed`、`blocked`、`incomplete`、`unexecuted`，不把共同前置条件阻断解释为所有业务功能失败。

沿用已有 `arc_matrix.py --requirements-only` 完成独立生成，再用 `package_arc_replay.py` 冻结两题应用，最后由 `experiments/hackathon-local/matrix.py` 逐场景回放。不新增测试设施，不重装 Runner 或浏览器；实施前只核实角色接口、包差异、模型入口与 WSL 剩余空间。两组完成后先向用户报告，再决定下一轮。
