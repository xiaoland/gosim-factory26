# I13：Braid 协作方法与 Requirements 树

2026-10-01。用户已审查本方案并认为没有问题，随后要求查看观察、研究与方案之间的推导，现进一步明确泛化边界：ARC特定适配限定在Agent Skill与root Issue description。本组尚未进入源码实施；[证据与推导说明](collaboration-requirements-rationale.md)及ARC compiler固定版本调查已完成。本方案按最新边界收窄，工具与提示词两条实现线已完成各自源码及材料反馈；Exa凭据由用户明天修正，不阻塞本组。

## 要改变的判断

分工使每位成员只处理部分问题，却不能使未完成的产品义务失去负责人。共享材料使成员可以复用决定和证据，但材料存在、已送达、已关联，都不等于接收者已经采用，更不等于候选兑现了原始要求。这是本组共同的问题；新增方法应解释怎样作这些判断，而非再列一套对象定义与命令清单。

已有研究提供三个不同的观察点：GitHub 的父节点包含首页入口要求，最初只摘叶子丢失了它；跨业务对象的原要求被局部范围排除后没有实际接手；最终整合虽读到原文和排除说明，仍将 ID mapping 和已有检查的通过当成完整覆盖。它们分别要求改善输入理解、责任承接和结果采用，不能归为“多读一次需求”或 Braid 丢信。具体因果边界仍按 [修复设计](repair-design.md) 与 [问题账](findings.md) 保留。

## 材料放在哪里

建议提供两项Factory独立技能 `harness/skills/braid-collaboration/` 与 `harness/skills/arc-bench/`。前者说明Braid成员如何组织工作、消费共同成果、处理变化和结束责任；后者说明如何阅读ARC需求包、形成工作、回核覆盖及遵守本次平台交付契约。原拟名称 `arc-requirements` 随边界核对改为 `arc-bench`，以涵盖需求和交付两面，不另建第三技能。正文提供判断方法及理由，reference展开共同案例与ARC交付条件。

| 来源 | 本组职责 |
| --- | --- |
| Braid system 与 CLI help | 身份、产品角色边界及真实操作语义；本组引用能力，不复制命令教程。 |
| `braid-collaboration/SKILL.md` | 可跨题目及输入格式使用的协作判断与必要Braid特性；不依赖ARC节点类型、文件格式或评分。 |
| `arc-bench/SKILL.md`及交付reference | ARC原树、父层与跨枝要求的阅读；来源追溯、视觉材料和平台交付契约。 |
| 既有 SVC 技能 | 项目知识、任务工作记忆、通用委派和 V&V 的理论与方法。Braid 方法只解释它们在工作项协作中的连接，不重抄正文。 |
| I13 profile及通用运行说明 | 通用角色政策、develop→main路线、工具环境与适用技能的发现；ARC语义和平台要求不进入此层。 |
| root Issue description | 本次任务目标、输入包位置、ARC技能入口、实际任务参数及交付要求的引用；不内联技能正文。 |

I13主成员通过已有skill发现机制获得名称、description和路径；开始组织或承接Braid工作时读取协作方法，处理ARC任务的需求、设计、实现或交付时读取适用的ARC技能及reference。根description给出本次任务与适配入口；后续工作项由负责人带上相关来源和合同入口，不能假定祖先正文自动进入子项上下文。原生child按自己的任务读取适用材料，调用方给出所需入口，不内联技能或传入整份父profile。

目前Braid源码没有现成独立技能分发入口；本组沿用Factory的技能构建和加载机制。选择及复制技能属于材料接线，运行时代码不解析其内容或依据ARC节点改变调度。具体实现与已完成的提示词去重结果核对，确认同一Agent输入中的方法与规则只有一个来源。

## 泛化边界及现有内容的迁移

用户原话：“比赛本意想要的是泛化的coding agent harness，我们得避免ARC反过来塑造我们的harness实现……将arc特定的适配限定在agent skill、root issue description。”据此，Braid/Pi及通用扩展保持对需求语义无感：不认识FOLDER/ATOMIC、需求dependencies、应用初态、测试层次或覆盖状态，不用这些信息自动建Issue、调度节点、限制工具或判断完成。通用协作技能也不反向依赖ARC技能。

当前 `run.py` 的 `RUN_CONDITIONS` 会追加到每个profile，其中已有ARC平台专属内容，需在本批迁出：frontend/backend目录及npm流程、Node 20.19.3、HOST/PORT与3000端口、120秒启动、平台保留目录、检查 `/usr/local/bin/node` 与工具Node区别等。它们集中到ARC技能的交付reference；root description给出入口及本次任务参数。混合句按归属拆分：portless工具用法与停止自有服务是通用环境，预留评测端口及正式应用安装/启动契约属于ARC材料。既定通用工具选择、角色与协作政策按已审方案保留。

`generate()`目前在模型启动前硬性要求 `requirements.yaml`；后续流程仅复制、记录身份并传递需求目录，没有运行时YAML消费者。本批改为仅确认输入是目录，复制读取失败保留实际错误；文件名、完整性及可读需求的解释归root description与ARC技能。移除这项门槛不引入新的解析器或适配接口。

赛事启动参数、输入/输出传输、应用导出以及 `deployment='arcbench'` 等记录身份继续归现有外围接入；这些协议不参与Agent的需求判断，本批不扩展成历史接入层重构。`braid-request`仍只传普通prompt、profiles、bindings和交付ref，不增加ARC语义字段。后续实现需将此稳定职责补入既有PRD/技术说明，不另造一套架构文档。

## 协作方法的内容

**按可消费的结果组织工作。** Issue 承担当前目标、决定与尚欠的义务，PR 承担候选实现、审阅和证据；分解依据是有意义的交付与判断边界。共享状态或完整操作需要一个能汇总结果的负责人，并不要求该负责人亲自实现全部代码。原生 sub-agent 可帮助当前成员独立处理工作，成员间正式责任仍通过 Braid 对象保持。

**按事实的生命周期选择位置。** 原始需求说明产品承诺，项目文档保存被采用的共同定义，packet 保存当前推理与工作状态，description 保存本项当前承诺或候选，讨论保存这次变化，原始输出保存观察。说明这些差别为何能减少冲突副本；入口仍需给足结论和用途，让接收者无需从一堆链接重建问题。已有 SVC 正文持有文档与 packet 的详细方法。

**交接要让责任和成果都可继续。** 接收者需知道要完成什么、依据在哪里、产物怎样供下一步采用。生产者发布成果只结束生产部分；实际接入、证据适用和剩余义务分别由相应负责人判断。局部排除可以合理，但整体负责人仍保留原要求，直到实际接手或有权改变原要求。正确后续行动已证明承接时即可采用，不另外制造 ACK 回合。

**变化针对真实消费者。** 共同定义改变时更新原定义，向受影响的当前负责人说明变化及下一动作；接收者判断采用、无影响或具体阻塞。新增消费者或派生状态同样可能改变旧更新路径的责任，不能以组件已经存在推断新的连接成立。咨询独立判断时保留会挑战当前解释的事实，避免先过滤掉矛盾再寻求结论。

**关闭判断消费成果，而非只看状态。** ready、merge、close 记录不同动作。交回时说明原始要求、现有判据的证明范围、实际候选结果和剩余缺口；接受有效结果可以避免重复工作，缺口则保持可定位、有责任。具体证据设计和解释链接现有 `svc-verification`，不复制另一套验收流程。

**维护服务于下一步工作。** 一个 thread 围绕可以独立结束的问题；结束讨论前让仍有效决定和未决义务有可用入口。根据新的事实、决定或责任变化更新当前材料；已经消费的回执和普通 head 前移本身没有维护价值。当前 root-only resolve、正文折叠与增量更新的操作含义取自 Braid 现行实现，旧研究中的 runtime 限制不再照搬。

用一个无题目专属答案的连贯示例说明上述关系：编辑器与导入器共享配置，二者都须修改并在重开后保留设置。局部负责人可以不实现另一入口，却仍需交回该义务；只检查编辑器的全绿支持局部结果；共享格式变化要被真实消费者采用。完整示例仅保存于协作技能的一个 reference，ARC 方法在相应判断点链接它；示例展示决定为什么改变，避免为每条原则堆一个模板。

## 需求树的内容

完整树是阅读和追溯的骨架。FOLDER 的正文可以包含自己的产品约束；祖先约束按语义适用，dependencies 也要理解是输入、状态一致性还是实施前提。工作包从目标节点与适用父层出发，还须识别跨枝对象、共享状态和完整操作；只取叶子或机械拼接祖先都不足以完成这项判断。

默认沿内聚子树分域；跨枝的完整用户操作由一个明确责任单元汇总，具体实现仍可分工。一个节点可以由多个 PR 兑现，若干节点也可以形成一项工作。既有任务有清楚的交付与责任时直接复用，不根据树深、节点数或类型自动创建 Issue。

原节点身份与原文位置保持可追溯。现有项目/任务材料中用足够的映射说明源范围、责任人、实现及证据入口；父节点自身约束、跨范围排除和尚未证明的观察面要能找回。只有出现查询或维护上的实际问题时再增加结构化索引，不默认制作逐节点长期同步的全量状态表。

区分需求层级、工作依赖、责任归属和证据支持：层级保留原始承诺，依赖说明成果的实际消费者，归属说明剩余义务由谁处理，证据说明哪些观察支持哪些承诺。在已有材料中表达必要关系；共享接口可以兑现多个节点，其合同须带上适用的父层或跨枝要求，局部普通要求直接进入实现和判据。父正文或共同合同变化时，按语义回查适用子路径、消费者及旧证据，不能只刷新节点自身或祖先状态。这是新ARC compiler参考对方法的补强，当前不引入其调度与状态框架。

场景的对象、角色、初态、入口、动作、结果和例外决定所需观察。初态需区分产品正常启动必须提供的数据、检查自己准备的数据和明确授权的外部条件；损坏输入保留原文与解释缺口。引用齐全只证明能定位来源；证据可支持哪些承诺仍交由 V&V 判断。

这部分只描述允许需求的阅读方法。开发侧历史失败、官方评分以及研究中两题的候选分工表不进入参赛材料，避免把已有赛题调查结论当成输入提示。

## 一个完整例子怎样体现两份方法

假设原树中有“设置”父节点，正文要求“设置修改后重新打开仍保留；无效修改不改变原状态”，其两个叶节点分别描述编辑器修改和文件导入。父节点的持久化与拒绝条件适用于两条路径，不能因为两个叶子没有重写这些句子就消失。

ARC方法首先帮助负责人读出这个完整承诺，再判断工作边界。如果两条路径都通过已有且稳定的配置事务接口，可以分别实施；如果事务语义仍在建立，先明确共同定义及其消费者，或将紧密相连的部分作为一个交付单元。树形给出理解入口，实际耦合和可交付结果决定分工，不要求一叶一Issue。

Braid方法随后处理各成员如何继续这份工作。编辑器负责人可以合理地不修改导入器，但其返回应让整体负责人看见导入路径仍欠什么；导入器的现任负责人采用共同接口或实际返回成果，就能证明工作已被承接。若没人接手，父项仍有开放义务。这样的交接把局部调查和实现留给接收方，只传来源、成果、问题及必要边界，而不是让父方预先列尽执行细节。

整合时，编辑器路径的检查通过可以直接复用；它并不回答导入后的重开、无效导入是否保持原状态。接收者分别判断既有判据足以证明哪些原要求、实际结果又适用于哪个候选，只补仍缺的依据。责任是否承接、判据是否足够、候选是否通过是三个不同判断；一份完整的ID表或一个merged状态不能替代它们。

这一个例子同时展示需求理解、内聚分工、局部排除、成果采用和结束判断。正文在相关决定点解释原因，完整故事只保留一个地址；工具命令和通用V&V细节使用各自已有入口。

## 实施范围与反馈

拟新增上述两项独立技能、一个共同引用的通用例子及一个ARC交付reference；更新I13的build/run技能选择、两份profile与root description，删除旧方法副本并迁出ARC平台契约。`run.py`另移除YAML文件名门槛，保留目录边界和现有调用/交付协议。受影响的技能索引及PRD/技术说明同步更新。Braid/Pi运行机制、原生工具权限、调度和验收状态不增加改动，已退出的三项SVC技能不重新打包。

复核使用已有历史事实判断方法能否区分几组不同情况：有子叶覆盖却漏父约束；范围合理排除但原义务仍无人接手；结果正确却只证明一个并列对象；共享定义已发布但消费者尚未采用。同时保留已有正确承接、有效证据复用和停止维护的正例。复核结果是方法可表达这些判断，不是模型已会执行的证据。

材料实施后通过编译和真实prepare-only读取 `braid-request.json`、`prompt.txt`、profiles及独立技能文件：ARC知识只出现在root description、技能正文/reference和发现元数据；profile不再含固定ARC目录、版本与端口，技能未内联，通用请求没有新增需求语义字段。从源码确认YAML门槛已移除、外围调用协议未改即可结束本轮边界核对，不新增测试设施或模型运行。通用技能按普通需求文本也可理解和使用；模型实际采用及性能仍由之后另获授权的实验观察，I12冻结材料与运行状态保持原样。

原研究的全节点候选表、六个题目示例、四次生成矩阵及重型静态清单保留为研究记录，不视为本组已批准交付物或实验安排。独立advisor此前已核对两技能分工与方法迁移，本轮又只读核对泛化边界：建议迁出profile的ARC契约、移除无实际消费者的YAML门槛、保留外围协议，并用真实材料验证职责，主线采纳。本方案已获先前认可并按用户最新约束修订；具体实施范围如上，尚未取得本组源码开工指示。
