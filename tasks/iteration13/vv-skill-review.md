## 结论与审查依据

两项问题成立，但现有内容并非完全没有解释。
当前技能保留了需求到判据的转换、双向挑战、保存设置的贯穿例、检查金字塔及结果归因方法，应保留这些有效内容。
缺陷在于：日常使用入口偏向纠错；基础判断关系被压成几句话；选择方法的依据和适用条件不够展开；反馈与演进分支没有从本技能中形成可达的阅读路径。
不能用“原则出现过”证明 Agent 已获得足够知识，也不能由文本缺陷直接推出某次低分的原因。

## 修订后的知识结构

```text
V&V：用可信、及时、成本可控的证据改善产品与工作决策
├─ 使用入口与基本前提［SKILL.md］
│  ├─ 需求、设计、实现、检查是不同表达，每次转换都可能有误
│  ├─ 正确性相对于要求和条件，同时保留符合要求的实现自由
│  ├─ 有限观察支持有范围的结论，多个通过也可能共享错误假设
│  └─ 反馈影响下一步搜索，成本包含等待、诊断、维护与错误约束
├─ 1. 规格与语义［check-design.md］
│  ├─ 意图、要求、设计假设；verification 与 validation 的不同问题
│  ├─ 状态、转移、流程、不变量、量化表现；性质与具体案例
│  └─ 转换的依据、双向挑战；既拒绝违约，也容纳合法实现变化
├─ 2. 证据设计［evidence-design.md］
│  ├─ 判据、条件选择、观察机制分别回答什么
│  ├─ 有限条件如何选择，依据与盲区是什么；测量及可比性
│  ├─ 检查金字塔、真实依赖与替代品、互补证据与总成本
│  └─ 可重复执行［repeatable-checks.md］：设置、操作、观察、重置与记录
├─ 3. 结果判断［interpreting-results.md］
│  ├─ 观察、解释、完成声明；验收与诊断证据
│  ├─ 共享假设、覆盖与适用范围，包含接受已有检查时的 G04
│  └─ 修改对象的选择；原始结果与交接一致，包含 G05
└─ 4. 反馈与演进［新增 feedback-and-evolution.md］
   ├─ 稳定行为适合 test-first；产品探索需要不同反馈
   ├─ 快反馈与完整结果互补，技术方案与验证方案共同设计
   ├─ 从反例完善行为模型，保留有不可替代价值的具体案例
   └─ 开发、交付、真实使用的证据回流与自动化判断的局限
```

保留四个稳定 reference 路径，只为缺失的完整分支增加一份正文。
树是知识导航，不是四阶段执行制度；Agent 根据当前决定直达对应内容。
基础前提在入口形成足够理解，相关方法在正文就地解释原因，不另设一层强制 foundations 导读。
具体 test-first 操作仍在 implementation/workflow，只维护一份；新分支解释适用性及其与整体反馈的关系，并直接链接该操作。
技能独立装载时，依然应能理解为什么选择某种反馈，不把基本判断全部委托给未安装的相邻技能。

## 入口措辞草案

下面保留获认可的设计草案；实际措辞以 `sources/svc/skills/svc-verification/SKILL.md` 为准，已进入源码，尚未部署到新的模型运行。

```yaml
name: svc-verification
description: >
  Design and use verification and validation throughout software development:
  clarify requirements and acceptance criteria, design tests and measurements,
  choose useful feedback during implementation and refactoring, interpret
  results, and assess readiness for delivery and behavior in actual use.
```

拟将标题改为 `Verification and Validation`，开篇为：

> Use this skill to decide what evidence is needed, how to obtain it, and what to do with the result while designing, building, changing, and evaluating software. It applies before implementation, during development, at delivery, and when observations from actual use challenge earlier assumptions.
>
> Verification asks whether the product meets its stated requirements. Validation also asks whether our interpretation of those requirements serves the intended goal. Tests, measurements, prototypes, and observations answer different parts of these questions; passing a check does not by itself answer all of them.

后接四个前提及分支间关系，再用问题路由表直达正文。
例如“正在决定如何实现并快速取得反馈”应能直接进入反馈分支，而不需要先报告某个失败。
description 负责让尚未读过 SVC 的 Agent 识别日常使用时机，不要求认识 oracle 等内部术语。

## 正文深度：恢复选择依据，而非只增加篇幅

以条件选择为例，现有正文说“选择有区分力的状态、边界或竞争者”。
修订后应能让读者完成以下推理：

> 有限执行不可能覆盖全部输入与历史，所以选择少数条件意味着采用了对行为的假设。
> 如果要求按一个阈值划分行为，可以在阈值两侧取代表值；这同时检查两个规则区域及容易写错的交界，但不能保证区域内部没有别的状态分支。
> 如果同一动作会因先前登录、权限变更或重试而改变含义，仅换输入值就不够，还要构造那段历史。
> 若两个规则可以同时生效，分别验证它们不能证明重叠时的优先级；必须选择一个实际可达的重叠状态，观察要求规定的结果。

这段同时给出为什么做、怎样做、基于何种假设以及能证明多少。
采用的划分来自需求与待决问题；实现可以帮助发现风险，但不能让当前代码分支反过来定义全部正确性。

主要方法应具有这样的解释完整性，不机械地把每节做成五字段模板。
保留“保存设置—重新登录”的贯穿例，并以排序丢重复元素说明一般性质与具体反例，以发票说明结果证据与过程信号。
不强迫一个案例承担所有理论，也不把案例细节升级为每个任务的新需求。
测量、mock、test-first 的取舍要说明哪种变化会改变选择，而不只写“按需”“成本合理”。

## 实施与复核方式

先完成入口及知识主干，再按原四个分支补全判断理由和执行内容，保留已有有效例子与近轮修复。
接着核对相邻技能的唯一归属和直达导航，将 G04/G05 纳入正文；最后核对实际分发入口及角色引用。
现有 SVC 工作树已有未提交修改，实施时以当前正文为基线，不用旧稿覆盖其他迭代的成果。

内容复核依据是：读者能否说明为何选择某方法、什么假设支持它、何种反例会改变选择，以及观察能支持多大结论。
具体检查普通需求设计、实现快反馈、已有 PASS 的覆盖判断、反例泛化、测量比较这些阅读路径。
材料对照和人工阅读不替代真实运行的采用证据；不创建 Corpus 内容测试、模拟运行或额外评审框架。
后续授权实验应观察决定与行为是否变化，不以读取了文件或出现术语计作采用。
