# 验收方案

本方案随设计复核，尚不授权新的模型运行或实验矩阵。
不新增 Factory、基础设施或 Corpus 的测试、模拟回归与断言；验收来自实际配置、工具调用、子会话与生成应用。

## 需要证明什么

| 主张 | 合适的观察 | 不足以证明的结果 |
| --- | --- | --- |
| 子 Agent 不继承父历史 | 实际 spawn 参数，以及子会话开头的消息来源；只有角色、选定技能、初始委派和后续显式消息。 | 只看角色中写了 fresh，或因子 Agent 没提父历史就认为未继承。 |
| 角色拿到了 SOP 和工具知识 | 实际生成的原生角色配置、装配来源、启动时有效系统/开发者指令；必要时依据原生读文件记录。 | 只看 skill 文件在 ZIP 中，或子 Agent 自称知道。 |
| 角色可使用配置工具 | 真实任务相关的 CLI/文档查询结果及原始错误；在预备环境和真实运行区分记录。 | 仅 npm 安装成功或 MCP tools/list 成功。 |
| 角色有用地完成局部任务 | 问题、采用的方法、返回物以及父 Agent 实际如何使用它，能形成简短因果链。 | 字数、调用次数、模型名，或另一个 Agent 口头认可。 |
| 委派没有固定流水线 | 主指令与角色定义不要求必经角色；运行选择有当前问题的依据。 | 强制四角色都调用一次，或把未使用某角色判成失败。 |
| 应用满足需求 | 同一冻结应用的公开需求自验与官方完整评分，区分不同初始状态/入口的覆盖。 | 将局部自测通过等同完整任务通过。 |

不继承父历史不禁止共享文件，也不禁止委派消息引用明确的任务事实。
不能用双方都读过同一需求文件作为 transcript 继承的证据。
若当前原生归档没有有效系统上下文，明确留下这一证据缺口，不从文件配置推断已经运行生效。

## 运行安排与结果解释

后续开工说明列出具体冻结包、benchmark 与并行安排；当前不另造一个为了覆盖工具而设计的实验矩阵。
沿用正式 benchmark 作为最终反馈，base/SVC 同时更新共同工具与角色边界，维持同一对照内这些因素一致。
如果下一轮某个角色或工具没有被任务自然使用，如实记为未观察，不强制增加无收益委派。
正式运行设施或角色接线的可修复故障继续处理到评分完成；不把它算作应用零分。
完整 benchmark 后分别汇报通过率、角色局部收益与证据限制，再由用户决定下一轮。

每个 run 仍交给独立分析 Agent，主 Agent 综合；定向保存原始证据，不将整段 rollout 常驻主会话。
特别关注主会话是否重复执行子工作、子 Agent 是否因缺信息往返、工具是否降低定位成本，以及错误结论是否源于共同假设。
这些是分析问题，不新增一个自动分数或诊断平台。
