# I15：需求结构为何没有形成工作边界

本轮重点是把 ARC requirements 自身的结构转化为 Braid 可采用的工作划分。拆分不仅服务并行速度，还让每位负责人在较小的相关材料范围内判断实现和遗漏，根负责人仍保留跨任务完整性责任。需求结构与协作边界方案已于2026-10-08获准实施。用户后续要求advisor问题不再暂缓，现恢复定向调查与方案判断，未批准此前被否定的改造。源码和材料反馈不能当作新运行已验证的收益。

## 冻结运行中的事实

来源为 Evo GitHub run `20261007-074221-a759c5e4` 的停止后冻结现场。定向证据在 `runs/iteration15/requirements-structure-inquiry/evidence.json`，包括对象正文、非系统评论、两个根原生 Session 的工具调用与原始行号；不复制整份 rollout。

初始根 Session 在北京时间 15:43:14 列出完整需求树，15:44:04 统计 52 个 ATOMIC、114 个场景，15:44:29 提取全部叶子的 Modified Feature Description，15:48:28 写 packet 时已经决定“单一基础 PR 承接全部实现”。15:53:41 创建 PR2，15:54:48 的第一次交接仍明确它是“本阶段唯一基础实现 PR”。该 PR 从一开始同时包含身份、组织、仓库、代码、Issue reactions 和全部缺失种子。没有证据支持“初始边界合理，后来失控扩张”的解释。

初始工具调用包含原 YAML 首 120 行、树与计数、Modified 摘录及基线代码查询；该 Session 没有逐范围读取父层正文、场景与图片的工具调用，也没有调用 vision 或 advisor。不能据此断言所有产品事实都理解错误，但它不足以支持正文所声称的完整材料理解。单 PR 的决定早于实施者逐条补全 GIVEN、场景和覆盖矩阵，理解成本被整体转移给一个实施 Session。

后续跟进 Session 有 86 个工具调用，73 条命令包含 `pr view`，多为 draft/state 查询；没有 `git diff` 调用。整个现场有 77 次根进展提醒。首次跟进确有 Issue 评论及 Git 状态检查，后续也检查审阅责任和冻结引用，因此不能概括为完全未检查。准确缺口是没有看到以实际业务改动、原始失败和需求边界为依据重新判断工作划分。已有提醒强调“没有新事实无需回执”，却没有明确怎样取得足以判断的新事实。根跟进修复已授权，直接在 I15 成员职责与已有提醒入口落地。

冻结根指令要求根 Issue 直接负责基础架构、脚手架与反馈设施。这并不等于要求全部业务进入基础 PR；原生 Agent 的决定把二者合并了。2026-10-08进一步定向取证发现，根确实考虑过多PR和子Issue，合并并非没有想到拆分。以下新增因果段取代此前仅由职责自述推测原因的判断。技能已读成功，证明问题不只是发现或读取失败。现有 `arc-bench` 和 `braid-collaboration` 能区分来源、依赖、责任、证据，也指出“一叶一项”并无保证，但对本次树应怎样产生初始边界没有提供足够明确的判断依据。这个缺口是具体决策约束不足，不能简单归因于技能采用原则形式。

## 本次决定的直接机制（2026-10-08补充）

初始根原生日志第32行把首次目录结果理解为只剩一个成员glm-2；第46行在识别完整缺失范围后，已形成按REQ1–6组织的能力阶段，并考虑多个PR及子Issue。它随后以“只有一个实施者”、协调成本较高、配方禁止将整套基础责任转成子Issue为依据，选择单一基础PR。这里保留的是决定依据的摘要及原件行号，不展开整份原生推理。证据入口为 `runs/iteration15/requirements-structure-inquiry/decision-context.json`、`decision-context-notes.md` 与 `decision-reason-summary.md`；冻结输入与目录机制由同目录 `input-chain.json`、`input-chain-notes.md`、`stages-input-chain.json` 保存。

第一项前提是资源能力误判。冻结Braid的assignee目录为每个普通profile返回下一可认领的具体成员，而不是该profile的全部实例或容量；认领glm-2后可继续取得glm-3。实际物理system也明确其它工作项从最新目录另选成员。因此目录只出现glm-2并不限制并行或独立业务负责人，根在未核实这一语义时，用不存在的单实施者限制压回了已考虑的拆分。

第二项前提是职责规则的作用域误套。“不把整套基础责任转为子Issue”约束共享架构、脚手架与反馈设施的归属，根却把它用于否决整套业务范围的子Issue方案。该规则既没有禁止业务拆分，也没有要求全部业务进入基础PR。根已知道需求很大，因此这不是持续相信仅有五处修改；它依据上述两个错误前提，将全部产品责任等同于一个PR的实施责任。协调成本高是根当时的判断，没有具体分支冲突、不可分共享语义或成本比较足以证明该判断客观成立。

输入设计上的支持性缺口是两个边界都不够容易被采用：目录展示下一名可认领成员，但其含义未被根正确理解；基础政策给出具体创建动作，业务分解的判断与基础成果的结束边界则较抽象。旧 `variants/pi-braid/run.py` 同时规定基础PR发布最小可消费接口，并正向要求多个业务子Issue；I13迁移后保留具体基础政策，将分解转入原则技能。这个演变能定位可能失去的约束，尚不能证明迁移单独造成误判，原则形式本身也不是原因。

同配方Stage1、Stage2和Evo的冻结root profile及物理instructions逐字相同。前两轮已完整读取相应需求和reading-requirements，Stage2还实际解读14张图片，仍形成单一全范围PR；这排除Evo漏读reference、未用vision或五处Modified锚定作为跨运行模式的充分解释，但较小阶段用单PR不必然错误。I11在相近基础政策下形成多个业务Issue，进一步否定“这一句基础政策必然造成单PR”。Stage1/2是否同样误读容量尚需各自决定证据，不从相同结果推断相同原因。

本次已能解释Evo为什么主动放弃拆分：资源能力误判与基础职责范围误套共同进入了决定。尚未确定为什么根没有采用system中已有的目录说明、为何抽象分工原则没有纠正范围误套，以及模型、措辞、发现面分别占多大影响。这些上游可靠性问题需要控制变量；不要再把未读技能、没看到树或没想过拆分写作本次根因。

| 现有表达 | 实际仍未解决的判断 | 需要锐化的含义 |
| --- | --- | --- |
| “一叶一项或一子树一项的数量规则没有独自保证结果” | 既然结构不保证正确，是否索性把所有叶子放在一起？ | 子树是已有的初始候选；只有具体跨枝消费者结果或不可分的共同语义支持调整，反对机械对应不等于放弃结构。 |
| “共享状态的权威来源、读写时机及刷新关系决定跨路径一致性” | 共用账户、权限或数据库是否需要同一负责人实现所有功能？ | 共享状态产生必须共同确定的合同；合同稳定后可由不同负责人实现各自完整能力，只有未决语义需要同步收敛。 |
| “成果的消费者与真实依赖提供分工理由” | 什么算足够小且可独立采用的成果？ | 边界要交付一个可观察的完整能力，并指出确切前提及相应需求范围；“全部功能能运行”虽有消费者，却不能据此消除原树中的独立能力。 |
| “覆盖是候选与原承诺之间的结论” | 场景已映射并通过，哪些父层义务还欠着？ | 除场景结果外，匹配对象、范围和条件的父层规则仍需证据；原文关系用于回查适用性，映射数量只是组织工具。 |

这些是对当前文本未约束决定的分析，尚未用同条件运行证明哪一句造成了行为差异。保留已有来源、责任与证据的有效区分，只锐化会影响拆分与覆盖的边界，避免把整份技能重写成强制操作流程。

## 利用原有结构的方案

需求树作为第一版工作地图：根与 FOLDER 正文提供适用范围和共同规则，子树提供候选业务边界，ATOMIC 提供行为义务，场景把同一义务展开为前态、动作、成功与失败结果，图片补充实际界面事实。先使用这些已有关系，再因跨枝用户结果与共享语义调整，而不是每次把整份材料扁平化后重新发明一套分类。

候选边界首先回答“这一子树交付什么完整能力、哪些规则从父层适用、哪些节点仍由其它任务负责”。将同一能力的成功、负向、权限和状态保持场景交给同一责任边界，避免按场景拆散同一语义；较大子树可沿其已有子层继续细分。跨枝行为明确整体消费者与局部负责人。出处保持原文路径与节点 ID，任务材料保存必要解释和未知，不复制整份原需求或另建强制全局台账。

`dependencies` 先作为待解释的关系：确认它要求已完成实现、已确定共享语义，还是仅要求验收时真实状态存在。前两者分别安排发布/采用与前置决定；最后一类不能自动串行化全部实施。共享登录或仓库数据不意味着身份、组织、文件编辑和 Issue reactions 必须在同一 PR 实现。

Evolution 还要沿同一结构核对每个范围的基线行为证据，区分明确修改、已有行为需要保留、缺失能力需要补齐与尚未核实。五个 Modified 段不能替代整树，114 个场景也不意味着每个任务都重新实现全部基线。共享种子任务可以持有增量补种机制与共同身份约定，各业务负责人仍核对其场景所需记录和关系，防止“全量种子”再次吸收所有产品语义。

每个工作边界应支持一个可独立演示或验收的结果，并容纳在负责人可理解的相关材料范围内。基础 PR 交付明确的共同前提，业务 PR 交付相应能力；二者各有完成依据。根回查整树是否仍有无人负责的义务、跨任务旅程是否有汇总责任、局部检查是否覆盖父层约束，不能用工作项数量、场景映射或测试通过数替代判断。

本题可用 REQ1 身份、REQ2 组织治理、REQ3 仓库资产、REQ4 代码版本、REQ5 Issue、REQ6 PR 的原树作为第一层候选，再沿 REQ2 的组织身份／成员团队／授权审计、REQ4 的浏览／分支／文件编辑等子层细化。它是解释该材料的候选地图，不是写进通用技能的固定题目答案。共享前提与现有基线会改变具体分组和可并行范围。

## 从 matt-skills 学习的模式

[writing-for-agents](https://github.com/mattpocock/skills/blob/main/skills/productivity/writing-for-agents/SKILL.md) 把触发指针、信息层级与完成依据分开处理：每种使用场景有明确入口，共用材料与条件材料分别放置，完成标准要求能区分已成立与未成立。它明确允许纯规则型正文；因此原则无需被流程取代，原则需要能改变判断的定义、条件和反例。

[codebase-design](https://github.com/mattpocock/skills/blob/main/skills/engineering/codebase-design/SKILL.md) 先定义术语，再用具体判断问题、因果和反例约束使用；[to-tickets](https://github.com/mattpocock/skills/blob/main/skills/engineering/to-tickets/SKILL.md) 将任务完成依据落在完整可演示结果、上下文容量和真实阻塞关系。可学习这种“概念有边界、规则有可判断条件”的写法，但它的逐票用户批准、tracker 模板和强制测试流程不属于无人值守 Braid 的现有合同，不直接移植。

拟修改入口仍归 `arc-bench`：在需求解释和任务拆分时明确触发结构阅读，并把上述关系写成可用于判断的原则与适量例子；`braid-collaboration` 负责按这些成果组织负责人、共享前提、并行和采用。不要复制二者的完整方法，也不把技能正文内联到 root prompt。验证先用公开材料做静态拆分预演，检查父层规则、跨枝依赖和场景是否仍有责任空洞；后续真实运行再比较首次可用成果耗时、重读范围、返工及遗漏，不能以读取次数或文本缩短宣称有效。

## 能解释什么，下一步怎样区分原因

时间只用于找到值得解释的位置；本轮结果优先看需求兑现与官网评分，再看token消耗。Evo实施者占主原生token约93.75%，其单次输入账面峰值537393，根跟进只有约2.38%；这定位到任务边界与实施上下文，而不能证明“缓存输入太长导致低分”。Evo没有最终官网评分，无法建立该运行的分数关系。

根当时已考虑拆分；定向原件把直接原因推进到“目录容量误判＋基础职责范围误套”。进一步改进应先纠正这两个具体前提，再检验requirements结构原则能否帮助形成边界。不能仅用技能读取、PR数量或角色自述证明机制，也不能把本次决定的直接原因扩展为所有I14/I15低分的统一原因。

| 未解机制 | 获授权后可区分它的比较 | 先观察的Agent行为及结果 |
| --- | --- | --- |
| 下一可认领成员是否被误读为唯一容量 | 固定Evo基线、需求、模型、runtime及旧技能，仅澄清目录的可增长语义 | 根是否改正“只有一个实施者”的前提，已识别的能力阶段是否形成独立责任。 |
| 容量理解改正后，基础职责是否仍吞并业务 | 与上一臂比较，仅明确基础责任与业务责任的区别及各自完成依据，保留root对整套开发基础的责任 | 根是否区分共同前提与业务责任，哪些真实依赖支持合并或并行。 |
| 纠正两个前提后，结构仍不能形成可用边界 | 保持上一臂角色和目录，仅替换arc-bench结构解释与拆分判据 | 是否沿原树形成初始候选、回查父层/跨枝义务、是否出现遗漏和整合返工。 |
| 245k压缩是否降低长实施消费却损失重要约束 | 另行固定任务划分与输入，仅开启/关闭原生阈值 | 压缩前后要求及未决事项的采用，重复读取/返工、input/cacheRead与最终结果。 |

拆分因果比较可以先止于首批责任形成，用小范围实际模型执行区分决定机制；正式收益再以完整生成、官网评分和token判断。本轮没有启动任一模型实验。
这些是控制变量的设计入口，不是本轮已启动的实验，也不将某个单次差异当机制证明。模型执行存在波动，单次发现反例可否定强保证，单次成功不足以证明可靠收益；需要根据行为差异和结果决定是否重复或增加下一变量。根跟进与运行时可靠性修复先沿已授权范围完成，再冻结实际材料身份，避免将设施故障与技能效果混在同一解释里。

## 成员机制与结构技能开工、advisor当时暂缓（2026-10-08，历史决定）

用户修正了上一版方案：CLI查询结果不增加重复说明；在Braid给profile注入的现有操作指令中简短说明名称机制。认可braid-collaboration中任务边界与执行并发分别决定的原则。advisor的用途是关键决策的成本收益判断，包括delegation与work-item breakdown，不能收窄为首次业务分工的一次咨询门槛。继续接续此前arc-bench需求结构改进。本轮维护方案与只读取证，源码开工仍按本任务明确授权范围处理。

普通成员机制归Braid注入指令，拟在已有指派段说明：“assignee目录为每类职责提供下一位可认领成员，不代表完整成员名单或并发名额；成功指派后，为其它工作项重新查询取得名称。实际使用遵守本次模型与会话限制。”沿用既有认领与陈旧候选处理，不改CLI输出或JSON，不扩展成员池。reviewer合同由侧会话维护，本段仅普通assignee。

braid-collaboration说明任务边界与执行并发是不同决定：有限执行资源仍可顺序交付独立能力，不能仅由成员数量或共享数据库推出单一全量PR。委派和拆分的价值包括缩小相关上下文、取得独立反馈、减少幻觉与遗漏、复用专长和并行收益；成本包括共同前提确定、背景传递、结果理解采用、集成、纠偏和重复验收。具体成本收益方法复用svc-sub-agents，而非在多个技能重复维护编号机制或成本清单。
