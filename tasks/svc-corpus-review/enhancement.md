## 目标与组织

让 Agent 更容易作出有依据的下一步选择，并用结果修正理解。
增强的单位是判断质量与反馈质量，不是条款数量、测试数量、角色数量或自我提醒频率。

```text
现有 Corpus
├─ methods/
│  ├─ index                 识别没有进展的重复，选择需要重开的工作
│  ├─ explore               围绕有区别的解释收集证据，知道何时足够
│  ├─ design/product        不完整想法下提出自己的方案和取舍
│  ├─ design/technical      用真实接口和状态归属约束方案
│  ├─ design/engineering-judgment
│  │                        问题必要性 → 责任/生命周期 → 实现复杂性
│  ├─ design/test           设计能改变结论的观察与判定
│  └─ implementation        提前消除会改变路线的未知，再按反馈推进
├─ verification/            评价产品结果和证据边界，指导后续行动
├─ sub-agents/              选择值得委派的工作及能胜任它的执行者
└─ task-packet/             保持当前认识、决策及下一步可恢复
```

保留现有文件地址，不新增反打转协议、reviewer 角色、进展状态机、模型评分表或强制阶段。
入口只给使用时机与链接，正文各有一个归属；模板只在现有含义发生变化时同步。

## 1. 打磨 V&V

Test Design 回答“要作什么判断、什么观察会改变它”；Verification 回答“实际观察支持了什么、下一步是什么”。
两者共同维持产品意图 → 行为性质 → 观察 → 判定的关系，但不各自复述整套方法。

区分两类问题：设计/实现是否满足明确要求，以及该要求的解释和所选方案是否实现了原本目标。
前者全绿不能自动回答后者；后者有时需要原型、实际使用或有理由的质性比较，而非捏造一个客观分数。
需求、可修改的设计假设、当前观察与判断分开表达。

设计证据时先选仍可能改变结论的重要性质，再选保留其语义的便宜观察边界。
明确直接结果和诊断线索各回答什么，不靠测试层数、角色身份或通过项数量增加信心。
已有可信机制覆盖的检查不让 Agent 重复；真实组合带来的新不确定性才需要补证据。
双向 oracle 辨别、输入/状态选择、mock 的限制、重复使用成本和错误标准的修订仍保留在 Test Design。

运行后分清产品不符合、检查自身错误、环境/设施失败、证据不足，以及实际支持的成功范围。
这是解释观察的区分，不新增固定状态枚举或要求填写全套表格。
能够定位的缺陷回到相关实现；假设被推翻回到设计；缺少关键观察就说清缺什么，不用重复同一种无效检查凑结论。
整体验收完成前不能用局部检查代替用户旅程；已经足够支持当前结论时也不无限扩大验证。

不安排“读代码找 bug”的通用 reviewer 工作。
可以为具体矛盾阅读相关实现以解释因果，但缺陷判断与验收要有对应的可观察行为、可靠静态机制或其他适合该性质的证据。
独立性来自证据/机制如何形成，而非换一个 Agent 得出同意。

## 2. Shift-left 与实现反馈

把注意力提前投入那些一旦判断错误就会推翻方案或造成大返工的未知。
先查所用版本的官方文档、接口定义、已有调用和可取得的真实行为；资料不足以回答关键兼容性或生命周期问题时，选择最小真实 spike。
写清 spike 要区分哪两种可能及它将如何改变路线即可，不为此建立新的文档或实验平台。

真实执行比模拟便宜时直接用真实执行；没有重要未知的机械改动直接做。
预演不是把全系统实现两次，也不是用更复杂的模拟替代现成的真实模型/工具。
实现计划只展开已经能判断的下一段，局部反馈仍保留，以发现无法提前排除的变化。

## 3. 识别打转，回到正确的问题层次

信号是同一解释、检索、修补或复核反复出现，当前认识和产物没有有用变化，而不只是耗时长或调用多。
先看最近工作消除了什么未知、排除了什么解释、改变了什么可观察结果。
没有变化时找缺失的判别：错误目标、证据不可得、工具不可用、边界设计错误或执行者能力不匹配，需要不同动作。
把当前解释和下一项有区分力的观察写回已有 packet，不堆积同样的搜索记录。
真实外部等待用合适的等待/通知机制；不是要求 Agent 不停“重新思考”。

反复出现时序、并发与补丁时，先重述产品结果与必要约束，检查我们是否在解一个自行引入的问题。
需求成立后，再审状态权威、生命周期、职责和依赖关系；能够通过消除重复状态或错误责任根除问题时，再改这些边界。
真实问题确需复杂机制则保留，但说明它消除了哪项具体矛盾。
不要自动把“越来越复杂”翻译成“缺少更强抽象”。

## 4. 开放设计与委派

开放问题需要主动形成可反驳的产品判断：从目标和语境提出具体方案，说明推荐理由、关键取舍和仍待确认的假设。
不要只顺着用户片段补细节，不因不存在唯一答案就停止；有证据时也应指出原想法的问题。
品味通过实际使用后果、连贯性、合适的复杂度和维护/改变成本表达，接受新证据修正。
不能把临时选择升格成用户原有要求或让测试反过来定义产品。

委派前比较直接处理、确定性工具与子代理的整体成本，包含说明上下文、等待、返工、验证和集成。
一句已知查询不必委派；噪声很多的定向取证可以隔离给子代理；需要全局取舍却只返回大量材料的委派可能反而增加主 Agent 负担。
每次返回应能直接推动某个决定或接入某个产物，不能让主 Agent 重做一遍才能知道其价值。

选择执行者时分别考虑：答案是否可客观判定、需要怎样的开放判断、所需上下文和错误代价。
“有界”不等于容易，“explorer”也不等于适合便宜模型。
已明确目标与检查方式的专项工作可以使用擅长这一类工作的执行者；尚未形成问题或需要自主产品判断的工作，需要相应能力。
具体型号、reasoning、profile 配置与基于实测的替换决策属于 Harness，Corpus 不规定模型排名。

## 用户 AGENTS.md 的采纳边界

采纳并改写：目标与观察分开、从第一性原理检验假设、提出自己的产品/技术判断、匹配范围、按理解和修改成本组织模块、为复杂性举出具体用途、按问题选择验证、按消费者组织说明、以总成本衡量委派。

## 复核、实施与验收

用户本轮同时认可设计并明确授权修改，无需再次请求开工确认。
实施前工作副本保存在 `runs/svc-corpus-review/enhancement-before/`，保留此前未提交改动。
实施时按 V&V → 工作方法 → 委派/packet 与导航去重的顺序更新各自唯一正文，再同步受影响引用。
这里不另开通用代码 reviewer 委派；是否需要独立预演只取决于具体未决问题及其收益，不默认安排第二名 Agent 泛读全文。
提交仍需明确指令。

不建立 Corpus 内容测试、盲读测试、提示词评分器、设施测试或改名自检。
编辑复核直接检查正文的职责、因果链、矛盾、重复与导航是否能支持上述使用；不能把这种文本复核当作方法已经有效的证明。
运行有效性沿用已约定的真实 bench 与原生 trace 验收，等待实验授权和输入确定后执行。
观察是否实际读到候选材料、关键未知是否提前解决、反复无信息增益的工作是否减少、是否采用能支持产品结论的证据，并结合完整评分判断。
若 trace 不足以归因，明确缺口；本轮不为此擅自扩建观测设施，也不从得分变动直接推断 Corpus 的因果效果。
