## 两种解释的判别与边界

若 Braid reset 是主因，应看到 @glm-4 在 09:40 正确检查之后、09:52 改写之前换成新 provider，且新输入缺少此前的需求依据；记录给出相反的身份与输入链。若通知混乱是主因，应看到相邻窗口大量与本判断无关的消息实际进入其原生输入；记录只显示后台排队。相反，SVC 执行偏移有正面证据：正确需求送达、正确断言初写、失败快照指向实现角色错误、模型仍主动改断言。另一个反例是它同期修复了 `Add member` 重复按钮的真实 UI 问题，说明不是一概只改测试；这使根因更精确地落在该入口的合同判断，而非笼统“不懂验收”。

现有材料不能测量长上下文、超时排障对这一判断的心理影响，也不能判定强制重读 SVC 是否会改变模型行为；单条轨迹没有对照。下一步应把重点放在**验收判据变更的依据与复核**：检查失败后，先用已送达的权威需求决定改实现还是改断言，并记录引用和观察；Braid 的 reset 与通知修正仍可因各自已证实的产品问题推进，但不应以这次 oracle 改写作为其质量收益的因果证明。不需要为此设计与具体题目耦合的修补规则。
