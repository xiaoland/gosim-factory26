# V&V 材料的具体修改与核验

当前规范输入是 tasks/verification-system.md；只改 SVC 的 `corpus/methods/design/test.md` 与 `corpus/verification/index.md`。现有正文读过，但尚未实施。非 V&V 方法、sub-agents 和 task-packet 正文保持冻结。

Test Design 保留从有权威的产品意图出发，明确可观察行为与观察边界；将现在并列罗列的 scenarios/oracle 拆清为两个问题：什么算正确，以及在哪些状态、输入、历史与失败条件下检查。加入两个方向的辨别：破坏需求应能失败，满足需求的等价实现不应误失败。用一个持久化例子说明成功提示不足以证明数据保留，API/存储检查与用户路径各有责任；不生成每需求测试或固定测试层数的规则。

Verification 保留“证据的范围、可信前提与未覆盖项”，减少抽象的 proof/qualification 复述。明确验收证据回答产品结果，诊断证据解释偏离位置；选择保留语义而成本/反馈合适的验证边界。快速局部检查与较慢组合检查提供互补证据，不按工具名或比例机械分层。验收依据可以修正，但必须说明需求变更、观察更新或原判据错误，不能和实现一起无理由放宽。确定性与独立 Agent 都不自动代表正确性，不增设 reviewer 门槛。

编辑前后的消费核验：给独立阅读者一个非 benchmark 的临时需求（持久化设置及跨会话读取），只给候选正文和需求，让其选性质、Oracle、输入/状态和观察方式。核验能识别“提示成功但未保存”，并接受保留需求的不同路由/DOM/存储实现；返回判据及其不能证明的范围。此为方法消费检查，不替代应用 bench，也不额外调用比赛模型。

机械核验复用 SVC catalog/link 检查；对比非 V&V Corpus hashes。SVC 发布规则要求 Corpus 内容与版本同步，局部澄清按 patch 记录版本和 fragment，这些机械发布元数据不算修改其它方法正文。安装后四组消费同一实际版本/内容 hash，不能只记录源码版本而继续用旧 wheel。

独立预演已复核范围和因果链，补充：阅读者仅交付其可追溯判断，不拥有批准权；以破坏/等价实现的受控反例检验候选判据。完成实现前提交后修改正文，当前不把候选文字当已消费事实。
