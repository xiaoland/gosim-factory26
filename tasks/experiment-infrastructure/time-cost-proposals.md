## 环境准备：先分解证据，撤回预制检查入口方案

用户明确：Harness 不能直接生成或修改应用内容，包括检查脚本；改进只能通过更好的外部工具或提示词进入 Agent 的工作。
本轮没有修改生成应用或植入检查入口，原建议已撤回。
2026-09-28 用户澄清：可复用检查辅助脚本可以随 Agent Skill 提供；边界是 Harness 不直接写入生成应用的 package.json、src、scripts 等源码位置。脚本内容与如何使用仍须保持通用，当前未据此新增资产，候选见 browser-feedback-audit cell。

逐动作取证已完成，见 [GitHub](../github-score-diagnosis/environment-cost.md)、[Sheet](../sheet-score-diagnosis/environment-cost.md)。
Sheet 七次互不重叠的检查/故障注入 job 总执行 12 分 15 秒，不是 29 分钟净环境耗时，也不是全部可省。
PBB 原始记录显示完成到首次读结果约 12–108 秒；有些外层 exitCode=0 是 tail/echo 掩盖失败，另一次诊断被清理时删除服务日志阻断。
GitHub 则出现端口 0、重复 JSON 编码、临时移动脚本导致相对路径错误、遗漏 BASE_URL；不是浏览器安装慢。

已核对本次冻结 runtime 内 pi-background-bash 1.0.5 的 README 和 runner 文档：现成能力包括每 job 的 PID/PGID、完整日志、真实命令结束通知，以及 pbb list/status/tail。Pi-lane 提供会话身份与存活信息，不是应用服务管理器。
因此第一步不新增等待、日志或进程句柄工具；先修接线与使用方式。PBB 记录的是调用 shell 的退出码，不能自动恢复被 tail/echo 掩盖的上游失败；应用端口归属也不等同于 Pi 会话存活。
修复按以下两步进行：
1. 先修工作方法。browser-checks 的启动/诊断入口说明显式 cwd/env、服务归属、失败日志保存；保留真实命令退出码（管道使用 pipefail 或原退出码，不以末尾 tail/echo 成功为准）。原生执行角色优先用现有 PBB 的任务完成结果，避免另起 sleep 或混用 subagent_wait。通用 V&V 只保留“先辨别执行环境、检查本身与应用行为”的方法，不塞 shell 专项细节。
2. 只有现有 PBB/Pi-lane 无法表达服务进程归属、存活与日志保留时，再给外部工具补所缺能力。工具只接受 cwd/env/argv 与资源句柄；不生成应用脚本，不预置应用健康路由、登录过程或业务断言。优先改原插件，不再建第二套服务框架。

验收从后续真实任务取证：真实退出码与原始失败可找到；日志不因清理消失；检查访问本次启动的候选；首次可用失败到定位性质的等待减少。
不以此次观察窗承诺固定收益；模型消息间隔仍不可归因。

## 并行前收敛共享契约，集成时保持小步

[Sheet 合并窗口](../github-score-diagnosis/shared-contract-cost.md) 已确认更精确的原因：消费者读懂根裁决，却因新实现未发布、旧 develop 的自检为绿，选择旧契约并把冲突留到集成。
28 分 23 秒是 rebase 开始到启动回归的观察窗，尚不是验收完成；其中本地 rebase 与迁移约 21 分 27 秒，其后约 6 分 55 秒为静态/测试调整和回归启动。
修复重点不是要求所有子任务串行，也不是增加一个泛化 reviewer。

建议负责拆分的 Agent 在设计与实施准备时识别真正共享的边界：数据形状、错误语义、路由、认证和共享文件所有权。
有依赖的任务以已发布的窄契约或最小基础实现为起点；先用最小生产者/消费者调用确认共同理解，再并行展开独立行为。
变更契约时在原 Issue/PR 讨论串说明权威来源、废弃形状与影响；尽早 push 最小契约提交或文档，让消费者不必等待整个功能完成。
消费者应依据已决议契约写检查；当前分支旧实现可通过旧检查不是推翻裁决的理由。不确定时通过原讨论串澄清。
更新通知是否实际投递和消费，交给 Braid 投递证据审查；共享契约的语义仍由 Agent 处理。
不采用“Braid 自动比对契约版本、禁止 PR 合并”的建议：这会让 Harness 解释应用语义。PR 提交与整合前的契约核对属于 Agent 的实施方法。
同一层共享文件反复冲突时，重新划分任务边界，而不是继续堆 rebase 指令。

落点是 SVC 的设计、计划与实现方法；Braid 只提供讨论、分支和合并能力，不推断依赖或强制拓扑。
验收观察：关键契约在消费者实现前已有可执行例子；合并失败的主要原因不再是双方独立定义同一个字段或错误形状。

## 完成后的通知不应无限消耗模型

已证实的 terminal_contact 回环不是环境或模型速度问题。
当前全对象终态的完成检查已让两题进入评分，但这只解决交付被阻挡。
独立审查进一步在原始数据库发现 GitHub 236 次、Sheet 441 次 terminal_contact 没有关联事件；旧事件重放未能重建 batch 关联却仍启动空批次，优先应修此调度根因，而非把全部回环归咎于 Agent 回执。
未全部完成时的无行动回执互相唤醒、context reset 恢复等生命周期问题由独立 Braid 审查确认根因后再修；不能用全局静默时间或禁用必要通知掩盖协作断点。

## 决策顺序

先消费 GitHub/Sheet 的行为诊断与 Braid 审查，核对低分是否还有更上游的需求或判据错误。
逐命令拆解已支持上述优先次序；先核查插件现有能力，再决定最小接线改动；具体提示词/技能改动按本轮已复核范围实施，不扩大到题目专有内容。

## 新的得分证据对方案的校正

GitHub 分析在同一实例复现了“自检通过、需求入口失败”：页面覆盖 link 为 menuitem，自检也按 menuitem 查找；API 能返回认证错误，但浏览器原生表单校验阻断了提交。
Sheet 的自检另建并填充工作簿，绕过了默认 Q3 Sales 工作簿缺少指定数据的事实。
因此，仅改善运行环境与集成效率可能更快地产生同样低分的应用。

后续方法改进还应保持验收输入、公共入口、判据来自需求，避免依据已生成实现反写预期；将默认数据与真实浏览器路径纳入同一可重复检查。
这不是添加题目名称或一套固定选择器规则，而是校正验收依据的来源。
具体运行证据及未知项以两个得分诊断 packet 为准。
