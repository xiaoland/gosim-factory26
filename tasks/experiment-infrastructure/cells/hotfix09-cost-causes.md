## 零委派的解释与设计判据

截至 07:20，Sheet 高用量 Issue #3 和 PR #8 会话无新 `subagent` 启动，原生 assistant 可见文本也没有明确的委派选择讨论；模型的未保存内部取舍未知。Issue #3 的“PR #9 合并后筛选隐藏行仍应导出”浏览器旅程理论上可交 `browser-operator` 独立复现，但当时父已有干净 worktree、固定候选 head、Playwright 回归和验收评论，另开角色需重复交代端口/种子/产物并复核结果，未必省用量。PR #8 归属会话可把某一隔离浏览器旅程交出去，但已有 Braid Issue #5 实施 owner，自己是审阅/集成判断者；再委派同一套检查可能与在途 Braid 工作重叠。GitHub 根同理已有 Braid 成员负责 PR，原生 `executor` 重做这些工作风险高。相反，GitHub #8 图片文字解读与父实现边界清楚，模型确实发现角色、委派、读取结果；这说明“08 零委派”只是早期 [07:04 截面](../../factory-subagents/cells/attempt08-validation.md)的事实，不是整个 08 的稳定状态。

因此不按调用数设固定 explorer→vision→executor 流水线。若要改变委派设计，应先找**父需要但与现有 owner 不重叠、能用明确输入/输出验收、可由父消费**的切口；候选是新的独立视觉事实或一个不占共享浏览器/工作树的浏览器旅程。计数、长回显和大缓存只能定位调查段，不能替代该条件。

当前足以支持的 09 行动是收窄 `subagent_wait` 空结果的 PBB 指路，避免睡眠命令替代完成唤醒；对 Sheet #3，先在角色工作方法上把进度评论与权威正文区分并合并必要正文更新，再观察 self-origin reset 是否仍频繁。若要动 Braid 失效规则或压缩视觉报告，尚需分别证明自身正文修改不影响当前语义、以及报告中哪些具体信息没有进入 UI/验收。没有这些证据不计算可省 token 百分比，也不以降模型档位代替流程修正。
