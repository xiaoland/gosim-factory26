# 实验端到端追溯与诊断设计

用户要求继续设计直到整个解决方案收敛，随后授权完成实施计划与排障。产品流程、默认行为与技术边界已确定，实施准备见 [计划](plan.md) 和 [预演](preplay.md)；尚未获得源码实现或新实验授权。调查与真实证据见 [packet](packet.md)，具体接口、生命周期、目录与验收约束见 [技术方案](technical.md)。这些文件供工程接续，面向用户只汇报主要决定，不要求逐份复审。

## 使用者要完成的工作

产品目标是缩短从提出实验问题到获得可采取行动的证据的时间，减少找文件、辨别记录、重复执行和人工拼接上下文的工作。并行吞吐、过程可见性与已完成工作的复用共同决定反馈速度。

结合当前使用方式，主要操作方包括开发/分析 Agent，以及需要审阅结果和决定下一步的人。Agent 需要稳定引用、有界查询、结构化输出和完成反馈；人需要简洁的实验概览、可读原因与可打开的证据。两者应使用同一组事实。这个使用者假设不限制设施可接入的 Harness 或分析工具。

| 使用场景与用户的问题 | 预期体验 | 当前可见障碍 |
| --- | --- | --- |
| 发起一次比较：“把这些配置按同一任务集并行运行。” | 选择已有配方或提供命令与输入，看到组合、运行位置、并发、生成/复评范围后启动；得到可以继续查询和交接的实验引用。 | 机器清单、运行根、服务配置与任务记录分散，使用者需要自行拼接。 |
| 运行中：“Agent 在做什么，是否需要介入？” | 实验概览显示各项阶段、最近的运行确认和过程证据；可进入所选 Agent 过程分析，未接入分析时明确可用的原始数据。 | 通用 status 原样返回保存的 JSON；received/absent 和批次数无法回答过程问题。 |
| 失败后：“哪个环节出了问题，依据是什么？” | 从异常任务直接进入具体错误、原文及相关过程；原因未明时说明已有事实和缺少的证据。 | 运行说明要求先辨别记录生产者，再选择查询命令；外层错误常只说明评测未完成。 |
| 继续实验：“能否只重跑评测，保留已经生成的应用？” | 对指定应用发起复评，动作明确说明复用内容、执行范围和是否调用模型；自动连接原生成执行。 | 回放包已有部分来源，但用户仍须找到包、路径并维护重试关系。 |
| 比较与交接：“变化在哪里，结论可靠吗？” | 并排看结果和实际条件差异，从结论到用例、应用、生成过程逐层进入；给另一位使用者一个稳定入口即可接续。 | 报告选择尝试和测试版本的依据不充分，重新分析时可能依赖当前 checkout。 |
| 接入新的 Harness/分析器：“怎样保留自己的过程数据？” | 外部命令接入执行，标准 OTLP 接入保存，自选程序消费证据；结果能够从对应实验找到。 | 原始批次保存已有，分析入口分散；不应要求新接入者理解 Factory/Braid 私有对象。 |

### 交互与默认行为

使用者以实验名称、任务/配置和可继续传递的引用工作；内部 ID 与来源关系由设施建立，不要求人工填写整条关系链。默认摘要先给出当前状态、需要关注的事项、关键证据入口和适用操作，再逐层展开阶段、原始错误与过程。哈希、批次编号、目录生产者等细节保留在详细查询中，不占据日常摘要。

具体入口分为三个层次，CLI 的结构化输出与可读视图沿用这些层次：

1. **实验概览。** 按本次清单的任务/配置显示当前执行、评测结果和过程入口，历史尝试在任务下展开。已完成数以计划任务为分母，执行次数另列；进度指实验工作完成程度，不推测 Agent 实现了百分之多少。用户能够筛选正在执行、执行异常、待分析的应用失败和全部任务。设施异常与完整评测中的低分分别呈现，后者不会触发自动重跑。
2. **任务详情。** 默认显示最新尝试、最近可用的有效结果及其条件，明确两者是否来自同一次执行。具体 run 引用始终打开原尝试，并显示已知后续记录，避免从旧故障入口重复发起补救。没有显式历史关系的旧数据只能显示有依据的候选关联。尚未收口的历史状态单列，不能累加到当前运行数。
3. **过程与证据。** 在当前上下文直接选择本次执行日志、输入应用的生成过程、用例现场或已保存的分析结果。回放评测明确没有新 Agent 生成过程，提供原生成过程的来源入口；不把旧事件放到本次时间线上。分析器已提供的会话/动作筛选由其负责，通用层提供批次查询、导出和证据引用；未接入语义分析也能取得原始数据。

一致的实验入口可以连接现有 CLI、静态查看页和用户提供的分析产物，不要求先建新的网页平台。可选分析器负责语义视图；通用入口负责让用户找到它、知道其来源和更新时间。未安装某分析器时仍能查询执行与原始数据，不自动运行任意分析程序。

本轮确定以 `python -m lab` 的 CLI/结构化查询作为主要操作入口，现有查看页消费同一事实。输入先按实验共享冻结，准备进度可见；启动后可以调整总执行并发，不按同题或 variant 串行。操作 Agent 可等待完成/异常事件并传递游标，用户无需反复追问或重新拼接全部实验上下文。

运行数据与派生报告都显示观察/生成时间；历史快照不能呈现为当前运行情况。等待支持完成与需介入的反馈，避免要求操作 Agent 反复读取未变化的心跳。过程查询按需要缩小到阶段、会话或错误附近，范围由所选分析器支持；摘要截断保留原文引用，不能为了输出短而丢掉具体错误。

启动与继续执行的摘要说明实际机器、输入、并发及会发生什么。已授权操作直接执行，预览不变成新的强制确认步骤。操作应明确区分停止等待、停止执行、重新生成和复评已有应用，避免使用含义模糊的“重跑”。无法核实模型用量或费用时说明未知；复评入口只有确认路径不调用模型时才声明不消耗模型调用。

**仅复评的完整体验**是：从任务或应用选定复评范围，设施带入原应用及冻结评测条件，说明将启动部署/评测、是否存在条件变化，然后建立新执行并连接原结果。使用者无需再寻找回放包或拼接机器路径。选定新测试集时明确记录新的比较条件；无法取得旧快照时说明缺项，不悄悄使用当前 checkout。应用是否可复用取决于它的实际来源与可用内容，不能仅因原 run 的后续评测失败就拒绝复用。

异常摘要先展示观察到的具体错误及来源，再给出已知影响与适用操作。例如 npm 安装报错且没有测试报告，应同时链接安装日志、已生成应用和复评入口；根因尚未确认时保留未知。后一次评测完成但用例未通过时，应提供用例现场与生成过程分析入口。所有操作建议都是可选入口，不把设施推测变成自动修复或再次模型消费。

### 产品优先级与验收依据

优先解决从实验进入 Agent 过程和具体错误的困难，并使并行矩阵的状态可理解。其次让复评、比较和交接复用已有工作；控制能力只补这些流程需要的可靠停止与状态核对。任务发现中的 P1/P2 是技术风险标记，不直接等同于产品建设顺序。

用既有真实记录进行操作走查，检查使用者能否完成以下工作，并记录人工查找次数、无关输出量和无法继续的环节；目前没有这些体验指标的基线，不声称已经改善：

- 只拿到实验引用，就能找到指定失败用例的实际错误、被测应用与生成执行，无需先阅读目录架构。
- 从生成执行到达可用的 Agent 过程；若无法解释问题，明确看到是没有上报、接收出错、尚未分析或分析器发现缺口，无法区分的部分保持未知。
- 查看多次尝试时识别当前执行与已采用成绩；仅复评时不重新生成，也不手工重建来源关系。
- 将结果交给另一个分析 Agent，后者能取得同一批证据和比较条件；更换当前源码不悄悄改变旧结果含义。

这些是操作验收场景，不新增设施测试。后续每项字段或接口改动都应指出改善了哪个场景；只有补齐字段但使用者仍需手工串接的方案不算完成产品目标。

## 支撑上述体验的组件职责

沿用当前 `lab/`、`lab/arc_bench/`、`lab/analysis/` 的边界，不引入新的服务平台、插件注册系统或统一 Agent 事件格式。

| 组件 | 应拥有的事实 | 边界 |
| --- | --- | --- |
| 实验控制器 | 实验清单、调度尝试、进程归属、控制操作、输入输出关系 | 不解释 Agent 会话或测试分数。 |
| Runner 适配器 | 实际镜像与 Runner、阶段、容器归属、交付应用、评测结果及原始错误入口 | 不通过某个 Harness 私有终态判断所有 Harness。 |
| OTLP Collector/backend | 批次归属、接收时间、原始 payload、接收失败与补采记录 | 不推断是否有全部子代理、工具返回或模型调用。 |
| Harness/模型网关 | 自己产生的过程、请求及有效配置 | 通过通用运行上下文建立外层关联，保留自身身份。 |
| 可选分析器/报告器 | 所选证据、解释、完整性判断、评分汇总 | 记录来源与工具版本，不反向修改原始事实。 |

## 身份与来源关系

新增的身份应回答具体问题；现有 `run_id` 直接表示一次执行尝试，无需再建一个同义 attempt UUID。

| 对象 | 建议的身份规则 |
| --- | --- |
| 实验实例 | 一份冻结的解析后清单及实验 ID。重新运行同一配方可以是新实例；修改输入或评测定义形成新实例。配方名称只是可复用标签。 |
| 逻辑任务 | 清单内的 job ID。同一实例中，相同任务的重试沿用它；不能靠题名、variant 或时间猜测。 |
| 执行尝试 | 每次启动分配新 run ID，记录所属实验/job 和明确的 `retry_of`。启动同一清单不会默默覆盖旧尝试。 |
| 冻结制品 | 内容身份、生成它的 run、冻结边界及可定位的产物。重新打回放 ZIP 不改变其中应用内容的身份。 |
| 复评 | 新执行显式引用旧应用。其评测 run 和原生成 run 不合并，模型消费归原生成执行。 |
| 分析/报告 | 引用实际采用的 run、制品、测试集、读取截止点、解释器版本和选择规则。保留未采用尝试及原因。 |

生成加评测仍可由同一外部命令完成，不强迫用户把每个内部步骤拆成独立 job。只复评时才创建消费既有制品的新任务，并保留来源关系。

制品路径用于定位，哈希用于核对内容，生产者 run 用于解释来源。三者缺一时分别报告缺口，不把哈希当作运行历史。现有 `lab.snapshot`、ARC `source_hash` 和回放应用清单采用不同的哈希输入规则；后续新记录必须同时标明身份算法/覆盖内容，历史值原样保留，不能仅凭同名 `sha256` 字段相互比较。ARC 可复用已有应用文件清单来形成明确的交付制品身份。

回放包是执行输入，应用是被评对象。比较应用评分应按应用、需求、测试集及实际 Runner 条件呈现；回放 ZIP 的差异仍记录，但不把“所有 ZIP 必须相同”当作唯一比较规则。配方可以明确 variant、模型等预期变化，应用差异正是许多实验要观察的结果，不要求不同配置生成相同应用。条件不同可以并排查看并注明差异，不能冒充相同条件下的一个总分。历史缺项保持未知，不拒绝整份历史记录。

`run.json` 继续拥有控制器事实；适配器结果、原始 Runner 文件和 Harness 证据保持各自归属。摘要中的复制字段要注明来源和读取时刻，而不是形成另一个可独立修改的权威状态。来源引用优先相对实验根目录，运行时 argv 中的原始绝对路径继续保留作证据。

## 过程观测与诊断

实验入口提供一次执行的通用上下文和 OTLP 连接参数。Collector 已通过 token 将 payload 绑定到 run，可继续使用这个能力；Harness 内部 session ID、trace ID、工具 ID 无需改成外层 run ID。一个 run 可以包含多条 trace，也可以只有 logs。

用户应能从同一入口看到以下三个独立事实：

- 执行到了哪里：排队、启动、适配器当前阶段、进程是否退出，以及最近一次确认这些事实的时间。
- 已有什么证据：原始日志/产物位置、最后接收时间、批次数及接收错误。收到数据不等于 Agent 有语义进展，没有新数据也不直接证明卡死。
- 这些证据能解释什么：分析器展示自己的解码/关联/覆盖结论及原始引用。未配置分析器时保持未分析，不用批次数代替完整性。

控制器记录自己管理的生命周期；适配器记录生成、部署、测试和收集等自己能够观察的阶段。共享的只是时间、生产者、执行引用、阶段/操作及原始证据入口，不统一各生产者的业务阶段词表。不要求 Harness 改用设施的阶段协议，其过程仍走 OTLP。

错误保留最初的具体消息、退出码或 HTTP 状态和来源位置。上层可以增加“评测未完成”的解释，但要链接到产生它的阶段及下层记录，避免只剩一串泛化错误。设施故障、生成应用缺陷和证据不足分别表达；不能从一个非零退出码自动推定根因。

模型配置由实际加载/变换它的组件记录：Harness 记录请求配置，网关记录最终路由及改写参数。只记录非秘密配置及版本，不复制整个环境文件。共享网关采用每 run 的本地凭据绑定，将自己的请求 ID 连接到该 run、上游尝试及结果；客户端仍使用普通的地址和密钥配置。此设计已核对当前 LiteLLM 接口，不依赖 Pi/Codex 自定义头。直连供应商继续可用；未提供请求与内部会话关联时明确诊断限制，不根据时间猜测。

Collector 记录能归属某 run 的拒收，以及接收服务自身的错误；无效 token 无法可靠归属，不能写到猜测的 run，也不记录凭据。发送端重试、离线原文保留和过程覆盖声明归发送方。接收端只承诺已确认保存的批次，不承诺语义完整或网络重试恰好一次。

运行结束后允许显式开启补采会话，向指定旧 run 追加证据，记录独立接收会话与时间；不改执行终态，不把旧事件伪装为新的 Agent 行为。查询与分析固定 batch ID 截止点，沿用现有 Braid viewer 的快照方式。无需为补采先引入常驻 daemon；旧 endpoint 失效必须明确可见。

## 状态、结果与最小控制

执行结果、评分结果、证据状态和清理结果分别保存。应用评测已经完成但过程证据缺失时，分数可保留，同时标明无法完成相应诊断。如果实验目标本身包括过程分析，实验目标尚未满足；这也不应抹去已得到的分数。执行退出与收集结束分开记录，收集异常不能覆盖已经观察到的原始退出结果。

默认状态展示最新尝试，包括尚在运行或失败的新尝试；旧有效成绩单独可见。报告明确选择哪次尝试，不能悄悄以旧成功覆盖新失败。测试附件、Playwright 最终状态和适配器结果冲突时保留冲突，不仅凭正文的 passed 附件计成功。

停止针对明确的实验/执行归属，分别记录请求、进程退出和容器清理确认。未启动任务写明取消；已运行任务确认结束前不能宣称停止成功。控制器保存主机、进程启动身份及适配器拥有的资源引用，不能用 PID 或容器名称前缀误停另一个实验。

控制器丢失时，状态查询先显示上次记录和当前核对结果。核对必须考虑主机启动与进程身份，不能凭最后更新时间推断已死；无法核对时标为未知。确认原执行已失联后保留确认时刻，不编造原结束时间。磁盘写入失败也不能承诺原子保存所有证据。

重试创建新尝试，消费明确输入；只复评消费既有应用。恢复 Agent 会话只有在该 Harness 明确支持并接受相应输入时才成立，不让通用设施假装能从任何上一 turn 续跑。当前任务不增加自动模型重跑、自动调参或动态限流调度。

## 用真实问题检验设计

| 已见问题或源码允许的失败 | 设计应让使用者得到的答案 |
| --- | --- |
| 同一场景留下 failed、历史 running、后续 completed | 显式尝试关系、最新执行与所选评分分别可见；历史 running 可核对，不静默改写。 |
| 应用已生成，后来部署/测试设施失败 | 能定位已经冻结的应用及生成证据；下一次复评引用它，不重新消费模型。 |
| OTLP 有批次但分析 Agent 报证据不足 | 能区分接收事实、发送错误、解析缺口和过程覆盖限制，并回到各自原文。 |
| Collector 已关闭而原始会话仍在 | 新建显式补采会话，保留旧执行及旧分析；新的分析注明新截止点。 |
| 更新测试源码后读旧结果 | 使用实际冻结的测试/coverage；没有快照的历史记录标明缺口，不用当前 checkout 冒充旧版本。 |
| 测试正文通过但 teardown 失败 | 同时保留附件与最终失败，不发布未经说明的 passed。此为源码审查发现的可能路径，尚无真实误计分证据。 |

## 方案收敛

已用真实历史记录完成两条主流程的只读走查，依据见 [流程走查](walkthrough.md)。其余产品决定如下，技术接线已在 [技术方案](technical.md) 中明确。

| 决定 | 对使用者的效果 |
| --- | --- |
| CLI 与现有查看页共用事实，分析程序由使用者选择 | 同一实验引用能够持续查询和交接，新 Harness 无需改基础设施的私有语义。 |
| 输入在实验内冻结一次，产物按需要发布 | 减少重复复制与收集等待，保持并行实验的隔离与来源。 |
| OTLP 接收补齐 gzip、可配置大小、具体错误与补采 | 标准 exporter 更容易接入；过程数据缺失时能定位传输层问题，不凭 received 宣称完整。 |
| 执行、评分、证据与资源清理分别呈现 | 用户知道应查看应用失败、处理设施问题，还是补充过程证据。 |
| 复评消费已有应用并带入冻结条件 | 避免不必要的模型消费，减少机器路径和清单拼接。 |
| 明确最新尝试与报告采用的尝试，保留失败和重试成本 | 完成比较后仍能追溯结论，避免旧成功遮蔽新失败或只报告成功样本。 |
| 本地主机所有权核对与显式停止/恢复 | 中断后能接续调查，保护其他并行实验；等待和停止执行含义明确。 |

当前没有需要用户补充的产品选择或阻断设计的接口未知。尚未实证的是新接线运行时的效果，特别是端到端实时过程、并行停止与网关流终态归属；实施后在另行授权的真实生成/应用评测中验收，不宣称已经验证。不编写或运行设施测试，不把设计收敛当作开工或实验授权。
