## 发现

### P1：取消与失联后，状态无法可靠收敛

`lab/run.py:250` 先建立全部 queued 记录；`:264` 仅处理 KeyboardInterrupt，`:268` 取消尚未执行的 future，但没有给这些 run 写终态。控制器没有 SIGTERM 收尾处理，子进程以独立进程组运行。`lab/status.py` 只返回保存状态；`lab/wait.py` 的 controller PID 由调用方临时提供，进程身份没有持久化。真实旧记录中存在上述 24 个非终态，证明此缺口已影响使用；不能把它们统一归因为某一个取消分支。

`lab/run.py:221` 收尾还依赖产物归档和 SQLite 查询完成后才写最终 run 状态。磁盘或数据库故障可能使终态没有保存。需要区分工作终态、收集失败与失联后的观察，恢复时不能伪造原停止时间。

### P1：实验、重试与结果选择缺少明确关系

`lab/run.py:104` 保存单次 run 身份和输入，但不保存矩阵执行身份、所属 job、重试来源或控制器归属。相同题名和随机 run ID 不能表达 retry_of。`benchmarks/hackathon/report.py:128` 按 finished_at 选记录，进行中的新尝试通常被已有终态盖住，未选择的历史尝试也没有随报告列出。

新报告已补测试快照身份，但还使用当前 checkout 的 coverage，且相同回放包不足以证明 Runner、镜像等条件相同。`:73` 返回附件声明的结果，没有核对 Playwright 最终状态或适配器终态；当前未观察到因此误计分，但源码允许测试正文通过、后续 teardown 失败时仍报告 passed。批次状态、测试业务结果、证据状态和结果纳入规则需要分别表达。

### P1：基础设施自身缺少可查询的阶段与失败来源

`lab/run.py:188` 只记录整次 running，到进程结束才写最终结果；生成、安装、启动、测试、收集的过程主要存在 Runner 日志中。`lab/arc_bench/results.py:77` 通过公开 Runner 的消息文本推断部署阶段，有助于事后分析，但不是稳定的阶段记录。

实例 `sheet-req-1-2-1-1327f9d013` 的适配器错误是 `local Runner did not return a complete evaluation`，嵌套官方结果为 `No Playwright report was produced`。原始日志保留了进一步排障入口，但统一状态还不能直接定位更早的依赖安装错误。需要保留原始错误及其来源位置，把设施负责的阶段连接起来。

### P2：遥测传输状态与 Agent 过程完整性之间有空白

`lab/otlp.py` 用 run token 将批次绑定到本次数据库，此设计正确；原始 payload 的语义不应进入通用层。当前 receiver 的 403/413/415/500 等拒收只返回给发送者，`:117` 禁用请求日志，没有持久的接收失败记录。`lab/run.py:223` 的 received/absent 只能说明是否存在批次，无法区分未配置上报、发送失败、尚未结束或已经丢失。

Collector 与当前 controller 共生命周期，关闭后没有通用的旧 run 补采接入。文档 `docs/deployment/braid-diagnostics.md:96` 已承认旧 endpoint/token 无效；可选 Braid 分析器可以重建并报告 gaps，但不能替代通用的接收状态和 run 关系。`variants/raw/raw_otlp.py:66` 发送失败后记录错误并清空批次，是一个具体发送方的尽力而为行为；改动归其发送方边界，不要求所有 Harness 采用该格式。

### P2：实际运行环境和共享网关尚未完整绑定到 run

`lab/arc_bench/arc_matrix.py:88` 把外部 env 文件路径放进 argv；`lab/run.py:190` 继承控制器环境，没有独立的非秘密有效配置记录。`scripts/hackathon_gateway_compat.py:16` 保存参数、时间与阶段，但没有 run/request 关联，多个并行 run 使用同一模型时无法仅凭这些日志准确归属一次上游调用。秘密内容不应被复制进普通 run，模型路由与实际参数需要可关联的非秘密证据。

`arc_bench_adapter.py:139` 查询 image ID 后仍用原 tag 启动容器，且 ID 主要到最终结果才保存；准备快照也没有冻结通用控制器/报告器版本。因此现有输入哈希改善了追溯，但并未覆盖完整执行与派生报告链。

### P2：内容身份的覆盖规则不同，回放声明不等于消费见证

`lab/run.py:snapshot` 的文件摘要包含文件名及 bytes，`package_arc_replay.py:package` 的应用摘要来自序列化文件哈希清单，`arc_bench_adapter.py:source_hash` 来自过滤后的相对路径与内容串。它们都叫 SHA256，但不能跨对象直接比较，也不能把包重命名当作应用变化。

回放入口 `arc_replay.py:main` 根据需求选择应用并复制，然后把包内 case 写到 `.arc/replay.json`；这个文件是来源声明，没有重新计算部署前的内容见证。现有两阶段 adapter/noop 已有冻结/消费哈希核对，可作为明确边界的先例。此处没有证据显示旧回放应用被篡改；问题在于新设计不能把声明与核实混为一谈。

## 已确认的设计方向

以明确关系连接实验定义、逻辑 job、执行尝试、阶段、生成应用、评测和报告。原始记录由各自生产者拥有，汇总是带来源引用的派生视图；无需将所有内部 ID 替换成一个 trace ID。

基础设施持有它实际观察到的调度、进程、容器、阶段、收集与操作记录。Runner 适配层连接部署与评测，Harness 通过 OTLP 上报自己的过程；用户选择分析器解释内容。先确定来源关系和证据归属，以 Agent 过程可诊断为首要使用场景；停止、失联和明确重试用于使这些关系可靠，不单独扩展成控制平台。

## 调查所回答的问题

2. 同一输入重试、仅复评旧应用、修改测试集后重评，哪些身份应保留，哪些必须新建？报告怎样暴露采用与排除的记录？
3. Agent 仍运行但没有遥测、Collector 已关闭后补采、主机中断等情况下，现有证据能证明什么？运输成功与内容覆盖由谁解释？
4. 停止、清理、失联确认和重试怎样作用于明确归属的执行，避免误停其他并行实验或自动重复模型消费？

## 当前设计与下一步

已沿生成、回放、评测、报告及过程上报完成端到端取证，方案见 [设计](design.md)。主要决定是：复用现有 run 和证据存储，增加实验/job/尝试及制品来源关系；分别呈现执行结果、评分、证据与清理状态；Collector 只负责协议与传输事实；通过显式补采会话和带读取截止点的分析支持后续诊断。

用户提醒后重新走读当前查询入口：`lab.status.read_status` 直接返回保存的 run JSON；`docs/deployment/index.md` 的“按记录生产者查询”要求先区分外层实验、Harness 内层记录和平台 journal。现有 ARC 摘要与 Braid viewer 已能解释部分证据，但选择入口和连接来源仍主要由使用者完成。这是用户完成诊断时的直接负担，不能只用增加身份字段解决。

设计已前置发起比较、运行中观察、失败诊断、复用应用、比较交接和外部接入六个使用场景。随后完成两条主流程的[只读走查](walkthrough.md)：原失败摘要有 1667 个字符，原生成摘要有 3472 个字符，但仍需人工借 replay.json 连接过程。定向读取安装日志发现 `npm error Exit handler never called!`；同场景后一次执行已有完整评测，但应用用例失败。不能将旧设施故障呈现为当前尚未解决的阻塞，或未经证据把 npm 错误归因为网络。

据此提出三个交互层次：按计划任务组织实验概览；任务下查看最新/指定尝试和结果；在同一上下文进入本次过程、输入应用的生成过程与用户分析。仅复评从已有应用发起并自动带入冻结条件，实际执行范围可见。源码还显示回放打包器要求整个 run completed，可能阻止复用已生成但后续评测失败的应用，应由制品可用性替代总状态作为复用依据。

全方案已进一步收敛，先前待定项均有明确选择：

- 主要操作入口为 CLI 与结构化查询，现有查看页连接同一事实；通用 job 不强制 ARC 标签。按任务显示进度，明确尝试历史、事件游标和分析来源。
- 输入按实验共享冻结，应用在入口结束后独立发布，复评携带原条件；实例、job、run、制品和报告各有明确归属，索引可重建而原始记录不改写。
- 适配器通过最小设施事件文件连接阶段、资源与错误；Agent 过程仍走 OTLP。Collector 补齐协议边界、信号专用配置、诊断与显式补采，分析固定证据截止点。
- 共享网关采用每 run 本地凭据及网关自分配请求 ID；已核对现用 LiteLLM 1.102.0 接口。直连供应商可用，不强制网关或客户端私有扩展。
- 控制器使用本机所有权记录和控制通道，支持总并发调整、明确停止与失联核对；未知不自动恢复模型调用，Collector 和辅助证据故障不抹去执行结果。
- 报告按明确选择清单与冻结条件生成，记录预期变化、额外差异和历史限制；旧数据不迁移、不补造关联。已有报告/查询入口收敛到同一套新逻辑，私有语义继续归各分析器。

具体记录契约、模块落点、默认行为、兼容和验收条件见技术方案。桌面推演的冲突已处理，没有需要用户补充的产品事实或阻断设计的接口未知。尚未验证的是实现后的运行效果，特别是实时过程、并行停止和模型流终态；这属于后续实施及另行授权的真实实验验收，不将静态接口核对当作完成证据。
