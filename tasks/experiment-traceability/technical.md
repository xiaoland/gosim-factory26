# 实验基础设施的实现约束

这是已收敛的技术方案，支撑 [产品设计](design.md)。内容描述待实现行为，不表示源码或运行环境已经具备这些能力。用户已授权实施计划与排障，尚未授权源码实现或新实验。实施顺序见 [plan.md](plan.md)，源码与独立预演的排障结论见 [preplay.md](preplay.md)。

## 1. 交付范围与入口

本轮交付是面向开发/分析 Agent 和人的本地实验工具：统一实验引用、可读摘要与 JSON 查询，保留原始证据，连接可选分析结果，提供并行执行和必要恢复操作。执行在 WSL；macOS 可读导出结果，操作 Agent 通过现有 SSH 通道调用 WSL 命令。引用记录实际主机及路径，不将 WSL 文件假装为 macOS 可打开的本地文件。无需增加远程调度服务或网页服务。

`python -m lab` 作为日常入口；现有 `python -m lab.run` 委托同一实现并保留已有参数。CLI 的摘要和 JSON 来自同一查询结果，默认隐藏长路径与哈希，原文按明确引用读取。根目录或引用显式传入，不使用跨主机的全局“最近一次 run”作为隐含选择。

| 用户操作 | 确定的行为 |
| --- | --- |
| `plan` | 读取现有 JSON 清单，解析并冻结输入，返回实验引用及组合/运行位置/并发/执行范围。可独立使用；直接 `run` 原清单时自动完成此步骤，不加人工批准关卡。 |
| `run` | 执行本次计划中选定的任务，正常等待并输出有意义的变化与终态。指定后台运行时返回持久引用和控制器日志。不会因某题低分自动重试。 |
| `show` | 接受实验、job 或具体 run 引用；实验按任务汇总，具体 run 始终指向原尝试，支持 JSON 与筛选。 |
| `events` / `wait` | 分别查询变化、安静等待。返回游标；按游标续接，不反复输出心跳或全部历史。停止等待不停止执行。 |
| `evidence` | 列出、读取、导出声明的文件或 OTLP 批次；保留完整原文引用和截断标记。协议字段及批次选择由通用层支持，Agent 内部查询归分析器。 |
| `retry` | 针对指定尝试创建新 run，保留原执行范围和冻结输入，明确是否重新调用模型。计划内的重复样本是独立 job，不用 retry 冒充统计样本。 |
| `stop` / `reconcile` | 分别停止明确归属的执行、核对失联状态；核对不会启动模型或自动续跑。 |
| `parallel` | 调整当前控制器总执行槽数并记入操作记录；减小只影响后续派发。无按赛题或 variant 的隐含锁。 |

仅复评由 ARC 接入的 `evaluate` 入口实现。它接受已有应用引用、评测集及选择范围，生成通用计划并交给 lab 执行；任务详情提供带上下文的完整调用方式。通用执行器不导入 ARC。其他适配器同样可以提供自己的后续命令；查看记录不自动执行它们，不建设动态插件注册系统。

## 2. 实验、输入和记录的归属

新清单使用 schema v2。通用 job 的核心是外部 argv、命名输入与结果约定；`competition`、`variant`、`task` 成为标签，通用运行不再强制要求 ARC 的三个字段。计划为未提供 ID 的 job 分配稳定 ID，用户不必手写。schema v1 继续读取并保留原标签；原始历史文件不改写。

新 run 以显式记录类型识别为 lab 执行，可选适配器类型只用于对应消费者解释。`result_path` 不再兼任记录类型标记。v1 规范化补入其原有默认结果文件，v2 未声明结果文件才表示仅观察进程。输入可以为空；对没有文件输入的外部命令，不人为增加占位输入。

一次实验的规范文件为冻结后的 `manifest.json`，包含实验 ID、原配方引用、job ID、命令、输入引用、初始并发及可选比较意图。控制器启动和重试不会改写它；新的输入/评测定义产生派生实验，并记录来源。运行次数、当前状态由 run 记录派生，不在清单中维护第二份可变状态。

```text
experiments/<experiment-id>/
  manifest.json                 冻结的计划及输入引用
  inputs/<input-id>/             本次实验共享的输入快照
  controllers/<controller-id>/
    controller.json             主机、进程身份、当前调度配置
    operations/                 已请求操作及其处理结果
    stdout.log / stderr.log
  runs/<run-id>/
    run.json                    本次尝试的执行事实
    inputs/                     指向已冻结输入的相对引用
    workspace/                  适配器及 Runner 的工作目录
    artifacts/index.json        已发布产物、来源和分析入口
    artifacts/                  独立冻结的输出，如应用快照
    events/                     各生产者自己的设施事件流
    stdout.log / stderr.log
    telemetry.sqlite            原始批次、接收会话与传输记录
  analysis/<analysis-id>/        固定证据范围的报告及分析产物
```

上述是新 `--experiment-root` 的标准布局。兼容入口 `--runs-root R` 继续把执行放在 `R/<run-id>`，本次实验的清单、共享输入和控制器记录放在 `R/.experiments/<experiment-id>/`，通过相对引用关联。同一个 R 可以保存不同实验；原父目录 manifest 不覆盖，旧 run 不搬动。只有这一处布局兼容例外，读取、调度及选择逻辑共用。

内部 run ID 继续表示一次尝试；另记所属实验、job、尝试序号及明确的 retry_of。选择最新尝试使用分配序号，不能让较早开始、较晚结束的并行尝试覆盖更新的尝试。准确引用打开原记录；模糊名称有多个匹配时返回可选择的候选，不能取目录 mtime 最大的一项。

当前 `prepare` 为每个 job 复制输入。新计划对同一解析后来源只冻结一次，各 run 通过相对链接/引用使用同一份只读快照；需要修改输入的命令先复制到自身 workspace。保留现有快照手段，不做跨实验全局缓存或垃圾回收平台。旧八次生成的 ZIP 输入合计 4,369,711,702 bytes、四份不同身份，此项直接减少重复准备与存储。冻结进度可见；无法完整冻结的输入不会标为可执行。

计划先保存请求及 job 身份，冻结时使用临时目录，完成后原子发布快照及最终清单；准备过程由独立事件记录。某输入失败时保留具体错误和受影响 job，其余已就绪 job 可运行。修正缺失输入形成派生计划；不能把尚未冻结的来源日后补进原不可变清单。语法无效或不能持久保存整个计划时不派发。

新文件身份为原始 bytes 的 SHA256；新目录/应用身份来自排序后的相对路径、文件内容摘要和执行位清单，使用明确版本的规范化编码。记录身份算法与包含范围，冻结时保存清单。旧摘要保留原算法标记，不改成新值或直接跨算法比较。绑定相同内容还需保留生产者 run；内容相同不能证明是同一次生成。

控制器保存实际 Python 版本与自身执行源码快照，适配器/Runner 继续作为命名输入冻结。ARC 在启动前记录镜像 inspect 的 ID，并用该 ID 启动，而不是再次解析 tag。分析工具在产生报告时记录自身版本/源码摘要。开发工作树可以有修改，不要求先 commit；冻结实际使用的内容。

控制器从冻结的 lab 源码启动，避免保存了快照却继续运行后来修改的 checkout。新 ARC 配方冻结适配器目录及其共享 helper，命令指向目录内脚本；不能继续只冻结单个 `.py` 后再从当前 checkout 导入新 helper。容器包装器与回放/noop 包只带实际需要的 helper。

环境继承保留现有使用便利。需要可重复使用的配置由配方声明；私密 env 文件仅保存引用，敏感值不进入清单、argv 或普通产物。实际加载配置的组件保存非秘密有效配置；未声明的隐式依赖标明未知，不宣称完整复现环境。新增每 run 私有运行目录承载临时 env 和凭据，权限限制且排除归档，退出后清理。

## 3. 外部执行与阶段接口

保留 `experiment-result.json` 作为外部程序的最终结果，不要求程序使用某个 Harness SDK。实验上下文通过已有 OTEL 环境变量及 `EXPERIMENT_RUN_ID`、`EXPERIMENT_RUN_DIR`、`EXPERIMENT_ARTIFACT_DIR` 提供，另提供设施事件目录。容器内端点和可访问路径由适配器映射；不把宿主绝对路径直接当作容器路径。

各生产者向独立 JSONL 文件追加设施事件，单个文件有一个写入者。公共外壳只含 schema、producer、run 引用、生产者内序号、发生时间、事件类别及证据引用；阶段名、细节保留命名空间。需要的类别限于阶段进入/结束、资源取得/释放、产物发布和具体错误。控制器与适配器各自写自己的文件，末尾未写完的行显示为尚未完成，不丢弃之前的有效记录。

这条文件接口供控制器和 Runner 适配器使用。Harness 不必上报阶段文件，Agent 内容仍走 OTLP。未实现阶段接口的外部程序照常执行，其内部阶段显示未知，stdout/stderr 始终可读。

`run.json` 由控制器单独写入执行事实；适配器最终结果归适配器；阶段/错误/资源归相应事件生产者。通用摘要连接这些来源，不重复创造一个可手工修改的总结果。读取旧内嵌 result 时注明其为当时收集的快照。每条错误保留原始消息、退出码/HTTP 状态、来源位置和上层影响，原因推断与原始观察分开。

v2 job 可不声明适配器结果文件，此时仅报告进程退出，不推断业务完成；声明了结果文件却缺失/损坏时报告契约错误，同时保留实际退出码。命令非零与结果自报 completed 冲突时分别保留，CLI 不宣称全部正常。ARC 的完整低分由适配器返回完成，应用分数继续归评测解释。

生产者先完成产物文件及自己的发布声明，再写发布事件。`artifacts/index.json` 是由控制器生成的可重建索引，生产者不并发修改它；引用的声明与内容才是依据。分析程序在自己的输出目录写 analysis.json，由查询层列出或显式关联，避免要求它改写原 run。工作区中的原始日志默认直接引用，发布的应用才单独冻结，减少重复归档整棵 workspace。

ARC 适配器按自己观察的边界记录准备、生成调用、应用冻结、部署/评测调用与收集。官方 Runner 的事件继续原样保存，解析时保留源行引用及 Runner 版本，不把其混合 `run_tests` 阶段强行解释成准确的单一阶段。现有 Runner 在 docker 启动前 flush 输出容器名，适配器可及时登记预期容器，再核实完整容器 ID 与 workspace bind。

应用在标准 Agent 入口结束后、后续部署/评测之前发布独立快照与 manifest，不能等整条 pipeline 成功。入口包装器只观察退出与交付文件，不解释私有 Agent 终态。ARC 的文件排除规则由 ARC 持有；通用层只保存制品。即使后续 npm/部署/测试失败，已经发布的应用仍可复评；生成未完成但用户显式选取的工作副本标为诊断输入，不伪装成正常交付。

官方 Runner 仅挂载 `/workspace`，因此包装器在 `/workspace/.lab-artifacts/` 原子发布独立应用和声明，部署仍只消费 `/workspace/template`。宿主的制品索引直接引用这份已冻结目录，无需复制后确认的握手；此处是上述 artifacts 目录的生产者落点例外，导出时依清单带走实际内容。包装器给原入口独立进程组，入口退出后沿用所固定 Runner 的组清理顺序（TERM、5 秒宽限、必要时 KILL），再冻结；这是入口退出后的收尾，不限制生成时长。清理确认另行记录，不宣称识别了主动脱离进程组的所有后代。

复评始终在新的 workspace 展开选定快照，保留选择范围、需求/测试/Runner/镜像身份；部署前核实载入内容。回放 ZIP 是传送方式，其重新打包不改变应用内容身份。当前 `package_arc_replay` 对整个 run completed 的检查改为校验所选制品可用性。冻结应用与单文件 Runner 入口的接线归 ARC，不移动到通用运行器。

本地 evaluate 直接使用冻结应用的 `--template` 与只做内容见证的 noop，无需中转 ZIP。需输出回放包时沿用已有打包入口；官方 ZIP 解压不恢复执行位，新回放入口按应用清单恢复后再计算消费见证。旧清单未保存执行位时只核实它已有的内容规则，不补造权限事实。

## 4. OTLP、过程查询与分析接入

继续提供 OTLP/HTTP protobuf 的 traces、logs、metrics 接收和原始批次存储。本轮补 gzip；gRPC、OTLP/JSON 和新的信号暂不扩展，启动信息与连接说明明确已支持的协议。协议级 envelope 校验使用官方生成的 protobuf 类型，保留原始 payload 和未知字段；不要求 Agent 属性、指定 service.name 或统一 trace ID。为协议校验使用最小的 `opentelemetry-proto`/标准 Status protobuf 依赖，不手写 protobuf 解码器或引入整套观测平台。

请求体上限默认 64 MiB，可配置，同时约束传输及解压后的大小；它是接收端资源边界，不截断已接收内容。持久提交成功才返回 200；坏数据返回 400，过大返回 413，暂时无法持久保存返回可重试的 503，并保留具体原因。错误响应按协议编码。接收错误优先写接收记录，存储也不可用时写独立 stderr；不承诺磁盘失效时仍能持久保存全部错误。协议依据见文末。

设施自动配置的 exporter 环境必须同时处理通用和三类 signal-specific 的 endpoint、headers、protocol、compression，避免宿主残留变量把某个信号发到另一个运行。保留生产者的 resource attributes 和原生身份。容器适配器转发同一套解析后的连接配置；主动使用其他出口的程序，其数据是否进入本地 Backend 单独说明。该行为依据 [OTLP exporter 配置优先级](https://opentelemetry.io/docs/specs/otel/protocol/exporter/)，不从 exporter 环境中的残留值猜测用户意图。

`telemetry.sqlite` 保留现有 batches 表，并增加接收会话身份、payload 摘要/编码元数据及传输诊断。gzip 解压后保存 protobuf 原始字节，不经解析后重新序列化，另记传输编码及字节数。token 只负责把批次绑定到 run，不进入展示。标准 OTLP 重试可能重复，存储不按内容 hash 静默去重；分析器按自己的事件语义处理。顺序按 batch ID 表达接收次序，不能用它推断并行 Agent 的因果顺序。

读取以 SQLite `mode=ro` 打开，数据库不存在就报告缺失，不因查询创建文件；旧数据库不在读取时升级。显式补采开启写入时才事务性增加会话/批次元数据表，保持原 batches 行和编号不变。保留 `list_batches`、`read_batch` 的既有调用形式，新增分页通过可选参数提供，避免旧 viewer 静默只读取第一页。协议依赖在 lab 自己的宿主依赖清单声明，不依赖 Codex runtime 恰好带有这些包；仅查询旧数据无需导入 protobuf。

查询提供 signal、接收时间、after-ID、until-ID 和条数范围，返回下一游标。分析开始固定截止 batch ID 并记录实际批次摘要；导出文件带清单，用户程序可以直接消费。既有原始文件按字节/行范围读取，提供继续读取位置，不默认把完整 rollout 注入操作 Agent 的上下文。

接收服务继续随控制器运行，正常结束时先等待已接受的请求完成写入，再关闭。执行终态和 Collector 可用状态分别呈现；run 结束时的统计注明截止点，后续查询以 Backend 的实际批次为准。需要追加旧证据时显式 `telemetry serve <run-ref>` 建立新的接收会话及临时连接信息，只追加数据，不恢复旧执行或继续模型调用。旧连接不可复用时错误可见；不建设常驻 daemon，也不保证控制器被强杀后仍能在线接收。原文保留与重发归发送者。

不默认采样、截断、按 TTL 删除过程数据或执行产物。存储错误可见，清理由用户显式选择；导出只携带所选证据及来源清单，不夹带私有运行目录。历史数据库导出前按 SQLite 正常读取/备份得到一致快照，不在写入中只复制主文件而遗漏 WAL。

分析器作为用户显式运行的独立程序存在。其输出用一个 `analysis.json` 描述标题、工具身份、源 run/制品、输入文件或 batch 截止点、生成时间和结果入口。基础设施将它列在相应任务下，详情与完整性判断均来自该程序；不自动加载插件或运行记录里携带的代码。运行中的分析可按新截止点重复生成；旧分析保留，不能覆盖其当时证据范围。

Braid viewer 继续作为 Braid 专用消费者，复用它已有的固定批次列表与重建逻辑。现有 Factory/native 读取器同样是可选消费者。新接入者只需外部命令、标准 OTLP 和可选分析输出引用；没有过程上报或分析器也能跑实验，并明确显示诊断能力的限制。

## 5. 模型调用关联与有效配置

共享网关采用**每 run 独立的本地网关凭据**，复用现有 LiteLLM，避免依赖 Pi/Codex 的额外自定义请求头。供应商凭据继续仅在网关私有环境中。此能力是可选模型服务接入，直连供应商仍合法；未提供请求级关联时标明缺口。

本机 LiteLLM 1.102.0 已确认具有 `general_settings.custom_auth`、`UserAPIKeyAuth`、pre/failure/streaming hooks 和 `litellm_call_id`。使用基本 custom_auth，不引入虚拟 Key 数据库、企业功能或新反向代理。网关为随机 token 保存受限权限的绑定文件，文件名可用 token 摘要，内容连接 run、网关实例和接收上下文；公开记录只含绑定 ID。认证层根据绑定返回请求上下文，忽略请求正文自报的 run 归属。

`scripts/hackathon_gateway.py` 增加命令包装模式：接收已有服务状态、原私密 env、调用方声明的 URL/key 环境变量名和待执行 argv；从实验上下文登记绑定、生成临时 env，执行外部命令，退出后撤销该绑定。ARC 配方选择自己的 env 名称和 Meter 凭据接线，通用控制器不识别这些变量。官方 Meter 的凭据与模型网关凭据保持明确分离，不能自动用第三方 key 覆盖前者。控制器失联后的 reconcile 可以撤销它明确拥有的网关绑定，不停止共享网关。

网关为每个入站请求分配自己的 request ID，把入站、参数规范化、上游尝试、流结束/异常与用量关联起来。客户端自带 ID、LiteLLM call ID 和供应商 ID 另行保留，不以客户端自报值替代本地唯一身份。记录实际 provider/model、请求参数及改写后的参数、状态码和原始错误内容；不新增默认采样限制或改变模型重试策略。客户端重新请求是新的 request；网关内部重试挂在同一入站 request 下。流式 HTTP 200 仅表示响应开始，完成记录需来自流终态；终态缺失保持未知。

网关保存自己的原始请求诊断文件，并可将同一证据通过 OTLP 发到所属 run。传输失败不丢掉已保存原文；补采由它显式重发。正文提示词不由基础设施强制采集，保留范围由该生产者决定。没有原生关联字段时只承诺请求属于哪个 run，不能按时间猜测它属于哪个子代理或工具调用。已有 traceparent/native request ID 可以原样保留作为进一步关联依据。

认证上下文来自绑定文件，每个请求固定自己的上下文；撤销绑定只拒绝后续请求，不抹去已经在途请求的诊断。原始证据写入失败输出具体错误，不能通过观测 hook 异常替换模型响应。新网关用新状态目录与端口部署，不重启其他实验正在使用的实例。可选 OTLP 发送由独立导出阶段消费持久记录，不在每个流式 chunk 的处理路径上同步等待 Collector。

非秘密配置快照由真正加载配置的组件提供。网关记录路由版本和参数政策，Harness 记录其实际请求配置；不能仅从 variant 名推导真实模型。账户费用与客户端 token 统计各自标明来源，缺失不填零，也不把共享账户余额变化摊成逐 run 费用。

## 6. 并行、停止、失联与等待

复用现有进程组与线程执行；控制器只派发当前槽位内的工作，未派发任务保持排队。单个实验同时只有一个拥有调度权的控制器，使用主机本地文件锁避免两个控制器重复派发；独立实验、同题 variant 和明确发起的重复尝试可以并行。总槽位与 LLM 请求并发是不同量，设施不按 Agent 数推导供应商限制。

以控制器单循环持有 ready/active/slot_limit，每个在途尝试一个线程运行 Popen，通过队列返回观察。取消一次提交全部 future 的方式；增加并发直接补派，减少时等待自然退槽。控制器集中分配尝试、受理控制操作并写 run 事实。启动前保存操作与已分配 run；Popen 成功但归属未落盘的窗口保留未知，不能自动补启动。

控制器保存 hostname/启动实例、Linux boot ID、PID 与进程启动时间。控制通道使用当前主机的 Unix socket，权限仅属主可访问，不复用容器能够访问的 OTLP token。CLI 为操作分配 ID 并在发送前保存请求，控制器保存处理结果；重复查询同一操作返回已有结果，不能重复启动模型。主动再次运行是新操作。启动是否受理不明时先查询同一操作及资源，不以自动重发制造第二次消费，也不承诺故障窗口中的恰好一次启动。后台运行显式脱离发起终端，日志与终态均落盘。

原配方再次 run 默认建立新实验；对已有实验引用 run 默认只安排从未分配过尝试的就绪 job。受理一次运行操作时先为所选 job 分配 queued 尝试，进入槽位才启动进程，因此 queued 取消也有明确记录。已有完成、取消或失联尝试只有显式 retry 才创建新尝试；查看或恢复 controller 不自动重跑。尝试数与实际已启动数分别统计。

操作请求与回执各自一个写入者，不让 CLI 和控制器覆盖同一文件。socket 放在当前主机的短私有目录并在 controller.json 保存位置，避免实验路径超过 Unix socket 长度限制。持久状态留在实验目录，临时通信目录不成为事实来源。

`run.json` 的执行状态与退出事实先保存，随后更新采集/清理结果。状态区分 preparing、queued、running、finished、cancelled、lost；finished 另外保留退出码与适配器结果，不能直接解释为测试通过。所有权核对失败与 confirmed lost 分开；确认失联时记录发现时间，不伪造原退出时间。旧 completed/failed/interrupted 作为旧字段读入并标明其语义。

收到 SIGINT、SIGTERM 或 stop 后，先禁止范围内的新派发，再结束所属进程组并由适配器清理已登记资源。未启动任务记为取消。停止有 grace 参数，默认 30 秒，只约束停止等待，不限制正常实验时长；超时后处理仍存活的所属资源并报告是否确认清理，过程补采未完成单独标记。辅助证据采集失败不能抹掉已观察的执行结果。

ARC 资源归属核对同时使用完整容器 ID、workspace bind 和已登记的执行引用，不能只用名字前缀或 PID。失联恢复使用冻结适配器提供的只读检查/清理 argv，通用层执行这些已声明命令但不导入 Docker 逻辑；任意证据文件不能新增清理权限。无法确认归属时保持未确认并提供检查依据，不操作其他实验资源。

Runner 输出预期名称后、取得完整 ID 前仍有中断窗口：只允许按已经记录的精确名称查询候选，再以 bind 与本次资源声明核对，得到完整 ID 后才可清理。没有足够记录时保持未确认，不扫描并批量删除容器。`reconcile` 默认只保存核对观察；实际清理须显式选择 stop/cleanup 操作，普通 show 不执行资源 hook。

异常策略按影响范围决定：某个 job 的输入或调用失败只终止它，其他已就绪任务继续；影响控制器持久记录/调度的故障停止新派发并尽力结束自己拥有的工作；仅 OTLP 或可选分析不可用时保留实验结果，暴露观测缺口。不会从一个 429 或一般网络错误自行判定整账户额度耗尽，也不自动改变实验矩阵。

`reconcile` 先读取已保存所有权，再观察进程/容器/终态产物。查询默认不改旧记录；显式核对操作保存新的观察及其依据。它不承诺重建丢失的进程退出码。需继续时，用户选择从未执行任务、原范围重试或仅复评已有应用；任一继续操作都产生明确的尝试关系。Harness 会话恢复只在其自行提供相应命令时可选，不作为通用自动恢复。

运行中的 wait 由控制器事件通道阻塞等待变化；断开后可用持久游标续接。无活动控制器时读取保存状态并做一次所有权核对，发现未知时返回需处理结果，不能无限等历史 running。不会让主 Agent 为无变化心跳反复产生模型调用。

控制器通知流只记录可展示的变化和原事件引用，游标包含控制器世代及其序号；原生产者序号仍独立保留。消费者先补读持久通知再订阅，控制器程序跟踪各生产者文件的完整行，不要求模型反复轮询。重启时追加新世代，不能把旧游标重新当成从零开始。

## 7. 比较、历史与源码落点

报告默认按 job 选择最新尝试并固定选择清单；最新未完成/失败时旧有效成绩单独可见，不悄悄回退。可以显式选择旧尝试形成另一份报告。报告同时保存所选和未选尝试及理由、应用与测试身份、环境差异、证据截止点和解释器版本，之后源码变化不会改变已发布报告。

比较目的由实验配方表达。variant、模型或应用差异可以是有意变化的变量，不能要求所有应用或 ZIP 相同。比较视图呈现共同条件、预期变化及其他差异；缺失条件和混合测试版本仍可查看，但不能声称为同条件单一分数。多次生成失败和重试用量保留在比较上下文，避免只展示最终成功样本而隐去失败成本。

Hackathon 报告从冻结 coverage/selection 读取分母，支持明确的本次选择范围和完整套件范围；两种分母同时标明，局部诊断不冒充全量完成。判分核对 Playwright 最终状态与附件，冲突则保留原始结果并标为待解释；设施中断与前置需求阻断分开。对旧缺快照数据可生成带限制的历史报告，不能用当前 checkout 补造旧事实。

历史 records 不移动、不重写。旧格式解释留在可选消费者和迁移读取边界，输出显式来源与核实程度。对旧 replay-manifest 中已有的来源可建立只读关系；没有依据的 retry/session 关系保持未知。历史数据能够继续查看，改进后的完整追溯从新记录开始。

源码仍留在现有职责目录：

## 8. 收敛依据与验收

设计选择均已明确；剩余未知是运行时效果而非需要用户补充的产品决策。实施时先用已有真实记录验收定位、选择、来源与历史兼容，再把并行、停止、OTLP 和网关行为放入另行授权的真实生成/应用评测中验收。不编写或运行设施单测、mock、smoke 或换名探针。本轮设计没有授权这些新实验。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 71 场景、122 执行的历史集合 | 任务与尝试分别计数；指定旧 run 不跳转；24 条未收口状态不伪装为当前活跃。 |
| Sheet 安装失败后已有新评分 | 错误链接到 npm 原文；显示原应用和后续记录；新评测完成但用例失败不被当作设施仍在故障。 |
| 从评测进入生成过程 | 能沿应用来源到原生成证据，区分本次无生成和原过程缺失；不把两次时间线合并。 |
| 原应用复评与局部范围 | 复用同一应用快照、不启动模型，条件及分母准确；变更套件形成新条件。 |
| OTLP 存储、传输失败与后补证据 | 真实收到的数据可原样导出；拒收原因可诊断；补采不改执行终态，旧分析仍使用旧截止点。 |
| 多任务共享网关 | 每个请求能归属正确 run；流异常与 HTTP 200 区分；不能据时间臆测子代理归属。 |
| 停止/重启/独立并行实验 | 只控制登记资源，未执行任务与未知终态明确；停止等待无执行副作用。 |
| 新 Harness 或自选分析工具 | 无需修改 lab 的私有会话识别逻辑，即可运行、上报和取得原始数据；分析输出可从实验找到。 |

本轮核实的接口依据：WSL `hackathon-runtime-codex/python/litellm` 的 1.102.0 源码，以及[基本 custom_auth](https://docs.litellm.ai/docs/proxy/custom_auth)、[请求与响应 hooks](https://docs.litellm.ai/docs/proxy/call_hooks)。[OTLP 协议](https://opentelemetry.io/docs/specs/otlp/)说明 gzip、可配置请求体边界、错误响应与可重试状态，以及重发可能产生重复数据；协议格式验证不涉及 Agent 业务语义。这些依据支持设计，不代替接线后的真实运行验收。
