# 审查处置方案：准确上下文与可信的协作语义

状态：2026-09-28，用户通过协调会话批准产品修正1—3及耗时前三项，现已实施源码/指引；实际清单与验证见 [实施记录](implementation.md)。用户已确认本批部署；独立Linux发布包正构建，当前冻结运行材料不变。SVC CLI/dev经适用性评估不默认接入；多服务与检查收据的小工具具体方案需先由用户复核，当前只做设计，暂停实现/应用。

语音纠正：用户强调的是减少大模型“幻觉”，不是“唤醒”。顶层目标是让成员拿到准确且不重复的当前依据，使熟悉的 Git/Issue/PR 操作具有可观察、可预期的结果，减少对责任、交付和操作效果的错误理解或臆测。通知重建是独立的已证技术问题，不能替代这一目标，也不承诺消除所有模型幻觉。GitHub 对齐不是扩充功能清单，而是让熟悉操作有可预期的结果。裸 origin 的 symbolic HEAD 已能提供默认分支，仅说明 Closes 实现无需另加配置；绝不是不修生命周期、通知或上下文的理由。

## 上下文与错误理解之间的具体因果链

- Closes写了但不生效：模型按GitHub经验可能以为Issue已关闭。兑现机械语义并让view呈现实际关闭目标/状态，比要求模型记住例外更可靠；但工具成功不证明产品验收合格。
- unsubscribe返回成功却继续自动收件：声明意图与实际体验不一致，成员可能误判自己仍被明确请求参与。修正收件规则能减少这种混淆，不能把每次多余通知等同模型幻觉。
- Pi反复追加旧Context：旧快照作为新输入重复出现，增加过时判断的显著性；一次性注入修正机械污染。不能凭此断言过去的验收漂移全由它造成。
- 旧评论与更正同时长期展开：可能留下相互矛盾的依据。让成员明确更正关系、维护当前说明并保留追溯，比无选择地截短或自动总结更能维护语义。
- 状态本身需要清晰边界：assigned不是已开工，ready不是验收通过，merged是发布了具体代码，delivered是原生输入接受而不是理解。沿用现有回执和实际状态，不再靠推断填补；此次不新增流程gate或“防幻觉”分类器。

后续验收分别证明工具声明与真实状态一致、修订依据进入实际输入，以及接续行动是否采用新事实；只有token下降或少启动会话不能证明幻觉降低。

## 已批准实施的产品修正

### 1. 让显式退订真正控制自动通知

证据：`set_subscription`写explicit inactive，`discussion_changed`仍将历史thread作者无条件UNION进收件人。影响是用户已退出的讨论仍可能触发输入、重建、重复阅读；尚无本轮实际unsubscribe失败样本，不估计节省比例。

在现有收件集合中，让explicit inactive排除“历史参与者”这一自动原因；负责人责任、明确@定向联系不被该退出覆盖。重新subscribe恢复自动关注。不增加通知分类器或thread设置表，也不删除已经接受的输入。对于变更后尚未投递的旧队列，第一版不倒推删除：历史事件可能还含其它联系原因，未经追溯不能删。

验收：实际comment路径覆盖参与→退出→普通回复不排队→明确@仍有收据→再次关注恢复。与批量修复独立：批量不减少错误的收件集合，此修正才改变后续自动收件决定。

### 2. 兑现 Closes 与合并的生命周期语义

证据：两条合并成功路径都只记录associated_pr_merged，不解析正文关闭声明。影响是明确结束意图无效，Issue仍在开放任务和Context中，可能延长根检查及手工交接；不能宣称所有开放Issue都是此原因。

以裸origin symbolic HEAD识别默认分支；保持普通上下文关联与关闭声明分开。支持PR正文内本仓库close/closes/closed、fix/fixes/fixed、resolve/resolves/resolved加#编号；创建/编辑后view显示适用关闭目标。合并准备时绑定声明目标及默认分支判断到merge intent，成功发布后与PR状态共同结算；恢复读取同一已绑定意图，避免正文事后变化让恢复关闭另一组Issue。普通close、冲突/CAS失败、非默认分支合并不自动关闭；已关闭Issue不重复发关闭通知。

覆盖正常合并、“已被Git整合”的成功路径和崩溃恢复。只关闭显式声明的对象，绝不把所有关联Issue或根的子Issue一起关闭。子PR→develop不触发，develop→main不会追溯执行早先子PR正文；最终PR可明确声明所关闭的Issue。commit message关键字/跨仓库引用此次不实现并在CLI说明边界，不称完整GitHub兼容。

验收：多目标、正文增删、两种成功路径、默认/非默认、失败/普通close、prepared后正文变化与恢复不重复通知。根Issue自动关闭会触及现有quiescent判定，应验证已接受执行仍正常结束；不再额外加入验收gate或自动关闭父项。

### 3. 把工作记忆整理说明变成可执行指引

证据：根讨论里旧判断和更正长期同时可见；CLI已有edit/hide-with-reason/resolve，而使用不稳定。重复Context缺陷会放大旧快照，但修它并不会自动整理原对象。

采用已有[具体正文](../braid-product-reaudit/cells/context-curation-design.md)：替换Braid现有工作记忆指引段，说明description保存当前稳定依据、comment/thread保存讨论和证据；更正先通知受影响者，再窄改/整条失效时hide附理由；保留结论后resolve。交接时核对当前说明，不要求每次进度都edit、也不按数量定时整理。仍由LLM判断有效性，Braid不自动摘要或隐藏。

验收在自然出现的更正/已解决讨论中核对对象投影、通知实际接受、重建后旧依据不再作为当前指导、结论与未决问题保留。没有机会即未验证；不用工具次数或Context变短代替正确性。

## 唤醒与休眠的剩余设计边界

跨休眠原生复用仍未实施，需单独收敛设计，不是撤销其优化方向。兼容条件包括同一逻辑成员和指派版本、profile与指令revision、Context revision、保留的原生文件、旧执行已退出且新CLI binding可用。满足时走既有resume并原子切换持久绑定；任一条件不满足走现有新会话路径。恢复失败不得将未接受消息标为delivered或占住过期writer。

还须核实后台bash完成事件的归属：Pi拥有内部进程，Braid不能为省启动成本接管Pi子代理/后台作业生命周期。尚无足够行为验证证明跨休眠事件可被无损接回，因此本页不把resume当现成可部署补丁。先部署已确定的批量修复后观察残余重建，结合上述协议核实再定具体实现；不停止必要联系，不以全局禁唤醒代替复用。

明确不新增：CI审批门、自动消息语义分类、评论量触发hide、通用GitHub模拟器、额外默认分支配置、进程沙箱。原生Git和现有对象足以表达的工作继续复用。
