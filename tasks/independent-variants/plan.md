# 线性实施计划（待开工确认）

本计划围绕一份贯通，再复制为真正独立的三份，避免四条并行实现路径同时排障。
主 Agent 持有运行语义和集成判断；独立 Agent 已负责消费者事实核实与旧原生输入预演，不用代码阅读 reviewer 代替验收。

1. 保存当前工作树中本任务输入的文件身份与四组原生输入基线，明确包含已完成 SVC skill 接线。
   如用户授权提交，只处理约定的本任务/前置改动；没有提交授权不打包提交混合工作区。
2. 主 Agent 完成 mixed 的本地完整入口、Pi 原生材料和 Braid 调用，先与输入基线核对。
   共同证据/交付操作只搬已有机械函数，所有行为选择留在 mixed。
3. 接通所选 variant 的 build.py 与现有打包命令，验证独立目录及 Linux 官方入口。
   一个边界明确的子 Agent 可负责打包载荷与黑盒 smoke；与主 Agent 约定支持模块接口后再派发，不同时改运行代码。
4. mixed 的边界通过后，以普通文件复制建立 deepseek、glm、vv 的完整实现，分别保留原有差异。
   使用预演基线逐份核对，不由持久化生成器生产它们。
5. 切换活动入口；删除失去消费者的 resolver/materializer，更新旧命令迁移提示和相关测试。
   保留 raw-core、历史官方恢复、开发 analysis 与旧原生检查接口。
6. 执行 [验收](verification.md)，完成运行文档和任务状态；真实接线及评分按照实际授权与外部条件执行，报告缺口。

停止条件：依赖边界无法满足独立运行、既有诊断无法保留关键证据、或迁移必须改变模型/协作语义时，先返回具体事实重新审视设计。
可修复的普通实现错误在获批范围内继续处理，不把一次 smoke 失败当作应停止的实验结果。

开工影响：会改变新 variant 的源码入口和 ZIP 内部布局，并退休旧的活动配方生成入口。
不会改写任何冻结 ZIP 或 journal；新版本产生新制品身份。
本计划和预演需向用户呈现后取得明确实施确认，不能仅凭总体设计获批越过该门槛。
