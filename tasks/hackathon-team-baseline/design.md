# 基线要回答的决策

目标是取得当前 pi-team-mixed 的可解释基线，让下一轮能选择改进需求处理、协作、实现、验证或平台接线中的哪一层。
Lite 与 Hackathon 各回答不同问题：Lite 先暴露设施与常见交付退化，正式题才检验长需求下的完整产品表现。

## 已发现的具体差异

2026-09-24 当前前端 `index-KN-S4Cyu.js` 的 createSubmission 提交 `credential_mode`。
比赛额度选项为 `official_evaluation`，自带 key 为 `self_funded`；页面说明前者由平台为单次 run 创建临时 Key，只有该模式进入排行榜。
队伍 `/api/teams/me` 当前显示 Hackathon 共享余额 500 CNY、初始额度 500 CNY；这与本地官方 API 的个人 key 是不同凭据和预算边界。
调查时 `competition.py` 未传 credential_mode 且强制 secret；本轮按用户明确要求补齐两种模式，真实平台效果仍待本次运行。
用户已确认本次官网实验使用 official_evaluation，让实际临时凭据进入原生 Pi；本地 Lite 使用已有官方 key。
主模型选择框只声明根成员模型，不能据此推断其他请求一定受限或一定可用。

当前公开需求文件大小：Lite Keep YAML 31,434 字节、BookStack 38,919 字节；Hackathon GitHub 292,270 字节、Sheet 202,240 字节。
Hackathon 下载物只有 requirements.yaml，未提供 requirements.md；参考图片分别为 27、9 张。
这是需求规模和输入形态差异，不把字节数当 tokens 或能力证明。实际运行以存在的 YAML 为权威输入。

## 核实正式比赛实际条件

| 条件 | 足够支持结论的实际证据 | 后续决定 |
| --- | --- | --- |
| 凭据和计费模式 | 冻结输入声明 official_evaluation，实际提交/运行返回模式和额度记录 | 确认正式临时 Key 路径；不以自带 key 的本地结果代替。 |
| 临时 Key 的多模型能力 | 同一官网 run 的真实角色调用、所请求模型、有效返回/usage 或具体拒绝；可得平台明细交叉核对 | 将凭据限制、请求参数和模型错误分开，不静默改单模型。未调用的模型仍为未知。 |
| 外部工具可达性 | 官网容器中的 mcporter resolve/query-docs、search/fetch 内容与具体错误 | 区分 DNS/TLS/HTTP、MCP、认证/限流。npm 可达、tools/list 成功均不足以证明真实查询成功。 |
| 输入、交付和评分 | 实际需求文件、生成/部署终态、冻结应用身份、已执行用例数和官网评分 | 无 Markdown 仍以 YAML 为权威；零项测试不算有效零分，部署成功不等于需求通过。 |
| 可诊断证据取得 | 能关联到当前 run 的原生角色、消息/工具结果及工作项，或明确缺失字段 | 先界定能支持的过程结论，不能把分数或客户端配置当完整过程证据。 |

网络不是一个布尔值。模型网关、npm、Context7、Exa 是不同外部依赖；WSL 容器成功不证明官网容器成功。
现有 Braid 原生会话采集保留工具动作和返回内容，usage 按原生 message 归集；这是客户端记录，不冒充服务端模型路由审计。

## 验证当前 variant 的迭代假设

条件可用只说明实验可以解释，不能证明改造有收益。
本轮是一套组合改造的基线，不是消融实验；逐项记录与假设一致的过程、反例和未观察事项，不从一次分差宣称因果。

| 假设 | 要追踪的因果链 | 反例或未支持情形 |
| --- | --- | --- |
| 独立上下文和有界委派降低协作负担 | 父会话传递关键事实 → 子角色完成局部工作 → 结果被采用 | 关键需求丢失、频繁补发背景、主会话重新做一遍；fresh 参数正确本身不证明收益。 |
| 方法和探索工具促使不确定性在实现前收敛 | 一个影响路线的未知 → 合适来源或实际观察 → 据此选择或修正方案 | 查询与决策无关，或先猜 API 完成实现再返工；工具调用次数不能证明有效探索。 |
| SVC V&V 与角色方法改善反馈循环 | 需求判据 → 可观察的验证 → 解释反馈 → 修复 → 重走原路径 → 有边界的完成判断 | 跳转/刷新掩盖失败，工具退出 0 被当成需求通过，明显失败信号被忽略，修复后未验证原场景。 |
| Braid 的共享工作项承载有用上下文 | 设计依据、发现或反馈写入工作项 → 另一成员据此推进或修订决定 | 仅创建阶段文件/PR，根成员已完成全部实现，评论没有消费者；不按 Issue/PR 数量奖励使用。 |

复用现有记录，不为补齐能力表强制所有角色运行，不新增合成测试或遥测系统。
未自然发生的行为保留具体缺口；不能写成假设已验证，也不因调用表不全判整场失败。

## 从既有低分记录获得的启发

现有 [Hackathon 分析](../hackathon-variants/packet.md) 中能直接确认的是 codex-base GitHub 的 1/100，不将其未经验证地推广为全部 Pi/Codex 运行的同一原因。
该 run 使用了 browser operator，并拿到失败反馈；登录检查三次输出仍停在 Redirecting…，主会话随后宣称回归通过。
检查脚本未判断预期登录页面状态，却用 page.goto 整页导航重建会话；后续 curl 登录/接口 200 和逐 URL 页面访问也不能支持连续用户旅程已通过。
因此当前假设重点是判据是否匹配需求、操作是否保持原场景、失败信号是否影响决定，以及修复是否闭环；不是仅增加浏览器使用或更多自测。
这些旧证据用于分析本轮反馈机制，不把隐藏测试、旧答案或题目专属修补灌入本轮 Factory 输入。

## 成绩与进入正式题的判断

历史 mixed 的 Keep 27/32、BookStack 30/34 是参考，不能把一两个用例波动当作明确退化，也不能用两题平均值掩盖基础流程失效。
用户明确 Lite 也是性能下限的预检查。取得完整 66 项结果后同时看分数与原因：分数过低本身就是暂不进入正式题的警讯，不能只因设施正常或缺陷分散就放行。
以旧 mixed 的两题成绩为参考；若显著退化或基础路径普遍失效，先分析和处理，再决定正式比赛安排。轻微波动不据单次结果过度解释。
尚未约定硬性百分比门槛，不自行替用户设定；本轮不扩展为多 variant 搜索。
最终以用户复核 Lite 的完整结果决定正式阶段，不根据本页单独扣用队伍额度。

另一个会话的 Sheet 官网回放已遇到测试枚举失败、0 项执行。这类结果不构成 0/100；正式题必须核对实际执行总数与完成状态。
分数与失败原因同报；如果官网只返回弱摘要，明确哪些因果不能确定，不从评分推断缺少证据的 Agent 行为。
修复设施后如冻结 ZIP 改变，记录新 identity；不把不同 Harness 版本的两题混成一次基线。
